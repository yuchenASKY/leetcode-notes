# LCP 08. 剧情触发时间

> **难度**：中等
> **标签**：二分查找 · 前缀和
> **原题链接**：https://leetcode.cn/problems/ju-qing-hong-fa-shi-jian/

---

## 一、题目描述

三种属性 **文明等级 C、资源储备 R、人口数量 H** 在第 0 天全为 0。`increase[d][j]` 是第 `d+1` 天第 `j` 种属性的增量（**非负**）。

`requirements[q] = [c, r, h]` 是第 `q` 条剧情的触发条件：某一天三个属性**同时**满足 `C >= c 且 R >= r 且 H >= h`，该剧情即在这一天触发。求每条剧情最早被触发的天数；永远不会触发则记 `-1`。

### 示例

```text
示例 1
输入：increase = [[2,8,4],[2,5,0],[10,9,8]]
     requirements = [[2,11,3],[15,10,7],[9,17,12],[8,1,14]]
输出：[2,-1,3,-1]
解释：初始 (C,R,H) = (0,0,0)；第 1 天 (2,8,4)；第 2 天 (4,13,4) 触发剧情 0；
     第 3 天 (14,22,12) 触发剧情 2。
     剧情 1 要求 C>=15，但 C 到第 3 天只有 14 ⇒ 永不触发；
     剧情 3 要求 H>=14，但 H 到第 3 天只有 12 ⇒ 永不触发。

示例 2
输入：increase = [[0,4,5],[4,8,8],[8,6,1],[10,10,0]]
     requirements = [[12,11,16],[20,2,6],[9,2,6],[10,18,3],[8,14,9]]
输出：[-1,4,3,3,3]

示例 3
输入：increase = [[1,1,1]]，requirements = [[0,0,0]]
输出：[0]        # 第 0 天三个属性已是 0，需求全 0 立即触发
```

### 约束条件

- `1 <= increase.length <= 10^4`
- `1 <= requirements.length <= 10^5`
- `0 <= increase[i][j] <= 10`
- `0 <= requirements[i][j] <= 10^5`

---

## 二、解题思路

### 核心思想

`increase[i][j] >= 0` ⇒ 三种属性的**前缀和序列单调不减** ⇒ 三维条件各自退化成一次 `lower_bound`：

```text
剧情 q 的触发天数 = max( 第一次满足 C>=c 的天, 第一次满足 R>=r 的天, 第一次满足 H>=h 的天 )
```

### 思路演进

1. **朴素解**：对每条剧情从第 0 天开始逐天累加三个属性并判断，`O(n·m)`。`n = 10^4`、`m = 10^5` ⇒ `10^9` 量级，必超时。
2. **瓶颈定位**：慢在**同一份前缀和被反复重扫**。对每条剧情都从第 0 天重算一遍，而"第一次达标的天"这件事只跟前缀和序列本身有关，与"从第 0 天重扫"无关 —— 每天的计算都在重复描述同一份数据。
3. **关键转化**：因为增量非负，前缀和数组 `pre[j][0..n]` 单调不减，"第一个满足 `pre[j][k] >= req[j]` 的 k"就是一次**下标二分**。三条条件的合取 `day >= d1 且 day >= d2 且 day >= d3` 等价于 `day >= max(d1,d2,d3)` —— 三个互不干扰的 `lower_bound` 各做一次，取 max 就是答案。**原来不行是因为在"天数"上线性扫，现在行是因为在"前缀和"上二分。**
4. **最优解**：一次预处理出三条前缀和，之后每条剧情 3 次 `bisect_left` + 1 次 max，`O(n + m log n)`。

### 判据与判据族定位

- **判据**：`day = max_j lower_bound(pre_j, req_j)`；其中 `lower_bound` 返回 `len(pre_j) = n + 1` ⟺ 该维度**永远不会**达标 ⟹ 整体 `-1`。`n + 1` 不是合法天数，合法天数只有 `0..n`。
- **判据族**：属 `05-binary-search` 里的「**有序序列上的单调谓词边界定位**」（下标二分），载体是**前缀和数组**（不是原数组自身）。
- **本题的"有序性从哪来"必须单独论证**：题面没有说 `pre` 有序，是 `increase[i][j] >= 0` 推出来的。若允许负增量，二分立刻失效，只能改用滑窗/单调队列一类结构。
- 与滑动窗口族（滑窗的"收缩方式 × 答案口径"四象限）**无关**，本题不是窗口问题，别串用那套判据。

### 关键点

- 三路 `lower_bound` 的结果是**各自独立**的下界，合取 ⇒ 取 max。这是"多条件同时满足"最常用的等价改写。
- `-1` 的判据是 `l >= len(pre)`（即 `l == n+1`），**不是** `l == n`；`l == n` 表示恰好在最后一天触发，是合法答案。
- 需求 `(0,0,0)` 的答案是 `0`（第 0 天），因为 `pre[*][0] = 0 >= 0`，`bisect_left` 返回 0。

## 三、代码实现

### 最终代码

用户提交并通过的版本。**截图里没有 `import`，已补全**（`bisect_left` / `List`），其余与截图逐行一致。

```python
from bisect import bisect_left
from typing import List


class Solution:
    def getTriggerTime(self, increase: List[List[int]], requirements: List[List[int]]) -> List[int]:
        cnt = [[0] for _ in range(3)]                     # cnt[j] = 第 j 种属性的前缀和，cnt[j][0] = 0
        for i in range(1, len(increase) + 1):
            cnt[0].append(cnt[0][i - 1] + increase[i - 1][0])
            cnt[1].append(cnt[1][i - 1] + increase[i - 1][1])
            cnt[2].append(cnt[2][i - 1] + increase[i - 1][2])
        ans = []
        for i in requirements:
            l1 = bisect_left(cnt[0], i[0])                # 第一次满足 C >= i[0] 的天
            l2 = bisect_left(cnt[1], i[1])                # 第一次满足 R >= i[1] 的天
            l3 = bisect_left(cnt[2], i[2])                # 第一次满足 H >= i[2] 的天
            if l1 >= len(cnt[0]) or l2 >= len(cnt[1]) or l3 >= len(cnt[2]):
                ans.append(-1)                            # 某个维度的上界都还没到 ⇒ 永不触发
                continue
            ans.append(max(l1, l2, l3))                   # 合取 ⇒ 取三个下界的最大者
        return ans
```

## 四、复杂度分析

> `n = len(increase)`（天数）、`m = len(requirements)`（剧情数）。三路前缀和长度都是 `n + 1`。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | `O(n + m log n)` | `O(n + m)` |
| G 预筛优化版 | 最好 `O(n + m)`（全部 -1）、最坏 `O(n + m log n)` | `O(n + m)` |
| E 值域表版 | `O(n + V + m)`，`V = max(requirements)` | `O(n + V)` |
| 朴素解法（逐天重扫） | `O(n·m)` | `O(n)` |
| 理论下界 | `Ω(n + m)`（读入 `n` 天 + 输出 `m` 个数） | — |

- 常数层面：`m = 10^5` 时每行 3 次 `bisect_left` ≈ **3m 次 C 层二分**，实测占端到端耗时的 **93.6% ~ 96.7%**（见 §五 阶段归因）。
- `O(m log n)` 里的 `log n = log 10^4 ≈ 13.3`；E 版把这 13 层比较压成 3 次下标访问，代价是 `O(V)` 建表。

## 五、优化评估

**结论**：主体写法已经抓住了正确的复杂度层级，但有两处可落地：**① 构建段**换 `zip(*increase)` + `accumulate`（稳定 ÷2.3）；**② 查询段**加"越界预筛"（`G` 版）—— 收益由 `-1` 占比决定，`-1` 多时 3.8 ~ 8.1 倍，全命中时仍不亏。另一条路线是**值域表**（`E` 版），在 `V` 与 `m` 同量级时稳定领先，但 `V >> m` 时会反噬（实测 4.75 倍）。手写二分（`D`）被证伪：稳定慢 4.1 ~ 7.6 倍。

### 瓶颈分析

阶段归因（同轮轮转、取最优，单位 ms）：

| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| A 构建段 | 3.075 | 3.061 | 3.025 | 2.520 | 0.050 | 2.955 | 2.923 |
| A 查询段 | 72.448 | 56.045 | 44.391 | 47.476 | 0.724 | 86.156 | 0.658 |
| C 构建段 | 1.319 | 1.224 | 1.420 | 0.901 | 0.022 | 1.373 | 1.292 |
| C 查询段 | 68.783 | 51.348 | 45.013 | 43.361 | 0.733 | 80.058 | 0.697 |
| E 构建段 | 27.102 | 13.274 | 24.823 | 10.868 | 0.381 | 23.611 | 17.222 |

- **查询段占 A 的 93.6% ~ 96.7%**（`m = 10^5` 时；只有 `S7-fewq` 因 `m = 1000` 掉到 18.4%）。⇒ 优化必须落在"减少 3m 次二分"上，构建段只占 3% 左右。
- 构建段本身也有 2.3 倍空间（3.08 ms → 1.32 ms）：每轮 `cnt[j][i-1] + increase[i-1][j]` 要做 6 次下标 + 3 次 `append`，换成 `zip(*increase)`（C 层转置）+ `accumulate`（C 层前缀和）后只剩 3 次 `accumulate`。
- E 版把查询段砍到 40% 左右，但**构建段涨到 10.9 ~ 27.1 ms**（`O(V)` 建表 + 求 `V` 的 `O(m)` 扫描），这正是它在 `S7` 反噬的原因。

### 可优化空间

| 版本 | 做法 | 收益来源 |
| :--- | :--- | :--- |
| F | 只把构建段换成 `zip` + `accumulate` | 每轮少 6 次下标、前缀和走 C 层 |
| C | F + 把「三路 `len()` 判断 + `continue`」换成「`max` 后判一次 `d > n`」 | 少两次比较与一个分支 |
| **G** | C + **越界预筛**：某维需求 `> ` 该维最终总量 ⇒ 直接 `-1`，跳过 3 次二分 | `-1` 比例越高越赚 |
| E | 值域表 `reach[v] = 第一个满足 pre[k] >= v 的 k`，查询变 3 次下标访问 | 消掉 `log n` |

### 优化代码

**主推：G 版（越界预筛 + max 后一次比较）** —— 不需要额外内存，且在任何输入结构下都不劣于用户版。

```python
from bisect import bisect_left
from itertools import accumulate
from typing import List


class Solution:
    def getTriggerTime(self, increase: List[List[int]], requirements: List[List[int]]) -> List[int]:
        a0, a1, a2 = zip(*increase)                  # C 层转置，避免逐元素下标
        c0 = list(accumulate(a0, initial=0))         # C 层前缀和，长度 n+1
        c1 = list(accumulate(a1, initial=0))
        c2 = list(accumulate(a2, initial=0))
        m0, m1, m2 = c0[-1], c1[-1], c2[-1]          # 三个维度的最终总量
        ans = []
        for a, b, h in requirements:
            if a > m0 or b > m1 or h > m2:           # 越界预筛：该维度永远达不到
                ans.append(-1)
                continue
            d = bisect_left(c0, a)
            t = bisect_left(c1, b)
            if t > d:
                d = t
            t = bisect_left(c2, h)
            if t > d:
                d = t
            ans.append(d)                            # 预筛已保证 d <= n
        return ans
```

**备选：E 版（值域表）** —— 仅在 `requirements[i][j] <= 100000`（本题约束）保证值域有界、且 `m` 与 `V` 同量级时值得用。

```python
from itertools import accumulate
from operator import itemgetter
from typing import List


class Solution:
    def getTriggerTime(self, increase: List[List[int]], requirements: List[List[int]]) -> List[int]:
        a0, a1, a2 = zip(*increase)
        n = len(increase)
        c0 = list(accumulate(a0, initial=0))
        c1 = list(accumulate(a1, initial=0))
        c2 = list(accumulate(a2, initial=0))
        # V = 该维度被查询到的最大值；表长只到 V，不浪费在更大的累积值上
        V0 = max(map(itemgetter(0), requirements))
        V1 = max(map(itemgetter(1), requirements))
        V2 = max(map(itemgetter(2), requirements))
        INF = n + 1

        def table(c, V):
            tbl = [INF] * (V + 1)
            for k in range(len(c) - 1, -1, -1):      # 倒序赋值 ⇒ 同一槽位留在最小下标
                v = c[k]
                if v >= V:
                    tbl[V] = k                       # 关键：跳过表尾的大值必须"钳到表尾"
                else:
                    tbl[v] = k
            acc = list(accumulate(reversed(tbl), min))   # 后缀最小值 = 第一个达标的天下标
            acc.reverse()
            return acc

        t0, t1, t2 = table(c0, V0), table(c1, V1), table(c2, V2)
        ans = []
        for a, b, h in requirements:
            d = t0[a]
            t = t1[b]
            if t > d:
                d = t
            t = t2[h]
            if t > d:
                d = t
            ans.append(-1 if d > n else d)
        return ans
```

读法（按"逐轮比值是否跨过 1.0"判稳定性）：

- **G 在 7 档全部不劣**（S3 只有一轮抖动到 1.196，该档绝对耗时仅 6.5 ms，属短耗时档的读数抖动）。`-1` 占比 87% ~ 100% 的档赚 3.6 ~ 8.1 倍（S3 100% `-1`：51.4 ms → 6.5 ms），半命中档 1.9 倍，**全命中档仍 0.833（不亏）** ⇒ 收益随 `-1` 占比单调上升，但不会翻车。
- **E 的适用边界很硬**：`V` 与 `m` 同量级时 1.2 ~ 2.7 倍且区间不跨 1.0；`S7`（`m = 1000`、`V = 10^5`）`V >> m` ⇒ **4.75 倍慢**（建表 17.2 ms vs 查询只省下 0.5 ms）。所以 E 的判据是 **`V` 相对 `m`**，不能只看"值域小"这个标签。
- **F / B / C 的收益幅度小（约 10%）**，且部分档逐轮区间跨过 1.0（B 的 S1/S2/S4、C 的 S5、F 的 S4/S5）⇒ 按本仓库口径记"**噪声内小幅偏优**"，不要当成决定性优化；A→F 那一档（构建段 ÷2.3）是其中唯一稳定的一项。
- **D（手写二分）是稳定的反向结论**：6/7 档区间完全落在 1.0 以上，整体慢 4.1 ~ 7.6 倍，原因与既有结论一致 —— 二分的 13 层比较全在 C 层 `_bisect` 里，搬到 Python 层就是 13 次解释器循环。

### 常数级优化

- **`max(l1, l2, l3)` → 两两内联比较**：省掉 `max` 的全局名称查找 + 函数调用 + 参数打包。C 版相对 B 版即含此项。
- **三路 `len(cnt[j])` → 一个局部整数 `n`**：`len()` 是 C 层但仍是 3 次调用；C 版改成只跟 `n` 比一次。
- **`zip(*increase)` + `accumulate(..., initial=0)`**：把 `n = 10^4` 轮 Python 循环换成 C 层，构建段 3.08 ms → 1.32 ms（**÷2.3**，7 档一致）。
- ⚠️ **不要手写二分**（D 版被证伪）；也**不要**用 `bisect` 去查 `deque`（本题没有这个问题，但同族里若把三路前缀和换成 `deque` 会立刻退化 —— `deque` 的分块链表结构让随机下标访问变成 `O(k/64)`）。

## 六、易错点与总结

### 易错点

- **`-1` 的判据写成 `l == n`**：正确的是 `l >= len(pre) == n + 1`。`l == n` 表示恰好在最后一天触发。
- **`max` 会先吃到"越界标记"**：三路结果里的 `n + 1` 是"永不达标"的哨兵，只要有一路是它，`max` 就必然 `> n`。所以「三路判断 + `continue`」可以等价压成「先 max 再判一次 `d > n`」—— 但**这个判断本身不可省**，否则会把 `n + 1` 当成合法天数返回。
- **值域表的上界必须容纳"越界的那一档"**：`V = max(需求值)` 时，累积值可能跳过 `V`（如 `pre = [0,2]`、`V = 1`）。若把"超过表尾的累积值"直接跳过，`reach[V]` 会留在 `INF`，静默返回 `-1`。最小反例（`n = m = 1`）：`increase=[[2,2,2]], requirements=[[1,1,1]]` → 真值 `1`、实得 `-1`。正确做法是把这些值**钳到表尾槽位**（`tbl[V] = k`）。
- **值域表路线依赖题面保证**：本题 `requirements[i][j] <= 100000` 才使 `O(V)` 建表可行；若需求值域到 `10^9`，这条路线直接出局（与"值域桶"类优化的通用前提一致）。
- **有序性来源要单独论证**：`pre` 有序**不是**题面给的，是 `0 <= increase[i][j]` 推出来的。若增量允许负数，二分失效。

### 题型套路沉淀

- **「若干维度同时达标」→「各维度各自的下界取 max」**：只要每个维度自身单调，合取就能拆成独立的一维定位问题。反过来，"至多/恰好"型条件一般不能这样拆。
- **「第一次满足阈值的位置」= 有序序列上的 `lower_bound`**，用 `bisect_left` 而不是手写循环（实测 4.1 ~ 7.6 倍差距）。
- **多路前缀和的建法**：`zip(*increase)` 转置 + `accumulate(..., initial=0)`，一轮 C 层搞定，比逐元素下标快 2.3 倍。
- **`-1` 型判据的两条优化路**：① **越界预筛**（用"该维最终总量"当阈值，`O(1)` 拦掉整个查询，收益 ∝ `-1` 占比）；② **值域表**（`O(V)` 建表换 `O(1)` 查询，收益 ∝ `m / V`）。
- **优化收益按输入结构分档测**：同一份候选改动在"`-1` 多"和"全命中"下收益差一个数量级（`G`：0.126 vs 0.833），"查询多"和"查询少"下方向相反（`E`：0.372 vs 4.750）。只看一档会把反向结论写成提速结论。

### 6. 微基准

7 档场景 × 7 个版本 × **7 轮同轮轮转**取最优，`time.perf_counter()`，单次读数内层重复到 ≥ 4 ms 再折算。各档的 `-1` 占比由用户版输出统计得到（87.4% / 0.0% / 100.0% / 98.4% / 88.1% / 51.1% / 87.1%），保证"命中率"这一维度是实测而非估计。数据见 §五 两张表。

### 7. 阶段归因

构建段 / 查询段分别计时（同轮轮转、5 轮取最优），三段之和与端到端吻合到 **1% 以内**（如 S1：A 75.52 vs 80.44 ms 端到端、C 70.10 vs 70.39、E 61.63 vs 63.52）；除 `S7`（`m` 小）外，**查询段占用户版总耗时的 93.6% ~ 96.7%**。

### 8. 计时设计备注

- 参与对比的每个版本都在**同一次运行的同一个轮转循环**里测（跨运行的绝对耗时会有 ±10% 量级漂移，混用会让倍数不可比）。
- `Solution()` 实例在计时循环外创建，被计时的只有 `getTriggerTime` 本身。
- 倍数判据用"**逐轮比值区间是否跨过 1.0**"，而不是只看最优读数：`G`、`D` 的区间在多数档完全落在 1.0 一侧（结论稳），`F/B/C` 部分档跨 1.0（记"噪声内小幅偏优"），`S3` 的 `G` 有一轮 1.196 属 6.5 ms 档的抖动。
