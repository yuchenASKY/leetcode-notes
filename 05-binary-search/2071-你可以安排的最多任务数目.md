# 2071. 你可以安排的最多任务数目

## 一、题目描述

有 `n` 个任务和 `m` 个工人。任务 `i` 需要 `tasks[i]` 点力量才能完成，工人 `j` 拥有 `workers[j]` 点力量，必须满足 `workers[j] >= tasks[i]` 才能接下任务；每个工人只能做一个任务。

此外有 `pills` 颗神奇药丸，每颗能让一个工人的力量 **+strength**，每个工人最多吃一颗。求最多能完成多少个任务。

### 示例

```text
示例 1：
输入：tasks = [3,2,1], workers = [0,3,3], pills = 1, strength = 1
输出：3
解释：药给工人 0（0+1 >= 1 做任务 1）；工人 1（3）做任务 2；工人 2（3）做任务 3。

示例 2：
输入：tasks = [5,4], workers = [0,0,0], pills = 1, strength = 5
输出：1
解释：药给工人 0，力量变成 5，完成需要 5 的任务；其余工人力量为 0，做不了剩余任务。

示例 3：
输入：tasks = [10,15,30], workers = [0,10,10,10,10], pills = 3, strength = 10
输出：2
解释：药给工人 0（0→10）和工人 1（10→20），分别完成 10 和 15；
     剩余工人即使吃药也只有 10+10=20 < 30，做不了最后一个任务，所以答案不是 3。
```

### 约束条件

- `n == tasks.length`，`m == workers.length`
- `1 <= n, m <= 5 * 10^4`
- `0 <= pills <= m`
- `0 <= tasks[i], workers[j], strength <= 10^9`

## 二、解题思路

### 核心思想

**答案具有单调性 —— 能完成 `k` 个任务就一定能完成 `k-1` 个（把其中最重的那个任务去掉即可）。** 于是把「求最大值」转成「**二分答案 + 判定可行性**」；判定 `check(k)` 内部再用贪心在线性时间内完成。

### 思路演进

1. **暴力解法**：枚举所有「工人 → 任务」的指派方案，逐个检查是否合法。方案数是指数/阶乘级的，`n, m` 到 `5 * 10^4` 时完全不可行。

2. **观察到**：直接求最大值很难，但**给定一个 `k` 判断「能否完成 `k` 个任务」很容易贪心**；而且这个「可行性」随 `k` 单调递减。于是把优化问题换成判定问题，外层套二分。

3. **优化为**：把「能否完成 `k` 个」拆成两个贪心前提 + 三条决策。

   - **取数前提**：要完成 `k` 个任务，一定是拿**最容易的 `k` 个任务**（`tasks` 排序后前 `k` 个）配**最强的 `k` 个工人**（`workers` 排序后后 `k` 个）。任意一个可行方案都能在不改变可行性的前提下换成这组最"放宽"的配对。
   - **单指针窗口**：工人从小到大枚举时，`w + strength` 单调不减，所以「当前工人够得着的任务」这个集合只会扩大。用一个有序队列 `valid_tasks` 承载它，单指针 `i` 只往前走，整体 O(k)。
   - **三条决策**（对每个工人 `w`）：
     1. 若 `w >= valid_tasks[0]`（窗口里最轻的任务不吃药就能做）→ 让这个工人去做，弹出队首。**弱工人配轻任务，不浪费药**。
     2. 否则窗口里最小的任务都得靠药才能做：若还有药，吃药并弹出**队尾（最难的那个）**；若没药 → 失败。
     3. 若窗口为空（这个工人连吃药都够不到任何候选任务）→ 失败。

   **为什么吃药时一定要挑最难的任务？** 吃药的机会是稀缺预算。窗口里那些 `> w` 的任务只能靠药解决，而后面更强的工人也许不吃药就能胜任其中较轻的几个。既然这一颗药非花不可，就应该让它一次覆盖窗口内**最难**的任务，把「不需要药」的轻任务留给后面的工人顺手带走；若先吃轻的，重任务会被推到后面，可能要额外吃药甚至直接失败。

### 关键点

- **二分的是"任务个数"这个答案，不是数组下标** —— 这是「二分答案」模型最典型的形态：先找到可判定性，再对答案域二分。
- **每次判断一定要取 `tasks` 的前 `k` 小 + `workers` 的后 `k` 大**，区间取错整个判定就失去意义。
- **窗口靠单调性增量维护**：因为 `w + strength` 随工人递增，队列只进不出（除被消费），无需每步重扫。
- **药丸数 `pills` 是单次判定的预算**：必须在每次 `check` 开始时重置，不能跨轮累积。

## 三、代码实现

### 最终代码

```python
from collections import deque
from typing import List


class Solution:
    def maxTaskAssign(self, tasks: List[int], workers: List[int], pills: int, strength: int) -> int:
        tasks.sort()
        workers.sort()

        def check(k: int) -> bool:
            i, p = 0, pills           # i：下一个可纳入窗口的任务下标；p：当前剩余药丸
            valid_tasks = deque()     # 当前工人够得着的任务（含吃药后够得着），按难度升序
            for w in workers[-k:]:    # 只取最强的 k 个工人，从小到大枚举
                while i < k and tasks[i] <= w + strength:
                    valid_tasks.append(tasks[i])
                    i += 1
                if not valid_tasks:
                    return False      # 连吃药都够不到任何候选任务
                if w >= valid_tasks[0]:
                    valid_tasks.popleft()   # 不吃药就能做，先消化最轻的
                    continue
                if p == 0:
                    return False            # 非吃药不可，但没药了
                p -= 1
                valid_tasks.pop()           # 吃药，去啃窗口里最难的那个
            return True

        lo, hi = 0, min(len(tasks), len(workers))
        while lo < hi:                    # 找最大的可行 k
            mid = (lo + hi + 1) // 2
            if check(mid):
                lo = mid
            else:
                hi = mid - 1
        return lo
```

> 截图中只显示到 `return True`（第 23 行），其余部分未入镜。`from collections import deque`、`from typing import List` 以及收口的 `while lo < hi` 二分部分由笔记补全。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n log n + m log m + K log K) | O(K) |
| 朴素解法（不二分，线性枚举 k 逐个判定） | O(n log n + m log m + K²) | O(K) |
| 理论下界 | Ω(n log n + m log m) | O(1) |

> 复杂度中的 n 指任务数 `len(tasks)`，m 指工人数 `len(workers)`，K = min(n, m)（答案的上界）。

时间上：排序 O(n log n + m log m)；二分答案共 ⌈log K⌉ 轮，每轮判定 O(K)（每个任务与每个工人各进出窗口一次），合计 O(K log K)。空间上是判定所用队列的容量，最坏装下全部 K 个候选任务。

## 五、优化评估

**结论**：在该模型下已经**到顶**，没有渐进层面的改进空间。

### 瓶颈分析

总时间由两块构成：① 排序 O(n log n + m log m)；② 判定 + 二分 O(K log K)。判定函数本身每个任务、每个工人只被处理一次，已是 O(K) 的线性下界；`log K` 这一因子完全来自「答案取值域有 K 种可能」这一点，属于二分答案的固有代价。

### 可优化空间

- **判定部分**：无法再降。任何"能否完成 k 个"的判定都至少要扫一遍这 k 个任务和 k 个工人，O(k) 已是下界。
- **二分部分**：`log K` 轮无法省，除非题目额外保证答案接近某个值（本题没有）。
- **排序部分**：若输入本身有序就可跳过，但题目不保证；即便有序，总复杂度也只降到 O(K log K)。

### 常数级优化（可选）

- `valid_tasks[0]` 在 `deque` 上虽可用，但队列的主要操作集中在两端，保持两端操作为 `append/popleft/pop` 即可，不必引入按下标随机访问的容器。
- 把 `len(tasks)` / `len(workers)` 提到二分之外算一次，避免在循环条件里重复求值。
- `check` 内部把 `strength`、`tasks` 直接闭包引用即可，无需反复做属性查找。

## 六、易错点与总结

### 易错点

- **二分的收口方向写反**：本题求**最大可行 k**，必须用 `mid = (lo + hi + 1) // 2` 配合 `lo = mid`（向上取整），否则 `lo + 1 == hi` 时会因 `mid == lo` 而**死循环**。
- **`p` 没有在每次 `check` 开头重置为 `pills`**，导致药丸预算跨轮累积、判定结果错误。
- **吃药时错取队首**：吃 `popleft()` 会浪费这颗药（轻任务本可以留给后续工人不吃药解决），重任务被推到后面后可能直接失败。必须 `pop()` 取最难的那个。
- **两条失败路径混淆**：`not valid_tasks`（够不着任何任务）与 `p == 0`（够得着但没药）是两回事，缺任意一条 `return False` 都会出错。
- **`workers[-k:]` 在 `k == 0` 时等于整个列表**（`-0 == 0`），此时判定会错误地返回 `False`。本解的二分会从 `mid >= 1` 开始取值，所以不会踩到，但手写判定时要意识到这个切片陷阱。
- **忘记取「最弱的 k 个工人」的反面**：这里要的是**最强**的 k 个，即 `workers[-k:]`，写成 `workers[:k]` 直接全错。

### 题型套路沉淀

- **「二分答案」三步模板**：① 说明答案具有单调性（可行 k ⇒ 可行 k-1）；② 写出 `check(k)` 的判定逻辑；③ 用 `while lo < hi` + 向上取整的 `mid` 收口求最大可行值。凡是「最大值 / 最小值 + 可行性容易判定」的题，都先套这个骨架。
- **「判定内贪心 + 单指针有序窗口」**：当候选集随枚举对象**单调扩张**时（此处 `w + strength` 随工人递增），用一个有序容器加单指针做增量维护，把每轮判定从 O(k log k) 降到 O(k)。
- **稀缺资源的贪心方向**：面对有限次数的"加成"（药丸、跳跃次数、修改次数），判定的核心往往是「非用不可才用」，且**一旦决定用，就用它换取当前能换取的最大价值**。
- 同型参照：`2141. 同时运行 N 台电脑的最长时间`、`1898. 可移除字符的最大数目`、`2576. 求出最多标记下标` —— 都是同一种「外层二分个数 + 内层贪心判定」的结构。
