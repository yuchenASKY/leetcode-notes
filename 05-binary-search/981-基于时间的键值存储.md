# 981. 基于时间的键值存储

> **难度**：中等
> **标签**：设计 · 哈希表 · 字符串 · 二分查找
> **原题链接**：https://leetcode.cn/problems/time-based-key-value-store/

---

## 一、题目描述

实现一个 `TimeMap` 类，支持在**不同时间戳**下为同一个 `key` 保存**多个** `value`，并能按时间戳检索：

- `TimeMap()`：初始化。
- `set(key, value, timestamp)`：在时刻 `timestamp` 为 `key` 写入 `value`。
- `get(key, timestamp)`：返回所有**已写入**的 `key` 中满足 `timestamp_prev <= timestamp` 的记录里、`timestamp_prev` **最大**的那条对应的 `value`；没有这样的记录则返回空字符串 `""`。

### 示例

```text
输入：
["TimeMap", "set", "get", "get", "set", "get", "get"]
[[], ["foo", "bar", 1], ["foo", 1], ["foo", 3], ["foo", "bar2", 4], ["foo", 4], ["foo", 5]]

输出：
[null, null, "bar", "bar", null, "bar2", "bar2"]

解释：
set("foo", "bar", 1)  后，get("foo", 1) 命中 t=1 → "bar"；
get("foo", 3)         时刻 2、3 没有写入，回退到最近的 t=1 → "bar"；
set("foo", "bar2", 4) 后，get("foo", 4) 命中 t=4 → "bar2"；
get("foo", 5)         回退到 t=4 → "bar2"。
```

### 约束条件

- `1 <= key.length, value.length <= 100`
- `key` 和 `value` 由小写英文字母和数字组成
- `1 <= timestamp <= 10^7`
- `set` 操作中的时间戳 `timestamp` 都是严格递增的
- 最多调用 `set` 和 `get` 操作 `2 * 10^5` 次

## 二、解题思路

### 核心思想

「同一 `key` 的写入时间戳**严格递增**」这一条约束，把每个 `key` 的写入日志变成了一条**按时间有序**的序列 ⇒ `get` 不再是「找最大的 `timestamp_prev`」，而是「**在有序序列里定位 ≤ timestamp 的最后一个位置**」。一次二分即可。

### 判据与判据族定位

- **判据**：设 `key` 的日志为 `a`（按 `t` 严格递增）。`get(key, ts)` 的答案 = `a[j][1]`，其中
  `j = #{ i : a[i][0] <= ts } - 1`；`j < 0` 时返回 `""`。
- **为什么是「前缀长度」**：因为日志按 `t` 严格递增，「`t <= ts` 的元素」恰好是日志的一个**前缀**，前缀长度 `k` 就是二分的边界，答案落在下标 `k - 1`。
- **载体与前提**：本题属「**有序序列上的单调谓词边界定位**」（下标二分）族，载体是「**每个 key 各自一条按时间递增的写入日志**」。注意：这个有序性**不是题面直接给的**（题面给的是 `set` 调用序列，不是数组），而是「**按时间 append**」这一构造带来的 ⇒ 写这类题必须单独论证一句「有序性从哪来」，且二分前提一旦被破坏（例如允许对同一 key 乱序写入）整套解法失效。
- 与「二分答案」族（最小化最大值 / 第 K 小 / 可行域二分）区分：那族二分的是**答案值**、谓词是 `check(x)` 可行性判定，`while` 写法与边界处理都不同，**不串用**。

### 思路演进

1. **朴素解**：`dict: key -> [(t, v), ...]`，`get` 时**从后往前线性扫描**，返回第一个 `t <= ts` 的 `v`。`set` 是 O(1)，`get` 是 O(m)（m = 该 key 的写入次数）。
2. **瓶颈定位**：m 最坏可以等于总调用次数 `2 * 10^5`（例如 10 万次 `set("k", ...)` 后接 10 万次 `get("k", ...)`），线性扫描的总代价是 `O(calls × m) ≈ 4 × 10^10` —— 这里必然超时。慢的原因不是「查找姿势不好」，而是**日志本来就已有序，扫描等于把二分能 O(log m) 做完的事重复做了 m 遍**。
3. **关键转化**：把「`t <= ts` 里最大的 `t`」从**值**的角度翻译成**下标**的角度 —— 由于日志按 `t` 严格递增，「所有 `t <= ts` 的记录」构成日志的**前缀**，于是「找最大的 `t`」⇔「数出前缀有多长，再退一格」。一次 `bisect` 拿到前缀长度 `k`，答案就是 `a[k - 1][1]`。
4. **最优解**：`set` 直接 `append`（时间戳递增保证 `append` 后仍有序，**不需要任何排序或插入**），`get` 用 `bisect_left(a, (timestamp + 1, ))` 求前缀长度。见下节代码。

### 关键点

- **`bisect_left(a, (timestamp + 1, ))` 为什么恰好是「前缀长度」**：`a` 的元素是二元组 `(t, v)`，搜索键 `(timestamp + 1, )` 是**一元组**。逐项比较时
  - `t < timestamp + 1` ⇒ 第一个元素就分出大小，元组不相等 ⇒ 算「小于」；
  - `t == timestamp + 1` ⇒ 第一个元素相等，继续比剩余部分：`(v,)` 与 `()` 相比**更长的元组更大** ⇒ 算「不小于」；
  - `t > timestamp + 1` ⇒ 算「大于」。
  于是「小于」的恰好是 `t <= timestamp` 的那些 ⇒ `bisect_left` 返回的就是前缀长度，减 1 得到目标下标。**这条等价依赖 `(v,) > ()` 这个元组长度规则**，换成 `bisect_left(a, timestamp + 1)`（标量比元组）会直接 `TypeError`。
- **`j > -1` 守卫不可省**：`key` 从未写过时 `self.cnt[key]` 是空列表，`bisect_left` 返回 `0` ⇒ `j = -1`；此时若不判断，`a[-1]` 会**静默取到日志的最后一条**（Python 负索引不报错），答案错成「一个时间戳更大的值」。实测最小反例只有 2 次调用：`set("a","x",1)` + `get("a",0)` —— 真值 `""`、去掉守卫后实得 `"x"`。
- **`defaultdict` 在 `get` 里是「读变写」**：`self.cnt[key]` 对不存在的键会**插入**一个空列表。本题不改变答案，但会让「大量查询从未写过的 key」这一路径额外承担建表开销（实测：把 `get` 改成 `dict.get` 后该场景快 **1.4×**，见第五节）。
- **不需要排序、不需要并发数据结构**：时间戳严格递增 ⇒ `append` 即有序；`bisect` 是纯 C 层实现，比手写二分快约一个数量级。

## 三、代码实现

### 最终代码

> 截图里只有 `class TimeMap:`，缺 `from bisect import bisect_left` 与 `from collections import defaultdict` —— 已按 §3.6 补全 import（截图代码本体未改动一个字符）。截图底部第 12 行即为代码末尾（状态栏显示「行 12，列 45」），**未被裁掉任何收尾语句**。

```python
from bisect import bisect_left
from collections import defaultdict


class TimeMap:

    def __init__(self):
        cnt = defaultdict(list)
        self.cnt = cnt

    def set(self, key: str, value: str, timestamp: int) -> None:
        self.cnt[key].append((timestamp, value))

    def get(self, key: str, timestamp: int) -> str:
        j = bisect_left(self.cnt[key], (timestamp + 1, )) - 1
        return self.cnt[key][j][1] if j > -1 else ''
```

## 四、复杂度分析

> 复杂度中的 **n** 指 `set` + `get` 的**总调用次数**（题面保证 `n <= 2 × 10^5`）；**m** 指某个 `key` 的写入次数（`m <= n`）；`Σm = set` 的次数。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | `set` O(1)、`get` O(log m)（dict 查找 + C 层 `bisect`） | O(n)（每条写入一个二元组） |
| 线性扫描版 | `set` O(1)、`get` O(m)；最坏 `O(n²) ≈ 4 × 10^10` | O(n) |
| 理论下界 | `set` Ω(1)、`get` Ω(log m) | O(n) |

- `set` 是**真 O(1) 均摊**：`append` 到列表尾部 + `defaultdict` 的 miss 建表。
- `get` 的下界论证：`get` 必须在「已写入的 m 个时间戳」中找出 `<= ts` 的最大者，这等价于在一个大小为 m 的有序集合上做**前驱查询**；比较模型下前驱查询的判定树深度是 `Ω(log m)`。本解正好取到 `O(log m)` ⇒ **渐进上已到最优**，不存在更优的大 O。
- 空间：每个 `key` 一个 Python 对象（list）承载其日志，每条写入一个二元组 ⇒ 与写入次数线性相关，与 `get` 次数无关（`defaultdict` 的插入副作用至多再引入「被查询过但未写入的 key 的数目」个空列表）。

## 五、优化评估

**结论**：**渐进上已是最优**（`set` O(1)、`get` O(log m) 触达前驱查询下界）。常数层面确实存在**可稳定复现的改写**，但**没有任何一个版本在四个场景里全胜**：

- 平行数组（B）在「深日志」「混合读写」「大量 miss」三档**逐轮稳定领先**（最快约 **1.8×**），在「一 key 一写」的宽表档只是**打平**（逐轮 0.93× ~ 1.03×）—— 是本次唯一"没有一档稳定落后"的候选；
- 手写二分（A3）**逐轮稳定更慢**（深日志档 **2.02× ~ 2.33×**）—— 本次唯一被明确证伪的改法；
- 其余两个候选（A2 少建表、C 哨兵键）各自只在**一个场景**稳定领先，属局部优化。

⇒ 是否替换用户原版取决于线上负载形态；若不确定，**保留原版**是安全选择（原版没有任何一档落后于这些候选）。

### 瓶颈分析

`get` 的一次调用 = ① 一次 dict 查找 + ② 构造搜索键 `(timestamp + 1, )`（一个元组 + 一个 `timestamp+1` 整数对象）+ ③ 一次 C 层 `_bisect`（每次比较先比 `t`，`t` 不等时短路、不碰字符串）。
`set` 的一次调用 = ① 一次 dict 查找（miss 时由 `defaultdict` 建表）+ ② 一个二元组分配 + ③ 一次 `append`。

⇒ 可动的只有三处：**搜索键的构造**、**载体的装箱方式**（元组 vs 平行数组）、**miss 路径的建表**。

### 可优化空间（逐个给机理）

1. **平行数组（B）—— 卖点是「搜索键零构造 + 纯整数比较」**：把 `(t, v)` 二元组拆成 `ts` 与 `vs` 两条平行数组后，`get` 直接 `bisect_right(ts_list, timestamp)`，**不需要构造任何搜索键对象**，二分时也退化成纯 `int` 比较（省掉每次比较那一层元组比较）。
   实测：深日志 0.55 ~ 0.66×、混合 0.60 ~ 0.70×、miss 0.82 ~ 0.88×（**三档逐轮稳定领先**）；宽表档 0.93 ~ 1.03×（**打平**，因为那里 `set` 的份额变成 100%，而它把 `set` 从「1 次 dict 查找 + 1 次 append」变成「2 次 append + 2 次 dict 查找」）。
   ⇒ **收益方向由「每个 key 的平均写入深度」决定**：写得越深越赚，几乎不重写就归零，但**不会反噬**。
2. **哨兵键（C）—— 省掉 `timestamp + 1` 的整数分配**：把「+1 再构造一元组」换成「原时间戳 + 一个常量哨兵字符串」（题面保证 `value` 只含小写字母与数字 ⇒ `'\uffff'` 大于任何合法 `value`）。等价性：`bisect_right(a, (ts, '\uffff'))` = 首个 `(t, v) > (ts, '\uffff')` 的下标 = `#{t <= ts}`。
   实测：只把 **wide 档**打到 0.77 ~ 0.94×（稳定的 1.1 ~ 1.3×）；focus / miss / mixed 三档**都跨过 1.0** ⇒ 只能当"浅二分的局部优化"。注意它把比较多推进一步（`t == ts` 时要比字符串），**在"查询时间戳大量命中已有时间戳"的输入上恰是最坏形态**，而本次 wide 档正是这种输入（10 万次查询全 `t == 1`）仍能领先 ⇒ 主导因素是省掉的那个整数对象。
3. **`dict.get` 替代 `defaultdict[key]`（A2）—— 只在 miss 路径生效**：`get` 里用 `dict.get(key)` + `if a is None: return ''`，既避免 `defaultdict` 在 miss 时**插入空列表**（10 万次 = 10 万个 `list` 对象 + 10 万次扩容），也省掉一次重复 dict 查找。实测 miss 档 0.70 ~ 0.73×（**稳定 1.4×**）、mixed 0.91 ~ 0.94×（小幅稳定）；focus / wide 跨 1.0 ⇒ **收益完全来自"查询未写过的 key"这一条路径**。
4. **被证伪：把 `bisect` 换成手写 `lower_bound`（A3）** —— 深日志档 **2.02 ~ 2.33× 更慢**、混合档 1.23 ~ 1.38× 更慢、宽表档 1.06 ~ 1.18× 更慢，**四档无一轮更快**。机理：`log m ≈ 17` 次迭代全部落在 Python 解释器里（每次还要做一次 `a[mid] < probe` 的元组比较），而 `bisect` 是 C 层实现。⇒ **本题上"手写二分"是纯粹的负优化，不因"更可控"而有价值。**
5. **`defaultdict(list)` 换 `dict.setdefault` 一类的"少一层工厂"改法未实测**，不写结论；本次只实证了上面 5 个版本。

### 优化代码

若负载是「**少数 key 反复写、`get` 远多于 `set`**」（深日志），可用下面的 B（平行数组 + 两个 dict）：

```python
from bisect import bisect_right


class TimeMap:

    def __init__(self):
        self.ts = {}
        self.vs = {}

    def set(self, key: str, value: str, timestamp: int) -> None:
        a = self.ts.get(key)
        if a is None:
            self.ts[key] = [timestamp]
            self.vs[key] = [value]
        else:
            a.append(timestamp)
            self.vs[key].append(value)

    def get(self, key: str, timestamp: int) -> str:
        a = self.ts.get(key)
        if not a:
            return ''
        j = bisect_right(a, timestamp) - 1
        return self.vs[key][j] if j > -1 else ''
```

**优化理由**：`get` 不再构造任何搜索键（省一个元组 + 一个整数对象），二分退化为纯整数比较；实测深日志档 **1.5 ~ 1.8×**、混合档 **1.4 ~ 1.7×**、miss 档 **1.14 ~ 1.23×**，宽表档打平。**没有任何一档稳定落后**。
**代价与耦合（必须一并知道）**：① `set` 要维护两条数组，代码比原版长；② 两条数组必须**恒等长**（`ts[i] ↔ vs[i]`），任何只动一边的改写（例如"相邻同值写入去重"）都会破坏对应关系；③ 查不到 key 时用 `ts` 判断即可，但 `vs` 必须与它同步存在，否则 `vs[key]` 会 `KeyError`。

### 常数级优化

- **`set` 里不需要排序 / 不需要插入到中间**：时间戳严格递增 ⇒ `append` 后仍有序，这是本题最重要的常数前提。
- **不要手写二分**：实测四档全慢（深日志档 2.02 ~ 2.33×）。`bisect` 是 C 实现，本题的二分深度可达 `log2(2×10^5) ≈ 17` 层，写进 Python 层就是 17 次解释器循环。
- **原版 `get` 里 `self.cnt[key]` 出现两次**（一次进 `bisect`、一次取返回值），缓存成局部变量可省一次 dict 查找 —— 但实测在非 miss 场景落在 0.94 ~ 1.02×，**跨过 1.0、属噪声**，不足以单独作为改写理由（真正有价值的那部分是"miss 时不建表"，见 A2）。

## 六、易错点与总结

### 易错点

- **`j > -1` 守卫漏写 ⇒ 静默错解**（不报错！）：空日志时 `bisect` 返回 0、`j = -1`，`a[-1]` 会取到最后一条记录。最小反例 2 次调用：`set("a","x",1)` + `get("a",0)`（真值 `""`、实得 `"x"`）。这是「**负索引静默取尾**」的典型，属 §3.6「顺手查负索引」那一类。
- **`get` 里查询「从未写过的 key」不要忘了早退**：`defaultdict` 会顺手插入空列表，虽然答案仍对，但白白付建表代价（实测该路径让"全 miss"场景总耗时多出约 **40%**）。
- **元组比较的短路规则要清楚**：`(t, v)` 与 `(timestamp + 1, )` 的长度不同，`t == timestamp + 1` 时靠「更长的元组更大」这条规则把该记录排除在"小于"之外 —— 换成一元组 / 标量顺手写错就会把边界算错一位。
- **别用 `bisect_left` 去"近似"实现 `bisect_right` 的语义**：在这道题里 `bisect_left(a, (ts+1,))` 与 `bisect_right(a, (ts, 哨兵))` 恰好等价，但这个等价**依赖元素是整数时间戳**（`t <= ts ⟺ t < ts + 1`）；把时间戳换成浮点立刻失效。
- **`defaultdict` 的读会变成写**：`d[k]` 在键不存在时静默插入，`d.get(k)` 不会。本题因键有界不影响正确性，但属"读操作改状态"，长期持有实例时要注意。

### 题型套路沉淀

- **「按时间戳追加」就是天然的排序**：凡是题面保证「时间戳严格递增」的设计题，写入侧永远只需要 `append`，查询侧一律翻译成**有序序列上的边界定位**。识别信号：`set(k, v, t)` / 「返回 `t_prev <= t` 中最大的那个」。
- **「找最大的 ≤ x」的标准动作 = 数前缀 + 退一格**：`k = bisect_right(a, x)`（或等价的 `bisect_left(a, x+1)`），答案在 `k - 1`；`k == 0` 就是"不存在"分支 —— 这一句几乎可以照抄到所有前驱查询题上。
- **这族题的第一件事是论证「有序性从哪来」**：题面直接给有序数组 / 靠元素非负推出的前缀和有序 / 靠 append 顺序得到的日志有序 / 靠遍历顺序得到的「值 → 下标表」有序 —— 四种来源都要在笔记里单独点一句，否则二分前提是悬空的。
- **常数优化要按「每个 key 的平均写入深度」分档验证**：平行数组这类"拆箱换零构造"的改法，在深日志上稳定赚 1.5 ~ 1.8×，在"一 key 一写"的宽表档收益归零（`set` 的份额涨到 100%）—— **同一个改动在不同输入结构下收益差一个量级**，必须分档测再下结论。
- **「取最优倍数」会骗人，必须看逐轮比值区间**：本次同一档在 7 轮里的比值有的跨到 1.0 两侧（如 wide 档 B2/A 为 1.00 ~ 1.51）⇒ 这类只能判"噪声内持平"，不能写进结论当收益。
- **手写二分在本题是纯负优化**：`bisect` 是 C 实现，而题面上限下二分深度可达 17 层（`log2(2×10^5)`），把循环写回 Python 层实测慢 **2.02 ~ 2.33×**（深日志档，四档无一轮更快）。
