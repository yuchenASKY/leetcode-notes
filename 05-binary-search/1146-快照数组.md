# 1146. 快照数组

> **难度**：中等
> **标签**：设计 · 二分查找 · 哈希表
> **原题链接**：https://leetcode.cn/problems/snapshot-array/

---

## 一、题目描述

维护一个长度固定、初值全为 `0` 的「快照数组」，支持三个操作：

- `set(index, val)`：把下标 `index` 处的值改成 `val`；
- `snap()`：给当前数组**拍一张快照**，返回这张快照的编号 `snap_id`（编号 = 调用 `snap()` 的总次数减一，即从 0 开始）；
- `get(index, snap_id)`：回到编号为 `snap_id` 的那张快照，读出下标 `index` 的值。

**关键约束**：`set` / `snap` / `get` 的**总调用次数不超过 5×10⁴**，而 `length` 最大也是 5×10⁴ —— 也就是说「操作次数」和「数组长度」是**同一个量级**，任何"每拍一次快照就复制一遍整个数组"的做法都会同时超时和爆内存。

### 示例

```text
输入：["SnapshotArray","set","snap","set","get"]
     [[3],[0,5],[],[0,6],[0,0]]
输出：[null,null,0,null,5]
解释：
SnapshotArray(3)            // 数组 = [0,0,0]
set(0,5)                    // 数组 = [5,0,0]
snap()  -> 0                // 拍下第 0 号快照
set(0,6)                    // 数组 = [6,0,0]（第 0 号快照不受影响）
get(0,0) -> 5               // 回到第 0 号快照，下标 0 处是 5
```

### 约束条件

- `1 <= length <= 50000`
- 题目最多进行 `50000` 次 `set`、`snap` 和 `get` 的调用（**三者合计**）
- `0 <= index < length`
- `0 <= snap_id <` 调用 `snap()` 的总次数
- `0 <= val <= 10^9`

## 二、解题思路

### 核心思想

**不按"版本"存整份数组，只按"时间"存增量写入。** 给每个下标单独维护一条 `(snap_id, val)` 的**写入日志**，`snap()` 只把快照号加一、不做任何拷贝；`get(index, snap_id)` 变成了在这条**天然有序**的日志上做一次二分：**最后一个 `snap_id ≤ 目标值` 的写入，就是答案**。

### 判据与判据族定位

**本题的判据**（可判定真假的命题）：

> `get(index, snap_id)` 的答案 = `history[index]` 中**最后一个 `stored_id ≤ snap_id` 的写入**所携带的 `val`；若不存在这样的写入，答案为初始值 `0`。

**判据族定位**：本题属 `05-binary-search` 下的「**有序序列上的单调谓词边界定位**」族（二分的对象是**下标**，而不是答案值）。本族的载体可以有多种：数组自身有序、前缀和有序、值 → 有序下标表、以及本题的「**每个 key 各自一条按时间递增的写入日志**」。四者的 `while` 写法与边界处理一致，但**判据各有不同，不得互相套用**。

本题**不属于**滑动窗口族（那一族的判据形式是「窗口合法 ⟺ 某个窗口内计数关系成立」），本族的判据与滑动窗口的判据没有任何可迁移之处。

### 思路演进

1. **暴力解法 —— 快照时整数组拷贝**：`set` 改当前数组，`snap()` 把当前数组 `arr[:]` 深拷贝一份塞进 `snapshots` 列表，`get` 直接 `snapshots[snap_id][index]`。

   ```python
   class SnapshotArray:
       def __init__(self, length):
           self.arr = [0] * length
           self.snaps = []

       def set(self, index, val):
           self.arr[index] = val

       def snap(self):
           self.snaps.append(self.arr[:])       # ← 瓶颈
           return len(self.snaps) - 1

       def get(self, index, snap_id):
           return self.snaps[snap_id][index]
   ```

   `set` / `get` 都是 O(1)，但 `snap` 是 **O(length)**。

2. **瓶颈定位**：拷贝量与"这一版快照到底改了什么"**完全无关** —— 一次 `snap()` 无论中间改过 0 个还是 5×10⁴ 个元素，都要付出 `length` 次拷贝。根因是它**按下标展开**，而信息是**按时间产生的**：题面给的总预算只有 5×10⁴ 次调用，即整串调用里最多发生 5×10⁴ 次写入，却要为每一次 `snap` 付 `length` 次拷贝。

   最坏情况（`length` 取满 5×10⁴、snap 次数取到预算允许的量级）下拷贝总量按 `S × length` 线性放大到 **10⁹ 元素**、快照裸内存到 **10 GB** 量级。实测（`length = 5×10⁴`）：20 次 snap 要 3.99 ms、200 次要 41.05 ms 且已占 80 MB、500 次要 111.29 ms 且已占 200 MB —— 而这 500 次只占 snap 预算的约 1/50。⇒ 朴素解必然 TLE + MLE。

3. **关键转化**：把存储的展开方向从「**按快照号 → 整数组**」翻转成「**按下标 → 写入日志**」。

   对每个 `index` 只记录真正发生过的写入，日志按 `(snap_id, val)` 追加。**这一步能成立的关键是：日志天然按 `snap_id` 递增。** 因为 `snap_id` 是全局单调不减的，而 append 的顺序就是时间顺序 —— 于是"某个快照里这个下标是多少"就等价于"日志里最后一个时间 ≤ 该快照的写入"，变成**有序数组上的右边界定位**，一次 `bisect` 解决。

   一句话：原来不行，是因为它按下标做无差别拷贝、与变化的稀疏性无关；现在行，是因为只记录发生过的写入，而记录的先后顺序**本身就是时间序**，右边界定位一次二分即可。

4. **最优解**：见「三、代码实现」。`snap()` 退化成一次整数自增，`set` 是一次 `append`，只有 `get` 需要 O(log k)。

### 关键点

- **日志的有序性来自"构造"，不是题目给的。** 原始数据（数组）本身毫无顺序，是"按时间 append"这一点给了日志有序性 —— 这是整个解法的地基，写这类题时值得单独论证一句。
- **`bisect_left(history, (snap_id + 1,)) - 1` 为什么对**：靠两点。① `history` 的元素是 `(snap_id, val)` **二元组，首元素决定字典序大小**（首元素不等时根本不会去比值）；② 对整数而言 `stored_id < snap_id + 1 ⟺ stored_id <= snap_id`（**整数性**，与值域是否连续、是否有重复无关）。因此 `bisect_left` 的返回值恰好 = "日志里 `stored_id ≤ snap_id` 的条数"，减一就是最后一条的下标。
- **`j >= 0` 守卫不可省**：`j == -1` 说明该下标在 `snap_id` 时刻**从未被写过**，答案应是初始值 `0`；若直接 `history[index][-1]`，会命中 Python 的**负索引**、静默取到"该下标最后一次写入"的值（那个写入的快照号**大于**查询的 `snap_id`），不报错但结果错。
- **初始值 `0` 与"显式 `set(index, 0)`"返回的都是 `0`**，判断依据只能是 `j >= 0`（有没有写入过），**不能是"值是不是 0"**。
- `snap()` 的编号规则是"**调用 snap 的总次数减一**"，第一次必须返回 `0`。

## 三、代码实现

### 最终代码

> 代码来自本人已提交通过的版本；截图里缺 `defaultdict` / `bisect_left` 的 import，**已补全**。

```python
from collections import defaultdict
from bisect import bisect_left


class SnapshotArray:

    def __init__(self, length: int):
        self.cur_snap_id = 0
        self.history = defaultdict(list)

    def set(self, index: int, val: int) -> None:
        self.history[index].append((self.cur_snap_id, val))

    def snap(self) -> int:
        self.cur_snap_id += 1
        return self.cur_snap_id - 1

    def get(self, index: int, snap_id: int) -> int:
        j = bisect_left(self.history[index], (snap_id + 1,)) - 1
        return self.history[index][j][1] if j >= 0 else 0
```

**写法说明**

- `snap()` 写成"先自增、再返回自增后的值减一"，与"先返回、再自增"等价；两种都行，但**不能直接返回自增后的值**（那样编号整体偏移 1）。
- `history` 是 `defaultdict(list)`：`set` 里 `self.history[index]` 在键不存在时自动建表；`get` 里对"只查过没写过"的下标也会建一个空 list（见「六、易错点」的"读变写"）。

## 四、复杂度分析

**符号约定**：`length` = 数组长度（≤ 5×10⁴）；`C` = `set` + `snap` + `get` 的总调用次数（≤ 5×10⁴）；`W` = `set` 次数；`S` = `snap` 次数；`Q` = `get` 次数；`k` = 某个下标被写入的次数（`k ≤ W`）。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | `set` O(1) 摊还 · `snap` O(1) · `get` O(log k) ⇒ 整体 O(C + Q·log W) | O(W + 被 get 触碰过的不同下标数) |
| 朴素解法（快照时整数组拷贝） | `set` O(1) · `snap` **O(length)** · `get` O(1) ⇒ 整体 O(C + S·length) | O(S · length) |
| 理论下界 | `set`/`snap` 已 Ω(1)；`get` 在比较模型下 Ω(log k) | Ω(W) |

> 最后一行空间里多出的"被 get 触碰过的下标数"来自 `defaultdict` 的"读变写"（`get` 会为未写入过的下标建一个空表）；两项都 ≤ `C`，所以本质仍是 **O(C)**，且与 `length` **无关** —— 这正是本题的要义。

**与朴素解的量级对比**：`length` 与 `S` 同时取满题面预算时，最终代码的 `get` 是 O(log 5×10⁴) ≈ 16 次比较；朴素解的 `snap` 是 5×10⁴ 次元素拷贝。二者在"总拷贝/比较次数"上差三个数量级以上。

## 五、优化评估

**结论**：**渐进复杂度已达下界，但常数上仍有明确可挖的空间** —— 本次实测出一个在 6 档场景上**全部领先**的改写版本（相对用户版 1.09× ~ 2.21×）。

### 瓶颈分析

时间几乎全部落在两处：

1. **每次 `get` 的二分**：用户版二分的是**元组列表**，每次比较都要走一遍元组的字典序比较；
2. **每个接口的 `self.history[index]` 字典查找**：`defaultdict.__missing__` 在"未写入过的下标"上会**凭空新建一个空 list**，而 `get` 里这一行还出现了**两次**。

`set` / `snap` 本身已经极廉价（各一次 `list.append` / 一次整数自增），无成本可挖。

### 拆开归因的实测

**测量方式**：6 档场景，每档一次完整回放（5×10⁴ 次 `set`/`snap`/`get` 混合调用），**9 个版本在同一轮里轮转测量、7 轮取最优**；复跑一次方向一致、各档差异 ≤ 4%。表中为**绝对耗时 ms（相对用户版 A 的倍数，> 1 表示更快）**。

| 版本（改动点） | focus 少量下标高频写 | spread 每次写不同下标 | readheavy 95% 是 get | writeheavy 90% 是 set | repeat 反复写同一个值 | dense 覆盖满 length |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **A**（用户版，基准） | 16.11 (1.00×) | 18.31 (1.00×) | 15.93 (1.00×) | 9.29 (1.00×) | 16.74 (1.00×) | 13.60 (1.00×) |
| A_key（键换 `(snap_id, INF)`） | 16.04 (1.00×) | 17.66 (1.04×) | 14.03 (1.14×) | 9.20 (1.01×) | 16.07 (1.04×) | 12.58 (1.08×) |
| A_sent（改键 + `bisect_right`） | 15.85 (1.02×) | 17.12 (1.07×) | 14.89 (1.07×) | 9.41 (0.99×) | 15.81 (1.06×) | 12.53 (1.09×) |
| A_fixed（`defaultdict` → 定长 list） | 19.20 (0.84×) | 16.50 (1.11×) | 13.42 (1.19×) | 12.18 (0.76×) | 18.78 (0.89×) | 11.64 (1.17×) |
| B（平行数组，二分只比整数） | 11.89 (1.36×) | 21.89 (0.84×) | 14.17 (1.12×) | 8.36 (1.11×) | 12.05 (1.39×) | 11.38 (1.20×) |
| B6（B + 单一 dict，lambda 工厂） | 11.05 (1.46×) | 23.69 (0.77×) | 20.29 (0.79×) | 7.54 (1.23×) | 10.41 (1.61×) | 10.28 (1.32×) |
| B6_dedup（B6 + 相邻同值去重） | 11.95 (1.35×) | 23.54 (0.78×) | 20.38 (0.78×) | 9.09 (1.02×) | 10.72 (1.56×) | 11.45 (1.19×) |
| **B7（B6 的 `dict.get` 改写）** | **11.48 (1.40×)** | **16.72 (1.09×)** | **7.20 (2.21×)** | **8.32 (1.12×)** | **11.28 (1.48×)** | **10.42 (1.31×)** |
| B6_fixed（B6 + 定长） | 20.66 (0.78×) | 26.14 (0.70×) | 21.83 (0.73×) | 18.29 (0.51×) | 20.51 (0.82×) | 9.25 (1.47×) |

**逐项归因**（每一步只改一处，才能把功劳落到正确的项上）：

1. **平行数组（A → B）**：把 `(snap_id, val)` 二元组拆成两个平行 list（`sids` / `vals`），二分只比整数、不再构造元组、不再走字典序比较。收益集中在**二分深度大**的档：focus **1.36×**、repeat **1.39×**、dense 1.20×。
   ⚠️ 但 spread 档 **0.84×（回退）** —— 那一档每个下标平均只被写 1 次，二分长度 ≈ 1，成本全落在哈希上，而 B 有**两个** `defaultdict`、每 op 要做两次字典查找。⇒ **平行数组不是无条件优化，它用"每 op 多一次字典查找"换"二分时少一层元组比较"。**

2. **单一 dict + 工厂函数（B → B6）**：focus 1.46× / writeheavy 1.23×，但 spread / readheavy 掉到 **0.77× / 0.79×** —— 因为 `defaultdict(lambda: ([], []))` 在 miss 时要一次新建 **1 个 tuple + 2 个 list**，而用户版的 `defaultdict(list)` 只建 1 个 list。

3. **miss 早退 + 零分配（B6 → B7）**：把工厂换成 `self.history.get(index)` + `if pair is None: return 0`，miss 时**一个对象都不建**。readheavy 从 0.79× 直接跳到 **2.21×**，spread 从 0.77× 转正到 1.09× ⇒ 六档全部领先。
   这一项同时解释了用户版在 readheavy 档为什么最慢：`self.history[index]` 对未写入过的下标会新建空 list，而这一行在 `get` 里**出现了两次**。

### 被证伪 / 被排除的改法

- **定长 `[[] for _ in range(length)]`——不推荐**。`length` 取满 5×10⁴ 时，光分配 5×10⁴ 个空 list 的固定成本就要 **2.02 ms**（实测：length = 100 → 0.002 ms、10⁴ → 0.38 ms、5×10⁴ → 2.02 ms），这在总共十几毫秒的预算里是纯开销。实测 A_fixed 只在小 `length` 档转正（dense 1.17×），大 `length` 档一律亏（**0.76× ~ 0.89×**）；B6_fixed 更差（**0.51× ~ 0.83×**），因为它要一次建 5×10⁴ 个 tuple + 10⁵ 个 list。
  ⇒ 判据：**只有 `length` 与"实际会被写到的下标数"同量级、且 `length` 本身不大时**（本题 `dense` 档 length = 1000）才值得。
- **相邻同值写入去重——不推荐**。B6_dedup 相对 B6 在 writeheavy 档 **0.81× ~ 0.84×（明显更慢）**（那一档值池 1000、几乎不去重，白付一次 `v[-1] == val` 比较），在 repeat 档（值池只有 2、本就大量重复）也只有 0.99× ~ 1.03×、**落在噪声内** ⇒ 净负。
- **`bisect_left` / `bisect_right` 之争在本写法里不构成独立变量**。本题的搜索键**一定不在**数组中（日志里只存 ≤ 当前快照号的写入，而键是 `(snap_id+1,)` 或 `(snap_id, INF)`），此时两者在 CPython 的 `_bisect` 里走同一条路径、结果必然相同。实测 A_key（只改键）与 A_sent（改键 + 换 `bisect_right`）两轮都落在同一条噪声带里、互有胜负 ⇒ **能动的只有"键怎么构造"，不是"用哪个 bisect"**。二者相对用户版本轮为 1.00× ~ 1.14×，属小幅常数收益（focus / writeheavy 两档复跑时回落到 1.00× / 1.01×），不要把它当主要收益来源。

### 为什么不可能更好（渐进下界）

- **`set` / `snap` 已无可降**：一次 `append` / 一次整数自增，本身即 Ω(1)。
- **`get` 的下界是 Ω(log k)**：该下标共被写过 `k` 次，答案必是这 `k` 条记录之一的 `val`（或初始值 `0`），`k+1` 个候选互不相同。在只允许比较的模型下，把这 `k+1` 种可能区分开至少要 `log₂(k+1)` 次比较 ⇒ 一次二分 O(log k) 已是下界，**无渐进改进空间**。
- **空间下界 Ω(W)**：每次写入都可能成为某个查询的答案，`snap()` 不能丢弃任何一次写入，必须保留其 (时间, 值)。

### 优化代码

```python
from bisect import bisect_right


class SnapshotArray:
    """平行数组 + 单一 dict + miss 早退。
    实测：6 档场景全部领先用户版 1.09× ~ 2.21×（详见「七、验证记录」）。"""

    def __init__(self, length: int):
        self.cur_snap_id = 0
        # index -> (snap 号列表, 与之逐位对应的值列表)；两个列表都按 snap 号严格非降
        self.history = {}

    def set(self, index: int, val: int) -> None:
        pair = self.history.get(index)
        if pair is None:                 # 该下标第一次被写：建一对空表
            pair = ([], [])
            self.history[index] = pair
        pair[0].append(self.cur_snap_id)
        pair[1].append(val)

    def snap(self) -> int:
        self.cur_snap_id += 1
        return self.cur_snap_id - 1

    def get(self, index: int, snap_id: int) -> int:
        pair = self.history.get(index)
        if pair is None:                 # 从未写过 ⇒ 就是初始值 0，且不新建任何对象
            return 0
        sids, vals = pair
        j = bisect_right(sids, snap_id) - 1
        return vals[j] if j >= 0 else 0
```

**优化理由**（三处改动各管一件事，均已单独实测归因）：

1. **平行数组**：二分只比整数，省掉每次比较的元组字典序比较 —— 二分越深收益越大（focus 1.36×、repeat 1.39×）。
2. **单一 dict**：每 op 的字典查找从 2 次降到 1 次。
3. **`.get` + 早退**：把"查询从未写入过的下标"这条最坏路径变成**零对象分配**（readheavy 2.21×）—— 这是本次收益最大的一项。

**使用前提（两条，缺一不可）**：

- 下标必须是**有界的整数键**（本题 `0 <= index < length` 满足），才能用 `dict` / 定长数组做外层索引；
- 两个平行 list 必须**恒等长**，写日志时**成对 append**。任何"只动一边"的改法（比如只在值没变化时跳过一次 append）都会破坏 `sids[j] ↔ vals[j]` 的对应关系 —— 本次实测的去重版正是因此多付一次比较而净负，已排除。

> 若本题的 `length` 很小（与调用次数同量级），可再把外层 `dict` 换成定长数组以省掉一次哈希（B6_fixed 在 dense 档 1.47× 优于 B6 的 1.32×）；但 `length = 5×10⁴` 时固定分配成本 2.02 ms 会把收益吃光 —— **按 `length` 的大小选结构**。本次未在 B7 上叠加测这一项。

### 常数级优化（可选）

- **键的构造**：`(snap_id, float('inf'))` 比 `(snap_id + 1,)` 少一次整数对象创建（`snap_id + 1 > 256` 时是新对象），实测 1.00× ~ 1.14×，幅度小、看场景。
- **不要在热路径里重复取同一个值**：用户版 `get` 里 `self.history[index]` 出现了两次，多一次完整字典查找（也是"读变写"的第二次触发）。
- 二分前先把 `sids, vals = pair` 解包到局部变量，避免多次元组索引。
- 去重、定长两个方向在本写法里**已实测为净负或不稳定**，不要顺手加上。

## 六、易错点与总结

### 易错点

- **`j >= 0` 守卫不可省（本题最危险的坑）**。删掉之后 `history[index][-1]` 会走 Python 的**负索引**、静默取到该下标**最后一次**写入的值 —— 而那个写入的快照号**大于**查询的 `snap_id`，程序不报错、结果错。触发条件是"该下标在 `snap_id` 时刻从未被写过，但之后被写过"，非常容易在随机数据里出现：本次实测 30 组小用例中 **14 组抛 `IndexError`、1 组静默错解**；穷举 `length = 1`、调用数 ≤ 4 的**全部合法序列**后，最小静默反例只要 3 次调用：

  ```text
  snap()  -> 0
  set(0, 1)
  get(0, 0)   // 快照 0 拍摄时下标 0 还是 0 ⇒ 真值 0；删守卫版返回 1（取到了快照号 1 的写入）
  ```

  ⇒ 与"抛异常"相比，"负索引静默取尾"这一类更难被发现，**必须靠对拍而不是靠官方示例**。
- **不要把 `cur_snap_id` 当成"当前快照号"直接用**：题面规定 `snap()` 返回"调用 `snap()` 的总次数减一"，第一次必须返回 `0`。用户版写成"先自增、再返回自增后的值减一"，与"先返回、再自增"等价；但若直接返回自增后的值，编号整体偏移 1，首组用例即错。
- **元组必须存成 `(snap_id, val)`**：顺序反了（存成 `(val, snap_id)`）时二分仍能跑，但比的是值的大小，结果无意义。
- **`val = 0` 的显式写入与"从未写过"返回的都是 `0`**：区分依据只能是 `j >= 0`（有没有写过），不能是"值是不是 0"。
- **`defaultdict` 的"读变写"**：`d[key]` 在键不存在时会**静默插入**。用户版 `get` 里两次 `self.history[index]` 会给"只被查过、没被写过"的下标各建一个空 list。本题不构成正确性问题（下标值域有界），但会额外吃内存，也正是本次性能优化要消掉的主要成本之一。

### 题型套路沉淀

- **「版本 / 快照 / 时间旅行」类的通式**：不要按版本号整块拷贝状态，改成**按时间追加增量日志** —— 每个 key 一条 `(版本号, 值)`，查询就是"在有序日志上定位 `≤ 目标版本` 的右边界"。识别信号：题面出现 snapshot / version / undo / point-in-time query 这类词。
- **二分的前置条件可以自己造**：本题原始数据毫无顺序，有序性是 **append 的时间顺序**给的。写这类题时，把"有序性从哪里来"单独论证一句 —— 前提一旦不成立（例如日志不是单调追加的），二分立刻失效。
- **整数性支撑的等价改写**：`stored_id ≤ snap_id ⟺ stored_id < snap_id + 1`，所以 `bisect_left(a, x + 1)` 与 `bisect_right(a, x)` 在这一族里是等价的；但这类等价**只依赖"两侧都是整数"**，题面允许浮点时立刻失效。
- **设计题必须分接口报复杂度**（`set` / `snap` / `get` 各自是多少），并指出各接口被调用的**总次数上界** —— 否则"摊还 O(1)"根本无从谈起。
- **判据族不通用**：本族的判据形式是「在**有序序列**上定位谓词边界」，与滑动窗口族（「窗口合法 ⟺ 某计数关系」）在结构上毫无交集，两边结论不可互相搬用。同族内部也要小心：二分"值区间两端"与二分"谓词边界"写法相近但判据不同。

## 七、验证记录

**验证范围（按约定）**：截图版用户代码为本人**已提交并通过**的版本，其正确性不再重复验证；参与对拍的是本次新写的 7 个变体（`B` / `B6` / `B6_dedup` / `B7` / `A_key` / `A_sent` / `A_fixed`）与 2 个暴力基准。

**1. 暴力基准自检**：用两条**互相独立**的暴力路线现互查 —— `BruteCopy`（`snap` 时整数组拷贝）与 `BruteReplay`（记下全部 `(当时的 snap 号, index, val)`，`get` 时从头重放取最后一次满足条件的写入）。12 组小用例（`length ≤ 8`、共 91 次 `get`）输出完全一致，偏差 0 ⇒ 基准可信。

**2. 官方示例**：通过（`snap()` 返回 `0`，`get(0, 0)` 返回 `5`）。

**3. 手工构造用例**：10 组 × 9 个实现 = **90 次比对，偏差 0**。覆盖：从未 `set` 返回 0 / 同一 snap 内连写两次取最后一次 / 显式 `set(index, 0)` / 跨下标互不干扰 / 连续 `snap` 无写入 / 值来回变 / `val = 10^9` 上界 / 两个快照各取各的 / `get` 与 `set` 交替。

**4. 随机对拍**：30 组（`length ≤ 12`、每个操作序列 ≤ 25 次调用，其中 21 组含 `get`），`B` / `B6` / `B6_dedup` / `B7` / `A_key` / `A_sent` / `A_fixed` **偏差全部为 0**。

**5. 删守卫（`j >= 0`）再对拍**：30 组中 **14 组抛 `IndexError`、1 组静默错解**。穷举 `length = 1`、调用数 ≤ 4 的全部合法操作序列，最小**静默**反例 = **`[snap, set(0,1), get(0,0)]`（3 次调用）**，真值 `0`、实得 `1`。（抛异常那一类第一组就暴露，静默那一类必须逐组比对才看得出来。）

**6. 实测表**：见「五、优化评估」中的 6 档 × 9 版本表 —— 每档一次完整回放（5×10⁴ 次调用），9 个版本**在同一轮里轮转**、7 轮取最优；复跑一次方向一致，各档差异 ≤ 4%。

**7. 定长 history 的分配成本**（9 轮取最优）：`[[] for _ in range(V)]` 在 V = 100 → **0.002 ms**、V = 10⁴ → **0.38 ms**、V = 5×10⁴ → **2.02 ms**。这是"定长在大 `length` 档必然亏损"的直接原因。

**8. 朴素解的实测成本**（`length = 5×10⁴`，同时列出同输入的最终优化版 B7）：

| snap 次数 | 总调用次数 | BruteCopy（整数组拷贝） | B7 | 拷贝量 | 快照裸内存 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 20 | 40 | 3.99 ms | 0.035 ms | 1.0 M 元素 | 8 MB |
| 200 | 400 | 41.05 ms | 0.341 ms | 10.0 M 元素 | 80 MB |
| 500 | 1000 | 111.29 ms | 0.251 ms | 25.0 M 元素 | 200 MB |

单次 `snap()` 的拷贝成本稳定在约 **0.22 ms**（`length = 5×10⁴`）。按 `S × length` 线性推算，当 `length` 与 snap 次数同时逼近题面预算（5×10⁴ 与 ~2.5×10⁴）时，拷贝量到 **10⁹ 元素**、快照裸内存到 **10 GB** 量级 ⇒ 朴素解**必然同时 TLE 与 MLE**（上表 500 次 snap 仅占 snap 预算的约 1/50）。
