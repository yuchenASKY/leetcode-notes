# 2300. 咒语和药水的成功对数

> **难度**：中等
> **标签**：数组 · 二分查找 · 排序
> **原题链接**：https://leetcode.cn/problems/successful-pairs-of-spells-and-potions/

---

## 一、题目描述

给两个正整数数组 `spells`（长度 `n`）与 `potions`（长度 `m`），再给一个整数 `success`。第 `i` 个咒语与第 `j` 瓶药水**能量相乘 ≥ `success`** 就算一对成功组合。要求返回长度 `n` 的数组 `pairs`，`pairs[i]` = 能与第 `i` 个咒语成功组合的药水**数目**。

### 示例

```text
示例 1
输入：spells = [5,1,3], potions = [1,2,3,4,5], success = 7
输出：[4,0,3]
解释：5 * [1,2,3,4,5] = [5,10,15,20,25] -> 4 个；
      1 * [...] -> 0 个；3 * [...] = [3,6,9,12,15] -> 3 个。

示例 2
输入：spells = [3,1,2], potions = [8,5,8], success = 16
输出：[2,0,2]
解释：3*8=24、3*5=15、3*8=24 -> 2 个；2*[8,5,8]=[16,10,16] -> 2 个（等于也算成功）。
```

### 约束条件

- `n == spells.length`，`m == potions.length`
- `1 <= n, m <= 10^5`
- `1 <= spells[i], potions[i] <= 10^5`
- `1 <= success <= 10^10`

## 二、解题思路

### 核心思想

**固定一个咒语 `s` 后，条件只跟药水有关：`p * s >= success` 等价于 `p >= ⌈success / s⌉`。** 右端是一个与 `p` 无关的**常数阈值**；于是把 `potions` 排序一次，对每个咒语只需二分找出**第一个 ≥ 阈值**的位置，其后缀长度就是答案。

### 判据与判据族定位

- **判据**：对整数 `p ≥ 1` 与整数 `s ≥ 1`，`p * s >= success ⟺ p >= ⌈success / s⌉`。
  等价性来自「`p` 取整数」：两边同时除以 `s` 得 `p >= success / s`，而满足它的最小整数恰是 `⌈success / s⌉`。
- **判据族**：本题属「**有序序列上的单调谓词边界定位**」（**下标二分**）族 —— 二分的是**数组下标**，谓词形如 `potions[k] >= t`，它关于 `k` 单调（排序后为先假后真），要定位的是真假分界点。标准动作是 `lower_bound`，Python 里就是 `bisect_left`；答案口径是「后缀长度 = `m - idx`」。
- **与相邻族的边界（本题最容易串的地方）**：
  - 与「**二分答案**」族不同：那一族二分的是**答案值**，谓词是 `check(x)` 可行性判定（最小化最大值 / 第 K 小 / 可行域二分）。本题阈值 `t` 是**已经算出来的常数**，二分的对象是下标，`while` 边界写法与它不同，不得互套。
  - 与「**滑动窗口 / 双指针**」族不同：本题不需要共享任何窗口状态。`potions` 排序后，每个 `spells[i]` 都是**独立**的查询；把 `success` 当成「窗口预算」去维护左右指针，属于把别的族的手法搬过来，本题用不上。

### 思路演进

1. **暴力解法**：对每个 `spells[i]` 遍历整个 `potions` 计数，时间 O(n·m) = 10^10 次乘法比较，在本题约束下必然超时。
2. **瓶颈定位**：内层循环在「对固定的 `s` 逐个试 `p`」。可实际上，固定 `s` 时条件对 `p` 是**单调**的（`p` 越大越容易满足），所以「满足条件的 `p`」在**值域**上天然是一段后缀。暴力做的是**无结构的线性扫描** —— 它没有利用这段结构，把「已排序的全体」当成「待逐个试的杂列表」。
3. **关键转化**：把「乘积比较」化成「单侧阈值比较」——`p * s >= success ⟺ p >= ⌈success / s⌉`。
   **为什么原来不行、现在行**：原来每个 `(s, p)` 都得算一次乘法再比较，n·m 次；把右侧写成只含 `s` 的常量后，同一个咒语的 m 次判定退化成「在有序数组里找一个分界点」这一次 `log m` 的定位。代价是**一次性排序** `potions`（O(m log m)），换来的是每个咒语从 O(m) 降到 O(log m)。
4. **最优解**：`potions.sort()` + 对每个咒语一次 `bisect_left`，总时间 O(m log m + n log m)。它离理论下界（Ω(n + m)，见复杂度一节）还差两个 log 因子；在本题「值域有界 ≤ 10^5」的前提下，这条差距可以彻底消掉 —— 见「五、优化评估」的结构级优化。

### 关键点

- **二分合法性来自「谓词关于下标单调」**：排序后 `potions[k] >= t` 对 `k` 是「前假后真」，这正是能用 `bisect` 的充要条件。不排序就不能二分 —— 这是本题唯一的结构性前提。
- **阈值必须「向上取整」，不能用整除**：`p >= success / s` 的最小整数解是 `⌈success / s⌉`。若写成 `success // s`（下取整），当 `success` 不能被 `s` 整除时会**漏掉恰好命中的那一瓶**（`p * s == success` 的情形）。例如 `spells=[3], potions=[2], success=6`：真值 1，用 `//` 得阈值 2 会答 0。
- **返回的是数量，不是下标**：`pairs[i] = m - idx`（下标从 `idx` 到 `m-1` 都是合格药水）。写成 `idx` 是最常见的低级错。
- **不需要记录原始下标**：答案要的是「个数」，与 `potions` 的顺序无关，所以可以放心原地排序；而 `spells` 的结果必须与输入顺序对齐，所以用「按 `spells` 顺序遍历 + 逐个追加」保证。
- **恰好相等算成功**（`>=`，不是 `>`）—— 上取整已经天然包含了这一点。

## 三、代码实现

### 最终代码

```python
from bisect import bisect_left
from typing import List


class Solution:
    def successfulPairs(self, spells: List[int], potions: List[int], success: int) -> List[int]:
        potions.sort()                          # 排序一次，后续每个咒语一次二分
        ans = []
        for i in spells:
            target = success / i                # p * i >= success  <=>  p >= success / i
            tindex = bisect_left(potions, target)
            ans.append(len(potions) - tindex)   # 合格药水是一段后缀
        return ans
```

> **代码来源说明**：上图截自提交记录，第 1 行即 `class Solution:`，**算法逻辑一字未改**。
> 截图里没有 import —— LeetCode 的 Python3 运行环境预置了 `bisect` 等常用模块，本地运行需要显式导入；此处**只补全了 `from bisect import bisect_left` 与 `List` 的导入**，属「补全」而非「改写」。
> 截图为完整 9 行（编辑器状态栏为「行 9」，末行就是 `return ans`），**不存在尾部被裁掉的情况**。

## 四、复杂度分析

> 复杂度中的 `n` 指 `spells` 的长度、`m` 指 `potions` 的长度、`V` 指 `max(potions)`（本题 ≤ 10^5）。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(m log m + n log m) | O(n)（输出；排序原地） |
| 朴素解法 | O(n·m) | O(1) |
| 理论下界 | Ω(n + m) | O(1) |
| 值域桶优化（见下） | O(n + m + V) | O(V + n) |

**几点说明**：

- 最终代码的 `m log m` 只付一次，之后的 `n` 次查询各付 `log m` —— 这是「预处理换查询」的典型形态。
- 与**理论下界 Ω(n + m)**（至少要把输入读完、把 `n` 个答案写出来）相比，最终代码还差 `log m` 因子；在「值域有界」的额外前提下这个因子可以被消掉，所以**不能**说最终代码已达到下界。
- 与**朴素解**相比：`n = m = 10^5` 时朴素是 10^10 次比较，最终代码约 `10^5 × 17` 次比较量级，差 3 个数量级以上。注意：这是「复杂度层面的差距」，不是「本题能不能 AC」的差距 —— 见优化评估里的实测口径说明。

## 五、优化评估

**结论**：**仍有优化空间，而且有两条互不冲突的路线** ——
① 常数路线（整数上取整替代浮点除法）：实测 **1.45× ~ 1.96×**；
② 结构路线（值域桶 + 前缀和，消掉 `log m`）：`n = m = 10^5` 时实测 **2.1× ~ 2.9×**，但当 `V` 相对 `n` 偏大且 `n` 小时会**反向变慢**（`n = m = 2000, V = 10^5` 时慢 **4.6× ~ 5.4×**）。

### 瓶颈分析（阶段归因）

`n = m = 10^5`、`potions` 取 `[1, 10^5]` 随机值（9 轮轮转取最优）：

| 阶段 | 耗时 | 占比 |
| :--- | :--- | :--- |
| `potions.sort()` | 12.24 ms | 18.8% |
| 查询段（浮点除法 + `bisect_left` × n） | 52.72 ms | 81.2% |
| 合计（用户原版口径） | 64.96 ms | 100% |

把**查询段单独拿出来**对照（输入已排序，两版都含同样的局部绑定）：

| 查询实现 | 耗时（n = 10^5） | 单次 |
| :--- | :--- | :--- |
| `bisect_left(p, success / s)` | 52.72 ms | 0.527 μs |
| `bisect_left(p, (success + s - 1) // s)` | 33.34 ms | 0.333 μs |

⇒ **瓶颈明确落在「n 次查询」上，其中相当一部分不是二分本身，而是每轮一次的浮点除法。** 排序只占 19%，且它是 C 层实现（timsort），动它收益有限。

### 可优化空间 A（常数级）：整数上取整 + 列表推导

把「每轮一次浮点除法」换成整数上取整，并把 `for/append` 换成列表推导、把 `bisect_left` 与 `len` 绑到局部变量。**四项改动拆开归因**（`max(potions) = 10^5`，9 轮轮转取最优）：

| n = m | 原版 for+浮点 | 推导+整数 | for+整数 | 推导+浮点 |
| :--- | :--- | :--- | :--- | :--- |
| 2000 | 0.80 ms (1.00×) | 0.55 ms (**0.70×**) | 0.57 ms (0.72×) | 0.74 ms (0.93×) |
| 5000 | 2.29 ms (1.00×) | 1.56 ms (**0.68×**) | 1.59 ms (0.70×) | 2.12 ms (0.93×) |
| 10000 | 4.89 ms (1.00×) | 3.25 ms (**0.66×**) | 3.32 ms (0.68×) | 4.55 ms (0.93×) |
| 20000 | 10.35 ms (1.00×) | 6.91 ms (**0.67×**) | 7.11 ms (0.69×) | 9.84 ms (0.95×) |
| 50000 | 29.02 ms (1.00×) | 19.35 ms (**0.67×**) | 19.39 ms (0.67×) | 27.31 ms (0.94×) |
| 100000 | 62.61 ms (1.00×) | 41.63 ms (**0.66×**) | 42.42 ms (0.68×) | 59.64 ms (0.95×) |

**拆开后的结论（必须拆，否则会记错功劳）**：

- 「推导 + 浮点」这一列只到 0.93× ~ 0.95×，即**列表推导 + 局部绑定本身只值 1.05× ~ 1.08×**；
- 「for + 整数」0.67× ~ 0.72× 与「推导 + 整数」0.66× ~ 0.70× 几乎重合 ⇒ **主要收益（约 1.4×）来自把浮点除法换成整数上取整**，与列表推导基本无关。
- 机理：`success ≤ 10^10` 在 CPython 里是**两位数字**的大整数（`> 2^30`），`int / int` 走 `long_true_divide`（要先算出正确舍入的双精度商），而 `int // int` 走 `long_floor_divide`，前者常数更贵。

### 优化代码 A

```python
from bisect import bisect_left
from typing import List


class Solution:
    def successfulPairs(self, spells: List[int], potions: List[int], success: int) -> List[int]:
        potions.sort()
        bl = bisect_left                    # 局部绑定，省掉每轮的全局查找
        m = len(potions)
        # 整数上取整：等价于 ceil(success / s)，且不引入浮点
        return [m - bl(potions, (success + s - 1) // s) for s in spells]
```

**优化理由**：`p >= ⌈success/s⌉` 与 `p >= success/s` 在整数 `p` 上完全等价（见下「浮点写法为什么也安全」），但整数版本①不引入浮点，②沿用本题约束下实测快 **1.45× ~ 1.96×**。渐进复杂度不变，仍为 O(m log m + n log m)。

### 可优化空间 B（结构级）：值域桶 + 前缀和

`potions[i] ≤ 10^5` 是题面直接给出的**值域上界** ⇒ 可以完全绕开排序与二分：把 `potions` 丢进计数桶 `cnt[v]`，一次前缀和得到 `le[v] = #(potions <= v)`，则每个咒语的答案就是 `m - le[t-1]`（`t = ⌈success/s⌉`）—— **O(1) 查询，`log m` 因子被彻底消掉**。

`max(potions) = 10^5` 固定，`n = m` 从 2000 递增（9 轮轮转取最优，倍数 = 本版 / 原版）：

| n = m | 原版（排序+二分） | 桶 + 前缀和 | 结论 |
| :--- | :--- | :--- | :--- |
| 2000 | 0.80 ms (1.00×) | 3.67 ms (**4.61×**) | 明显更慢 |
| 5000 | 2.29 ms (1.00×) | 4.24 ms (1.85×) | 更慢 |
| 10000 | 4.89 ms (1.00×) | 5.10 ms (1.04×) | 打平（交叉点） |
| 20000 | 10.35 ms (1.00×) | 6.92 ms (**0.67×**) | 反超 |
| 50000 | 29.02 ms (1.00×) | 12.71 ms (**0.44×**) | 2.3× |
| 100000 | 62.61 ms (1.00×) | 22.46 ms (**0.36×**) | 2.8× |

再看**值域小**的那档（`potions` 随机取 `[1, 100]`，即 `max(potions) = 100`）：`n = m = 2000` 时桶版 0.45×、`n = m = 10^5` 时 0.34× —— **小值域下桶版连小规模都是赚的**。

⇒ **判据（由实测得出，不要只看「值域是否有界」）**：桶版的固定成本 ≈ `(V + 1) × 约 16 ns`（`[0]*(V+1)` 分配 + `accumulate` 扫一遍），必须靠 `n` 次查询把它摊薄。`V = 10^5` 时交叉点在 `n = m ≈ 1 万`；`V = 100` 时 `n = m = 2000` 就已经赚。**收益取决于 `V` 相对 `n` 的大小，而不是「值域小」这个标签本身。**

### 优化代码 B

```python
from itertools import accumulate
from typing import List


class Solution:
    def successfulPairs(self, spells: List[int], potions: List[int], success: int) -> List[int]:
        mx = max(potions)                       # 桶的上界（本题 ≤ 10^5）
        cnt = [0] * (mx + 1)
        for p in potions:
            cnt[p] += 1                         # 计数桶，O(m)，不需要排序
        le = list(accumulate(cnt))              # le[v] = #(potions <= v)，C 层前缀和
        m = len(potions)
        out = []
        ap = out.append
        for s in spells:
            t = (success + s - 1) // s          # 阈值上取整，恒 >= 1
            ap(m - le[t - 1] if t <= mx else 0)  # t > mx 时无药水合格
        return out
```

**优化理由**：用「值域桶 + 前缀和」把「排序 + 二分」整条路线替换掉，复杂度从 O(m log m + n log m) 降到 **O(n + m + V)**，且查询段全是 O(1) 数组访问（实测 `n = 10^5` 时查询段 15.58 ms，对比 `bisect_left` 整数版 33.34 ms，快 2.14×）。
**代价与适用条件**：空间由 O(1)（原地排序）升到 **O(V)**，且**要求值域有界并已知上界** —— 若把 `potions[i]` 放宽到 `10^9`，这个数组直接就爆了，此时只有二分路线可用。

### 被证伪的改法

| 改法 | 想法 | 实测结果 |
| :--- | :--- | :--- |
| **排序 `spells` + 双指针**（`t` 随 `s` 增大而单调不增，分界点随之单调，可省掉 n 次 `bisect` 调用） | 「n 次 C 函数调用 vs 一次 Python 指针扫描，应该后者快」 | `n = m = 2000` 时 0.90× ~ 0.96×（略有收益）；`n = m = 10^5` 时 **0.99× / 1.14× / 1.12× / 1.19×**（四档里三档更慢）。原因：指针总移动量是 O(m)，于是内层 `while` 把工作量从「n 次 C 层二分」换成了「n + m 次 **Python 层**迭代」，而 Python 层迭代单价远高于一次 `bisect` 调用 |
| ~~用 `Counter(potions)` 替代计数循环~~（期望把 n 轮降到 distinct 轮） | 「C 层 `_count_elements` 总比 Python 层自增快」 | **未通过**：`n = m = 10^5` 随机值域（distinct = 63320）桶建造 7.84 ms → **14.27 ms（1.82× 更慢）**；`maxv = 100`（distinct = 100）4.61 ms → 4.60 ms（打平）；全同值 5.17 ms → 5.16 ms（打平）。原因：`Counter` 走的仍是 O(n) 的 dict 哈希插入，而直接数组自增是编译期特化过的 `STORE_SUBSCR` 快路径，两者单价接近，distinct 大时 `Counter` 还要多付 6 万次 dict 建表 |
| ~~把桶的计数循环换成「先 `sort` 再 `groupby`」~~ | 同「建段再扫段」思路 | 未单独实现；由上一行的结论可知，凡是「把 O(n) 的 C 层操作换成一趟 Python 层循环」的改法，在本题都不划算 |

### 常数级优化（可选）

实测留下的两条：

- **`bisect_left` 与 `len` 局部绑定**：消掉每轮的 `LOAD_GLOBAL` + 方法解析，与列表推导合计 1.05× ~ 1.08×（上面 2×2 表里的「推导 + 浮点」列）。
- **`for/append` → 列表推导**：省掉每轮的 `LOAD_METHOD append` + 调用，本题实测落在 1.03× ~ 1.05×，属噪声边缘，**别把它当主要优化**。

### 浮点写法为什么在本约束下也安全（不是「碰巧测得对」）

最终代码用的是 `success / i`（双精度除法），而推荐版改成 `(success + i - 1) // i`。二者在本题约束下**恒等**，可以证明：

- 真实阈值 `x = success / i`，其中 `1 <= success <= 10^10`、`1 <= i <= 10^5`，故 `x <= 10^10`。
- 双精度除法是**正确舍入**的，相对误差 `|δ| <= 2^-53`，于是绝对误差 `|fl(x) - x| <= 10^10 × 2^-53 ≈ 1.1e-6`。
- 比较的另一侧是**整数** `p`。若 `x` 本身是整数（`success % i == 0`），`fl(x)` 精确等于它（`x <= 10^10 < 2^53`，整数可精确表示）；若 `x` 不是整数，则它与**最近整数**的距离至少是 `1/i >= 10^-5`。
- `1.1e-6 << 10^-5`，**误差比最小间距小一个数量级** ⇒ 舍入不可能把「`p >= x`」的真假翻转。

⇒ 因此浮点写法在本题**不是错误的写法**（这也是它能 AC 的原因），只是**更慢**（见 2×2 表）。但这个安全性**严格依赖约束**：一旦把 `success` 放宽（例如到 `10^18`），`10^18 × 2^-53 ≈ 111` 会远超阈值间距，同一份代码就会静默错算。**推荐整数写法是因为它无条件安全且更快，不是因为浮点版答错了。**

## 六、易错点与总结

### 易错点

- **阈值向下取整**：写 `success // i` 而不是上取整，`success` 不能整除 `i` 时会漏掉 `p * i == success` 的药水。最小反例：`spells=[3], potions=[2], success=6`，真值 1、下取整得 0。
- **答案口径写反**：`pairs[i]` 是合格药水的**个数** `m - idx`，不是分界下标 `idx`。
- **忘了排序**：不排序就没有「前假后真」的单调谓词，`bisect_left` 的结果没有任何意义（它不会报错，只会静默给错）。
- **桶版漏掉上界守卫**：删掉 `if t <= mx` 后，`t-1` 越过 `le` 的末尾。实测 33 组用例里 **24 组直接抛 `IndexError`**、**0 组静默错解** —— 也就是说这道守卫防的是**硬崩**，不是像某些题那样防「答案变负」的静默错误；最小触发例 `spells=[1], potions=[1], success=10`（`t = 10 > mx = 1`）。
- **桶版的下标下界**：`t = ⌈success/s⌉ >= 1` 恒成立（`success >= 1, s >= 1`），所以 `t - 1 >= 0`，不会出现 Python 负索引静默取到尾元素的坑 —— 这一条要在写之前确认，而不是靠测试碰运气。
- **把「值域有界」当成无条件收益**：桶版的 O(V) 空间和 O(V) 时间成本在 `V` 大、`n` 小时是纯亏（`n = m = 2000, V = 10^5` 时慢 4.6×）。用之前先算 `V` 和 `n` 的量级。

### 题型套路沉淀

- **「乘积/和 ≥ 目标」的对数统计 ⇒ 固定一端、排序后二分**：本题是这个套路的原型。见到「统计有多少对 (i, j) 满足某单调条件」，先问一句「固定 `i` 之后，`j` 的可行集合有没有结构」；只要有「排序后是前缀/后缀」的结构，就是排序 + `bisect` 的模板：
  `potions.sort()` → 每个查询 `idx = bisect_left(potions, t)` → 答案 `m - idx`（后缀）或 `idx`（前缀）。
- **`A * B >= C` 的标准变形**：`B >= ⌈C / A⌉`。这类「把乘法化为单侧阈值」的变形是二分得以成立的前提，也是「上取整」这个易错点的来源。
- **「阈值计数」的两种实现，选哪个看值域**：
  - 值域**无界**或 `V` 远大于 `n` ⇒ 排序 + `bisect_left`，O(m log m + n log m)；
  - 值域**有界且已知**、且 `V` 相对 `n` 不大 ⇒ 计数桶 + 前缀和，O(n + m + V)，`log` 因子消失。
  两条路线的切换点是 `V` 与 `n` 的相对大小（本题 `V = 10^5` 时约在 `n = 10^4`），**不是「值域小」这个形容词**。
- **二分族内部的自我检查清单**（二刷时按这个顺序过一遍）：
  ① 谓词关于二分对象单调吗？② 二分的是**下标**还是**答案值**（本题是下标，不是 `check(x)` 那族）？③ 边界取 `lower_bound` 还是 `upper_bound`（本题要第一个 `>= t`，即 `lower_bound`）？④ 阈值是整数还是浮点，取整方向对吗？⑤ 答案口径是分界点还是它到端点的距离？

## 七、验证记录

### 1. 官方示例与暴力对拍（本次新写的变体）

暴力基准按题面直写：`[sum(1 for p in potions if p * s >= success) for s in spells]`，O(n·m)。

- 用例构成：官方示例 3 组 + 手工边界 16 组（`n = m = 1`、全命中、全不命中、`success = 10^10` 极限、`p*s == success` 恰好相等、重复值、整除/不整除各一组等）+ 随机对拍 30 组（`n, m <= 20`，值域 `[1, 20]`）+ 大值域随机 10 组（值域 `[1, 10^5]`、`success` 到 `10^10`）。
- 结果：**5 个变体全部偏差 0/59**（V1 整数+推导、V2 浮点+推导、V3 桶+前缀和、V4 排序+双指针、V5 桶 + `math.ceil`）。
- 期望值来源：官方示例直接用题面输出；其余**全部先经暴力基准核实**后再写入脚本。手工用例中有两条（`[10^5] * [1] * success = 10^5` 与 `10^5 + 1` 的乘积边界）是我刻意构造的「刚好命中 / 差 1 不命中」对，跑前已按暴力解手算确认。

### 2. 浮点精度对抗（针对「浮点写法是否安全」）

构造 100 个 `(success, spell)` 组合专打舍入边界：`success = i * k + 1`（真值刚越过整数 `k`，最容易被舍入拉回）与 `success = i * k`（可整除），取 `i ∈ {1, 2, 3, 7, 1024, 65535, 99991, 100000}`、`k ∈ {1, 2, 100, 99999, 100000}`，另加 20 组随机大值。

- 结果：判据翻转 **0** 次，最大 `|float - ceil| = 1.000e+00`（该数值出现在 `spells[i] = 1` 且 `success` 为 `10^10` 量级时，差值等于阈值本身的整数部分，属正常量级而非舍入问题）。
- 更要紧的是**推导**（写进第五节）：绝对误差 `<= 10^10 × 2^-53 ≈ 1.1e-6`，而「真值非整数」时它与最近整数的距离 `>= 1/10^5 = 10^-5`，差一个数量级 ⇒ **舍入不可能翻转比较结果**。所以这里给的是**证明 + 小批量抽查**，不是「测了 100 组没出错所以没问题」。

### 3. 删掉再对拍（定位桶版 `t <= mx` 守卫的作用）

把桶版的 `if t <= mx else 0` 删掉，用同一套 33 组用例（官方 3 + 随机 30）跑：

- **异常 24 组（全部 `IndexError`）、静默错解 0 组**。
- 最小触发例：`spells = [1], potions = [1], success = 10` → `t = 10 > mx = 1`，`le` 长度只有 2，`le[9]` 越界。
- ⇒ 这道守卫的作用是**防崩溃**，与「删掉守卫导致答案变负」那类静默错误不是一回事。同时确认 `t >= 1` 恒成立（`success >= 1, s >= 1`），故 `t - 1 >= 0`，不存在负索引取到尾元素的隐患。
