# 2389. 和有限的最长子序列

> **难度**：简单
> **标签**：贪心 · 数组 · 二分查找 · 前缀和 · 排序
> **原题链接**：https://leetcode.cn/problems/longest-subsequence-with-limited-sum/

---

## 一、题目描述

给定长度为 `n` 的正整数数组 `nums` 和长度为 `m` 的正整数数组 `queries`。对每个 `queries[i] = q`，求 `nums` 的**子序列**中「元素之和 ≤ `q`」的最大长度，返回长度为 `m` 的答案数组。

注意题面里「子序列」的措辞有迷惑性：它只限制**相对顺序不变**，而本题的目标函数（元素和）与顺序完全无关 —— 所以它实质上是「任选若干元素」的子集问题。

### 示例

```text
输入：nums = [4,5,2,1], queries = [3,10,21]
输出：[2,3,4]
解释：
  q = 3  → 最小的两个 1+2 = 3 ≤ 3，长度 2
  q = 10 → 1+2+4 = 7 ≤ 10，长度 3
  q = 21 → 全部取，1+2+4+5 = 12 ≤ 21，长度 4

输入：nums = [2,3,4,5], queries = [1]
输出：[0]
解释：最小的元素 2 已经大于 1，只能取空子序列，长度 0
```

### 约束条件

- `n == nums.length`，`m == queries.length`
- `1 <= n, m <= 1000`
- `1 <= nums[i], queries[i] <= 10^6`

## 二、解题思路

### 核心思想

**「和与顺序无关」这一句把决策空间从 2ⁿ 压成 n+1。** 决定答案长度 `k` 之后，最优选择必然是**最小的 k 个元素**；于是把 `nums` 排序、求前缀和 `S_k = nums[0] + … + nums[k-1]`，答案就是 `S_k ≤ q` 的最大 `k` —— 一次排序预处理后，每个查询退化成**有序数组上的上界二分**。

### 思路演进

1. **暴力解法**：对每个 `q` 枚举 `nums` 的全部 `2ⁿ` 个子序列，求和后取「和 ≤ q 的最大长度」。时间 `O(2ⁿ · n · m)`，`n = 1000` 时约 `10^300` 量级，不可行。
2. **瓶颈定位**：慢在把问题当成「组合枚举」。但目标函数里**只有『和』这一个量** —— 与元素位置、与选了哪些具体元素都无关，只与「选了哪些**值**」有关。也就是说，成千上万个子序列在「和的视角」下是同一个东西，枚举它们纯属重复劳动。
3. **关键转化**：既然只关心「选几个、值是多少」，就先对 `nums` 排序（排序不丢解，因为和与顺序无关）。对固定长度 `k`，字典序最优的选择就是**最小的 k 个**，于是问题变成「找最大的 k 使 `S_k ≤ q`」。而 `nums[i] ≥ 1 > 0` ⇒ 前缀和序列 `S` 严格递增 ⇒ **`S` 本身就是一个有序数组**，`S_k ≤ q` 这个谓词在它上面是「前真后假」的单调谓词，二分即可定位边界。
4. **最优解**：`nums.sort()` → 原地改写成前缀和 → 每个查询 `bisect_right(pre, q)`。`O(n log n + m log n)`。

### 判据与判据族定位

- **判据**：`answer = #{k : S_k ≤ q}`，其中 `S_k` = 排序后前 `k+1` 个元素之和。等价地：`answer = bisect_right(pre, q)`（`pre` 不补 0 哨兵时）。
- **判据族**：属 `05-binary-search` 下「**有序序列上的单调谓词边界定位**」（下标二分）族，且是其中一个子形态 —— **二分对象不是输入数组自身，而是它的一个保序变换（前缀和）**。这与「在原数组上直接二分」的题（如找插入位置）在写法上只差一行预处理，但判据的单调性来源完全不同：原数组的有序性是题目给的，前缀和的有序性**是元素非负性推出来的**。
- 与同目录另一族「**二分答案**」（二分的是答案值 `x`，谓词是 `check(x)` 可行性判定）的区别：本题自变量是**下标**，`check` 就是数组自身的取值比较，不存在「先猜答案再判定」这一层。

### 关键点

- **前缀和不是「辅助数组」，它是被二分的那个数组。** 直接对排序后的 `nums` 二分是错的（见 §六 错版 X2）。
- **`bisect_right(pre, q)` 的值天然就是答案**，不需要 ±1 —— 前提是 `pre` 里第 `k` 个元素表示「前 `k+1` 个之和」（下标从 0 起、不补哨兵）。
  若改用补 0 的 `n+1` 长前缀和 `pre[0] = 0`，答案才是 `bisect_right(pre, q) - 1`。**两种约定必须配套**，混用即错（错版 X）。
- 严格 `<` 与 `≤` 的区别在本题是实质性的：`bisect_left(pre, q)` 求的是「`< q` 的个数」，答案会少 1（错版 X3，最小反例 `nums = [2], q = 2`）。
- **单调性前提是「元素非负」**：题面 `nums[i] ≥ 1` 保证前缀和严格递增。如果题目允许负数，前缀和不再有序（甚至不单调），二分立刻失效 —— 那时连「取最小的 k 个最优」都要重新论证（负元素下最小 k 个确实仍是最小和，但 `S_k` 的单调性没了，得换结构）。
- 原地改写 `nums` 会让它从「原数组」变成「前缀和」，原地改写 `queries` 会改变入参 —— LeetCode 无妨，但真实项目里这是两个副作用。

## 三、代码实现

### 最终代码

```python
from typing import List
from bisect import bisect_right


class Solution:
    def answerQueries(self, nums: List[int], queries: List[int]) -> List[int]:
        nums.sort()
        for i in range(1, len(nums)):
            nums[i] += nums[i - 1]          # nums 原地变成前缀和数组 pre
        for i, q in enumerate(queries):
            queries[i] = bisect_right(nums, q)   # 上界 = 前缀和 ≤ q 的个数 = 最大长度
        return queries
```

> **关于代码来源**：以上为用户已提交并通过（AC）的版本。截图里只有 `class Solution:` 起的内容，`numpy` 之外的两个 `import`（`List`、`bisect_right`）原本缺失，已补全以保证笔记里的代码可直接运行。
> 截图共 9 行（第 9 行为空行），第 1~8 行完整未截断：末行是收尾的 `return queries`，与编辑器状态栏一致。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | `O(n log n + m log n)` | `O(1)` 额外（原地改写，不计 `sort` 内部临时区） |
| 朴素解法（枚举子序列） | `O(2ⁿ · n · m)` | `O(1)` |
| 理论下界 | `Ω(n log n + m)`（比较模型下需排序） | — |

> 复杂度中的 `n` 指 `nums` 的长度，`m` 指 `queries` 的长度。
> `list.sort()` 内部会申请最多 `n/2` 个指针的临时空间（Timsort），严格说是 `O(n)` 辅助空间；相对输入本身不构成额外开销，故仍记 `O(1)`。
> 下界的论证：输出 `m` 个答案至少要读一遍输入 `Ω(n + m)`；而答案本质上要求出「排序后的前缀和序列」，比较排序下界给出 `Ω(n log n)`。因此 `O(n log n + m log n)` 在比较模型下与下界同阶（`m log n` 与 `m` 同阶的部分差异见 §五）。

## 五、优化评估

**结论**：算法骨架（排序 + 前缀和 + 上界二分）已经是比较模型下的下界，**不可能换成渐进更优的做法**；但**实现层面存在一个稳定全胜的改法** —— 前缀和数组**只建到「第一个超过 `max(queries)` 的前缀」为止**（下称 F 版），相对用户版在六档场景实测 0.58× ~ 0.95×（**全档不亏**）。

### 瓶颈分析

把 A 版（用户版）拆成三段同轮轮转计时（内层重复到 ≥2 ms，20 轮取最优）：

| 场景 | 排序 | 前缀和 | 查询循环 | 合计 |
| :--- | ---: | ---: | ---: | ---: |
| S1 `n=m=1000`，值域 1e6 | 0.027 ms（13%） | 0.058 ms（27%） | 0.128 ms（60%） | 0.212 ms |
| S2 `n=m=1000`，值域 1..10，queries ≤ 50 | 0.023 ms（11%） | 0.056 ms（28%） | 0.121 ms（60%） | 0.200 ms |
| S4 `n=m=1e4`，值域 1e6 | 0.865 ms（29%） | 0.623 ms（21%） | 1.481 ms（50%） | 2.969 ms |
| S3 `n=m=1e5`，值域 1e6 | 13.363 ms（35%） | 6.811 ms（18%） | 18.119 ms（47%） | 38.293 ms |
| S5 最坏档 `n=m=1000`，`nums` 全 1000、`queries` 全 1e6 | 0.005 ms（3%） | 0.057 ms（34%） | 0.105 ms（63%） | 0.167 ms |
| S6 最坏档 `n=m=1e5`，`nums` 全 10、`queries` 全 1e6 | 0.973 ms（4%） | 6.423 ms（28%） | 15.628 ms（68%） | 23.024 ms |

结论：**耗时的大头是两段 Python 层循环（查询循环 47%~68% + 前缀和 18%~34%），排序只占 2%~36%**（且输入越「扁平」，Timsort 越快：S5/S6 全同值时只占 2%~4%）。所以优化要往「少跑 Python 字节码」和「少做无用轮次」上使劲，而不是去换排序算法。

### 可优化空间

1. **前缀和的构建方式**：`nums[i] += nums[i-1]` 每轮要「读 `i-1`、读 `i`、加、写 `i`」，而 `pre.append(s)` 式只需「加、append」，后者少了索引偏移与列表存取。
2. **前缀数组的有效长度可以截断**：所有查询都 `≤ max(queries)`，设 `k*` 为**使 `S_{k*} > max(queries)` 的最小下标**，则任何 `q ≤ max(queries)` 都有 `bisect_right(pre, q) ≤ k*` —— 截断点之后的前缀**永远不会被二分读到**。于是只需建 `pre[0..k*]`（含第一个超限项，它是天然的右侧哨兵）。截断收益有两份：省掉后半段的 Python 循环轮次，**并把二分数组的长度从 `n` 缩到 `k*`**（比较次数 `log` 变小）。
   - 题面量级下这个收益是实实在在的：`S_k` 是**排序后前 k 个之和**，随 `k` 平方级增长（均匀随机数据下 `S_k ≈ k²·Δ/2`），而 `max(queries) ≤ 10^6` ⇒ `k*` 只有几十到几百，远小于 `n` 的上限 1000。
3. **值域桶 + 前缀和路线**（理论上可把 `log` 因子彻底消掉）：因为 `queries[i] ≤ 10^6`，可以开一个长度 `max(queries)+1` 的计数桶，把「≤ 某个值的前缀和有几个」做成数组下标查询，复杂度变 `O(n log n + V + m)`。本题**不划算**（见下表实测）。
4. **排序 queries + 双指针合并**（把 `m` 次 `bisect` 换成一次线性归并）：**随机 queries 下更慢**，原因见下。

### 优化代码

**F 版（推荐）：截断 + append 式构建**

```python
from typing import List
from bisect import bisect_right


class Solution:
    def answerQueries(self, nums: List[int], queries: List[int]) -> List[int]:
        mx = max(queries)
        pre = []
        ap = pre.append
        s = 0
        for x in sorted(nums):
            s += x
            ap(s)
            if s > mx:          # 第一个超过 mx 的前缀 = 天然右哨兵，之后的不可能被读到
                break
        return [bisect_right(pre, q) for q in queries]
```

**优化理由**（两处改动，各自收益已拆开实测，见下表）：

- 用 `sorted(nums)` + `append` 建 `pre`：把每轮 4 条字节码的索引式累加换成 2 条（`s += x` / `ap(s)`）。
- 累加到 `s > mx` 即 `break`：`pre` 长度由 `n` 降到 `k*`，同时缩短后续 `m` 次二分的搜索区间。

**截断为何不丢答案**（正确性论证，非实测推断）：设 `k*` 为使 `S_{k*} > mx` 的最小下标。对任意 `q ≤ mx`，有 `S_{k*} > mx ≥ q`，而 `pre` 单调递增 ⇒ 所有下标 `≥ k*` 的前缀都 `> q` ⇒ `bisect_right(pre_trunc, q) ≤ k*`，即答案**永远不会落到截断点右侧**，`pre_trunc = pre[0..k*]` 与完整 `pre` 对每个 `q` 的返回值恒等。若 `S_n ≤ mx`（不存在这样的 `k*`），循环自然走完、保留全部前缀，同样正确。（该结论在 40 组随机对拍 + 14 组手工用例、含 2 组专门构造的截断用例上偏差 0/40。）

### 常数级优化（实测）

**六档场景 × 7 变体，内层重复到 ≥2 ms、20 轮轮转取最优；倍数为「相对 A 版」，含各自的 `list()` 拷贝成本：**

| 变体 | S1 `1e3/1e6` | S2 `1e3/小值域` | S4 `1e4/1e6` | S3 `1e5/1e6` | S5 `不截断/1e3` | S6 `不截断/1e5` |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| A 用户版 | 1.00× (0.208 ms) | 1.00× (0.196 ms) | 1.00× (2.997 ms) | 1.00× (38.524 ms) | 1.00× (0.172 ms) | 1.00× (22.778 ms) |
| B `accumulate` | 0.75× | 0.73× | 0.79× | 0.91× | 0.72× | 0.79× |
| C `bisect_left(pre, q+1)` | 0.83× | 0.77× | 0.85× | 0.95× | 0.81× | 0.84× |
| D 排序 queries + 双指针 | 1.03× | 0.88× | 1.08× | **1.31×** | 0.78× | 0.75× |
| E 值域桶 + 前缀和 | **115.28×** | 0.47× | 8.95× | 1.93× | **219.41×** | 2.41× |
| F2 仅换构建风格（不截断） | 0.84× | 0.83× | 0.87× | 0.97× | 0.81× | 0.87× |

**拆开归因**（同一改动里两项收益必须分开量，否则会把一项的功劳记到另一项头上）：

- **构建风格**（F2 vs A）：0.81× ~ 0.97×，即省下 3%~19%。
- **截断**（F vs F2）：**截断生效时** 0.69× ~ 0.75×（再省 25%~31%）；**截断失效时** 1.08× ~ 1.14×（反而慢一点，因为白付了一次 `max(queries)` 的 `O(m)` 扫描）。
- ⇒ 合起来 F 在六档全部快于 A（0.58× ~ 0.95×）；最坏情况（`sum(nums) ≤ max(queries)`，一次都不截断）也只是 0.92×/0.95×，**不会出现反向结论**。

**被证伪 / 不适用的改法**：

- ~~`bisect_left(pre, q + 1)` 替代 `bisect_right(pre, q)`~~ —— 两者**数学上完全等价**（`pre` 与 `q` 都是整数：`pre[k] > q ⟺ pre[k] ≥ q+1`；40 组随机对拍输出逐位相同），但实测**慢 8%~13%**（C 0.77×~0.95× vs B 0.73×~0.91×）：每轮多一次整数加法，而 `q + 1 > 256` 时还会新建一个 `int` 对象。等价不等于等贵。
- ~~排序 `queries` + 双指针合并~~ —— 随机 queries 下慢 **31%~34%**（S3 1.31×）：省下的是 `m` 次 C 层二分，付出的是 `O(m log m)` 的**带 key 排序**（每轮一次 `__getitem__` 调用）加上 `m` 次 Python 层迭代。但它在 **queries 大量重复/接近有序**时反超（S5 0.78×、S6 0.75×，因为此时 Timsort 几乎退化成线性扫）。⇒ 这个改法的成立条件是「`queries` 的**逆序数**小」，而不是「`m` 大」。
- ~~值域桶 + 前缀和~~ —— 只有 `V = max(queries)` 与 `n` 同量级或更小时才划算：S2（`V = 50`、`n = 1000`）**快 2.1×**；`n/V = 0.1` 时反过来慢 1.93×/2.41×；本题最坏档（`V = 10^6`、`n = 1000`）慢 **115× ~ 219×**。桶的成本是固定的 `O(V)`（分配 + 一遍计数 + 一遍 `accumulate`，约 25 ns/格），要靠 `n` 次 `O(1)` 查询摊薄 —— **判据是 `V` 相对 `n` 的大小，不是「值域有界」这个标签**。本题题面 `queries[i] ≤ 10^6` 而 `n ≤ 1000`，`V/n` 最大到 1000，路线直接出局。
- ~~只把 `accumulate` 换进来就够了~~ —— B 版确实稳赚（0.72× ~ 0.91×），且在**不截断**的档还反超 F（S5 0.72× vs 0.92×、S6 0.79× vs 0.95×，因为 F 要白付一次 `max(queries)`）；但在**会截断**的档 F 明显更好（S1 0.58× vs 0.75×、S2 0.58× vs 0.73×、S3 0.73× vs 0.91×）。⇒ 若输入不保证 `sum(nums) > max(queries)`，B 是更稳的通用选择；F 是「题面量级下大概率截断」时的更强选择。

> **口径提醒**：题面约束只有 `n, m ≤ 1000`、值域 `≤ 10^6`，**在题面上限下 A 版本身就是 0 ms 级**。上表所有倍数都是把规模推到 `10^5` 的**泛化研究**，用于说明「哪些改法在方向上是对的」，**不能读成「不优化会 TLE」**。

## 六、易错点与总结

### 易错点

- **在原数组上二分，而不是在前缀和数组上二分**（最常见）：`bisect_right(sorted(nums), q) - 1` 数的是「元素值 ≤ q 的个数」，与「前缀和 ≤ q 的个数」是两件不同的事。实测 40/40 错，**最小反例 `nums = [5], q = 5`**（真值 1、实得 0），官方示例 1、2 **都挂**。
- **±1 与「是否补 0 哨兵」不配套**：
  - `pre` 不补 0（`pre[k]` = 前 `k+1` 个之和）⇒ 答案直接是 `bisect_right(pre, q)`；再 `-1` 就错（错版 X，40/40 错，最小反例 `nums = [3], q = 6`：真值 1、实得 0）。
  - `pre` 补 0（长度 `n+1`）⇒ 答案必须 `-1`；两种约定混用是同一个坑的两面。
- **严格比较写错**：`bisect_left(pre, q)` 求的是 `< q` 的个数，比答案少 1（错版 X3，14/40 错，最小反例 `nums = [2], q = 2`：真值 1、实得 0）。
  > 值得一提：以上三个错版的**最小反例都退化成 `n = 1`**，并且**都能被题目自带的示例 1 拦住**（X/X2 连示例 2 也挂）。这类「越界 ±1 / 严格性」错误与「示例全过、要靠随机对拍才现形」的逻辑错误（如判据本身写错）是两类不同的风险 —— 前者危险度低，后者危险度高。
- **把 `queries[i] ≥ 1` 当成废话**：本题 `q` 恒为正，所以 `-1`/越界问题只出现在前缀下标侧；若 `q` 可为 0 或负，`pre[-1]` 这类**负索引会静默取到最后一个元素**（Python 不报错），错误会以「答案莫名其妙很大」的形式出现。
- **二分单调性的前提被忽视**：`S` 有序靠的是 `nums[i] ≥ 1`。换成含负数的版本，`S` 不再单调，`bisect` 会给出貌似合法实则错误的下标 —— 这类题一旦看到「元素可达负数」，就该立刻放弃这条路。
- **原地改写入参**：`nums` 被改成前缀和、`queries` 被改成答案数组，两个副作用在需要复用入参时都是 bug。

### 题型套路沉淀

- **「子序列 / 子集」+「和不超过 q」+ 多个 q** ⇒ 标准三件套：**排序 → 前缀和 → 上界二分**。识别信号是「答案与顺序无关，只与『选哪几个』有关」，此时排序永远不丢解。
- **判据写法**：把答案写成一条可判定真假的命题 —— 「`answer = #{k : S_k ≤ q}`」，然后一步到位选对 `bisect_right` / `bisect_left` 与哨兵约定。判据一明确，`±1` 就不会再凭感觉写。
- **族内定位**：本题属 `05-binary-search` 的「**下标二分**」族，且二分的是**输入数组的保序变换**（前缀和）。写代码前先问一句：「被二分的那条单调性，是题目给的，还是我从别处推出来的？」—— 本题是后者，所以前提（元素非负）必须记在笔记里，否则换个题面就会踩空。
- **同型题**：结构上最接近的是各类「排序 + 前缀和 + 二分上界」的贪心计数题（排序解决「选哪几个」，前缀和解决「和」，二分解决「多个 q」）。值域桶路线的适用边界可参照本 skill 修订记录里的两个数据点 —— `1385`（区间存在性 + 前缀和，`n/V = 0.25` 时桶反慢 2×）与 `2300`（阈值计数 + 后缀和，`n/V ≈ 1` 时桶快 2.8×）；加上本篇的 `n/V = 0.1` 慢 1.9×/2.4×、`n/V = 20` 快 2.1×，四个数据点把「桶划算」的分界收敛到 **`V` 与 `n` 同量级附近**。
