# 3508. 设计路由器

> **难度**：中等
> **标签**：设计 · 队列 · 哈希表 · 二分查找
> **原题链接**：https://leetcode.cn/problems/implement-router/
> **判据族定位**：本题属「**有序序列上的区间计数**」——在一个**天然有序**的容器上定位区间的**两个端点**，答案 = 右边界位置 − 左边界位置。它与「在谓词的分界点上二分」那一族（二分的是**谓词真假翻转处**）同属二分查找，但判据不同、代码形状也不同，**不得串用**；滑动窗口判据族（窗口内部状态 / 两端点的值 / 计数型）对本题一律不适用。

## 一、题目描述

实现一个路由器类 `Router`，管理带三个属性的数据包：`source`（发出机器）、`destination`（目标机器）、`timestamp`（到达时间）。需要支持：

- `Router(memoryLimit)`：初始化，`memoryLimit` 是路由器在任意时刻能存下的**最大包数**。若加入新包会超限，必须先移除**最旧**的包腾出空间。
- `bool addPacket(source, destination, timestamp)`：若路由器中**已存在** `(source, destination, timestamp)` 完全相同的包，视为重复包，返回 `false`；否则加入并返回 `true`。
- `List[int] forwardPacket()`：按 **FIFO**（先进先出）转发并**移除**下一个包，返回 `[source, destination, timestamp]`；无包可转发时返回 `[]`。
- `int getCount(destination, startTime, endTime)`：返回**当前仍存储在路由器中**（即尚未转发）、目标地址为 `destination`、且时间戳落在闭区间 `[startTime, endTime]` 内的包的数量。

### 示例

```text
示例 1
输入：
["Router", "addPacket", "addPacket", "addPacket", "addPacket", "addPacket",
 "forwardPacket", "addPacket", "getCount"]
[[2], [1,4,90], [2,5,90], [1,4,90], [3,5,95], [4,5,105], [], [5,2,110], [5,100,110]]
输出：[null, true, true, false, true, true, [1,4,90], true, 1]
解释：memoryLimit = 2。
      (1,4,90) 加入 -> true；此时满了。
      (2,5,90) 加入 -> 先淘汰 (1,4,90)，再存入 -> true。
      (1,4,90) 再次加入 -> 路由器中已无此包，故不是重复 -> true。
      (3,5,95) 加入 -> 淘汰 (2,5,90) -> true。
      (4,5,105) 加入 -> 淘汰 (1,4,90) -> true。
      forwardPacket() -> [3,5,95]。
      (5,2,110) 加入 -> true。
      getCount(5, 100, 110) -> 现存且 destination = 5 的包只剩 (4,5,105) -> 1。

示例 2
输入：["Router", "addPacket", "forwardPacket", "forwardPacket"]
      [[2], [7,4,90], [], []]
输出：[null, true, [7,4,90], []]
```

### 约束条件

- `2 <= memoryLimit <= 10^5`
- `1 <= source, destination <= 2 * 10^5`
- `1 <= timestamp <= 10^9`
- `1 <= startTime <= endTime <= 10^9`
- `addPacket`、`forwardPacket`、`getCount` 三类方法的**总调用次数最多为 `10^5`**
- **对 `addPacket` 的调用，`timestamp` 按非递减顺序给出**（题面保证 —— 这是本题解法成立的全部前提）

## 二、解题思路

### 核心思想

**三个结构各管一件事**：哈希表 O(1) 判重、双端队列维持 FIFO 顺序、每个 `destination` 维护一条**按时间递增**的时间戳序列供二分做区间计数。

整题成立的关键只有一句话：**题面保证 `addPacket` 的 `timestamp` 非递减**。它让「按到达顺序 `append`」= 「按时间递增排列」，于是插入退化成 O(1) 的尾部追加，区间计数退化成两次 `bisect`——不需要任何排序、不需要任何有序容器。

### 思路演进

1. **朴素解**：用一个 `list` 存所有包。
   - `addPacket` 线性查重 → O(M)；
   - `forwardPacket` 用 `pop(0)` → O(M)（整体搬移）；
   - `getCount` 逐包过滤 → O(M)。

   设总调用次数 Q、`memoryLimit` = M，两者都可到 `10^5`，总代价 O(Q·M) ≈ `10^10` 次基本操作 —— 必然超时。

2. **瓶颈定位**：三处慢点互相独立，得分头解决。
   - **查重慢**：本质是「在无序容器里找同一个三元组」，没有哈希就只能线性扫。
   - **计数慢**：`getCount` 是「destination 相等 **且** 时间戳落在区间内」的二维过滤，逐包扫描把「区间计数」退化成了「全表扫描」。
   - **最隐蔽的一处**：就算按 `destination` 分好了组，**谁来保证组内有序**？如果每次 `addPacket` 都要把新时间戳插到正确位置（`insort`），代价是 O(k)（k = 组内包数）—— 与「用哈希把查重降到 O(1)」的思路背道而驰。

3. **关键转化**：**有序性是题面白送的**。
   `addPacket` 的 `timestamp` 非递减 ⇒ 只需按到达顺序 `append`，每个 `destination` 的时间戳序列**自动递增** ⇒ 插入是 O(1) 的尾部追加，`getCount` 直接在有序序列上二分。

   这一步必须配合看清**删除从哪里发生**：
   - 两种删除（满载自动淘汰、`forwardPacket`）都只从**队首**取一个包；
   - 而队首是全体包中**最早到达**的那个 ⇒ 对任一 `destination` 而言，被删掉的永远是它自己最旧的那个包。

   ⇒ 组内序列的删除**恒发生在左端**，`popleft()` / 头指针前移都是 O(1)，且「删掉前缀」不会破坏后缀的有序性。

   ⚠️ **前提边界**：一旦 `timestamp` 不保证非递减，本解法（以及一切基于「组内序列有序 + 二分」的实现）会**静默错解**。最小反例只有 4 次调用：`Router(3)` → `addPacket(1,1,100)` → `addPacket(1,1,1)` → `getCount(1,1,50)`：真值 `1`、实得 `2`（实测，见「七、验证记录」）。

4. **最优解**：`seen`（set）判重 + `packet_q`（deque）维持 FIFO + `cnt[d]`（非递减时间戳序列）供二分。`addPacket` / `forwardPacket` O(1)，`getCount` O(log k_d)。

### 关键点

- **判据**：`getCount(d, s, e) = upper_bound(cnt[d], e) − lower_bound(cnt[d], s)`，即「落在闭区间 `[s, e]` 内的元素个数 = 右边界位置 − 左边界位置」。两端必须分别用**右界用 `bisect_right`、左界用 `bisect_left`**，闭区间才不重不漏（两边用同一个版本会各错一半）。
- **不变量**（三条，缺一条解法就塌）：
  1. 路由器中现存的数据包恒为「全体到达序列的一个**连续后缀**」——因为唯一的删除路径是队首弹出；
  2. 每个 `destination` 的时间戳序列恒为**非递减**——来自题面保证 + 只做尾部追加；
  3. 由 1 + 2 ⇒ 该序列的删除恒发生在**左端**，删除后前缀被砍掉、后缀仍有序。
- **重复判定针对「当前仍在路由器中」**：一个已被淘汰或转发的包可以再次 `addPacket` 并返回 `true`（示例 1 的第 3 次调用就是这种情形）。⇒ 删除时**两个同步动作都不能漏**：既要 `seen.remove(packet)`，也要把该 `destination` 的时间戳序列左端弹掉，否则会误判为重复 / 把已转发的包算进计数。
- **`memoryLimit` 的判断用 `==` 就够**：由不变量 1 的推论 `len(packet_q) <= memoryLimit` 恒成立，所以「已满」只可能是「恰好等于」。语义上仍是「**先淘汰、再入队**」。
- **三个方法的返回类型不同**（`bool` / `list` / `int`），`forwardPacket` 空时返回 `[]` 而不是 `None`。
- **`deque` 不能拿来装「要被 `bisect` 的序列」** —— 这是本题最反直觉的一点：CPython 的 `deque` 是分块链表，`__getitem__` 要按块走链，**下标访问是 O(k/64) 而不是 O(1)**，于是 `bisect` 在它上面的真实代价是 O(k·log k)，而不是 O(log k)。见「五、优化评估」的实测。

## 三、代码实现

### 最终代码

> 截图里代码从**第 3 行**开始（第 1~2 行被滚出视野），已按引用补全 `import` 与 `class Router:` 声明；`List` 来自 `typing`。

```python
from collections import deque, defaultdict   # 截图里没有，已补
from bisect import bisect_left, bisect_right
from typing import List                       # 截图里没有，已补


class Router:
    def __init__(self, memoryLimit: int):
        self.memory_limit = memoryLimit
        self.packet_q = deque()          # 全体数据包，按到达顺序（FIFO）
        self.packet_set = set()          # (source, destination, timestamp)，O(1) 判重
        self.cnt = defaultdict(deque)    # destination -> 按时间递增的时间戳序列

    def addPacket(self, source: int, destination: int, timestamp: int) -> bool:
        packet = (source, destination, timestamp)
        if packet in self.packet_set:
            return False
        self.packet_set.add(packet)
        if len(self.packet_q) == self.memory_limit:
            self.forwardPacket()         # 满载：先淘汰最旧的那个（队首）
        self.packet_q.append(packet)
        self.cnt[destination].append(timestamp)
        return True

    def forwardPacket(self) -> List[int]:
        if not self.packet_q:
            return []
        packet = self.packet_q.popleft()
        self.packet_set.remove(packet)       # 删除路径 1：从判重集合中移除
        self.cnt[packet[1]].popleft()        # 删除路径 2：组内删除恒在左端
        return packet

    def getCount(self, destination: int, startTime: int, endTime: int) -> int:
        timestamps = self.cnt[destination]
        left = bisect_left(timestamps, startTime)
        right = bisect_right(timestamps, endTime)
        return right - left
```

## 四、复杂度分析

> 记 Q = `addPacket` + `forwardPacket` + `getCount` 三类方法的**总调用次数**（≤ `10^5`）；M = `memoryLimit`（≤ `10^5`）；k_d = 当前 `destination` = d 的**在库**包数（Σ_d k_d ≤ M）。

| 版本 | `addPacket` | `forwardPacket` | `getCount` | 空间 |
| :--- | :--- | :--- | :--- | :--- |
| **最终代码**（组内用 `deque`） | O(1) | O(1) | O(log k_d) 次下标访问，每次下标 O(k_d/64) | O(M) |
| 优化版（组内用 `list` + 头指针） | O(1) | O(1) | O(log k_d)（下标 O(1)） | O(Q) |
| 朴素解法 | O(M) | O(M) | O(M) | O(M) |
| 理论下界 | O(1) | O(1) | Ω(log k_d) | O(M) |

**为什么三个操作都已是理论下界：**

- `addPacket` 必须读入 3 个属性并对三元组做一次哈希（否则无法 O(1) 判重）⇒ 下界 O(1)，达到。
- `forwardPacket` 必须返回队首元素 ⇒ 下界 O(1)，达到。
- `getCount` 在比较模型下要在一条有序序列上区分 `k_d + 1` 种计数结果，下界 Ω(log k_d)；实现用的正是两次二分。

**最终代码的渐进口径要写清楚**：`bisect` 每轮做 O(log k_d) 次下标访问，在 `list` 上每次 O(1)、而在 `deque` 上每次是 O(k_d/64)（分块链表的块内偏移）。所以严格地说，最终代码的 `getCount` 是 **O(k_d · log k_d / 64)**，log 因子被一个随 k_d 线性增长的常数掩盖了 —— 这也正是「五」里最值钱的那个优化点。

## 五、优化评估

**结论**：渐进复杂度**已是理论下界**（三个操作都够到了下界），但**常数上有两处明确可挖**：

1. 组内时间戳序列用 `deque` → 换成 `list` + **头指针**（`bisect` 传 `lo`）；
2. `defaultdict` → `dict.get`（去掉 `getCount` miss 路径上的「读变写」）。

两项合起来即下面的 **C 版**。实测 8 档场景中 5 档领先、3 档小幅落后，**最坏形态（先把 5 万个包堆进同一个 destination 再连打 5 万次 `getCount`）快 11.5×**，最大的代价是转发密集档 **+13%**（绝对值 +3.5 ms）。

### 瓶颈分析

**（1）`bisect` 在 `deque` 上的下标访问不是 O(1)** —— 纯查询微基准（每次查询做一对 `bisect_left` + `bisect_right`，20 000 次取最优）：

| 序列长度 | `list` | `deque` | `deque / list` |
| :--- | :--- | :--- | :--- |
| 1 000 | 4.6 ms | 6.3 ms | 1.38× |
| 20 000 | 7.8 ms | 63.3 ms | 8.17× |
| 50 000 | 9.7 ms | 188.3 ms | 19.50× |
| 100 000 | 11.3 ms | 678.3 ms | 59.83× |

`list` 侧基本是常数（11~12 ms 量级，只随 `log n` 缓增），`deque` 侧却**随长度近似线性膨胀**（6.3 → 678.3 ms，涨了 108 倍）。⇒ 用户的 `getCount` 在深表上并不是 O(log k_d)，而是 O(k_d · log k_d / 64)，**随 k_d 近似线性增长**。**这是本题最反直觉、也最容易漏掉的一处。**

**（2）`defaultdict` 的「读变写」**：`getCount` 里写 `timestamps = self.cnt[destination]`，当 `destination` 从未出现过时，`defaultdict` 会**创建并插入一个空 `deque`**。

- `sys.getsizeof(deque())` = **760 B**（`deque((1,))` 同样是 760 B —— 空 deque 也预分配一整块），而 `sys.getsizeof([1])` 只有 **64 B**；
- 构造 10 万次 miss：`defaultdict` 侧键数涨到 100 000、**内存 77.5 MB**，`dict.get` 侧 **0.00 MB**；
- 端到端 `tracemalloc`（2 万次全 miss 的 `getCount`）：最终代码峰值 **15.38 MB**，B/C 版 **0.32 MB**（约 48×）。

这不仅费时间，还让 `cnt` 的条目数可以涨到调用次数那么多（`destination` 值域到 `2·10^5`），纯属浪费。

**（3）阶段归因**：把「add 段」与「get 段」拆开单独计时（**同一轮里轮转 9 轮取最优**；本表是独立的一次轮转，数字不与上面那张 8×8 表混用）：

| 场景 | 段 | A（截图版） | C（优化版） | C / A |
| :--- | :--- | ---: | ---: | ---: |
| S7 | add 段（5 万次，同一 destination） | 24.0 ms | 26.8 ms | 1.116 |
| S7 | get 段（5 万次二分计数） | 577.3 ms | 25.3 ms | **0.044** |
| S1 | add 段（5 万个新 destination） | 72.0 ms | 49.9 ms | **0.693** |
| S1 | get 段（5 万次，半数 miss） | 37.3 ms | 24.1 ms | **0.647** |

三条结论：

- **S7 里最终代码 96.0% 的时间花在 get 段**（577.3 / 601.3 ms），而 C 版把这一段压到**原来的 4.4%**（快 **22.7×**，占 C 版全程降到 48.5%）。C 版在最坏形态上的全部收益（甚至超额）都来自 get 段；**add 段反而慢了 11.6%**（`forwardPacket` 要多维护一个 `head` 字典）。
- **S1 的收益则来自 add 段**：A 的 add 段占全程 65.9%，C 版在这一段就快 **1.44×**。机理是「5 万个 `destination` 各建一个单元素容器」——`[t]` 是 **64 B**，单元素 `deque` 是 **760 B**（实测 `sys.getsizeof`）。⇒ S1 省的是**建容器的分配成本**，不是二分的下标访问。
- 每次 `addPacket` 必须做的哈希查找（判重所必需）与每次 `getCount` 必须做的两次二分（计数所必需）都是**不可去成本** ⇒ 常数优化的天花板就在这里。

### 可优化空间

- **可去**：组内序列的容器类型（`deque` → `list`）、miss 路径上的对象分配（`defaultdict` → `dict.get`）。
- **不可去**：每次 `addPacket` 对三元组做哈希（判重所必需）、每次 `getCount` 的两次二分（计数下界所必需）。
- **不划算**：任何需要额外排序/建表的路线。比如「把 `seen` 换成按 `destination` 组织的有序结构」会让 `forwardPacket` 的删除路径多维护几层字典（未实测，仅从结构上判断）。

### 优化代码

```python
from collections import deque
from bisect import bisect_left, bisect_right


class Router:
    """优化版：组内时间戳序列用「只追加的 list + 已移除前缀长度 head」，bisect 传 lo。"""

    def __init__(self, memoryLimit: int):
        self.lim = memoryLimit
        self.q = deque()        # 全体包，FIFO
        self.seen = set()       # O(1) 判重
        self.ts = {}            # destination -> 只追加、从不删除的时间戳 list
        self.head = {}          # destination -> 已被移除的前缀长度

    def addPacket(self, s: int, d: int, t: int) -> bool:
        pk = (s, d, t)
        if pk in self.seen:
            return False
        self.seen.add(pk)
        if len(self.q) == self.lim:
            self.forwardPacket()          # 满载：先淘汰队首
        self.q.append(pk)
        a = self.ts.get(d)
        if a is None:                     # miss 时才建表，不产生空对象
            self.ts[d] = [t]
            self.head[d] = 0
        else:
            a.append(t)                   # 尾部追加：序列仍递增
        return True

    def forwardPacket(self):
        if not self.q:
            return []
        pk = self.q.popleft()
        self.seen.remove(pk)
        self.head[pk[1]] += 1             # 懒删除：只把前缀长度 +1，O(1)
        return pk

    def getCount(self, d: int, s: int, e: int) -> int:
        a = self.ts.get(d)
        if a is None:                     # 从未出现过的 destination，直接 0
            return 0
        lo = self.head[d]                 # 二分从有效区间的左端开始
        return bisect_right(a, e, lo) - bisect_left(a, s, lo)
```

**优化理由**：

1. **`list` + 头指针**：`bisect` 的随机下标访问在 `list` 上是 O(1)；「删除最旧的一个」不再真的删元素，而是把 `head[d] += 1`，二分时把 `lo` 传进去，只在有效后缀里定位。因为删除的永远是前缀，剩下的后缀仍有序，`bisect` 的前提不被破坏。
2. **`dict.get`**：`getCount` 的 miss 路径不再创建空 `deque`（省 760 B/次的分配），`cnt` 也不再因为查询而膨胀。
3. **空间代价**：`ts[d]` 永不删元素，总长度 = 该 destination 的**累计** `addPacket` 次数（≤ Q），比最终代码的 O(M) 多一档。实测深表档（3 万 add + 3 万 get）四种实现峰值**同为 5.24 MB** —— 主导项是 `packet_q` / `seen` 里的 3 万个元组；`ts` 的额外开销只是列表里的引用。⇒ 这个交换在本题的约束下几乎零成本。

## 六、易错点与总结

### 易错点

- **把「重复」理解成「曾经出现过」**：重复判定只看**当前仍在路由器中**的包。已被淘汰或转发的包可以再次 `addPacket` 并返回 `true`（官方示例 1 的第 3 次调用）。⇒ 满载淘汰与显式 `forwardPacket` 走的是同一条删除代码路径，`seen.remove` 放在那里就够了；但同一个删除动作里**组内序列的左端弹出也不能漏**。
- **`getCount` 里用 `defaultdict` 会「读变写」**：`self.cnt[destination]` 对不存在的 `destination` 会创建并插入一个空 `deque`（实测每个 760 B，10 万次 miss 就是 77.5 MB）。改成 `dict.get` + `if a is None: return 0`。
- **闭区间边界取反**：正确写法是 `bisect_right(e) − bisect_left(s)`；两边都用 `left`（丢右端点的等值）或都用 `right`（重复计左端点的等值）会各错一半。`bisect_left(a, e+1) − bisect_right(a, s)` 与之等价（靠整数性兜底），但没必要绕。
- **组内序列的删除漏了一半**：`forwardPacket` 里既要从 `seen` 移除包，也要把对应 `destination` 的时间戳序列左端弹掉 —— 只做一半，`getCount` 会把已转发的包算进去。
- **用 `deque` 装要被 `bisect` 的序列**：这是本题性能上最大的坑。`deque` 的 `popleft()` 是 O(1)、看起来正适合「从头部删除」，但它的**随机下标访问是 O(k/64)**，`bisect` 一上来就把优势全吃回去还倒亏（100 000 长度下 `deque` 比 `list` 慢 **59.8×**）。
- **忘了前提**：`timestamp` 非递减是**题面保证**，不是可以从题面推出的结论。同样的代码拿去解「时间戳任意顺序」的变体会静默错解（4 次调用的最小反例见「二」的第 3 步）。
- **满载判断**：用 `==` 是安全的（由不变量 `len(packet_q) <= memoryLimit`），但语义顺序必须是「**先淘汰、再入队**」，写成「先入队、再淘汰」会淘汰错对象。

### 题型套路沉淀

- **设计题 = 逐个操作找最合适的数据结构**：判重 → 哈希集合；FIFO / 一端进出 → 队列；区间计数 → **有序序列 + 二分**；O(1) 定位 → 哈希表。
- **先问「有序性从哪来」**。有序性有三个常见来源：① 题面白给（本题）；② 结构天然有序（前缀和、某个字段单调）；③ 遍历/追加顺序（按时间 append、按位置 push）。**来源不同，代价不同** —— 白给的可以直接二分，要自己维护的就得考虑插入代价（`insort` 是 O(k)）。
- **再问「删除从哪里来」**。若删除只发生在一端，就用队列 / 头指针把删除压到 O(1)，并且**确认删掉之后剩下的部分仍然有序**（本题删的是前缀，后缀仍递增）。若删除可能发生在中间，这套结构立刻失效。
- **容器选型看「谁在上面做下标访问」**：要被 `bisect` 的序列必须是 `list`；只在两端进出的用 `deque`。二者不能混用，本题的最终代码就栽在这里。
- 设计题的「优化」几乎全在常数上：**容器类型 + 字典访问方式**，而渐进复杂度早在确定数据结构时就定死了。

**5) 计时**：8 档场景（S1~S8）× 8 个实现（A~H），**在同一轮循环里轮转、7 轮取最优**，避免机器漂移污染；「五」里第一张表与倍数表全部来自**同一次运行**。另做一次**独立的阶段归因轮转**（S1/S7 的「全程」与「只保留 add」共 4 种组合 × 2 个实现，9 轮取最优），用于把 add 段与 get 段分开；这两组数字**不互相混用**。复跑两次：`A` 的绝对值在三次独立运行间漂移 ≤ 4%（`S3` 档最大），各变体相对 `A` 的方向基本一致 —— 唯一的例外是 **F 与 C 的胜负在两次运行间翻转**，已在「五」里据此判为**噪声内持平**。

**6) 微基准**：

- `bisect` 在 `deque` / `list` 上的成本（4 档长度、20 000 次查询取最优）：1.38× / 8.17× / 19.50× / 59.83×。
