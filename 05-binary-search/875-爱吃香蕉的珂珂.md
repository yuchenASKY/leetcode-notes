# 875. 爱吃香蕉的珂珂

> **难度**：中等
> **标签**：数组 · 二分查找
> **原题链接**：https://leetcode.cn/problems/koko-eating-bananas/

---

## 一、题目描述

有 `n` 堆香蕉，第 `i` 堆有 `piles[i]` 根。珂珂每小时选一堆吃 `k` 根；若这堆不足 `k` 根，就把它吃完，这一小时不再吃别的（**即每堆的耗时是 `⌈piles[i]/k⌉` 小时**）。求在 `h` 小时内吃完所有香蕉的**最小速度 `k`**。

一次判定只能得到"这个 `k` 行不行"，而题目要的是"最小的可行 `k`" —— 这是本题的全部结构。

### 示例

```text
示例 1：输入：piles = [3,6,7,11], h = 8        输出：4
示例 2：输入：piles = [30,11,23,4,20], h = 5   输出：30
示例 3：输入：piles = [30,11,23,4,20], h = 6   输出：23
```

### 约束条件

- `1 <= piles.length <= 10^4`
- `piles.length <= h <= 10^9`
- `1 <= piles[i] <= 10^9`

（`piles.length <= h` 这个看似不起眼的约束是上界可行性的唯一依据，见 §二 关键点。）

## 二、解题思路

### 核心思想

把"枚取值"换成"**定位单调谓词的边界**"：`k` 越大越省时间，所以「`k` 可行」这个谓词关于 `k` 单调，答案就是它的第一个真值点。

### 思路演进

1. **朴素解**：令 `k = 1, 2, 3, …`，对每个 `k` 用 `O(n)` 算出 `hours(k) = Σ⌈piles[i]/k⌉`，返回第一个 `hours(k) <= h` 的 `k`。
   复杂度 `O(n · M)`，其中 `M = max(piles)` 可达 `10^9` —— 值域本身就是瓶颈，逐值扫不可能。

2. **瓶颈定位**：慢在"**逐个值检查**"，而不是"单次检查慢"。单次检查只有 `O(n)`，但被乘上了值域 `M`。

3. **关键转化**：`hours(k)` 关于 `k` **单调不增**（每一项 `⌈p/k⌉` 都随 `k` 增大而不增），于是
   `P(k) := hours(k) <= h` 是**单调谓词**：`false … false true … true`，可行集是一段**后缀**。
   ⇒ 不需要逐值检查，只需二分定位这一段后缀的左端点，即 `ans = min{k : Σ⌈piles[i]/k⌉ <= h}`。
   一句话："原来不行"是因为把值域当成了搜索空间；"现在行"是因为**可行性关于值单调**，答案值域只需 `log` 次询问。

4. **最优解**：**二分的对象是"答案值"而不是下标** —— 两端不是数组边界，而是两个必须自己证明的哨兵：
   - `right = max(piles)`：`k = max(piles)` 时每堆只需 1 小时 ⇒ `hours = n <= h`，**必可行**（依据就是题面的 `piles.length <= h`）。
   - `left`：必须取一个**已证明不可行**的值（哨兵式二分的循环条件 `while left + 1 < right` 不含等号，从不检查 `left`）。
   循环写 `while left + 1 < right`：`mid` 只可能落在 `(left, right]` 内，判定 `P(mid)` 后收缩，`right` 始终可行、`left` 始终不可行，收敛时二者相邻，返回 `right`。

### 判据与判据族定位

- **本题判据**：`ans = min{ k : Σ⌈piles[i]/k⌉ <= h }`，`P(k)` 关于 `k` 单调不增。
- **判据族 = 05 目录下的「二分答案」族**：二分对象是**答案值**，两端是**先验哨兵**（可行性/不可行性都要自己证），单调性来自**谓词的数学性质**（`⌈p/k⌉` 随 `k` 单减）。
- 与同目录「**下标二分**」族（二分对象是下标，单调性来自数据本身有序：原数组 / 前缀和 / 值→有序下标表）**不是同一族**：那两族的 `while` 写法与边界处理不同，**边界写法不可互抄**。

### 关键点

- **两个哨兵都是承重的，不是"顺手写的初始值"**：
  - `right` 必须**真的可行**（靠 `n <= h`）；
  - `left` 必须**真的不可行**，且这件事要能证出来。用户代码用的是
    `left = max(min(piles) // h - 1, 0)`，它的正确性来自"只盯最小的那一堆"：
    设 `m = min(piles)`，`d = ⌊m/h⌋ ≥ 2` 时 `⌈m/(d-1)⌉ ≥ d·h/(d-1) > h` ⇒ 该 `k` 下光这一堆就超时 ⇒ **确实不可行**（`d ≤ 1` 时退化成 `left = 0`，速度 0 当然不可行）。
    **这个界是对的，但很弱** —— 见 §五。
- **`mid` 不会为 0**：`left >= 0` 且 `left + 1 < right` ⇒ `right >= 2` ⇒ `mid = ⌊(left+right)/2⌋ >= 1`，`(x-1)//mid` 无除零风险。
- **上取整的写法**：`⌈p/k⌉ = (p-1)//k + 1`（整数运算，不碰浮点）。
- **`helper` 里的局部变量 `h` 遮蔽了外层参数 `h`**：因为 `helper` 内**只写不读**外层 `h`（`h = 0` 赋值使它成为局部变量），所以这里无害；但一旦哪天想在 `helper` 内部**读**外层 `h`（例如加早退判断），就会 `UnboundLocalError` —— 加早退时必须换一个计数器名。

## 三、代码实现

### 最终代码

用户提交并通过的版本（截图逐行核对：共 17 行、末行是 `return right`，**未被裁切**）：

```python
class Solution:
    def minEatingSpeed(self, piles: list[int], h: int) -> int:
        def helper(mid):
            h = 0
            for x in piles:
                h += (x - 1) // mid + 1
            return h

        left = max(min(piles) // h - 1, 0)
        right = max(piles)
        while left + 1 < right:
            mid = (left + right) // 2
            if helper(mid) <= h:
                right = mid
            else:
                left = mid
        return right
```

> `piles: list[int]` 用的是内建泛型注解（Python 3.9+），**不需要补任何 `import`**；截图里的代码也确实是完整的 `class Solution`。

## 四、复杂度分析

复杂度里的符号：

- `n = len(piles)`：香蕉堆数（`≤ 10^4`）。
- `M = max(piles)`：答案的上界（`≤ 10^9`），也是搜索区间的初始长度量级。
- 单次判定 `hours(k)` 必须扫全部 `n` 堆，`O(n)`；哨兵式二分的轮数是 `⌈log2(right - left)⌉`。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | `O(n log M)`（约 30 轮 × n） | `O(1)`（不计输入） |
| 朴素解法（逐值枚举 k） | `O(n M)` | `O(1)` |
| 理论下界 | `Ω(n log M)` | `O(1)` |

> 下界的口径：答案值域是 `[1, M]`，任何基于单调谓词的判定树都至少要 `log2 M` 次询问；而 `M` 可达 `10^9`、`n` 可达 `10^4`，本题单轮判定无法在 `o(n)` 内完成（每个堆的贡献与 `k` 都相关），所以 `Ω(n log M)` 是这一模型下的实用下界，最终代码已经达到（常数差见 §五）。

## 五、优化评估

**结论**：渐进复杂度已是答案，无更优的渐进解法；但**有明确的常数级优化空间**，且其中最大的一笔（收紧下界）在特定输入结构上能带来 **100× 量级**的收益。

### 瓶颈分析（阶段归因）

### 可优化空间

#### 方向一：收紧下界（收益最大，且是结构性的）

两种更强、且都能证明的下界：

1. **单堆界**（盯最大的那一堆）：每堆至少占 1 小时，所以 `⌈p/k⌉ + (n-1) <= h`，即 `⌈p/k⌉ <= h-n+1`。取 `p = mx = max(piles)`：

   $$\lceil mx/k\rceil \le h-n+1 \iff \lfloor (mx-1)/k\rfloor \le h-n \iff k > \frac{mx-1}{h-n+1} \iff k \ge \left\lfloor \frac{mx-1}{h-n+1}\right\rfloor + 1$$

   ⇒ 所有 `k <= ⌊(mx-1)/(h-n+1)⌋` 都不可行，可把 `left` 直接提到 `(mx-1)//(h-n+1)`。
   （末步用到的恒等式 `⌊a/k⌋ > L ⟺ k <= ⌊a/(L+1)⌋` 已单独抽查 200 组一致。）

2. **总和界**：`Σ⌈p_i/k⌉ >= ⌈S/k⌉`（上取整超可加），故必有 `⌈S/k⌉ <= h` ⇒ `k >= ⌈S/h⌉` ⇒ `left >= ⌈S/h⌉ - 1 = (S+h-1)//h - 1`。

取 `max(单堆界, 总和界, 0)`。三种下界带来的**轮数**差异（同一份代码只换 `left`，返回值全部一致）：

| 场景 | 原下界 `min(piles)//h - 1` | 轮数 | 总和界 `⌈S/h⌉-1` | 轮数 | 最强界 `max(单堆, 总和)` | 轮数 | 答案 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| S1 随机/1e9/h=n | 11 | 30 | 495859546 | 29 | **999760484** | **0** | 999760485 |
| S2 随机/1e9/h=1e9 | 0 | 30 | 4993 | 29 | 4993 | 29 | 4994 |
| S3 全同值1e9/h=n | 99999 | 30 | 999999999 | 0 | **999999999** | **0** | 10^9 |
| S4 小值域[1,10]/h=n | 0 | 4 | 5 | 3 | **9** | **0** | 10 |
| S5 n=1000/1e9/h=1e9 | 0 | 30 | 494 | 29 | 494 | 29 | 495 |
| S6 偏斜/h=n | 0 | 30 | 100005 | 30 | **999999999** | **0** | 10^9 |

- 原下界在 7 档里有 5 档直接退化成 `0`（等于没设）。
- 单堆界在 **`h` 接近 `n`** 时几乎把区间压没：`h = n` 时 `h-n+1 = 1`，`left = mx-1`，区间只剩 `{mx}` ⇒ **0 轮**（S1/S3/S4/S6）。此时答案恰好就是 `max(piles)`，与"`h = n` ⇒ 每堆必须 1 小时 ⇒ `k = max`"的推导一致 —— 收紧后的下界相当于**自动识别了这个塌缩**。
- 总和界在答案很小时几乎紧（S5：界 494、答案 495）。

#### 方向二：把判定搬到 C 层（恒等变形，`Σ⌈p/k⌉ = Σ⌊(p-1)/k⌋ + n`）

预计算 `pm1 = [x-1 for x in piles]`，判定写成 `sum(map(mid.__rfloordiv__, pm1)) <= h - n`。
关键点是**用哪个可调用对象**：`mid.__rfloordiv__` 是"实参的绑定方法"（单迭代器 ⇒ `map` 走快速路径），而 `map(int.__floordiv__, pm1, repeat(mid))` 是"槽包装 + 双迭代器"（每元素多一次迭代器步进 + 参数解包）。同一件事的六种写法（都返回 `days(mid)`，`mid` 取该档答案，单位 μs，9 轮取最优）：

- **绑定方法 map 稳定快 1.48~1.90×**，且不需要排序 —— 这是可以无条件采用的。

#### 方向三：截断 —— `(x-1)//mid == 0 ⟺ x <= mid`，小堆完全不产生工作量

对升序数组用一次 `bisect_right(asc, mid)` 就能定位"所有 `> mid` 的元素"这一段后缀，判定只需对这一小段求和。这是方向二的"极端版"：在"少数大堆 + 大量小堆"的结构下，它能把每轮判定从 `n` 个元素降到"大堆个数"。

代价是 `sorted()` 一次 `O(n log n)`（`n = 10^4` 时 40~865 μs，视输入的"有序程度"而定）。

### 优化代码

**推荐版（Q2）：最强下界 + 绑定方法判定 + 区间空时不建表。**

```python
class Solution:
    def minEatingSpeed(self, piles: list[int], h: int) -> int:
        n = len(piles)
        S = sum(piles)                        # 总和界：Σ⌈p/k⌉ ≥ ⌈S/k⌉
        right = max(piles)                    # 上界：k = max ⇒ 每堆 1 小时 = n ≤ h
        L = h - n                             # 预算：已扣掉"每堆至少 1 小时"
        # 单堆界：每堆至少占 1 小时 ⇒ ⌈p/k⌉ ≤ L+1 ⇒ k ≥ ⌊(mx-1)/(L+1)⌋+1
        left = max((right - 1) // (L + 1), (S + h - 1) // h - 1, 0)
        if left + 1 < right:                  # 区间塌成 1 个候选时不付 O(n) 建表钱
            pm1 = [x - 1 for x in piles]      # Σ⌈p/m⌉ = Σ⌊(p-1)/m⌋ + n
        while left + 1 < right:
            mid = (left + right) // 2
            if sum(map(mid.__rfloordiv__, pm1)) <= L:   # x // mid，全程 C 层
                right = mid
            else:
                left = mid
        return right
```

**优化理由**：

1. `mid.__rfloordiv__(x)` 恰好是 `x // mid`（实参的绑定方法 ⇒ `map` 单迭代器快速路径），把 `Σ⌊(p-1)/mid⌋` 整段压到 C 层：单次判定快 **1.48~1.90×**，七档端到端全部 ≤ 0.72。
2. 下界取 `max(单堆界, 总和界, 0)`：`h` 接近 `n` 时区间直接塌成 `{max(piles)}`，**0 轮**（S1/S3/S4/S6 实测 0.008~0.059，即 16~125×）。
3. `pm1` 只在区间非空时构建：区间塌缩的档省下 190~260 μs 的建表钱（Q→Q2 实测 2.4~2.9×，其余档持平）。
4. 七档端到端全部 ≤ 0.65，最差档（S2/S5 的"答案很小、区间无法塌缩"）也有 **1.55×**。

> 可读性折中：面试手写时用 `sum((x - 1) // mid for x in piles) <= L` 语义完全相同、约慢 1.8×（见 §五 方向二的表）。

**分档加强版（T2）：当输入呈"少数大堆 + 大量小堆"时，再加排序 + 切片截断。**

```python
from bisect import bisect_right

class Solution:
    def minEatingSpeed(self, piles: list[int], h: int) -> int:
        n = len(piles)
        asc = sorted(piles)                    # 一次性 O(n log n)
        am1 = [x - 1 for x in asc]
        S = sum(piles)
        right = asc[-1]
        L = h - n
        left = max((right - 1) // (L + 1), (S + h - 1) // h - 1, 0)
        while left + 1 < right:
            mid = (left + right) // 2
            j = bisect_right(asc, mid)         # asc[j:] 才是贡献非零的元素
            if sum(map(mid.__rfloordiv__, am1[j:])) <= L:
                right = mid
            else:
                left = mid
        return right
```

**采用判据（本次实测划出来的界线）**：`sorted()` 的成本是 40~865 μs，只有当"答案附近仍有大量元素 `<= mid`"时才划算 —— 即**元素值分布中"远低于答案"的那部分质量**要够大。
- S7（9800/10000 个元素是 `1`，答案 3847）⇒ 每轮只处理 200 个大堆，T2 比 Q/Q2 再快 **12×**（0.40 ms vs 4.8 ms）；
- S2（答案 4994，元素均匀分布在 `[1,10^9]`）⇒ 几乎所有元素都 `> mid`，截断省不下任何东西，排序纯亏 **约 1.07×**；
- S1/S4/S6 ⇒ 区间已经塌缩，排序成本（0.46~0.86 ms）白付，比 Q2 慢 2.0~2.9×。
⇒ **两条路线不是替代关系**：先看下界能否塌缩区间（能 ⇒ 用 Q2），再看元素分布是否"重尾"（是 ⇒ 换/叠 T2）。

> `islice(am1, j, None)` 与 `am1[j:]` 语义相同，但 **`islice` 慢 3~4 倍**（S7：26.2 μs vs 6.2 μs；空后缀时 20.4 μs vs 0.3 μs）—— `map` 对 `list` 有快速路径，对 `islice` 只能走通用迭代器协议（每元素两次 `next`）。

### 常数级优化（被证伪 / 记录在案）

| 候选改法 | 实测结果 | 判定 |
| :--- | :--- | :--- |
| `map(int.__floordiv__, pm1, repeat(mid))`（槽包装 + 双迭代器） | 单次仅 0.98~1.14×；端到端 S4 1.066、S6 1.026、S7 1.004 | ❌ 不用（同一意图换可调用对象差 1.8×） |

## 六、易错点与总结

### 易错点

- **把 `left` 当成"随便一个初值"**。哨兵式二分 `while left + 1 < right` **从不检查 `left`**，`left` 一旦可行，返回值就会大于真答案；这是"**承重哨兵**"，必须能证明它不可行。
- **上界必须自己证**。`right = max(piles)` 可行**只因为**题面保证 `n <= h`；如果放开这条约束（比如 `h < n`），本题无解，代码也不能照用。
- **两种二分骨架不能各取一半**：`while left + 1 < right` 配 `left = mid + 1`（或 `while left < right` 配 `left = mid`）要么死循环、要么漏解，是本题最常见的翻车点。
- **`⌈p/k⌉` 不要用浮点**：`(p-1)//k + 1` 是纯整数运算，既没有 `p/k` 的舍入风险，也比 `math.ceil(p/k)` 快。
- **`helper` 内的 `h = 0` 会遮蔽外层参数 `h`**：本题无害（只写不读），但若要在判定里做"超过 `h` 就早退"，必须换计数器名，否则会 `UnboundLocalError`（或更糟：写成 `if h > h` 静默失效）。
- **`mid` 不为 0 这件事依赖循环条件**：`left + 1 < right` 保证首轮 `mid = ⌊(0+right)/2⌋ >= 1`；如果改成别的骨架（例如 `left = 0, right = 1` 还要判一次 `mid = 0`），就会除零。

### 题型套路沉淀

- **「二分答案」通用骨架**：先证两端哨兵（`P(right) = true` 要**证**、`left` 要**证明它不成立**），再写 `while left + 1 < right` + `mid` 判定 + 返回 `right`。判据写成一条可判真假的命题（本题：`Σ⌈p_i/k⌉ <= h`），边界条件会自然浮出来。
- **下界永远有得挖，而且常常是最大的一笔**。三个层次的界，从弱到强：
  `min(piles)//h - 1`（本题原版，弱） → `⌈S/h⌉ - 1`（总和） → `(mx-1)//(h-n+1)`（单堆 + "其余每堆至少 1 小时"）。
  构造技巧：**把"每堆至少占用 1 小时"这类常数开销从预算里扣掉**（本题 `L = h - n`），剩下的预算才是"额外整除损耗"的配额 —— 一旦这么看，`⌈p/k⌉ <= L+1` 这条不等式就自己冒出来了。
- **判定里的 C 层化有讲究**：`sum(expr for x in seq)` → `sum(map(seq_method_of_x, ...))` 要看**谁是实参**。形式为 `变量 // 元素` 时用 `map(变量.__rfloordiv__, 元素列表)`（绑定方法、单迭代器，最快）；错写成 `map(int.__floordiv__, 元素, repeat(变量))` 只能拿到 1/10 的收益。
- **"元素完全不影响结果"时可以直接跳过整段**：本题 `(x-1)//mid == 0 ⟺ x <= mid`，所以排序后一个 `bisect` 就能定位"真正要处理的元素"，`O(n)` 判定降成"大堆个数"。识别信号：**判据里的元素贡献存在一个平凡的 0 区间**。

### 计时设计

- **11 版本 × 7 场景在同一轮里轮转**、15 轮取**最优值**，同时打印**逐轮比值区间与中位数**（只看 `min` 倍数会把噪声写成结论）；另对 Q2/Q、T2/Q 做了**直接配对**的同轮比值。
- **跨运行的绝对值不可互比**：同一版本在不同次运行间读数漂移约 ±10%，因此本文两张表的所有数字都取自同一次运行。
- **基准设计教训（本次踩到）**：判定写法横向对比的第一版里，5 种写法返回 `Σ⌊(x-1)/mid⌋`、1 种返回 `Σ⌈x/mid⌉`（差一个 `n`），被脚本里的 `assert len(set(所有写法返回值)) == 1` 当场抓出（打印 `VAL MISMATCH`）。⇒ 与"参与对比的计时对象必须同构"是同一条：**比较不同语义的表达式得到的时间差没有意义**。修正后六种写法统一返回 `days(mid)`，断言通过、数值全等。

### 实测结论摘要

1. **下界是本题最大的一笔优化**：`max((max(piles)-1)//(h-n+1), (S+h-1)//h - 1, 0)` 在 `h = n` 时把区间压成 `{max(piles)}`，直接 **0 轮**；七档端到端 0.008~0.960（S1/S3/S4/S6 为 0.008~0.059）。
2. **判定写法差 1.8×**：`sum(map(mid.__rfloordiv__, pm1))` 相对 Python 循环稳定 1.48~1.90×（同为 O(n)，只是移到了 C 层）；换成槽包装写法（`int.__floordiv__` + `repeat`）只剩 0.98~1.14×，端到端反而略亏。
3. **推荐版 Q2**：七档全部 ≤ 0.65，最差档（S2）1.55×，最好档（S6）**125×**；且 Q2 相对 Q 在四档大胜（2.4~2.9×）、三档持平（逐轮区间跨 1.0）。
4. **截断路线 T2（排序 + `bisect` + 切片）只在"少数大堆 + 大量小堆"时成立**：S7 再快 12×，但 S1/S4/S6 反向 2.0~2.9×、S2 1.07× —— **不是通用替代**，判据是"元素值分布中远低于答案的那部分质量"。
5. **加法模型成立**：`建界（~160 μs）+ 轮数 × 单次判定` 在七档上与端到端吻合到 ~5%，判定段占 91%~100%，这解释了为什么"收紧轮数"和"压判定常数"是仅有的两条路。
