# 34. 在排序数组中查找元素的第一个和最后一个位置

> **难度**：中等
> **标签**：数组 · 二分查找
> **原题链接**：https://leetcode.cn/problems/find-first-and-last-position-of-element-in-sorted-array/

---

## 一、题目描述

给定一个**非递减有序**整数数组 `nums` 和目标值 `target`，返回 `target` 在数组中的**起始位置和结束位置**；若不存在则返回 `[-1, -1]`。题面硬性要求实现 **O(log n)** 的算法。

### 示例

```text
输入：nums = [5,7,7,8,8,10], target = 8
输出：[3,4]

输入：nums = [5,7,7,8,8,10], target = 6
输出：[-1,-1]

输入：nums = [], target = 0
输出：[-1,-1]
```

### 约束条件

- `0 <= nums.length <= 10^5`
- `-10^9 <= nums[i] <= 10^9`
- `nums` 是一个非递减数组
- `-10^9 <= target <= 10^9`
- **必须设计并实现时间复杂度为 O(log n) 的算法**

---

## 二、解题思路

### 核心思想

**不要"找值"，要"找边界"。** 把问题改写成：找一个**单调谓词 `P(i) = nums[i] >= x` 的第一个 `True` 的位置**（即下界 `lower_bound`）。

于是「第一个 `target`」= `lower_bound(target)`，「最后一个 `target`」= `lower_bound(target + 1) - 1` —— 同一个函数调两次，左右边界一起拿到。

### 思路演进

1. **朴素解法**：线性扫描。从左往右找第一个 `target`，再从右往左找最后一个，**O(n) 时间、O(1) 空间**。逻辑显然正确，但直接不满足题面的 O(log n) 要求。
2. **瓶颈定位**：慢在**信息利用率**——每次比较只消掉 1 个候选元素。哪怕已经确定 `target` 只可能出现在右半区，代码仍然一格一格地往右挪。**"数组有序"这个结构信息完全没被用上。**
3. **关键转化**：把"在数组里找一个值"换成"在**单调谓词**上找分界点"。
   令 `P(i) = (nums[i] >= x)`。数组非递减 ⟹ `P` 必然是形如 `F F F … F T T T … T` 的**单调 01 序列**（这就是本题单调性的来源）。
   一旦看清"要找的是 `P` 的第一个 `True`"，二分立刻可用：在 `mid` 处探一次 `P(mid)`，就足以判定分界点在 `mid` 左侧还是右侧 —— **每次比较把候选区间减半**，而不是消掉一个元素。logn 次比较即可定位分界点。
4. **最优解**：写出 `lower_bound(x)`（下界二分），再注意到 `target + 1` 恰好是"第一个严格大于 `target` 的位置"的等价键，于是**两次调用同一个 `lower_bound`** 就同时得到左右边界，无需另写一个 `upper_bound`。

### 关键点

- **判据（把解法压缩成一条命题）**：答案 ⟺ 单调谓词 `P(i) = nums[i] >= x` 的**分界点**。判据写清楚之后，"左右边界 = 两次下界"就是自然推论，不用背模板。
- **`target + 1` 是整数专属的等价改写**：因为数组元素是**整数**，`nums[i] >= target + 1 ⟺ nums[i] > target` 严格成立，所以「最后一个 `target`」= `lower_bound(target + 1) - 1`。
  ⚠️ 这个等价**只对整数成立**。若数组换为浮点数，必须另写一个 `> target` 的 `upper_bound` —— 否则 `lower_bound(target + 1)` 会越过整数值之后的答案，把右边界算错。
- **半开区间写法 `left = -1, right = n`**（语义：恒有 `nums[left] < x`、`nums[right] >= x`），好处有三：
  1. 循环退出时 `right` **直接就是答案**，不需要任何 `+1 / -1` 修正 —— 少一处 off-by-one；
  2. `left` / `right` 是**哨兵**、不落真实下标，所以 `n = 0` 无需特判（`while` 直接不进，返回 `0 == n`，随后被 `start == len(nums)` 拦下）；
  3. 循环条件写成 `while left + 1 < right`，天然对应"区间内至少还剩一个元素"。
- **只写一个二分函数就够**：「找第一个 `> target`」与「找第一个 `>= target + 1`」是同一件事，不必写两个函数。
- **`lower_bound` 不存在时返回 `n`**（而不是 `-1`）：这是"哨兵语义"的一部分，也是空数组能被统一处理的原因。

## 三、代码实现

### 最终代码

```python
from typing import List


class Solution:
    def lower_bound(self, nums: List[int], target: int) -> int:
        """返回第一个满足 nums[i] >= target 的下标；全部元素都小于 target 时返回 len(nums)"""
        left = -1                 # 哨兵：nums[left] < target 恒成立
        right = len(nums)         # 哨兵：视 nums[right] = +inf >= target
        while left + 1 < right:   # 区间 (left, right) 内至少还有一个元素
            mid = (left + right) // 2
            if nums[mid] < target:
                left = mid        # 分界点在 mid 右侧
            else:
                right = mid       # 分界点在 mid 处或左侧
        return right              # 退出时 left + 1 == right，right 即分界点

    def searchRange(self, nums: List[int], target: int) -> List[int]:
        start = self.lower_bound(nums, target)
        if start == len(nums) or nums[start] != target:
            return [-1, -1]
        end = self.lower_bound(nums, target + 1) - 1
        return [start, end]
```

> 截图里只有 `class Solution`，`from typing import List` 是补全的（LeetCode 提交框自带该导入，本地直接跑需要显式写）。截图代码**末尾完整**（最后一行就是 `return [start, end]`，行号连续到 18），无需按缩进补全。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(log n) | O(1) |
| 朴素解法（左右各扫一遍） | O(n) | O(1) |
| 理论下界 | O(log n) | O(1) |

> 复杂度中的 n 指数组 `nums` 的长度（最多 10^5）。两次 `lower_bound` 各自在 `n + 1` 个候选位置（下标 `0..n`，含"不存在"）上二分。

**为什么 O(log n) 是下界，而不是"感觉已经够快了"**：
本题的答案空间是「不存在」+「一对 `(first, last)`，`0 <= first <= last <= n-1`」，合计 `n(n+1)/2 + 1` 种可能。任何基于比较的算法每次最多获得 1 bit 信息，所以至少需要 `ceil(log2(n(n+1)/2 + 1))` 次比较。
取 `n = 10^5`：答案空间 `5 000 050 001` 种 ⟹ 下界 **33 次比较**；本解法最坏走 `2 × ceil(log2(n+1)) = 2 × 17 =` **34 次比较**。
⇒ **只比信息论下界多 1 次**，已经不存在可降的阶，连常数都只剩 1 次比较的余地。

## 五、优化评估

**结论**：**时间复杂度已是最优**（贴着信息论下界），不可能再降阶。剩下的空间**全部在常数层**，而这块空间相当可观 —— 实测有 **6.12× ~ 7.17×** 的可挖余地。

### 瓶颈分析

时间上，`2 × ceil(log2(n+1))` 次比较已经贴着下界，**比较次数本身压不动了**。真正贵的是**"每一次比较"的单价**：

- 手写版每轮要走一遍 Python 层的 `while`：算 `mid`、两次下标访问 `nums[mid]`、整数比较、分支跳转，以及 `left` / `right` / `nums` 的每次名字查找 —— 全是解释器级开销；
- 而 `bisect_left` / `bisect_right` 是标准库里的 **C 实现**（`_bisect` 模块）。同样次数的比较，单价低一个数量级。

空间上 O(1)，已是下界（除几个局部变量外零分配）。

### 可优化空间

两处，且**必须拆开归因**（否则会把一边的功劳记到另一边头上）：

| 改法 | 相对上一档 | 场景1 随机·命中中部 | 场景2 随机·不存在 | 场景3 全同值·命中 |
| :--- | :--- | :--- | :--- | :--- |
| A 手写×2 → B bisect（第二次仍全区间） | 比较循环从 Python 换到 C | **6.80×** | **6.12×** | **7.17×** |
| B → C（第二次搜索下界抬到 `start`） | 只动区间 | 1.14× | 1.09× | 1.06× |
| A → D（同样收窄，但仍手写） | 只动区间 | 1.02× | 0.99× | 1.00× |

读法：

- **`bisect` 一项吃掉了几乎全部收益**（6.12× ~ 7.17×），是唯一值得动手的改动；
- **"第二次搜索收窄"本身只值 6% ~ 14%，而且只在 C 层显形**：手写版做同样的收窄（D vs A）落在 **0.99× ~ 1.02×**，即噪声内。原因是收窄省下的迭代次数只有 `log2(n+1) - log2(n-start+1)` 次 —— 命中中部时恰好 1 次（17 → 16，约 6%），这点便宜在手写版里被"方法多传一个参数"的调用开销抵掉了。
  ⇒ 这条能推广成一句判断：**"减少迭代次数"的优化，在单价贵的实现里会被调用开销淹没，在单价便宜的实现里才显形。** 别拿一种实现上的收益去推断另一种。
- ⚠️ **场景 3 的 1.06× 要打折看**：全同值数组上 `start = 0`，`lo = start` 实际没有收窄任何区间，这一档的读数应视为噪声水平。该场景真正有意义的信息是"最坏数据（全同值）下 bisect 版照样领先 **7.17×**"。

### 优化代码

```python
from bisect import bisect_left, bisect_right
from typing import List


class Solution:
    def searchRange(self, nums: List[int], target: int) -> List[int]:
        start = bisect_left(nums, target)              # 第一个 >= target
        if start == len(nums) or nums[start] != target:
            return [-1, -1]
        # 已知 nums[start-1] < target，故第二次的搜索下界可抬到 start（lo=start）
        end = bisect_right(nums, target, start) - 1    # 最后一个 <= target
        return [start, end]
```

**优化理由**：

- `bisect_left(nums, target)` 与手写 `lower_bound(nums, target)` **逐位等价**（实测 55 条正确性用例偏差 0）；
- `bisect_right(nums, target, start)` 返回"第一个 `> target` 的下标"，减一即最后一个 `target`；`lo=start` 这个参数就是"收窄区间"那一项的唯一来源（去掉它即退化为上表的 B 版）；
- 顺带省掉一个自定义方法：两次调用同一个 C 函数，少一层 Python 方法查找 —— 这也是它比"Python 层手写收窄"划算的原因。

### 常数级优化（可选）

- **用 `bisect` 而不是手写，是本篇最值钱的一条。** 代价为零：标准库、无额外空间、语义完全等价、也不需要额外 import 之外的依赖。
- 若坚持手写，**顺手收窄第二次搜索区间**可以写（`left` 初值取 `start - 1`，因为 `nums[start-1] < target < target+1` 恒成立，不会漏掉分界点）—— 但实测在 Python 层**没有稳定收益**（0.99× ~ 1.02×）。写它的理由是"逻辑区间更紧"，不是"更快"。
- 手写版还隐含一个可读性与正确性的权衡：复用 `target + 1` + 同一个 `lower_bound` 比再写一个 `upper_bound` 少 6 行，代价是把"整数专属等价"这条前提藏了起来。**如果这段代码可能被搬去浮点数组，宁可多写一个 `upper_bound` 把前提显式化。**

## 六、易错点与总结

### 易错点

- **`while` 条件写成 `left < right` 会死循环。** 半开区间写法下，`left + 1 < right ⟹ r >= l + 2 ⟹ mid = (l+r)//2 >= l+1`，所以 `left = mid` 必定前进；但条件放宽成 `left < right` 后，`left`、`right` 相邻时 `mid == left`，`left = mid` 原地踏步。
- **`target + 1` 依赖整数域。** 浮点数组里必须显式写 `> target` 的上界二分。
- **越界检查顺序不能反**：`if start == len(nums) or nums[start] != target` —— 必须先判 `start == len(nums)`。写反了会直接 `IndexError`，因为 `nums[start]` 会先求值。
- **`nums[start] != target` 是在判 `>`**：由 `lower_bound` 的定义必有 `nums[start] >= target`，所以这个不等号实际含义是 `nums[start] > target`，即"数组里根本没有 `target`"。它与 `start == len(nums)` 合起来覆盖了全部"不存在"的情形。
- **别用 `nums.index(target)` + 反向扫描凑答案**：那是 O(n)，直接违反题面的 O(log n)（还要额外接 `ValueError`）。
- **`right = len(nums)` 是哨兵、不是下标。** 写成 `right = len(nums) - 1` 会漏掉"所有元素都 `< target`"这一情形（此时正确答案是返回 `n`，而不是 `n - 1`）。

### 题型套路沉淀

- **判据族：单调谓词找分界。** 核心从来不是"数组有序"，而是"**要找的东西是某个单调谓词的分界点**"。
  动手写二分前先问三句：① 谓词 `P(i)` 是什么？② 它是否形如 `F…F T…T`（单调）？③ 我要的是第一个 `True` 还是最后一个 `False`？
  三句答清楚，模板都不用背 —— **二分能成立，只需要`mid` 处的判定能排除掉"一半候选"**。
- **`lower_bound(x)` / `upper_bound(x)` 是这一族的两个标准出口**，且整数域上 `upper_bound(x) == lower_bound(x + 1)`。
  同型题：`35. 搜索插入位置`（就是 `lower_bound` 本体）、`704. 二分查找`、`69. x 的平方根`、`278. 第一个错误的版本`、`LeetCode 34`（本题）。
- **与相邻族的差别（最容易串用判据的地方）**：
  - **三分 / 峰谷族**（`162. 寻找峰值`、`852. 山脉数组的峰顶索引`）：谓词**不是**单调 01 序列，而是"先增后减"；二分靠的是比较**相邻两项的方向**，不是比较真值；
  - **二分答案族**（`875. 爱吃香蕉的珂珂`、`1011. 在 D 天内送达包裹的能力`、`410. 分割数组的最大值`）：二分的是**解空间上的可行性谓词**（"答案 ≤ x 是否可行"），自变量是答案本身而非数组下标 —— 判据同构（可行域必须是前缀或后缀），但搜索空间要自己构造；
  - **旋转数组族**（`33. / 81. / 153.`）：有序性被破坏，全局谓词不再单调，必须额外判断"哪半边有序"，**不能**直接套本篇的 `lower_bound`。
- **`left = -1, right = n` 的半开区间模板值得单记**：它的价值是"退出即答案、不用特判空数组、不用 `+1/-1` 修正"。**只记这一套就够**，别同时记 `while (l <= r)` 那一套 —— 两套混用是二分最常见的 bug 来源（`mid` 配错 `+1` 就是死循环）。
- **什么时候不该用二分**：谓词非单调时（无序数组，或 `P` 有多个 `True` 段）二分不成立。二分**不依赖数组有序，依赖谓词单调**；"数组有序"只是最常见的单调谓词来源。
