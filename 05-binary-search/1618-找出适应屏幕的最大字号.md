# 1618. 找出适应屏幕的最大字号

> **难度**：中等
> **标签**：二分
> **原题链接**：https://leetcode.cn/problems/maximum-font-to-fit-a-screen/

---

## 一、题目描述

给定字符串 `text`、屏幕宽 `w` 与高 `h`，以及一个**升序且不重复**的可用字号数组 `fonts`。通过 `FontInfo` 接口查询指定字号下的字符宽度（`getWidth(fontSize, ch)`）与字符高度（`getHeight(fontSize)`），两者单次调用都是 O(1)。

文本**只能排一行**：某字号下文本的宽度是 `sum(getWidth(fontSize, text[i]))`，高度是 `getHeight(fontSize)`。求能同时满足「宽度 ≤ `w`」且「高度 ≤ `h`」的**最大字号**；若任何字号都放不下，返回 `-1`。

接口本身还保证了单调性：字号越大，高度与各字符宽度**非递减**。

```
interface FontInfo {
    public int getWidth(int fontSize, char ch);   // O(1)
    public int getHeight(int fontSize);           // O(1)
}
```

### 示例

```text
输入：text = "helloworld", w = 80, h = 20, fonts = [6,8,10,12,14,16,18,24,36]
输出：6
解释：6 号字可以放下；8 号字的高度或宽度已经超出屏幕。

输入：text = "leetcode", w = 1000, h = 50, fonts = [1,2,4]
输出：4

输入：text = "easyquestion", w = 100, h = 100, fonts = [10,15,20,25]
输出：-1
解释：字号 10 已经超出宽度，因此没有任何可用字号，返回 -1。
```

### 约束条件

- `1 <= text.length <= 50000`
- `text` 仅由小写英文字母组成
- `1 <= w <= 10^7`
- `1 <= h <= 10^4`
- `1 <= fonts.length <= 10^5`
- `1 <= fonts[i] <= 10^5`
- `fonts` 按升序排列且不含重复元素

## 二、解题思路

### 核心思想

**可行性关于字号单调，所以在 `fonts` 的「下标」上二分，取最后一个可行的下标。** 判定某个字号是否可行只需把宽度累加一遍。

### 思路演进

1. **暴力解法**：把 `fonts` 里每个字号都试一次，对每个字号累加一遍 `text` 的宽度。判定一次是 O(L)（L = `text.length`），枚举 m 个字号（m = `fonts.length`）总代价 O(m · L) —— 按约束上限 5×10^4 × 10^5 = 5×10^9 次接口调用，完全不可行。
2. **观察到**：题目保证了 `getHeight(fontSize) <= getHeight(fontSize+1)` 且 `getWidth(fontSize, ch) <= getWidth(fontSize+1, ch)`。于是「放不下」这个性质是**单调**的：某个字号放不下（高度超 `h` 或宽度超 `w`），比它更大的字号必然也放不下；反过来，某个字号放得下，比它更小的字号必然也放得下。在升序的 `fonts` 上，可行性单调排列成 `[可行…可行][不可行…不可行]` 两段。
3. **优化为**：二分这个分界点，只做 O(log m) 次判定。用 `left = -1`、`right = len(fonts)` 的**左开右开**写法维护两个不变式：`left` 永远落在可行侧（初值 -1 表示"还没找到可行字号"），`right` 永远落在不可行侧。循环结束时 `left` 就是最后一个可行元素的下标，`left == -1` 即"没有任何字号放得下"。

### 关键点

- **二分的是 `fonts` 的下标，不是字号数值**。字号数组只保证升序，并不连续（如 `[6,8,10,...]`、`[1,2,4]`），把字号当值域去二分是典型错误。
- **答案是 `fonts[left]` 而不是 `left`**，两者一个是字号、一个是下标。
- **两个约束必须同时满足**：高度是 O(1) 的 `getHeight`，宽度要累加 L 次 `getWidth`。先判高度可以在这条最便宜的约束上先行返回，超限时直接跳过整段宽度累加。
- **开闭口径**：宽度恰好等于 `w`、高度恰好等于 `h` 都算放得下，所以判定写成 `> w` / `> h` 才是"放不下"。
- **哨兵天然处理 -1**：`left = -1` 的初值让"全都不可行"这种情况不需要额外分支，最后 `fonts[left] if left != -1 else left` 直接返回 -1。
- **单调性来自接口保证**，不是自己臆断的规律；没有这条保证，二分不成立。

## 三、代码实现

### 最终代码

> 截图里没有 `List` 的 import，已补 `from typing import List`；`FontInfo` 由评测系统注入，仅作类型标注。

```python
from typing import List


class Solution:
    def maxFont(self, text: str, w: int, h: int, fonts: List[int], fontInfo: 'FontInfo') -> int:
        def check(k: int) -> bool:
            t = fonts[k]                              # 第 k 个候选字号
            answ = 0
            ansh = fontInfo.getHeight(t)              # 高度约束：单次 O(1)
            if ansh > h:
                return False
            for i in text:
                answ += fontInfo.getWidth(t, i)       # 宽度约束：累加每个字符
                if answ > w:
                    return False
            return True

        left = -1                 # 可行侧哨兵
        right = len(fonts)        # 不可行侧哨兵
        while left + 1 < right:
            mid = (left + right) // 2
            if check(mid):
                left = mid
            else:
                right = mid
        return fonts[left] if left != -1 else left     # left == -1 表示无任何可用字号
```

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(L · log m) | O(1) |
| 朴素解法（逐个字号试） | O(L · m) | O(1) |
| 理论下界 | O(L · log m) | O(1) |

> 复杂度中的 n 指：L = `text.length`，m = `fonts.length`。判定次数上限是 ⌈log₂ m⌉；每次判定最坏要遍历 `text` 一遍，即 L 次 `getWidth` 调用。

判定函数只有常数个额外变量；二分也只用 `left` / `mid` / `right` 三个下标，所以空间是 O(1)。

## 五、优化评估

**结论**：时间与空间**都已是最优**。

### 瓶颈分析

- 时间上，每次判定至少要读完整个 `text` —— 宽度是 L 个字符宽度的和，而接口只提供单字符查询，不读完就无法确认宽度是否超限，所以单次判定 O(L) 是必需的；又因为分界位置在 m 个候选里，确定它至少需要 log m 次判定（每次判定只能给出一个二值答案，信息量 1 bit）。两个下界相乘就是 O(L · log m)。
- 空间上只用了若干下标变量，已是常数。

### 可优化空间

没有任何渐近改进空间。可能的替代路线都不划算：把 `text` 的字符先做去重计数（宽度只与字符种类有关）能减少单次判定的调用次数，但需要额外的字典空间，且当 `text` 里字符几乎不重复时收益为零 —— 属于依赖输入分布的常数优化，不改变大 O。

### 常数级优化（可选）

- 把 `fontInfo.getWidth` / `fontInfo.getHeight` 绑定到局部变量再调用，可省掉循环内的属性查找。
- 循环内用 `for ch in text` 直接迭代字符串，避免按下标取字符。
- 高度约束先判：它只需 1 次接口调用，且与 `text` 长度无关，能在超限时省掉整段宽度累加。

## 六、易错点与总结

### 易错点

- **返回 `left` 而不是 `fonts[left]`** —— 把下标当成了字号。
- **按字号数值域二分**：`fonts` 只是升序、并不连续，二分必须落在下标上。
- **漏掉高度约束**：只累加宽度会在「`w` 很大但 `h` 很小」的用例上判错。
- **开闭写反**：宽度等于 `w`、高度等于 `h` 是合法的，判定要用 `>` 而不是 `>=`。
- **闭区间写法下忘记兜底**：如果用 `left = 0, right = len(fonts) - 1`，循环结束后必须再校验 `check(left)`，否则"全都放不下"时会错误地返回 `fonts[0]` 而不是 -1。本题的左开右开写法用 `left = -1` 把这个分支吸收掉了。
- **对不满足单调性的数据套用二分**：这里单调性由接口保证（`getWidth` / `getHeight` 对字号非递减），脱离该前提二分不成立。

### 题型套路沉淀

- **「最后一个满足条件的元素」型二分**：只要判定函数在有序数组上呈现 `[true…true][false…false]` 或反向的单调形态，就在**下标**上二分。
- **左开右开模板**（`left = -1`、`right = n`，循环条件 `left + 1 < right`）：
  - `left` 是"最后一个可行下标"，`right` 是"第一个不可行下标"；
  - 天然支持"无解返回 -1"的哨兵语义，不需要在循环外补判定；
  - 天然支持空数组，不会出现越界。
- **多约束判定的顺序**：把代价最低的约束放前面（O(1) 的高度先判），代价高的（O(n) 的宽度累加）放后面，能在前一个约束失败时省掉后一个。
- **二分前提要写清楚**：二分答案/二分的题，笔记和面试里都要能说出"单调性从哪来"，这是这类题唯一的正确性依据。
