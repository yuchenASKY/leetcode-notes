# 911. 在线选举

> **难度**：中等
> **标签**：设计 · 数组 · 二分查找 · 哈希表
> **原题链接**：https://leetcode.cn/problems/online-election/

---

## 一、题目描述

给两个等长数组 `persons`、`times`：第 `i` 张票在 `times[i]` 时刻投给候选人 `persons[i]`。要求实现 `TopVotedCandidate`：

- 构造时 `TopVotedCandidate(persons, times)`；
- `q(t)` 返回**时刻 `t` 的领先者**。

两条规则：**`t` 时刻投出的票也算数**；**平局时最近获得投票的候选人获胜**。

### 示例

```text
输入：
["TopVotedCandidate", "q", "q", "q", "q", "q", "q"]
[[[0, 1, 1, 0, 0, 1, 0], [0, 5, 10, 15, 20, 25, 30]], [3], [12], [25], [15], [24], [8]]
输出：
[null, 0, 1, 1, 0, 0, 1]

解释：
q(3)  = 0   票为 [0]，0 领先
q(12) = 1   票为 [0,1,1]，1 领先
q(25) = 1   票为 [0,1,1,0,0,1]，1 与 0 各 3 票打平，1 最近获得投票 ⇒ 1 领先
q(15) = 0
q(24) = 0
q(8)  = 1
```

### 约束条件

- `1 <= persons.length <= 5000`，`times.length == persons.length`
- `0 <= persons[i] < persons.length`
- `0 <= times[i] <= 10^9`，**`times` 严格递增**
- `times[0] <= t <= 10^9`
- `q` 最多被调用 `10^4` 次

## 二、解题思路

### 核心思想

**预处理一遍，把「每张票投完后的领先者」存成一张长度 n 的答案表 `tops`；查询时二分定位「`t` 之前最后一张票」的下标，直接查表。**

一条票投出后，领先者只可能在「新投票的那个人」和「原领先者」之间产生 —— 其余候选人的票数没变、最近投票时间也没变，不可能反超。所以预处理只需 O(1) 判一次。

### 思路演进

1. **朴素解法**：`q(t)` 被调用时，把 `times[i] <= t` 的所有票重放一遍，逐票更新票数与领先者。单次查询 O(n)，`Q` 次查询 O(nQ)；`n = 5000`、`Q = 10^4` 时约 5×10^7 次操作，非常危险。
2. **瓶颈定位**：`q(t)` 之间只有 `t` 在变，投票数组是**静态**的。可每次查询都把同一段前缀重算一遍 —— 重复计算，且这段前缀本身就是「数组的前缀」，可以预先算好。
3. **关键转化**：（a）把「时刻 → 领先者」提前到构造阶段算完，存储为 `tops[i] =「第 i 张票投出后」的领先者`；（b）查询退化成「在严格递增的 `times` 里找最后一个 `<= t` 的位置」，这正是**下标二分**能 O(log n) 解决的标准形态。**原来不行，是因为每次查询都在重算前缀；现在行，是因为把前缀结果一次算完，剩下的只是"定位"，而定位有单调性可用。**
4. **最优解**：构造 O(n) + 每次查询 O(log n)。

### 判据与判据族定位

**本题的判据**：

- 预处理不变量 `tops[i] = argmax_p (cnt_i(p), last_i(p))`，其中 `cnt_i(p)` 是前 `i+1` 张票中 `p` 的票数、`last_i(p)` 是 `p` 最后一次被投票的下标（不存在记 −1）。`argmax` 按 `(票数, 最后投票位置)` **字典序**取最大 —— 这条等价刻画把「平局取最近投票者」写成了一个纯偏序关系。
- 查询判据：`answer(t) = tops[ last_index_of(times, times[j] <= t) ]`，右边界定位（`bisect_right(times, t) - 1`）。

**判据族定位**：本题属「**有序序列上的单调谓词边界定位**」（下标二分）族 —— 与第十二~二十例同族。**非滑窗题，`§3.4 ①~⑫` 的目标族与本族无关，不得套用。**

本族的**前置条件**是「被二分的序列有序」，本仓库已记录过四种有序性来源：题面白给 / 非负前提推出的前缀和有序 / `append` 顺序 / 值→下标表的遍历顺序。本题是**第一种：题面直接保证 `times` 严格递增**。

⚠️ 但这不等于「白给的不值钱」：本题整套解法（能二分定位）的**唯一依据**就是这条保证，一旦 `times` 不是递增的（例如乱序给出的投票时间），`bisect_right` 会静默返回错误的边界、**不报错**。所以这里的有序性是**算法正确性的前提**，而不是一个可选的加速条件。

### 关键点

- **平局判据必须是 `>=`**：`voteCounts[p] >= voteCounts[top]` —— 新投票者追平当前领先者时要**顶掉**它，因为它是"最近获得投票的人"。
- **哨兵 `voteCounts[-1] = -1`**：让第一次迭代的 `1 >= -1` 成立，`top` 从 `-1` 直接晋级为第一个候选人。它的 key 取 `-1`，靠 `persons[i] >= 0` 这条约束保证不撞车。
- **`bisect_right(times, t)` 而不是 `bisect_left`**：要找的是「最后一个 `times[j] <= t`」，右边界定位取到的才是含 `t` 时刻那张票的位置。
- **减 1 之后不会负索引**，靠的是题面保证 `times[0] <= t`。这条保证一旦不成立，代码会**静默返回 `tops[-1]`**（见「易错点」）。
- 查询只做「定位 + 取值」，**没有任何逐候选人的计算** —— 这是把 O(n) 压到 O(log n) 的全部意义。

## 三、代码实现

### 最终代码

用户截图版本（逻辑一字未改），**截图里没有 `import`，已补 `from collections import defaultdict` 与 `from bisect import bisect_right`**：

```python
from collections import defaultdict
from bisect import bisect_right


class TopVotedCandidate:

    def __init__(self, persons: list[int], times: list[int]):
        tops = []
        voteCounts = defaultdict(int)
        voteCounts[-1] = -1
        top = -1
        for p in persons:
            voteCounts[p] += 1
            if voteCounts[p] >= voteCounts[top]:
                top = p
            tops.append(top)
        self.tops = tops
        self.times = times

    def q(self, t: int) -> int:
        l = bisect_right(self.times, t) - 1
        return self.tops[l]
```

## 四、复杂度分析

> 复杂度中的 **n** 指 `persons`/`times` 的长度（= 票数，题面上限 5000）；**Q** 指 `q` 的调用次数（上限 10^4）。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | 构造 O(n) + 单次查询 O(log n) | O(n) |
| 优化版（值域数组计数） | 构造 O(n) + 单次查询 O(log n) | O(n) |
| 朴素解法（每次查询重放） | 单次查询 O(n)，Q 次共 O(nQ) | O(n) |
| 理论下界 | 构造 Ω(n) + 单次查询 Ω(log n) | Ω(n) |

- **构造 Ω(n)**：不读一遍票就无法知道任何时刻的领先者。
- **单次查询 Ω(log n)**：「时刻 → 最后一个不超过它的下标」是一次**比较式定位**，有序数组上的信息论下界即 Ω(log n)。想降到 O(1) 只有"值域桶"一条路，而 `t` 的值域是 10^9、远比 n 大，桶直接出局（本仓库已多次量到：`V/n` 达到 10^3 量级时桶版慢两个数量级）。
- **空间 Ω(n)**：`tops` 每个位置都可能存不同的领先者（如两候选人交替投票），无法压缩到常数。

## 五、优化评估

**结论**：渐进复杂度**已是本路线的下界，无可压缩**；但**构造段的常数有明显空间**，实测可稳定快 **1.8× ~ 3.0×**。

### 瓶颈分析

本题代码由两段构成，耗时结构完全不同：

- **构造段**：n = 5000 次迭代，每轮做 3 次字典操作（`voteCounts[p] += 1` 是"读 + 写"、`voteCounts[top]` 是 1 次读）。这段是**一次性**的，但由于每轮都是 Python 层循环，绝对值并不小。
- **查询段**：最多 10^4 次 `q`，每次 1 次 C 层 `bisect_right` + 1 次列表取值。**没法再省** —— 二分的时间几乎全在 CPython 的 `_bisect` C 循环里，Python 层只剩"减少调用次数"和"换掉查表方式"两条路可动，而本题查询必须逐次定位。

### 可优化空间

**① 构造段：把哈希表换成值域数组（采纳）**

题面给了 `0 <= persons[i] < persons.length` —— **值域有界且小于 n**，这是值域数组的适用条件。同时用一个局部变量 `top_cnt` 缓存当前领先者的票数，省掉每轮一次的 `voteCounts[top]` 查表。

**② 查询段：无改进空间**。`bisect_right(self.times, t) - 1` 已经是"一次 C 层定位 + 一次下标访问"的最小形式。

### 优化代码

```python
from bisect import bisect_right


class TopVotedCandidate:

    def __init__(self, persons: list[int], times: list[int]):
        # persons[i] < len(persons) ⇒ 值域有界，用列表计数替代 defaultdict
        cnt = [0] * len(persons)
        tops = []
        top = -1
        top_cnt = 0                      # 缓存当前领先者的票数，省掉每轮 cnt[top] 查表
        for p in persons:
            c = cnt[p] + 1
            cnt[p] = c
            if c >= top_cnt:
                top = p
                top_cnt = c
            tops.append(top)
        self.tops = tops
        self.times = times

    def q(self, t: int) -> int:
        return self.tops[bisect_right(self.times, t) - 1]
```

**优化理由**：两处改动各自有独立依据 ——（a）`persons[i]` 值域是 `[0, n)`，列表下标访问比 `dict` 哈希快，且不需要处理哈希冲突与扩容；（b）`top` 的票数每轮只在"新投票者追平/超越"时才变，用一个局部变量跟着走，就不必每轮回表查一次 `voteCounts[top]`（Python 里 `dict` 查找要走完整的哈希 + 比较流程，而局部变量是 `LOAD_FAST`）。

**实测（n = 5000，7 轮同轮轮转，倍数 = 优化版 / 基线，区间为逐轮比值）**：

| 构造段场景 | 基线 A（ms） | B：`dict.get` + 局部票数 | C：值域数组 + 局部票数 |
| :--- | :--- | :--- | :--- |
| 少数候选人（值域 3） | 0.735 | 0.727~0.799（中位 0.748） | **0.546~0.586（中位 0.555）** |
| 值域 ≈ n（人人一票） | 1.220 | 0.459~0.771（中位 0.504） | **0.299~0.405（中位 0.331）** |
| 两候选人交替 | 0.754 | 0.713~0.810（中位 0.730） | **0.548~0.576（中位 0.555）** |
| 全同候选人 | 0.733 | 0.670~0.750（中位 0.742） | **0.520~0.613（中位 0.558）** |

- **C 版四档逐轮区间全部远低于 1.0，是本次唯一"全档稳定"的优化**；幅度最大的一档恰是「值域 ≈ n」——那里字典有 5000 个键，哈希与扩容的代价最重，列表下标直接绕开。
- **B 版（`dict.get`）也全档领先（逐轮区间 0.459 ~ 0.810，中位 0.504 ~ 0.748）**，但幅度小于 C —— 它只省掉一次查表，值域大时仍要付哈希成本。
- 注意 C 用空间换了常数：`cnt` 由 O(不同候选人数) 升到 O(n)。本题 `persons[i] < n` 有题面保证，**值域无界时此路不可用**。

### 常数级优化（可选）

**被证伪 / 已排除的改法（全部实测）**：

| 改法 | 实测结果 | 结论 |
| :--- | :--- | :--- |
| 查询改 `bisect_left(times, t + 1) - 1` | 逐位等价（官方示例 + 40 组随机对拍 0 偏差）；**隔离测量**（20 万次调用）43.622 ms → 48.055 ms，慢 **10.2%**；端到端四档比值 **0.893 ~ 1.113，全部跨过 1.0** | 噪声内持平（真实差异 ≈ 10%，被端到端噪声盖住），**不建议改** |
| 查询改手写二分 | **4.517 ~ 6.061（四档区间均不跨 1.0）**，中位慢 5.3× | 明确反向，排除 |
| 答案表游程压缩（只存领先者变化的时刻） | 见下表 | 收益完全由输入结构决定，**不能通用替换** |
| 删掉 `voteCounts[-1] = -1` 哨兵行 | 官方示例 + 40 组随机对拍偏差 **0**；耗时比 **0.996 ~ 1.015** | 属"删掉不影响正确性"的**纯常数行**，不是必要守卫 |

**关于「答案表游程压缩」的实测**（构造时只在 `top` 变化处记录，存成 `ct`/`cv` 两条表，查询在更短的表上二分）：

| 场景 | 压缩后段数 | E/C 构造段 | E/C 查询段 |
| :--- | :--- | :--- | :--- |
| 少数候选人（值域 3） | 73 | 1.407~1.512（中位 1.478） | **0.560~0.616（中位 0.608）** |
| 值域 ≈ n | 5000 | 1.239~1.993（中位 1.722） | 0.892~1.126（中位 0.918） |
| 两候选人交替 | 5000 | 1.820~1.981（中位 1.901） | 0.941~1.035（中位 0.979） |
| 全同候选人 | 1 | 1.309~1.442（中位 1.384） | **0.461~0.498（中位 0.478）** |

- **收益的开关是「压缩后段数相对 n 的量级」，不是"`t` 查了多少次"**：段数 ≪ n 时查询段稳定领先（全同档 0.478、值域 3 档 0.608）；段数 = n 时二分深度一点没变，比值跨 1.0（0.918 / 0.979）＝ 持平。
- **而构造段一律更慢（1.24× ~ 1.99×）**：多了一轮 Python 层循环 + 每组一次 `list.append`；"两候选人交替"档最惨，段数 = n，白付一遍压缩成本。
- 本题构造只做 1 次、查询最多 10^4 次，且**数据分布未知**（值域 3 档 vs 全同档的收益差 1.3×，而"两交替"档净亏 1.2×）⇒ **不采纳**：要覆盖最坏情况就退回 C 版。

> 一条与本仓库既有记录同向的提醒：**"取最优倍数"会骗人**。上表"值域 ≈ n"档的查询段逐轮比值一路读到 **1.126**（跨过 1.0），只看取最优值（0.892）会把它写成"快 1.1×"。判据必须是**逐轮比值是否跨过 1.0**，跨过的一律记"噪声内持平"。

## 六、易错点与总结

### 易错点

- **平局判据写成 `>`**：`voteCounts[p] > voteCounts[top]` 会让"追平"的那一票不生效，违反"平局取最近投票者"。实测这个错版**在官方示例上就挂了**（`q(25)` 返回 0、期望 1；整个示例得 `[0,1,0,1,0,0]`，期望 `[0,1,1,0,0,1]`）—— 属"示例即可拦住"的低危型错误。
- **`bisect_right(times, t) - 1` 依赖题面保证 `times[0] <= t`**。一旦 `t < times[0]`，`bisect_right` 返回 0 ⇒ 下标 −1 ⇒ **Python 负索引静默取到 `tops[-1]`**（表里最后一个元素，即"最终领先者"），既不报错也不返回哨兵值。这是「顺手查负索引」的典型形态：**代码不崩，只是答非所问**。
- **哨兵键 `-1` 与候选人 id 的冲突面**：`voteCounts[-1] = -1` 之所以安全，靠的是题面 `0 <= persons[i]`。若候选人 id 允许为负，这个哨兵会与真实候选人共用同一个键，票数统计直接被污染。
- **`bisect_left` / `bisect_right` 用反**：本题要找的是"最后一个 `times[j] <= t`"，用 `bisect_left(times, t)` 会把"恰好等于 `t` 的那张票"排除在外，直接违反"`t` 时刻投出的票也算数"。
- **不要把 `times` 当成"查询时刻表"**：`tops[i]` 的下标是**票的序号**，不是时刻；时刻只在二分里做比较键。两者混用是这题最容易想歪的地方。

### 题型套路沉淀

- **「预处理 + 二分定位」是设计题的标准骨架**：凡是「同一份静态数据被反复按时间/数值查询」的设计题，先把「查询要的答案」按查询轴预计算成表，查询时只做一次定位。本题把「每张票后的领先者」预计算，把 O(n) 的重放压成 O(log n) 的定位。
- **在线维护 top 的通用手法**：每轮只有一个量在变（新投票者的票数）⇒ 与其重新扫描全部候选人，不如只比较「新投票者 vs 当前领先者」。这类"每轮只可能有一个挑战者"的结构，在 `2537`（相等对数）、`3859`（频次达标的种类数）那类滑窗题里也以增量维护的形式出现过，但**判据的推导必须由本题自身给出，不与他族混用**。
- **平局规则的两种等价写法**：逐步模拟（追平就顶掉）与事后取 `(票数, 最后投票位置)` 字典序最大者。写暴力基准时**换一种写**，构成互查 —— 本次两条基准（事后统计式 / 逐步重放式）在 15 组小用例上 0 偏差。
- **值域数组的适用判据**（本仓库已累积多条）：做**计数**用时看 `V` 与 `n` 的量级；做**索引**用时看 `V` 的绝对值与分配成本。本题 `V = max(persons) + 1 <= n`，是最理想的形态。
- **给出"等价改写"时必须一并给出常数**：`bisect_left(times, t + 1)` 与 `bisect_right(times, t)` 结果逐位相同，但每次多做一次整数加法、且 `t + 1 > 256` 时会新建 `int` 对象 —— 本次隔离测量就是慢 10.2%。

| 随机对拍 | 40 组（n ≤ 20，964 次断言） | A / B / C / 三个查询变体 / 消融版 / 两条基准 **偏差全部为 0** |
| 压缩版 E 对拍 | 30 组（995 次断言） | 偏差 **0** |

- 生成器对题面保证加了 `assert`（`times` 严格递增、`persons[i]` 在 `[0, n)` 内），避免拿违反保证的输入去对拍。
- 手工边界覆盖：单元素、`t == times[0]`（下界）、`t == times[-1]`、`t` 落在两次投票之间、`t = 10^9`（上界）、两候选人交替、三人混投。
- 用例计数：**95 组输入**（官方 1 + 基准自检 15 + 手工 8 + 随机 40 + 压缩版 30 + 越界探针 1），另含 4 档微基准输入 —— 远低于 500 组的上限。

### 2) 消融（删掉 / 改掉某处，看哪些输入开始出错）

| 消融项 | 结果 | 说明 |
| :--- | :--- | :--- |
| 删掉 `voteCounts[-1] = -1` | 偏差 **0**（官方示例 + 40 组随机）；耗时比 0.996~1.015 | **纯常数行**：`defaultdict` 会让 `voteCounts[-1]` 隐式为 0，`1 >= 0` 照样成立 |
| 把 `>=` 改成 `>` | 官方示例即失败 | 破坏平局规则，**低危型**（示例可拦，不必加用例） |
| 越过题面保证给 `t < times[0]` | 返回 `tops[-1]`（不报错） | 负索引静默取尾，**静默错解**型 |

### 3) 实测（`time.perf_counter()`，7 轮**同轮轮转**取逐轮比值区间；跨运行的绝对值不可互比）

- 构造段（n = 5000，4 档场景）：C 版中位 **0.331 ~ 0.558**（逐轮区间 0.299 ~ 0.613），B 版中位 **0.504 ~ 0.748**（逐轮区间 0.459 ~ 0.810），两版均全档领先且逐轮区间不跨 1.0。
- 查询段（m = 10^4，4 档场景，基线绝对耗时 2.128 ~ 2.433 ms）：`bisect_left(t+1)-1` **0.893 ~ 1.113（四档全部跨 1.0 → 噪声内持平）**；手写二分 **4.517 ~ 6.061（四档均不跨 1.0 → 明确反向）**。
- `bisect` 等价写法隔离测量（20 万次调用，排除端到端噪声）：43.622 ms → 48.055 ms，**1.102×**。
- 压缩版 E vs C：构造段 **1.239 ~ 1.993（一律更慢）**，查询段段数 ≪ n 时 **0.461 ~ 0.616**、段数 = n 时 **0.892 ~ 1.126（跨 1.0）**。

> 本仓库既有结论「等价写法 ≠ 等价代价」又添一个数据点，且方向一致（`bisect_left(a, x+1)` 慢 8% ~ 13%）。新增的可复用观察是：**端到端噪声（本机约 ±10%）会把这种量级的真实差异整个盖住** —— 想要结论就得做隔离测量（固定有序数组 + 十万次以上调用），端到端的逐轮比值只能用来判"是否跨 1.0"。
