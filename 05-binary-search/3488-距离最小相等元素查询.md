## 一、题目描述

给你一个**环形**数组 `nums` 和一个数组 `queries`。对每个查询 `i`，求下标 `queries[i]` 上的元素，与**任意**其他下标 `j`（满足 `nums[j] == nums[queries[i]]`）在环上的**最小距离**；不存在这样的 `j` 时该查询结果为 `-1`。返回与 `queries` 等长的答案数组。

环上两点的距离定义为 `min(|a-b|, n - |a-b|)`，即可以沿「绕过去」的短边走。

### 示例

```text
输入：nums = [1,3,1,4,1,3,2], queries = [0,3,5]
输出：[2,-1,3]
解释：
  查询 0：下标 0 的元素为 1，最近的相同值下标为 2，距离 2。
  查询 1：下标 3 的元素为 4，不存在其他 4，结果为 -1。
  查询 2：下标 5 的元素为 3，最近的相同值下标为 1，距离 3（沿环：5 -> 6 -> 0 -> 1，绕过去了）。

输入：nums = [1,2,3,4], queries = [0,1,2,3]
输出：[-1,-1,-1,-1]
解释：所有值都唯一，全部 -1。
```

### 约束条件

- `1 <= queries.length <= nums.length <= 10^5`
- `1 <= nums[i] <= 10^6`
- `0 <= queries[i] < nums.length`

> 注意第一条：查询数**不超过** n；第二条：值域上界 `10^6` 与 n 同量级但**可以远大于 n**。

## 二、解题思路

### 核心思想

把「相同值的下标」按值聚成组；在环上，一个位置的最近同值点**只可能是它在环序里的前驱或后继**。于是把组的两端各补一个「环绕副本」，环形问题就变成在一条升序数组上「找 i 的左右邻居」。

### 思路演进

1. **暴力解法**：对每个查询 `q`，扫一遍整个数组，枚举所有 `j != q` 且 `nums[j] == nums[q]`，取 `min(|q-j|, n-|q-j|)`。时间 `O(n·Q)`，额外空间 `O(1)`。
2. **瓶颈定位**：慢在**同一份信息被反复重算**。任一时刻「值 x 出现在哪些下标」这个集合与查询无关，却被每个查询各自重建一遍；而且同一个值若被问 k 次，k 次都在做同一件事。
3. **关键转化**：注意到答案其实是「位置的属性」而不是「查询的属性」—— 对位置 `i`，答案只由**同值出现下标集合**里 `i` 的环序前驱 `pred` 与后继 `succ` 决定，与其它位置无关。证明只用一句话：环上比 `succ` 更远的同值点，其正向距离必然 ≥ 到 `succ` 的距离，不可能更近。所以先按值建「升序下标表」，再处理环形：
   - 把 `[v_1, …, v_L]` **断环成链**成 `[v_L - n, v_1, …, v_L, v_1 + n]`；
   - 补完后整表仍严格升序（`v_L - v_1 ≤ n-1 < n`，故 `v_L - n < v_1`，右端同理），所以二分定位的前提没有被破坏；
   - `bisect_left(p, i)` 恰好落在 `i` 自己那一格（因为 `i ∈ p`），于是 `p[j-1]`、`p[j+1]` 就是环上前驱、后继，答案 = `min(i - p[j-1], p[j+1] - i)`。
4. **最优解**：用户代码（A 版）已是这条路线。再往下推一步可得 **B 版**：既然答案只依赖组内相邻两格，而**组内下标天然升序**（`append` 顺序 = 遍历顺序），那么「前驱」就是数组里的前一格，**不需要二分**——建组时一次顺序扫描就能把每个下标的答案填好，查询退化成 `O(1)` 数组下标，整体 `O(n + Q)`（详见「五、优化评估」）。

### 判据与判据族定位

本题属「**有序序列上的单调谓词边界定位**」（即下标二分）族，与滑动窗口族（双指针 / 尺取）无关，故滑动窗口的各类判据（窗口合法性、收缩方式 × 答案口径的四象限等）一律不适用。

- 本族的载体是**「值 → 升序下标表」这种多路索引**：二分的对象不是原数组自身，而是「按值分好组、组内已有序」的位置表。
- **本族的有序性来自构造方式，不是题面白给的** —— 题面只说 `nums` 是环形数组，是 `append` 的遍历顺序让每组天然递增；一旦改成打乱顺序建组，必须先排序。
- 与相邻族的差别：本族的判定是「目标值在有序表中的**插入位置**」（`bisect_left`），而「二分答案」族判定的是 `check(x)` 的可行性。两族的 `while` 边界写法不同，不要串用。

### 关键点

- **断环成链**：左哨兵必须取 `p[-1] - n`（最大下标绕一圈后的副本），右哨兵取 `p[0] + n`；两者一起用才能同时覆盖「往前绕」和「往后绕」。
- **`bisect_left` 而非 `bisect_right`**：`i` 本身在表内，`bisect_left` 定位到 `i` 自己 ⇒ 取 `j-1 / j+1`；若改用 `bisect_right`，指针会落到 `i` 的右边一格，此时必须取 `j-2 / j`（两者逐位等价，实测见「七、验证记录」）。
- **`len(p) == 3` ⟺ 该值只出现 1 次**：补哨兵恰好贡献 2 个元素，所以判长度 3 即可，不必额外存原组长度。
- 组内元素互不相同，且 `±n` 后不与原区间重叠 ⇒ 补完哨兵后表内无重复元素，`bisect` 结果唯一。

## 三、代码实现

### 最终代码

用户提交并通过的版本（A 版）。截图里的 `import` 缺失，已补：

```python
from collections import defaultdict
from bisect import bisect_left
from typing import List


class Solution:
    def solveQueries(self, nums: List[int], queries: List[int]) -> List[int]:
        indices = defaultdict(list)
        for i, x in enumerate(nums):
            indices[x].append(i)

        n = len(nums)
        for p in indices.values():
            i0 = p[0]
            p.insert(0, p[-1] - n)
            p.append(i0 + n)

        for qi, i in enumerate(queries):
            p = indices[nums[i]]
            if len(p) == 3:
                queries[qi] = -1
            else:
                j = bisect_left(p, i)
                queries[qi] = min(i - p[j - 1], p[j + 1] - i)
        return queries
```

> 补全说明：截图只有 `class Solution:` 起的正文，缺 `defaultdict` / `bisect_left` / `List` 三处 import，已补。截图共 20 行、末行即 `return queries`，与编辑器状态栏「行 20, 列 23」一致，**没有尾部被裁掉**，无需按缩进补全。
>
> 两个保持原样的细节：① 代码**就地修改并返回 `queries`**，与题面「返回一个数组 answer」不冲突（LeetCode 只比对返回值）；② `for qi, i in enumerate(queries)` 是「边遍历边写」——它安全的原因是**写入位置恒等于当轮读取位置**，而位置 `qi` 在它自己那轮之前从未被写过，所以每轮读到的都是原值。这属于「恰好成立」，改成先取 `queries` 再写别处就会读到已改值（见「六、易错点」）。

## 四、复杂度分析

> 复杂度中的 n 指 `len(nums)`（即题面里的 `nums.length`），Q 指 `len(queries)`；题面保证 `Q <= n`。值域记作 V（`max(nums) - min(nums) + 1`），本题 `V ≤ 10^6`。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码（A 版）** | `O(n + Q log n)` | `O(n)` |
| 优化版（B 版，见第五节） | `O(n + Q)` | `O(n)` |
| 朴素解法（逐查询重扫） | `O(n · Q)` | `O(1)` 额外 |
| 理论下界 | `Ω(n + Q)` | — |

- A 版的三项成本：建组 `O(n)`；铺哨兵 `O(不同值个数)`；查询 `Q × O(log L)`（`L` 为该值出现次数）。
- B 版把查询降到 `O(1)`，预处理通过「组内已升序」直接取相邻格，`O(1)` 摊还 per position，故总和 `O(n)`。总时间达到下界 `Ω(n + Q)`（至少要读一遍 `nums`、要写出 Q 个答案）。
- 注意 `log` 因子**不是**下界的一部分：它来自「每次查询独立定位」这个实现选择，而不是问题本身；B 版通过「把定位搬到建表阶段、用相邻关系替代二分」把它消掉。

## 五、优化评估

**结论**：**仍有优化空间**。A 版的查询循环（Q 次「字典查表 + 二分 + `min`」）占总耗时 **55% ~ 85%**，而它做的事情完全可以提前到建表阶段一次做完 —— 因为答案只是「下标的属性」，且**组内下标天然升序**，前驱/后继就是数组里的相邻两格。给出 B 版（`O(n + Q)`），实测在全部 6 档场景上优于 A 版。

### 瓶颈分析

把 A 版拆成三段计时（n = Q = 10^5，7 轮轮转取最优，单位 ms）：

| 场景 | 建组（dict） | 铺哨兵 | 查询循环 | 合计 |
| :--- | ---: | ---: | ---: | ---: |
| 值域 ~10^6（几乎全唯一） | 24.6 | **10.4** | **45.2** | 80.2 |
| 全部互不相同 | 17.7 | 10.4 | 36.2 | 64.3 |
| 值域 ~100（重重复） | 7.0 | 0.06 | 47.8 | 54.9 |
| 全部同值 | 5.3 | 0.04 | 55.7 | 61.0 |

两个结论：

- **铺哨兵的成本 ∝ 不同值的个数，而不是 n**。值域大时 `indices` 里有近 10^5 个组，每组要付一次 `list.insert(0, …)` + 一次 `list.append`，实测 10.4 ms；值域 ~100 时只有 100 个组，降到 0.06 ms ——**相差约 170 倍**。
- **查询循环是最大的单项**，且它每轮做的是「Python 层的 `enumerate` + 字典查表 + C 层 `bisect_left` + 内置 `min`」的混合调用链，`Q` 一大就成主项。

### 可优化空间

| 可去的成本 | 实测占比（值域 ~10^6 档） | 代价 |
| :--- | :--- | :--- |
| 查询循环（`bisect` + `min` + 字典查表） | 45.2 / 80.2 ≈ **56%** | 预处理一次顺序扫描，6.3 ms |
| 铺哨兵（每值一次 `insert`+`append`） | 10.4 / 80.2 ≈ **13%** | 无（相邻关系取代哨兵） |
| 建组（dict 构建） | 24.6 / 80.2 ≈ **31%** | 不可去：必须扫一遍 `nums` |

⇒ 单改动天花板约为 `1 / (1 − 0.56) ≈ 2.3×`。B 版同时吃掉前两项，实测 **0.401× ~ 0.837×（即快 1.19 ~ 2.5 倍）**，与天花板同量级。

### 优化代码

```python
from collections import defaultdict
from typing import List


class Solution:
    def solveQueries(self, nums: List[int], queries: List[int]) -> List[int]:
        n = len(nums)
        pos = defaultdict(list)
        for i, x in enumerate(nums):
            pos[x].append(i)

        res = [-1] * n                      # 只出现一次的值保持 -1
        for p in pos.values():
            L = len(p)
            if L == 1:
                continue
            prev = p[-1] - n                # 环上前驱的「左副本」
            for k in range(L):
                cur = p[k]
                nxt = p[k + 1] if k + 1 < L else p[0] + n   # 环上后继的「右副本」
                d1 = cur - prev
                d2 = nxt - cur
                res[cur] = d1 if d1 < d2 else d2
                prev = cur

        return [res[q] for q in queries]
```

**优化理由**：

1. **消掉 log 因子**：同一值的出现下标在 `p` 里天然升序，所以 `cur` 的环上前驱永远是循环里上一次的 `cur`（首元素的前驱是 `p[-1] - n`），环上后继永远是下一个元素（末元素的后继是 `p[0] + n`）。一次顺序扫描即可，无需 `bisect`，也无需真的构造哨兵数组。
2. **把「查询」变「查表」**：每个下标的答案在建表阶段一次算好（总工作量 `Σ L = n`），查询退化为 `res[q]`，`O(1)`。
3. **顺手去掉两处小成本**：不再有 `len(p) == 3` 的补长判断（改用 `L == 1` 在原表上判），不再有每值一次的 `insert(0, …)`（`list` 头部插入要整体搬移）。

### 被排除的路线

| 路线 | 实测 | 结论 |
| :--- | :--- | :--- |
| **值域数组当索引**（`pos = [[] for _ in range(V+1)]`，省掉 dict） | 建 10^6+1 个空 list 单独就要 **214.8 ms**；端到端 `max(nums) ≈ 10^6` 档 **335.8 ms vs B 版 38.8 ms（8.66× 更慢）**；`max(nums) ≈ 100` 档 1.00×（持平） | ❌ 直接出局。分配成本本身就是天花板：`V` 上界 10^6，光分配就超过 B 版全流程的 5 倍。分配成本随 V 增长实测为 10^3→0.042 ms、10^4→0.47 ms、10^5→5.5 ms、10^6→214.8 ms |
| `bisect_right` 取代 `bisect_left`（取 `j-2 / j`） | 逐位等价（40 组随机 + 官方示例 0 偏差）；同一轮转内端到端 **0.943× ~ 1.023×**（7 档，6 档略快、1 档略慢，幅度均在 6% 以内） | ❌ 无可利用的稳定收益。多一次比较偏移、要额外保证 `j-2 ≥ 0` 的边界心算，而收益落在噪声带里 |

> 值域数组那条路线踩到的真实 bug 见「六、易错点」最后一条 —— 空桶（`L == 0`）会让 `if L == 1` 形同虚设，第一组用例就 `IndexError`。

### 常数级优化（可选）

**已证伪**：把 `min(i - p[j-1], p[j+1] - i)` 拆成两个局部变量 + 内联比较（「少一次内置函数调用」的经典直觉）：

| 场景 | 9 轮最优 | 15 轮复核最优 | 15 轮逐轮比值区间（E/A） |
| :--- | ---: | ---: | :--- |
| 值域 ~10^6 | 1.06× | 1.014× | 0.865 ~ 1.089（中位 1.009） |
| 值域 ~100 | 1.05× | 1.007× | 0.846 ~ 1.135（中位 0.991） |
| 全部同值 | 1.01× | 0.956× | 0.931 ~ 1.679（中位 0.997） |

⇒ 逐轮比值区间**跨越 1.0 两侧**，判为**噪声内持平，不构成有效优化**；首轮读到的 1.06× 是机器漂移。这条与既有记录里「把 `max()` 换成内联比较稳定领先 1.05×~1.08×」的方向**不一致**，建议复核（本次基线的 `min` 只吃两个参数、已是该写法的最简形式，差异可能出在基线不同；本次未做进一步分离）。

**真正有效且已写进 B 版的两处**：① 用「相邻格」替代二分定位；② 把答案缓存成数组、查询退化为下标访问。二者都比上述常数改写高一个量级。

## 六、易错点与总结

### 易错点

- **忘记「断环成链」会漏掉跨 0 点的邻居**。示例 1 的查询 2 就是跨圈的（`5 -> 6 -> 0 -> 1`，答案 3 而非 2）；只在一条直线上取相邻位置，会把这个答案算成「向后无邻居 → -1」。
- **左哨兵取错下标会破坏升序**。左哨兵必须是 `p[-1] - n`（最大下标的副本），写成 `p[0] - n` 会让 `i = p[0]` 时读到「自己的副本」，距离算成 `n`，答案错。取 `p[-1] - n` 的合法性依据是 `p[-1] - p[0] ≤ n - 1 < n`，即补完后 `p[-1] - n < p[0]` 恒成立。
- **漏铺左哨兵时是「静默错解」而不是崩溃**：`bisect_left` 会返回 `0`，此时 `p[j-1]` 变成 `p[-1]` —— Python 负索引**静默取最后一个元素**，于是 `i - p[-1]` 是**负数**，`min` 直接把它当答案返回。**答案为负就是判据/口径写错的信号**；排查这类题时先断言 `p[j] == i`。
- **`bisect_left` 与 `bisect_right` 的下标偏移不能混用**：用 `bisect_left` 取 `j-1 / j+1`；用 `bisect_right` 必须取 `j-2 / j`。两者结果相等，但如果只把函数名换掉、下标不动，取到的是 `i` 自己，`min` 恒为 0。
- **`len(p) == 3` 这个判据依赖「恰好补 2 个哨兵」**：若哪天改成只补一侧，该判据立刻失效（会漏判或误判）。B 版改用原表长度 `L == 1`，不受哨兵个数影响，更稳。
- **就地修改输入 + 同时迭代是「恰好安全」**：`for qi, i in enumerate(queries)` 里每轮写的是 `queries[qi]`，而该位置在被读之后才被写，后续轮次读的是各自尚未被写的位置 —— 所以安全。但它**脆弱**：只要循环体内再多读一次别的位置（比如 `queries[qi-1]`），拿到的就是已改值。返回新数组（B 版）可以完全规避。
- **本机实现细节**：`indices[nums[i]]` 用的是 `defaultdict`，读一个不存在的键会**静默插入**一个空列表（本题 `nums[i]` 必在表中，故无影响）；换成 `dict.get` 或先 `in` 判断可避免副作用。

### 题型套路沉淀

- **环形数组 → 线性**的两条常规手法：① **断环成链**（在有序表两端补 `±n` 的环绕副本，本题用的这条，适用于「找环上邻居」）；② **取模**（`(i + d) % n`，适用于按距离枚举）。手法 ① 的前提是「补完后仍有序」，用之前先验一下。
- **「值 → 升序下标表」是多路索引的标配**：用 `append` 建表，组内天然升序，永远不需要再排序；`bisect` 定位后取左右邻居，就能把「环上最近同值点」这类问题一次算清。
- **答案只是「下标的属性」时，把查询批量化**：本题 Q 次查询问的都是同一个函数 `f(i)`，所以「建表时预处理 `f(i)` 全部值 + 查询查表」严格优于「逐查询实时定位」。识别信号是「查询数 Q 与 n 同量级、而每个查询独立做一次 `O(log)` 定位」。
- **「预处理替代二分」的一般前提**：被查的结构本身有局部性（邻居可直接由数组顺序给出）。若邻居关系需要动态维护，就得退回二分或有序容器。

### 7. 计时基准的设计说明

- 各变体**同轮轮转**测量（`for rep: for variant: …`），避免机器漂移污染；
- 单次读数 ≥ 20 ms 量级（n = Q = 10^5），无需内层重复摊薄计时器噪声；
- 建组阶段统一用 `defaultdict`（与 A 一致），故各变体的建组成本可直接对比；
- 一处**已修正的基准缺陷**：首版阶段归因脚本在 B 的查询阶段混入了 `for q in qs: res[q] = res[q]` 这句无意义的自赋值，会虚高查询耗时 —— 改后 B 的查询阶段为 5.0 ~ 9.1 ms；
- 一处**已知噪声**：A 版（值域 ~10^6 档）在三次独立运行间读出 88.6 ms / 90.8 ms / 83.2 ms，跨度约 9%，故所有倍数结论一律取自**同一轮转内**得到的比值，绝不跨轮比较。
- 一次**已纠正的自查**：初稿曾把「A、B 来自一次运行、C 来自另一次运行」的数字并排列进同一张表，两个倍数因此不可比（C 的 1.01× 是按另一次运行的 A 算的）。现已改为 A / B / C 三者同轮轮转重测，表中全部数字来自同一次运行。
