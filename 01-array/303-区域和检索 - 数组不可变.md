# 303. 区域和检索 - 数组不可变

> **难度**：简单
> **标签**：设计 · 数组 · 前缀和
> **原题链接**：https://leetcode.cn/problems/range-sum-query-immutable/

---

## 一、题目描述

给定一个整数数组 `nums`，实现 `NumArray` 类，支持多次闭区间求和查询 `sumRange(left, right)`，返回 `nums[left] + nums[left+1] + ... + nums[right]`。数组在初始化之后**不会再被修改**（题名里的 *Immutable*），这意味着可以在构造阶段做一次性预处理。

### 示例

```text
输入：
["NumArray", "sumRange", "sumRange", "sumRange"]
[[[-2, 0, 3, -5, 2, -1]], [0, 2], [2, 5], [0, 5]]
输出：[null, 1, -1, -3]
解释：
nums = [-2, 0, 3, -5, 2, -1]
sumRange(0, 2) = -2 + 0 + 3 = 1
sumRange(2, 5) = 3 + (-5) + 2 + (-1) = -1
sumRange(0, 5) = -2 + 0 + 3 + (-5) + 2 + (-1) = -3
```

### 约束条件

- `1 <= nums.length <= 10^4`
- `-10^5 <= nums[i] <= 10^5`
- `0 <= left <= right < nums.length`
- 最多调用 `10^4` 次 `sumRange`

---

## 二、解题思路

### 核心思想

**闭区间和可以写成两个「从头开始的前缀和」之差。** 前缀和只跟数组有关、跟查询区间无关，所以它该被预计算并缓存，而不是每次查询现算。

### 思路演进

1. **暴力解法**：每次查询直接 `sum(nums[left:right+1])`。单次代价 O(right - left + 1)、最坏 O(n)；Q 次查询合计 O(nQ)。n = Q = 10^4 时是 10^8 量级，而且 Python 里每次还要先切片复制出一份子数组，很容易卡在时限上。
2. **观察到**：`nums` 是不变的，相邻两次查询里「从头到 `right` 的那一大段」被反复重新累加，这部分重复劳动完全是浪费。把区间和改写成 `sum(nums[:right+1]) - sum(nums[:left])`，就把「区间求和」变成了「两个前缀相减」。
3. **等价变形（最终代码的形态）**：把右端点从切片里单独提出来，写成 `sum(nums[:right]) - sum(nums[:left]) + nums[right]`。这个写法把「前缀差」的思想表达得更直白，方向完全正确；但它**仍然在每次查询时现场重算前缀**，复杂度并没有真正降下来 —— 切片长度从 `right - left + 1` 变成了 `right` 与 `left` 之和，本质还是 O(n) 每次（详见「五、优化评估」的反直觉对比）。
4. **真正的最优**：既然前缀和是静态量，就把它搬到构造函数里算一次。预计算 `pre[i] = nums[0] + ... + nums[i-1]`（长度 `n + 1`，`pre[0] = 0`），查询退化成一次减法 `pre[right+1] - pre[left]`，O(1)。代码见「五、优化评估」。

### 关键点

- **闭区间 → 前缀差的口径**：`[left, right]` 对应 `pre[right+1] - pre[left]`。前缀数组多留一格 `pre[0] = 0`，`left = 0` 时天然成立，不需要任何特判。
- **`+ nums[right]` 是承重的**：`sum(nums[:right])` 只累加到下标 `right - 1`，减掉 `sum(nums[:left])` 后得到的是半开区间 `[left, right)`，必须补上右端点才闭合。
- **分清「静态量」与「查询量」**：构造完就固定的量（前缀和）进构造函数，随查询变化的量（left / right）进查询函数。这是所有「不可变数组 + 多次区间查询」题型的共同切入点。
- 题目保证数组不被修改，预处理做一次就永远有效；若中途会改，方案要换成树状数组或线段树。

## 三、代码实现

### 最终代码

```python
class NumArray:
    def __init__(self, nums: list[int]):
        self.nums = nums

    def sumRange(self, left: int, right: int) -> int:
        # sum(nums[:right])  覆盖 [0, right-1]
        # 减去 sum(nums[:left]) 覆盖 [0, left-1]，得到 [left, right-1]
        # 再补上右端点 nums[right]，才是闭区间 [left, right] 的和
        return sum(self.nums[: right]) - sum(self.nums[: left]) + self.nums[right]


if __name__ == "__main__":
    # 本地自测，LeetCode 上不需要
    obj = NumArray([-2, 0, 3, -5, 2, -1])
    print(obj.sumRange(0, 2), obj.sumRange(2, 5), obj.sumRange(0, 5))  # 1 -1 -3
```

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码**（每次现算前缀差） | 构造 O(1)；单次查询 O(n)；Q 次共 O(nQ) | O(1) |
| 朴素解法（切片求和） | 构造 O(1)；单次查询 O(right - left + 1)，最坏 O(n) | O(1) |
| 预计算前缀和（见第五节） | 构造 O(n)；单次查询 O(1)；Q 次共 O(n + Q) | O(n) |
| 理论下界 | 构造不少于 O(n)；单次查询 O(1) | O(n) |

> 复杂度中的 n 指 `nums` 的长度，Q 指 `sumRange` 的调用次数。注意「单次查询 O(1)」必须配合「构造 O(n)」才有意义 —— 单看查询那一侧是可以无限快的，代价都压在预处理上。

## 五、优化评估

**结论**：思路正确，但**还没到最优** —— 每次查询仍在 O(n) 现算前缀，Q 次查询乘上去就是 O(nQ)。把前缀和搬进构造函数，查询可以做到 O(1)。

### 瓶颈分析

- **时间**：`sum(self.nums[:right])` 和 `sum(self.nums[:left])` 每次查询都要重新切片（复制一份列表）再从头累加。工作量只跟 `right`、`left` 的大小有关，跟「真正要算的那一段有多长」无关 —— 同一份前缀在 Q 次查询里被重算了 Q 遍。
- **空间**：O(1)，一个字节都没有缓存。省下的空间恰好就是浪费掉的时间来源。
- **一个反直觉的对比**：朴素版单次代价是 `right - left + 1`，最终代码是 `right + left`（两次切片长度之和）。当区间很短而右端点很靠后（如 `left = right = 5000`）时，最终代码要处理约 10^4 个元素，朴素版只要 1 个 —— 这时候它比朴素版**慢得多**；只有当 `left` 也很大、区间也很大时才打平。所以这次等价变形本身**没有带来任何复杂度收益**，它的价值是把「前缀差」的结构暴露出来，真正的收益要等下一步缓存。

### 可优化空间

前缀和是**静态量**：`nums` 一旦固定，`pre` 就固定，跟查哪一段毫无关系。它的 O(n) 计算应该只发生一次（构造函数里），于是 Q 次查询的总代价从 O(nQ) 降到 O(n + Q)。

为什么不可能更好：要让单次查询 O(1)，查询侧只能做常数次算术；而完全不预处理的话，区间内任一元素的变化都无法被 O(1) 感知，所以至少得把 n 个元素看一遍。于是「O(n) 预处理 + O(1) 查询 + O(n) 空间」就是这题的下界，预计算前缀和正好顶到它。

### 优化代码

```python
class NumArray:
    def __init__(self, nums: list[int]):
        # pre[i] = nums[0] + nums[1] + ... + nums[i-1]，多留一格 pre[0] = 0
        self.pre = [0] * (len(nums) + 1)
        for i, x in enumerate(nums):
            self.pre[i + 1] = self.pre[i] + x

    def sumRange(self, left: int, right: int) -> int:
        # 闭区间 [left, right] = 前缀 [0, right] - 前缀 [0, left-1]
        return self.pre[right + 1] - self.pre[left]
```

**优化理由**：把「与查询无关的重算」挪到只执行一次的构造函数里，查询侧只剩一次减法；`pre` 多留一格 `pre[0] = 0` 顺手消掉了 `left = 0` 的特判，边界条件自然成立。

### 常数级优化（可选）

- 前缀数组可以用标准库一行建出来，语义与上面的循环完全等价：`self.pre = list(accumulate(nums, initial=0))`（需 `from itertools import accumulate`）。`initial=0` 正好对应 `pre[0] = 0`。
- 反过来看：如果 `Q` 远小于 `n`（只查一两次），预处理的 O(n) 就是净亏，此时直接用朴素切片求和更划算。这是「预处理成本 vs 查询次数」的取舍，不属于常数优化。

## 六、易错点与总结

### 易错点

- **口径写反：写成 `pre[right] - pre[left]`** —— 少算一个右端点，`left == right` 时结果直接是 0。用长度 `n + 1` 的 `pre` 并从 `pre[right + 1]` 开始减，就不会踩。
- **`sum(nums[:right]) - sum(nums[:left])` 忘了补 `+ nums[right]`** —— 这个式子得到的是半开区间 `[left, right)`，恰好差一个右端点，是最容易在最终代码里漏掉的一块。
- **`left == 0` 的特判写反或忘写**：如果坚持用长度 n 的前缀数组（`pre[i] = nums[0..i]`），`left == 0` 必须单独处理；漏掉就会让 `pre[left - 1]` 变成 `pre[-1]`，从数组尾部倒着取一个值 —— **不抛异常、答案全错**，这类「静默错误」最难查。
- **把预处理留在查询里**：`nums` 明明不变，前缀和却写在 `sumRange` 里重算。小数据能过，大数据是 O(nQ)。
- **数组长度开错**：`pre` 要按 `n + 1` 开，不是 `n`。`len(nums) + 1` 这个 `+1` 是这个模板的全部边界安全性所在。

### 题型套路沉淀

- **前缀和模板（闭区间版）**：`pre = [0] * (n + 1)`；`pre[i + 1] = pre[i] + nums[i]`；`sum(l, r) = pre[r + 1] - pre[l]`。「多留一格」的写法把所有边界特判都消掉了，一律优先用它。
- **看到「数组不可变 + 多次区间查询」就条件反射想预处理**：一次 O(n) 换掉 Q 次 O(n)，是空间换时间最标准的形态。若数组会被修改，就升级为树状数组（单点改 + 区间查）或线段树（区间改 + 区间查）。
- **设计题的第一动作**：先问一句「哪些量在构造完之后就固定了」，把它们全部搬到构造函数里去。这一类题（缓存 / 预计算 / 索引）几乎都是这个套路。
- **写完先对一遍极端用例**：`(0, 0)`、`(n-1, n-1)`、`(0, n-1)`、以及 `left` 大而 `right` 紧邻（区间长度 1 但偏移很大）。这一段专门用来暴露「切片长度口径」和「右端点漏算」两类错。
