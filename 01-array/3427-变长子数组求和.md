# 3427. 变长子数组求和

> **难度**：简单
> **标签**：数组 · 前缀和
> **原题链接**：https://leetcode.cn/problems/sum-of-variable-length-subarrays/

---

## 一、题目描述

给定长度为 `n` 的整数数组 `nums`。对**每一个**下标 `i`（`0 <= i < n`），取子数组 `nums[start..i]`，其中起点由 `nums[i]` 自己决定：`start = max(0, i - nums[i])`。把这些 `n` 个子数组的元素总和全部加起来返回。

也就是说：`nums[i]` 既是**值**，又顺手充当了「向左覆盖多远」的**长度参数**。

### 示例

```text
输入：nums = [2,3,1]
输出：11
解释：
i = 0：start = max(0, 0-2) = 0，子数组 [2]，和 2
i = 1：start = max(0, 1-3) = 0，子数组 [2,3]，和 5
i = 2：start = max(0, 2-1) = 1，子数组 [3,1]，和 4
总和 = 2 + 5 + 4 = 11
```

### 约束条件

- `1 <= n == nums.length <= 100`
- `1 <= nums[i] <= 1000`
- 每个子数组长度不超过 `i + 1 <= 100`，单项和不超过 `10^5`，总和规模在 `10^7` 量级，不会溢出

---

## 二、解题思路

### 核心思想

所有 `n` 个子数组的**右端点都等于 `i`**，差异全在左端点。既然要反复求「原数组某一段连续区间的和」，就先用一趟前缀和把区间查询压成 `O(1)`，再枚举 `i` 直接做减法。

### 思路演进

1. **暴力解法**：对每个 `i` 算出 `start`，再从 `start` 循环累加到 `i`。区间长度最长可达 `n`，总共 `O(n²)`。`n <= 100` 时这已经能过（约 5000 次加法），但复杂度上是平方级 —— 一旦数据规模上调就崩。
2. **观察到**：所有子数组都是**同一个数组**上的连续区间，且右端点恰好是当前下标。被重复计算的不是「某个元素」，而是「同一段前缀」：`nums[0..i]` 在 `i` 较小时几乎每个区间都要重算一遍。
3. **优化为**：定义前缀和 `s[0] = 0`、`s[k] = nums[0] + ... + nums[k-1]`（长度 `n+1`，多出来的一位是哨兵）。于是任意闭区间 `[l, r]` 的和就是 `s[r+1] - s[l]`，一次减法搞定。总时间降到 `O(n)`。

### 关键点

- **下标口径**：`s` 的长度是 `n+1`，`s[k]` 表示「前 `k` 个元素之和」。闭区间 `[l, r]` 对应 `s[r+1] - s[l]`，用本题变量就是 `s[i+1] - s[start]`。写成 `s[i] - s[start]` 就整体错位一格。
- **`start` 的下界必须夹到 0**：`i - nums[i]` 可能为负（`nums[i]` 比 `i` 还大，说明这题想让它一路覆盖到数组开头），`max(0, ...)` 就是题面给的这道保险。
- **`nums[i]` 的双重身份**：它既是子数组里的一个值，又是决定左边界的参数。不要顺手把 `nums[i]` 当成「区间长度」写 `i - start + 1 == nums[i]` —— 只有 `i >= nums[i]` 时才恰好差 1，`i < nums[i]` 时区间被截断到数组头。
- **结果是「所有区间和之和」而不是「所有区间合并后的和」**：同一个元素会被多个区间重复统计，`nums[0]` 在示例里就进了三个区间。不能去重。

## 三、代码实现

### 最终代码

```python
# 截图里没有、已补：LeetCode 判题环境已内置 typing 导入，本地运行需要显式写
from typing import List


class Solution:
    def subarraySum(self, nums: List[int]) -> int:
        n = len(nums)

        # s[k] = nums[0] + ... + nums[k-1]，s[0] = 0 作为哨兵
        s = [0] * (n + 1)
        for i in range(n):
            s[i + 1] = s[i] + nums[i]

        ans = 0
        for i in range(n):
            start = max(0, i - nums[i])      # 左边界夹到 0
            ans += s[i + 1] - s[start]       # 闭区间 [start, i] 的和
        return ans
```

## 五、优化评估

**结论**：时间复杂度已是理论下界，**无需再优化**。

### 瓶颈分析

时间上，每个下标 `i` 都必须被枚举一次、每一次都可能改变答案，所以至少 `O(n)`；而前缀和方案正是 `O(n)` 建表 + `O(n)` 枚举，只有常数开销（两趟循环）。空间上唯一的花费是那张 `n+1` 长的前缀和数组。

### 可优化空间

**时间没有**：不可能比「把所有元素看一遍」更快。

**空间上也省不掉**：本可以幻想用滑动窗口把窗口和增量维护到 `O(1)` 空间，但这题的左端点 `start = max(0, i - nums[i])` 随 `nums[i]` 忽左忽右（不是单调的）——`i` 前进一步时左指针可能向右跳很远，也可能向左回退，回到曾经的区间就得把元素重新加回来，来回抖动累计代价可能退化到 `O(n²)`。所以 `O(n)` 的前缀和表反而是这笔账里最划算的：用一趟线性预处理，换掉「历史前缀不可回看」这个结构性麻烦。

### 常数级优化（可选）

- 建表那一趟可以合成一趟：边累加 `cur` 边往 `s` 里写，等价于本代码。
- 若只想少一次列表分配，可用 `itertools.accumulate(nums, initial=0)` 直接生成前缀和序列。
- 本题 `n <= 100`，任何常数级改动都不会体现在结果上，**不建议为它牺牲可读性**。

## 六、易错点与总结

### 易错点

- **前缀和错位一格**：写成 `s[i] - s[start]`（漏掉 `s[i+1]`）会让每个区间都少算最后一个元素。
- **忘了 `max(0, ...)`**：`i - nums[i]` 为负时直接拿去做下标，在 Python 里会变成「从尾部倒数」的负索引，**不报错但答案全错** —— 这是最隐蔽的一类 bug。
- **把 `nums[i]` 当区间长度**：`i < nums[i]` 时区间被截断，实际长度是 `i + 1` 而不是 `nums[i] + 1`。
- **误以为要合并区间去重**：题面是「每个下标定义的子数组之和，再全部加起来」，重复统计是要求而不是缺陷。

### 题型套路沉淀

- **看到「求很多个区间的和」就上前缀和**：`s[k] = 前 k 项和`、`s[0] = 0` 做哨兵、闭区间 `[l, r] → s[r+1] - s[l]`，这三件套背下来，能覆盖绝大多数区间求和题。
- **前缀和是「一次预处理、多次查询」的典型模式**：判断是否值得预处理，看区间查询次数是否达到 `O(n)` 量级 —— 本题查询 `n` 次、每次 `O(1)`，正好把 `O(n²)` 拉成 `O(n)`。
- **右端点固定、左端点由元素自身决定**是本题的辨识特征：这类题的左端点通常不单调，所以别急着套滑动窗口，先用前缀和把「区间求值」这件事解耦出来。
