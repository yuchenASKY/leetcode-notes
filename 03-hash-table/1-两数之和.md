# 1. 两数之和

> **难度**：简单
> **标签**：数据结构 · 哈希表 · 数组
> **原题链接**：https://leetcode.cn/problems/two-sum/

---

## 一、题目描述

给定长度为 n 的整数数组 `nums` 与目标值 `target`，找出数组中**和恰好等于 `target`** 的两个元素，按任意顺序返回它们的**下标**。保证每组输入只对应一个答案，且同一个下标不能被用两次。

### 示例

```text
输入：nums = [2,7,11,15], target = 9
输出：[0,1]
解释：nums[0] + nums[1] == 2 + 7 == 9

输入：nums = [3,2,4], target = 6
输出：[1,2]

输入：nums = [3,3], target = 6
输出：[0,1]
```

### 约束条件

- `2 <= nums.length <= 10^4`
- `-10^9 <= nums[i] <= 10^9`、`-10^9 <= target <= 10^9`
- 只会存在一个有效答案
- 进阶：能否设计出时间复杂度小于 O(n²) 的算法

---

## 二、解题思路

### 核心思想

**把「找另一个数」从遍历变成查表。** 扫到 `x` 时唯一要回答的问题是「`target - x` 之前出现过吗、下标是多少」，这正是哈希表最擅长的 `O(1)` 查询。

### 思路演进

1. **暴力解法**：对每个 `i` 再扫一遍 `j > i`，判断 `nums[i] + nums[j] == target`。时间 `O(n²)`，n = 10⁴ 时是 10⁸ 量级的两两比较 —— 能不能过全看测试数据，不能当正解。
2. **观察到**：内层循环真正做的事只有一件 —— **查 `target - nums[i]` 在不在数组里**。它花了 `O(n)` 的时间去做一次「存在性查询」，而查询结果只有「在（且下标是几）/ 不在」两种。
3. **关键转化**：既然只关心「出现过没有」，就把**已经扫过的元素**记成 `值 -> 下标` 的哈希表。扫到第 `j` 个元素时，先查 `target - nums[j]` 是否已在表中：在就直接返回；不在就把 `nums[j]` 及其下标放进表里，继续往后扫。
4. **得到最优解**：一次遍历同时完成「查」与「记」，时间降到 `O(n)`，代价是 `O(n)` 的额外空间。

### 关键点

- **顺序承重：先查、再插，不能反。** 若先把当前元素插进表再查，`nums = [3,3], target = 6` 时第一次迭代就会拿自己和自己配对，返回 `[0,0]`。先查后插等于保证「表里只有前面的元素」，天然满足「同一元素不能用两次」。
- **存的是 `值 -> 下标`。** 查找依据是值，返回依据是下标，方向反了就没法出答案。
- **只扫到当前元素之前的部分** 还带来一个好处：不需要额外的 `j != i` 判断，也不必预先判断「配对元素是否在自己后面」。
- **题目保证有唯一解**，所以循环走完的情况实际不会发生；当前代码没有写兜底 `return`，若把它挪到「可能无解」的场景务必补上。

## 三、代码实现

### 最终代码

```python
class Solution:
    def twoSum(self, nums: list[int], target: int) -> list[int]:
        idx = {}                                  # 值 -> 下标
        for j, x in enumerate(nums):
            if target - x in idx:                 # 先查：配对数是否已出现
                return [idx[target - x], j]
            idx[x] = j                            # 再插：把当前元素记入表中
```

> 截图里没有 import，本题也确实**不需要 import**：`list[int]` 是内置泛型（Python 3.9+ 可直接写在注解里）。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) | O(n) |
| 朴素解法（双重循环） | O(n²) | O(1) |
| 理论下界 | O(n) | O(1) |

> 复杂度中的 n 指数组 `nums` 的长度：时间上每个元素最多被访问一次（哈希表操作均摊 O(1)），空间上哈希表最坏要存下前 n-1 个元素（答案出现在末尾时）。

- **时间**：单层循环 n 次，每次是「一次哈希查找 + 一次哈希插入」，均摊 `O(1)`，总计 `O(n)`。降到 `O(n)` 已经是下界 —— 最坏情况下答案藏在最后两个位置，任何算法都必须看完整个数组才敢下结论。
- **空间**：额外 `O(n)` 的字典，与朴素解法的 `O(1)` 相比是典型的**空间换时间**：用一整个数量级的空间，换掉一整个数量级的时间。

## 五、优化评估

**结论**：时间已经到理论下界，**没有进一步优化的余地**；空间上的 `O(n)` 是「输入无序」+「要返回下标」这两条约束共同决定的必要代价。

### 瓶颈分析

- **时间**：答案可能落在最后两个位置，任何算法都必须把数组看完才敢下结论，所以 `O(n)` 是硬下界。当前每个元素只被访问一次，没有多余遍历。
- **空间**：`O(n)` 全部花在哈希表上。要把它压到 `O(1)`，就必须放弃「边扫边随机查询」这条路。

### 可优化空间

**若输入有序**，可以让左右指针从两端向中间夹：和偏小就右移左指针、偏大就左移右指针，每次必定排除一个元素，空间降到 `O(1)`。

但本题输入**无序**，排序本身要 `O(n log n)`，还会打乱原始下标（题目要的恰恰是下标），重建下标的代价又回到 `O(n)`。因此：**无序输入下 `O(n)` 空间无法避免**。

另一条路是「排序 + 二分」：固定一个元素后二分查 `target - x`，空间 `O(1)`（不算排序副本），但时间退化到 `O(n log n)` —— 只适合内存极度受限的场景，不如哈希表。

### 常数级优化（可选）

当前写法 `if target - x in idx` 之后又取了一次 `idx[target - x]`，**命中时做了两次哈希查找**。改成一次 `get` 可以省掉第二次：

```python
class Solution:
    def twoSum(self, nums: list[int], target: int) -> list[int]:
        idx = {}
        for j, x in enumerate(nums):
            p = idx.get(target - x)      # 一次查找，顺便拿到下标
            if p is not None:            # 必须用 is not None：下标 0 为假，不能用 if p
                return [p, j]
            idx[x] = j
```

**优化理由**：把「判断是否存在」和「取下标」合并成一次字典查找。大 O 不变，只是少一次哈希查询 —— 属于锦上添花，原写法已经完全够用。

## 六、易错点与总结

### 易错点

- **先插后查**：`nums = [3,3], target = 6` 时第一次迭代就会拿自己配对，返回 `[0,0]` —— 同一个元素被用了两次。
- **表和值方向写反**：存成 `下标 -> 值` 就没法按值反查，必须是 `值 -> 下标`。
- **返回下标而不是值**：题目要的是 `[i, j]`，别顺手写成 `[nums[i], nums[j]]`。
- **兜底遗漏**：当前代码依赖「题目保证唯一解」省略了 `return []`，一旦挪到可能无解的场景（比如自己改造的版本），函数会静默返回 `None`。

### 题型套路沉淀

- **哈希表配对模型**：凡是「凑出某个和 / 差 / 关系」的题，先想能不能把内层线性查找压成 `O(1)` 哈希查询。同族题：`167. 两数之和 II - 输入有序数组`（有序 ⇒ 双指针 `O(1)` 空间）、`15. 三数之和`、`454. 四数相加 II`。
- **「只记已扫描前缀」是通用骨架**：边遍历边登记，查询只看历史、不看未来 —— 既天然满足「同一元素不能用两次」，也省掉了额外的越界与顺序判断。
- **顺序承重**：先查后插这一动作要形成肌肉记忆，写反是这类题最常见的 WA 来源。
