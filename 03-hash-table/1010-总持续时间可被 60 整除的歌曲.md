# 1010. 总持续时间可被 60 整除的歌曲

> **难度**：中等
> **标签**：数组 · 哈希表 · 计数
> **原题链接**：https://leetcode.cn/problems/pairs-of-songs-with-total-durations-divisible-by-60/

---

## 一、题目描述

给定歌曲时长数组 `time`，统计满足 `i < j` 且 `(time[i] + time[j]) % 60 == 0` 的下标对 `(i, j)` 的数量。即两首歌的时长之和是 60 的整数倍（1 分钟、2 分钟、3 分钟……）。

### 示例

```text
输入：time = [30,20,150,100,40]
输出：3
解释：三对分别是 (0,2) → 180、(1,3) → 120、(1,4) → 60
```

```text
输入：time = [60,60,60]
输出：3
解释：任意两首之和都是 120，C(3,2) = 3 对
```

### 约束条件

- `1 <= time.length <= 6 * 10^4`
- `1 <= time[i] <= 500`

---

## 二、解题思路

### 核心思想

**`(a + b) % 60 == 0` 只取决于 `a % 60` 和 `b % 60`，与时长本身无关。** 于是问题从「按值配对」降维成「按余数配对」：维护一张「各余数已出现过多少次」的哈希表，遍历到 `t` 时直接查它的互补余数有多少个，累加即得答案。

### 思路演进

1. **暴力解法**：双重循环枚举所有 `(i, j)`，逐对判断 `(time[i] + time[j]) % 60 == 0`。时间 O(n²)，n 最大 6×10⁴ 时约有 1.8×10⁹ 次判断，必然超时；空间 O(1)。

2. **观察到**：判断式里真正起作用的只有余数。`time[i] <= 500`，所以余数最多 60 种取值 —— 这意味着「所有时长」可以被压缩进一个只有 60 个槽位的表里，`time[i]` 的具体大小反而是噪声。

3. **优化为**：一次遍历，把「往后找配对」改成「回头数伙伴」。
   - 对当前 `t` 求余数 `r = t % 60`；
   - 它的互补余数是 `need = (60 - r) % 60`（满足 `(r + need) % 60 == 0`）；
   - 哈希表里 `need` 的计数，就是**当前 `t` 能与之配对的所有更早元素**的个数，直接累加；
   - 最后把 `r` 的计数 +1，供后面元素查询。

   `i < j` 不需要额外处理：因为查询时表里只存了「已经扫过的元素」，天然满足「配对对象的原始下标更小」。

### 关键点

- **`need` 必须写成 `(60 - r) % 60`，不能写成 `60 - r`**。当 `r == 0` 时 `60 - r = 60`，而余数 60 是永远不可能出现的键 —— 会把「余数 0 与余数 0 配对」这一整类（示例 2 就是它）无声漏掉。
- **顺序必须是「先累加、后计数」**。若先 `cnt[num] += 1` 再查，当 `2 * r` 也是 60 的倍数时（`r == 0` 或 `r == 30`），当前元素会把自己算成一个配对。
- 值域极小时（只有 60 种余数），哈希表的规模上界与 `n` 无关 —— 这是空间能压到 O(1) 的根本原因。
- 题目只问**数量**，不问具体下标对，所以表里存「计数」即可，不必存下标列表。

## 三、代码实现

### 最终代码

```python
from collections import defaultdict


class Solution:
    def numPairsDivisibleBy60(self, time: list[int]) -> int:
        cnt = defaultdict(int)          # 余数 -> 已出现次数
        ans = 0
        for t in time:
            num = t % 60
            temp = (60 - num) % 60
            ans += cnt[temp]            # 之前出现过的互补余数，全部构成合法配对
            cnt[num] += 1
        return ans
```

> 说明：截图里的代码没有 `from collections import defaultdict`，已补齐（截图里没有、此处已补）。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) | O(min(n, 60)) 即 O(1) |
| 朴素解法 | O(n²) | O(1) |
| 理论下界 | O(n) | O(1) |

> 复杂度中的 n 指数组 `time` 的长度。空间项写 `min(n, 60)` 是因为余数只有 60 种取值，无论数组多长，表里最多只有 60 个不同的键。

## 五、优化评估

**结论**：时间复杂度已是理论下界；空间复杂度已经是 O(1)，但**常数与每秒开销仍可再压**。

### 瓶颈分析

时间上无法再降：题目要求统计任意两两组合，任何一个被漏看的元素都可能导致漏解，所以 Ω(n) 是硬下界，当前的 O(n) 已经对齐。

空间上，`dict` 在这里其实被大材小用了 —— 它的键只有 60 种可能，槽位固定，用哈希 + 溢出探测来承载一张 60 格的计数表并不划算。

### 可优化空间

把 `defaultdict` 换成**长度 60 的 `list` 计数桶**：余数 `r` 天然落在 `[0, 60)`，直接拿它当下标，省掉哈希计算与 miss 时创建默认值的开销，同时空间精确固定为 60 个槽，不再随 `n` 增长。

### 优化代码

```python
class Solution:
    def numPairsDivisibleBy60(self, time: list[int]) -> int:
        cnt = [0] * 60
        ans = 0
        for t in time:
            r = t % 60
            ans += cnt[(60 - r) % 60]
            cnt[r] += 1
        return ans
```

**优化理由**：值域已知且极小（60 个余数）时，直接用「下标即键」的定长数组，是把哈希表降级成数组的典型场景 —— 逻辑一字未改，只是把「查表」换成了「按下标取」。

### 常数级优化（可选）

- 把 `cnt` 与方法内其他对象在循环外先取成局部名，减少循环体里的属性查找；`len(time)` 同理。
- 若用 C++ 实现，`ans` 需要 `long long`：`n = 6×10^4` 时最大配对数为 `C(6×10^4, 2) = 1,799,970,000`，虽仍小于 `INT_MAX`（2,147,483,647），但差距已经很小，留足余量更稳妥。

## 六、易错点与总结

### 易错点

- **互补余数漏写 `% 60`**：`60 - r` 在 `r == 0` 时得到 60，是个不存在的余数，导致「两个 60 的倍数相加」这一类配对全部丢失。示例 2（`[60,60,60]`）就会直接得到 0 而不是 3。
- **先计数后累加**：会让当前元素与自身配对，`r` 为 0 或 30 时答案偏大。
- **误以为要排序或去重**：本题问的是下标对的数量，不是不同的时长组合，重复值必须逐个计数，不能去重。
- **只想到「按值配对」**：一旦把 `time[i]` 原样当作键，空间就退化成 O(n)，且没有任何必要 —— 判据里只用得到余数。

### 题型套路沉淀

- **余数 / 模运算配对 → 余数哈希 + 先查后插**：凡是「两数之和满足某个模约束 / 整除关系」的题，第一步都做「把元素映射到模数后的余数」，把 O(n²) 的两两判断压成一次遍历的单次查询。
- **互补量要套 `% M`**：写 `need = (M - r) % M` 而不是 `M - r`，`r == 0` 的边界只有这一步能兜住。这是同族题里最稳定的出错点。
- **值域小 → 哈希降级为数组**：当键的可能取值是个小常数（如 26 个字母、60 个余数、固定范围整数）时，定长数组前缀和 / 计数桶通常比 `dict` 更合适。
- **计数型配对题的固定三段式**：求当前元素的贡献（`ans += cnt[need]`）→ 更新结构（`cnt[key] += 1`）→ 顺序不可交换。
