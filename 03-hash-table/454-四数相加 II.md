# 454. 四数相加 II

> **难度**：中等
> **标签**：数组 · 哈希表
> **原题链接**：https://leetcode.cn/problems/4sum-ii/

---

## 一、题目描述

给定四个长度都为 `n` 的整数数组 `nums1`、`nums2`、`nums3`、`nums4`，统计有多少个四元组 `(i, j, k, l)` 满足 `nums1[i] + nums2[j] + nums3[k] + nums4[l] == 0`。

注意三个前提：四个下标**分别**取自四个不同数组（互不干扰）；下标可以重复出现在不同的四元组里；统计的是**四元组的个数**而不是「不同的解」，所以数组里有重复值时，每一个下标组合都要单独计数。

### 示例

```text
输入：nums1 = [1,2], nums2 = [-2,-1], nums3 = [-1,2], nums4 = [0,2]
输出：2
解释：
1. (0, 0, 0, 1)：nums1[0] + nums2[0] + nums3[0] + nums4[1] = 1 + (-2) + (-1) + 2 = 0
2. (1, 1, 0, 0)：nums1[1] + nums2[1] + nums3[0] + nums4[0] = 2 + (-1) + (-1) + 0 = 0
```

### 约束条件

- `n == nums1.length == nums2.length == nums3.length == nums4.length`
- `1 <= n <= 200`
- `-2^28 <= nums1[i], nums2[i], nums3[i], nums4[i] <= 2^28 - 1`
- 答案保证在 32 位整数范围内

## 二、解题思路

### 核心思想

**把四个数的问题拆成两组「两数之和」的问题。** `a + b + c + d == 0` 等价于 `a + b == -(c + d)`：先用哈希表记下 `nums1`、`nums2` 所有两两之和的出现次数，再枚举 `nums3`、`nums4` 的所有两两之和，用 `-(c + d)` 去表里查配对次数。

### 思路演进

1. **暴力解法**：四重循环枚举 `(i, j, k, l)`，和为 0 就计数。时间 O(n⁴)，n = 200 时是 1.6×10⁹ 次枚举，远超时限。

2. **观察到**：四重循环的内层两层做着和「两数之和」一模一样的事 —— 对每个固定的 `(i, j)`，需要知道有多少个 `(k, l)` 使 `nums3[k] + nums4[l] == -(nums1[i] + nums2[j])`。这是一个**计数型配对查询**，每次用 O(n²) 线性扫描去找，浪费在了完全相同的一组候选上。

3. **优化为**：把「数对」整体当成一个元素来看待。`nums1 × nums2` 能产生至多 n² 个和（带重复计数），`nums3 × nums4` 同理。于是问题退化成「两个长度为 n² 的数组，问有多少对元素之和为 0」—— 这就是 `1. 两数之和` 的**计数版**：一边建 `和 -> 出现次数` 的哈希表，另一边 O(1) 查表并累加频次。总复杂度从 O(n⁴) 降到 O(n²)。

4. **为什么不能像两数之和那样「边查边插」**：`1. 两数之和` 可以在一次遍历里边扫边插，是因为它只有一个数组、配对双方共享同一个遍历序列，先扫到的一方必然已经入表。本题两侧是**两个互不相干的枚举空间**，没有先后依赖关系 —— 如果交错插入，早出现的 `CD` 和会查不到后建立的 `AB` 和，必然漏解。所以必须**先把 `AB` 一侧建完，再整体枚举 `CD`**。

5. **为什么是「两两分组」而不是「三数 + 一数」**：三数一侧要枚举 n³，另一侧 n，总代价 O(n³)，比 O(n²) 差一个数量级。分组越均衡越好，四个数最优就是 2+2。

### 关键点

- **表里存的是次数，不是「存在性」**：多个下标组合可能得到同一个和，每一条都对应一组不同的 `(i, j)`，所以 `hashmap[和]` 要累加而不是置 1。
- **查表时累加 `hashmap[key]` 而不是 `+1`**：命中一次代表 `hashmap[key]` 个不同的四元组。
- **两侧方向相反**：`AB` 侧存 `a + b`，`CD` 侧查 `-(c + d)`，符号写反是这类题最常见的错误。
- **建表与查询的顺序不可交换**：先建完 `AB` 全表，再做 `CD` 的枚举。
- 题目问的是**方案数**，不是「是否存在」，所以遍历必须走完全部 n² 对，不能提前 return。

## 三、代码实现

### 最终代码

```python
from typing import List


class Solution:
    def fourSumCount(self, nums1: List[int], nums2: List[int],
                     nums3: List[int], nums4: List[int]) -> int:
        hashmap = dict()                       # a + b -> 出现次数
        for n1 in nums1:
            for n2 in nums2:
                s = n1 + n2
                if s in hashmap:
                    hashmap[s] += 1
                else:
                    hashmap[s] = 1

        count = 0
        for n3 in nums3:
            for n4 in nums4:
                key = -n3 - n4                 # 需要匹配的 a + b
                if key in hashmap:
                    count += hashmap[key]      # 累加次数，不是 +1
        return count
```

> 截图的原始代码里没有 `from typing import List`，这里补上，否则非 LeetCode 环境直接运行会 `NameError`。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n²) | O(n²) |
| 朴素四重循环 | O(n⁴) | O(1) |
| 三数 + 一数分组 | O(n³) | O(n²) |
| 理论下界 | Ω(n²) | O(n²) |

> 复杂度中的 n 指每个数组的长度（四者相等，均为 `n <= 200`）。哈希表最多存 n² 个不同的和，故空间为 O(n²)。

几组量级感受（n = 200）：朴素解 1.6×10⁹ 次枚举，`三数 + 一数` 约 8×10⁶ 次，本题解法约 8×10⁴ 次（建表 n² + 查表 n²）。每降一个 O 的指数都是一次数量级上的跳跃。

## 五、优化评估

**结论**：时间复杂度 **O(n²) 已是该思路下的最优**，且是 4SUM 类计数问题在本题规模下的标准解法。

### 瓶颈分析

时间全部花在两侧各 n² 次的枚举上，这部分无法省略 —— 要把 4 个数组的所有组合都「看过一遍」，至少需要把 `nums1 × nums2` 和 `nums3 × nums4` 这两批数对生成出来，而每批就是 n² 个，所以 **Ω(n²) 是天然下界**，除非引入 FFT / 多项式乘法一类的代数手段（那属于超纲且常数巨大，n = 200 时毫无意义）。

空间上，哈希表规模上界是 n² = 4×10⁴ 项，远在内存限制之内，不构成瓶颈。

### 可优化空间

- **两侧规模不等时可以倾斜分组**：若四个数组长度不同，应让**较短的两个数组建表、较长的两个数组做枚举**，这样哈希表的键数（较短一侧）更小。本题四者等长，无收益。
- **同一和的重复计数无法省掉**：因为答案要的是下标组合数，重复出现的值必须各自计数，不能去重。这也正是不用 `set` 而用 `dict` 的原因。

### 常数级优化（可选）

- 把 `n1 + n2` 提到变量里缓存（原始代码在 `if`、`+=`、`=` 三处各算了一遍 `n1 + n2`），省两次加法。
- 建表一侧可写成 `hashmap[s] = hashmap.get(s, 0) + 1`，或用 `collections.Counter` 配合生成器表达式；查表一侧用 `count += hashmap.get(key, 0)` 省掉一次 `in` + 一次下标访问。
- 两个循环变量的遍历顺序无关紧要，`for n1 in nums1: for n2 in nums2` 与外层内层互换等价。

## 六、易错点与总结

### 易错点

- **用 `set` 存 `AB` 的和**：只能判断「有没有」，无法回答「有几个」，答案会退化成「存在配对的 CD 个数」，严重偏小。
- **`count += 1` 而非 `count += hashmap[key]`**：同一对 `CD` 和值可能对应多组 `(i, j)`，漏乘频次。
- **符号写反**：查表应该用 `-(n3 + n4)`；写成 `n3 + n4` 或 `n3 - n4` 都只能过极小部分用例。
- **边建表边查询**：两侧交错会导致 `CD` 中先出现的组合查不到尚未插入的 `AB` 和。
- **误以为要去重**：题目统计的是下标元组个数，`nums` 中的重复值是合法且必须分别计数的。
- **题目要求返回方案数，不是具体方案**：不要在找到第一组时就 return。
- 截图代码缺少 `from typing import List`，脱离 LeetCode 环境会报 `NameError`。

### 题型套路沉淀

- **「多数组 + 求组合数 + 和为零/定值」→ 分组哈希**：把 4 个数分成 2+2，一侧存和频次、另一侧查补数。这是 `1. 两数之和` 的计数版推广，套路固定为「**建表一侧存频次 → 枚举另一侧累加频次**」。
- **分组的均衡性决定复杂度**：k 个数的最优分组是尽量均分，总复杂度约为 O(n^(k/2))。四个数 → O(n²)，三个数 → O(n^1.5)，一个数 → O(n)。
- **计数型 vs 存在型哈希**：题目问「有多少种方案」用 `dict` 存频次；只问「是否存在」才用 `set`。看到「求方案数」四个字就该想到哈希表里要装计数器。
- **两数组独立 vs 同一数组**：本题四个数分属四个数组，所以下标天然不冲突、无需考虑「同一元素不能用两次」；若退化成同一数组内取四个数（如 `18. 四数之和`），就必须额外处理去重与下标互异，那是另一套做法。
