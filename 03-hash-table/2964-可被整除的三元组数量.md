# 2964. 可被整除的三元组数量

> **难度**：中等
> **标签**：数组 · 哈希表
> **原题链接**：https://leetcode.cn/problems/number-of-divisible-triplet-sums/

---

## 一、题目描述

给定一个下标从 0 开始的整数数组 `nums` 和一个整数 `d`，返回满足 `i < j < k` 且 `(nums[i] + nums[j] + nums[k]) % d == 0` 的三元组 `(i, j, k)` 的数量。

三元组按**下标**计（不是按数值去重），下标互不相同且严格递增。

### 示例

```text
输入：nums = [3,3,4,7,8], d = 5
输出：3
解释：能被 5 整除的三元组是 (0,1,2)、(0,2,4)、(1,2,4)。

输入：nums = [3,3,3,3], d = 3
输出：4
解释：任意三元组的和都是 9，可被 3 整除，答案即三元组总数 C(4,3) = 4。

输入：nums = [3,3,3,3], d = 6
输出：0
解释：任意三元组的和都是 9，不能被 6 整除。
```

### 约束条件

- `1 <= nums.length <= 1000`
- `1 <= nums[i] <= 10^9`
- `1 <= d <= 10^9`

---

## 二、解题思路

### 核心思想

**整除只看余数，不看数值。** 三个数之和能被 `d` 整除，等价于三者对 `d` 的余数之和能被 `d` 整除。于是问题从「枚举三个数」变成「固定其中两个、用余数表查第三个」——固定中间下标 `j`，左侧余数频次表 + 枚举右侧 `k`，把三重循环压成二重。

### 思路演进

1. **暴力解法**：三层循环枚举 `i < j < k`，逐一判断 `(nums[i] + nums[j] + nums[k]) % d == 0`。组合数 `C(n,3)`，n = 1000 时约 `1.66 × 10^8` 次判定 —— 每次都要求值、取模，Python 下几千倍地超时。

2. **观察到**：取模运算对加法可分配，
   `(a + b + c) % d == 0` ⇔ `(a%d + b%d + c%d) % d == 0`。
   也就是说，`nums[i]` 具体是 `3` 还是 `1000000003` 完全无关，只由 `nums[i] % d` 决定。而 `d` 的取值虽然可到 `10^9`，但数组里**实际出现的余数最多只有 `min(n, d)` 种** —— 频次表是稀疏但小规模的。

3. **再观察到**：三元组带**下标顺序**约束，所以不能把「有没有配对」当成无序的集合查询。按中间下标 `j` 切分是最自然的分解方式：
   - 锁定 `j` 后，`i` 必须全部来自 `j` 左侧、`k` 必须全部来自 `j` 右侧，两段互不重叠，**顺序约束自动满足**；
   - 剩下的判据只有一句：`nums[i] % d == (d - (nums[j] + nums[k]) % d) % d`，即「在左侧找一个指定余数」。

4. **优化为**：既然只需要「左侧某个余数出现了几次」，就让一个**前缀余数频次表**随 `j` 右移同步扩张。对每个 `(j, k)` 做一次哈希查询，`O(1)` 拿到配对数。总时间 `O(n²)`。

   当前代码的写法是把每个位置的前缀频次表都存下来（`pre[i]` = `nums[0..i]` 的余数分布），查询时直接取 `pre[j-1]`。写法直观、查表零成本，代价是空间变成 `O(n²)`（见第五节）。

### 关键点

- **中间的才是"支点"**：固定左端点会让右侧要枚举两个下标（仍是 `O(n³)`）；固定中间下标，左右各一个，才能一次哈希查询吃掉一层循环。
- **补齐余数的公式** `need = (d - s % d) % d`：外层那个 `% d` 不能省。当 `s % d == 0` 时，`d - 0 == d` 越界成一个不存在的余数，再取一次模才会落回 `0`。
- **频次表只包含 `j` 左侧的元素**：`pre[j-1]` 而不是 `pre[j]`，否则 `i == j` 会被算进去，同一个下标被用两次。
- **下标按值计**：`[3,3,3,3]` 这种重复值不合并，`C(4,3)` 四个三元组各算一次 —— 频次表天然处理了这点（存的是计数而不是布尔）。

## 三、代码实现

### 最终代码

```python
from typing import List
from collections import Counter


class Solution:
    def divisibleTripletCount(self, nums: List[int], d: int) -> int:
        n = len(nums)
        ans = 0

        # pre[i][r] = nums[0..i] 中余数为 r 的元素个数
        pre = [Counter() for _ in range(n)]
        pre[0][nums[0] % d] += 1
        for i in range(1, n):
            cnt = pre[i - 1].copy()
            cnt[nums[i] % d] += 1
            pre[i] = cnt

        # 锁定中间下标 i 与右端点 j，问左侧有几个余数能凑整除
        for i in range(1, n):
            for j in range(i + 1, n):
                need = (d - (nums[i] + nums[j]) % d) % d
                ans += pre[i - 1][need]
        return ans
```

> 截图里的代码没有写 `from typing import List` 与 `from collections import Counter`，已补上。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n²) | O(n · min(n, d))，最坏 O(n²) |
| 朴素解法（三层枚举） | O(n³) | O(1) |
| 理论下界 | O(n²) | O(min(n, d)) |

> 复杂度中的 n 指数组 `nums` 的长度；`d` 是除数，余数种类不超过 `min(n, d)`。

- **时间**：外层 `i` 与内层 `j` 合计约 `n²/2` 次循环，每次是一次取模加一次哈希查询，均为 `O(1)`；建前缀表是 `O(n · min(n, d))`，被 `O(n²)` 吸收。
- **空间**：`pre` 有 n 个 `Counter`，第 `i` 个最多存 `min(i+1, d)` 个不同余数，合计 `O(n · min(n, d))`。当元素余数互不相同时就是 `O(n²)`。

## 五、优化评估

**结论**：时间复杂度已是该框架下的最优 `O(n²)`，**但空间有明显冗余 —— 可以从 `O(n²)` 压到 `O(min(n, d))`**。

### 瓶颈分析

时间上，必须对每个 `(j, k)` 对做一次判定：不同 `(j, k)` 对应的补齐余数 `need` 各不相同，无法合并同类项，`O(n²)` 次查询无法再摊薄。这一层没有优化空间。

空间上，`pre` 把**每个位置**的前缀分布都留了一份。但注意内层循环的推进顺序：`i` 从 `1` 递增时，`pre[i-1]` 只会在 `i` 变大时被丢弃，返回 `i` 时不再需要更小的 `i`。也就是说这些快照里**只有当前这一份是活的**，其余全是历史遗留。

### 可优化空间

把「预先算好 n 份快照」改成「随 `i` 增量维护一份活表」：进入新的 `i` 之前，先把 `nums[i-1]` 的余数并入表中（这样表里恰好是 `nums[0..i-1]`），再枚举 `j > i`。空间从 `O(n · min(n,d))` 降到 `O(min(n, d))`，时间不变。

### 优化代码

```python
from typing import List


class Solution:
    def divisibleTripletCount(self, nums: List[int], d: int) -> int:
        n = len(nums)
        ans = 0
        left = {}                       # 余数 -> 左段中出现次数（只会存实际出现过的余数）

        for i in range(1, n):
            r = nums[i - 1] % d
            left[r] = left.get(r, 0) + 1    # 并入 nums[i-1]，left 覆盖 nums[0..i-1]
            for j in range(i + 1, n):
                need = (d - (nums[i] + nums[j]) % d) % d
                ans += left.get(need, 0)
        return ans
```

**优化理由**：只留一份**活表**，随 `i` 前进增量维护，把「历史快照」这种把空间放大 n 倍的存储去掉 —— `left` 的条目数不超过实际出现过的余数种数，即 `O(min(n, d))`，而不是 `O(n · min(n, d))`。时间仍是同一组 `O(n²)` 循环。

> 这里用 `dict` 而不是 `[0] * d`：`d` 可到 `10^9`，按 `d` 开数组不现实；而余数只有 `min(n, d)` 种，稀疏映射才是对的。若坚持用列表，长度必须取 `min(n, d)`，并且读之前要判断 `need < len(left)`，否则 `d > n` 时 `left[need]` 会直接越界 —— 正是这个坑让 `dict` 成为更省心的选择。

### 常数级优化（可选）

- `need` 的计算可以写成 `(-(nums[i] + nums[j])) % d`，Python 的取模对负数已返回非负结果，少一次加法和一次取模。
- 内层循环里 `nums[i] % d` 与 `nums` 的下标访问在循环外提一次，避免 `n²` 次重复取值。
- 若 `n < 3`，直接返回 `0`，省去建表。

## 六、易错点与总结

### 易错点

- **`pre[j]` 写成 `pre[j-1]` 之外的位置**：查询左段必须用严格左于 `j` 的快照。用 `pre[j]` 会让 `i == j` 参与配对，`[3,3,3,3], d=3` 这类用例会明显偏大。
- **补齐余数少一层取模**：`d - s % d` 在 `s % d == 0` 时得到 `d`，而 `d` 不是合法余数（合法范围 `0..d-1`），会漏掉所有「前两个数已凑齐整除」的情况。必须写 `(d - s % d) % d`。
- **左侧频次表用 `defaultdict` 会静默插入**：`defaultdict` 的 `d[k]` 对不存在的键会**先建一个 0 计数条目再返回**，`n²` 次查询会把表撑到 `O(n²)` 条；而 `Counter` 的 `[]` 只读不插，读到不存在的键返回 `0`。这类「查询不能有副作用」的场合必须用 `Counter` 或 `dict.get(k, 0)`。
- **`d` 很大时不能按 `d` 开数组**：`d <= 10^9`，但实际余数种类不超过 `min(n, d)`，开数组只能开 `min(n, d)` 并对越界情况兜底。
- **跨语言溢出**：`nums[i] <= 10^9`，三个数相加可达 `3 × 10^9`，超出 32 位有符号整数上限。Python 无此问题，但改成 C++/Java 时要先把每个数取模再相加（`(a%d + b%d + c%d)` 最大 `3d`，仍可能溢出 `int`；用 `long long` 或边加边取模）。
- **`i`、`j` 的起始值**：`i` 从 `1` 开始（要有左邻）、`j` 从 `i+1` 开始（要有右邻），这是 `n < 3` 时自动返回 0 的来源。

### 题型套路沉淀

- **「余数化」是整除类问题的第一动作**：见到 `(a + b + c) % d == 0` 这类条件，立刻转成「余数互补」，把按值枚举换成按余数计数。同型思路：`1010. 总持续时间可被 60 整除的歌曲`（配对类和，两数版）、`2453. 摧毁一系列目标`。
- **三元组计数固定中间下标**：`i < j < k` 的三元组，固定 `j` 就把「左侧选一个 + 右侧选一个」拆成两个独立部分，可以各用一张频次表维护。这是把 `O(n³)` 降到 `O(n²)` 的通用切口；固定左端点做不到这件事。
- **前缀频次表 vs 滚动单表**：需要「任意左段的历史分布」时才存多份快照；只需要「当前左段」时用一个活表边扫边更（本题就属于后者），空间能省一个维度。
- **计数的查询必须无副作用**：`Counter` / `dict.get` 是读，`defaultdict` / `setdefault` 是写。混用会让「只读查询」悄悄扩张内存。
