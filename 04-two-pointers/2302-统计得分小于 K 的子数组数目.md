# 2302. 统计得分小于 K 的子数组数目

> **难度**：困难
> **标签**：数组 · 二分查找 · 前缀和 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/count-subarrays-with-score-less-than-k/

---

## 一、题目描述

一个数组的**分数**定义为它的**元素之和乘以它的长度**。给定一个**正整数**数组 `nums` 和一个整数 `k`，统计有多少个非空连续子数组的分数**严格小于** `k`。

### 示例

```text
输入：nums = [2,1,4,3,5], k = 10
输出：6
解释：分数小于 10 的 6 个子数组为 [2](2)、[1](1)、[4](4)、[3](3)、[5](5)、[2,1](6)。
      注意 [1,4] 的分数恰好是 (1+4)*2 = 10，不满足「严格小于」，必须排除。
```

```text
输入：nums = [1,1,1], k = 5
输出：5
解释：除 [1,1,1]（分数 (1+1+1)*3 = 9 >= 5）外，其余 5 个子数组的分数都小于 5。
```

### 约束条件

- `1 <= nums.length <= 10^5`
- `1 <= nums[i] <= 10^5`（**全为正整数**，这是本题解法成立的前提）
- `1 <= k <= 10^15`
- 子数组是数组中的一个连续元素序列，非空

## 二、解题思路

### 核心思想

**固定右端 `r`，合法左端恰好构成一段后缀。** 因为 `nums` 全为正，当右端固定时，把左端 `l` 往右推会让「和」变小、同时让「长度」变小，分数**单调不增**；所以存在唯一的阈值 `L(r)`，使得 `[l, r]` 合法当且仅当 `l >= L(r)`。于是每轮只需把左指针往右推到刚好合法，再累加「以 `r` 结尾的合法子数组数 = `r - left + 1`」。

### 思路演进

1. **暴力解法**：枚举所有 `(i, j)`，对每个子数组累加求和再乘长度，判断是否 `< k`。时间 O(n²)，空间 O(1)。n = 10^5 时是约 5 × 10^9 次内层操作，必然超时。
2. **瓶颈定位**：双重枚举里存在重复求和，但这只是表层；真正的问题是**两个下标都在自由变化**，把「一个一维的约束，做成了二维的搜索」。而本题的约束对固定右端来说，只把左端限制在一个区间里 —— 有大量左端是"注定合法/注定不合法"的，枚举它们纯属浪费。
3. **关键转化（单调性）**：记 `score(l, r) = (a[l] + ... + a[r]) * (r - l + 1)`。由于每个 `a[i] >= 1`：
   - **对 `l` 单调**：`l` 增 1，和至少减 1、长度恰好减 1，两个因子同时不减 ⇒ `score(l+1, r) < score(l, r)`。所以合法左端是后缀 `[L(r), r]`。
   - **对 `r` 也单调**：若 `[l, r+1]` 合法，则 `score(l, r) < score(l, r+1) < k` ⇒ `[l, r]` 也合法。所以 `L(r)` **随 `r` 单调不降**。

   两条合起来 ⇒ **左指针只会前进、永不后退** ⇒ 双指针一趟扫完，总时间 O(n)。原来"两层都自由"的搜索空间，被压成了"两个单调指针"。
4. **最优解**：右端 `for` 推进、内层 `while` 把左端收缩到刚好合法，再 `ans += right - left + 1`。所谓"刚好合法"= 收缩到**第一个**满足 `score < k` 的左端，也就是 `L(r)`。

### 关键点

- **判据**：`[left, right]` 合法 ⟺ `temp * (right - left + 1) < k`，其中 `temp` 是窗口内元素和。等价说法：合法左端集合 = 后缀 `[L(r), right]`。
- **收缩必须用 `while` 而不是 `if`**：一次只新增一个元素，但它可能把窗口的分数顶出合法区间很远（加法累积 + 再乘长度，违规量**无上界**），单轮需要连缩多格。`if` 版每轮最多缩一格 —— 见「六、易错点」里的最小反例。
- **答案口径是"每轮累加"**：`ans += right - left + 1` 累加的是「以当前 `right` 结尾的合法子数组个数」。每个子数组按其右端点被唯一计数一次。这是**计数型**口径，和"最长窗口取 max""最短窗口取 min"不是一回事，不能混用。
- **空窗口是安全的**：当 `nums[right] >= k` 时，任何包含它的窗口分数都 `>= k`，`while` 会把窗口抽空（`left = right + 1`，`temp = 0`）；此时判据变成 `0 * 0 = 0 < k`，循环自然停下，且**不会**再访问 `nums[left]`（越界）。这一步依赖题面的 `k >= 1`；若 `k <= 0`，原版会退化成死循环 + 越界。
- **单调性前提 = 元素非负**：题面保证 `nums[i] >= 1`。如果允许负数，左移左端不再使和单调增，上面两条单调性全部失效，滑窗直接不成立（得改走前缀和 + 单调队列/二分一类结构）。

### 正确性论证

- **不变量**：每轮进入 `for` 体之前，`[left, right-1]` 是「以 `right-1` 结尾的最紧合法窗口」，即 `left = L(right-1)`。
- **归纳步**：加入 `a[right]` 后，由 `L` 的单调性有 `L(right) >= L(right-1) = left`，所以左指针不必回退；`while` 每轮把 `left` 加 1，退出时停在**第一个**满足分数 `< k` 的左端，正好是 `L(right)`（合法集是后缀，中间不会跳过合法值）。
- **终态**：`ans = Σ_r (r - L(r) + 1)`，每一项恰是「以 `r` 结尾的合法子数组数」；每个非空子数组都由其右端点唯一确定，故被计数且仅被计数一次 ⇒ `ans` 即答案。
- **边界约定**：若以 `r` 结尾不存在任何合法窗口，`while` 会把窗口抽空（`left = r + 1`），累加项为 0，与令 `L(r) = r + 1` 的约定一致。

## 三、代码实现

### 最终代码

```python
from typing import List


class Solution:
    def countSubarrays(self, nums: List[int], k: int) -> int:
        ans = left = 0          # ans：答案；left：当前窗口左端（= 以 right 结尾的最紧合法左端）
        temp = 0                # 窗口 [left, right] 内元素之和
        for right, j in enumerate(nums):
            temp += j           # 右端扩张一格
            while temp * (right - left + 1) >= k:   # 分数 >= k：收缩到刚好合法
                temp -= nums[left]
                left += 1
            ans += right - left + 1                 # 以 right 结尾的合法子数组数
        return ans
```

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) | O(1) |
| 朴素解法（枚举所有子数组） | O(n²) | O(1) |
| 理论下界 | O(n) | O(1) |

> 复杂度中的 n 指数组 `nums` 的长度。
>
> - **为什么内层 `while` 不把总时间拖到 O(n²)**：`left` 全程单调不减、总共只前进 n 次，因此内层循环的**总**迭代次数 ≤ n，摊还到每轮是 O(1)。单轮最坏可连缩 n 格，但那一定发生在最后一轮左右，均摊后不影响总量级 —— 这是"左指针只走一趟 ⇒ 内层用 `while` 逐格收缩而不是用 O(log n) 查找"更优的典型场景（拿二分去替代它是**负优化**）。
> - **空间为什么是 O(1)**：只用滚动和 `temp` + 三个计数器，没有开前缀和数组。前缀和虽然也能做（O(n log n)），但空间和时间都不如双指针。

## 五、优化评估

**结论**：**大 O 层面已是理论下界，无法再优化；但常数项有实测收益（n = 10^5 各场景约 1.3×~1.6×）。**

### 瓶颈分析

时间几乎全部落在 `for` 循环体的**每轮固定开销**上：一次乘法 + 一次比较，外加 `right - left + 1` 这个长度表达式的**重复求值**。内层 `while` 反而不是瓶颈 —— 左指针全程只前进 n 次，收缩本身的总代价是 O(n) 且常数极小。

n = 10^5 实测（各取 7 次最优）：用户原版四个场景耗时 12.9 / 14.6 / 19.1 / 22.7 ms；其中"随机数据、窗口较宽"的场景最贵（每轮都要算乘法）。

### 可优化空间

- **大 O 上不可能更好**：任何正确解都必须把每个元素至少看一遍（否则可以构造出"漏掉的元素改变答案"的输入），所以 Ω(n) 是硬下界；答案是计数、不是可抽样/可剪枝的目标，也无法用二分或跳表跳过元素。
- **空间上不可能更好**：O(1) 已是下界（输出只是个数）。
- **常数项有两处可压**：① 每轮重算 `right - left + 1`，改成用 `win` 变量增量维护；② `enumerate` 的元组拆包换成直接迭代值。

### 优化代码

```python
from typing import List


class Solution:
    def countSubarrays(self, nums: List[int], k: int) -> int:
        ans = left = temp = win = 0
        for j in nums:                 # 直接迭代值，省掉 enumerate 的拆包
            temp += j
            win += 1                   # 长度增量维护，不再算 right - left + 1
            while temp * win >= k:
                temp -= nums[left]
                left += 1
                win -= 1               # 收缩时长度必须同步减 1
            ans += win
        return ans
```

**优化理由**：把每轮一次"减法 + 加法"求长度换成两个整数的自增/自减，并去掉一次元组拆包。实测（n = 10^5，单位 ms，各取 7 次最优，轮转测量）：

| 场景（n = 10^5） | 用户原版 | 只换 `win` 变量 | `win` + 直接迭代 | 除法版 | 短路版 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| A 全 1，k = 10^15（全合法） | 12.93 | 9.85 | **7.93** | 23.30 | 14.44 |
| B 全 1，k = 1（全不合法） | 14.55 | 12.77 | **10.53** | 16.82 | 5.34 |
| C 随机 1~1000，k = 10^6 | 19.11 | 17.41 | **14.53** | 28.26 | 19.97 |
| D 随机 1~10^5，k = 10^12 | 22.67 | 18.26 | **16.52** | 38.29 | 24.06 |

提速主要来自 `win` 变量（1.1×~1.3×），去掉 `enumerate` 再贡献一小部分，两者合计 1.3×~1.6×。**代价**是多维护一个必须与 `left` 同步更新的变量，漏写 `win -= 1` 就会死循环/越界 —— 追求可读性时，原版的 `right - left + 1` 更不容易写错。

### 常数级优化（可选）

以下三种改法都实测过，**结论是不要用**：

- ~~把乘法比较改成除法比较~~（`temp * L >= k` ⟺ `temp >= ceil(k / L)`）：不仅更慢（表中最右两列，耗时是原版的 **1.2×~1.8×**，因为 Python 的整除比乘法贵），而且**会崩** —— 窗口被抽空后 `L = 0`，`-(-k // 0)` 直接 `ZeroDivisionError`。乘法版靠 `0 * 0 = 0 < k` 天然停机，这条"空窗口自动安全"的性质被改写丢了，必须额外补 `L > 0` 守卫。
- ~~把 `while` 换成 `if`~~（每轮最多缩一格）：**错误**，见「六、易错点」最小反例。
- ~~短路 `if j >= k: 直接清空窗口`~~：只在"大量元素 ≥ k"的场景占优（场景 B 5.34 ms vs 14.55 ms，约 2.7×），其余场景反而略慢（A 14.44 ms vs 12.93 ms、D 24.06 ms vs 22.67 ms）；收益场景太窄、又平白多一个分支，作为通用写法不推荐。

## 六、易错点与总结

### 易错点

- **`while` 写成 `if` ⇒ 漏判（本题最典型的错法）**。一次新增元素可能让分数超出 `k` 很远，需要连缩多格；`if` 每轮只缩一格，会留下分数 `>= k` 的非法窗口继续参与计数。**最小反例：`nums = [4, 85], k = 7`** —— 真值 1（只有 `[4]` 分数 4 合法）；`if` 版得 2，因为它把分数高达 85 的窗口 `[85]` 也计了进去。另一例 `nums = [1,1,100], k = 50`：真值 3，`if` 版得 5。同一套 40 组随机小用例下，`if` 版偏差 4/40。
- **严格小于的方向**：收缩条件是**分数 `>= k`**。写成 `> k` 会把分数恰好等于 `k` 的子数组计进去 —— 示例 1 里的 `[1,4]` 分数正好是 10，就是专门用来卡这个的。
- **答案口径写错**：必须每轮 `ans += right - left + 1`。漏掉 `+1` 会丢掉所有单元素窗口；只在循环结束后取一次"窗口长度"，则把"计数题"当成"最长窗口题"做，答案会小若干个数量级。
- **把双指针当成万能**：本题成立的前提是 `nums` 全为正。一旦有负数，`score` 对 `l` 不再单调，合法左端可能变成"中间一段"甚至"多段"，`left` 单调不减的性质崩掉，必须换结构。
- **非 Python 语言的溢出**：单个元素最大 10^5、长度最大 10^5，分数可达 `(10^5 × 10^5) × 10^5 = 10^15`，超出 32 位整数范围（C++ 用 `int` 会溢出，要 `long long`；Java 要 `long`）。Python 无整数溢出，这点可以放心。
- **负索引陷阱**：`nums[left]` 只在窗口非空时被访问。空窗口时判据 `0 * 0 = 0 < k` 先一步成立、循环退出，不会出现 `left = right + 1` 时仍读 `nums[left]` 的情况 —— 但这是靠 `k >= 1` 撑着的，别的题里不能想当然。

### 题型套路沉淀

- **判据族：'窗口内度量 ≤ 上限'的预算/代价型滑窗。** 本题的度量 = 「和 × 长度」，仍属"逐元素累加 × 长度因子"，且元素非负 ⇒ 固定右端时度量随左端右移单调不增 ⇒ 双指针成立。**识别信号**：题面出现"分数/开销(cost)/预算(budget)/最多翻转 k 个/乘积小于 k"这类"窗口内数值比较"的措辞。
- **与"按键数"族（窗口内不同种类数 ≤ K）的分野**：那族收缩要靠**删键**，被淘汰的必然是"最后出现位置最小"的那一类；本题度量是**纯数值、没有键的概念**，收缩完全由数值比较驱动。判据串用是这类题最常见的错误来源。
- **收缩方式怎么选 —— 先问"违规量是否有上界"**：每轮只新增一个元素时，如果违规量有上界（例如计数最多超 1），`while` 可以退化成"一次跳转/一个 `if`"；如果违规量无上界（本题：加法累积后再乘长度，一次能顶飞很远），就**必须**`while` 逐格收缩。
- **答案口径要跟着题型走**：计数型 ⇒ 每轮累加窗口长度；最长型 ⇒ 每轮或终值取 `max`；最短型 ⇒ 每轮取 `min`。三种口径互不通用，换口径就等于换算法，必须重新验证。
- **滑窗模板（计数型 / 预算型）**：

  ```python
  ans = left = 0
  metric = 0
  for right, x in enumerate(nums):
      metric += x                 # 1. 右端扩张，更新度量
      while metric 违反上限:        # 2. 收缩到刚好合法
          metric -= nums[left]
          left += 1
      ans += right - left + 1     # 3. 以 right 结尾的合法窗口计数
  ```

  三行分别对应"扩张 / 收缩 / 结算"，任何一步写成别的形式（`if` 收缩、`max` 结算）都要重新论证一遍。
