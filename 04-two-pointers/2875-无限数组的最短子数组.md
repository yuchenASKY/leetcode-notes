# 2875. 无限数组的最短子数组

> **难度**：中等
> **标签**：数组 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/minimum-size-subarray-in-infinite-array/

---

## 一、题目描述

`infinite_nums` 是把 `nums` 无限重复拼接得到的数组。求 `infinite_nums` 中**元素和恰好等于 `target`** 的最短子数组长度，不存在则返回 `-1`。

本题的矛盾在于：数组"有效长度"与 `target` 同阶（`nums = [1]`、`target = 10^9` 时要看 10^9 个元素），**不能真的展开**，必须先把重复结构压掉。

### 示例

```text
输入：nums = [1,2,3], target = 5
输出：2
解释：infinite_nums = [1,2,3,1,2,3,...]，取 [2,3]（下标 1~2），和 = 5，长度 2 最短。

输入：nums = [1,1,1,2,3], target = 4
输出：2
解释：最短解跨过了份边界 —— 上一份末尾的 3 接下一份开头的 1，长度 2。

输入：nums = [2,4,6,8], target = 3
输出：-1
解释：全偶数，任意子数组和都是偶数，凑不出 3。
```

### 约束条件

- `1 <= nums.length <= 10^5`
- `1 <= nums[i] <= 10^5`（**元素全部为正** —— 后文所有单调性都靠这一条）
- `1 <= target <= 10^9`

## 二、解题思路

### 核心思想

设 `total = sum(nums)`，把 `target` 对 `total` 做一次除法：

```text
target = Count * total + rem      (Count = target // total, 0 <= rem < total)
```

和等于 `target` 的窗口，**去掉其中恰好 `Count` 个完整份之后，剩下的一定是 `nums` 中一段和为 `rem` 的连续片段（允许跨过末尾，即"环形片段"）**。于是

> **答案 = Count × n + 「nums 中一段和为 rem 的最短连续片段」的长度**

无限长的数组被压回 `nums` 自身，问题规模与 `target` 彻底脱钩。

### 思路演进

1. **暴力解法**：按定义展开 `infinite_nums`，用前缀和枚举所有区间取最短。展开长度至少要 `Count × n`，最坏 10^9，时间和空间同时爆炸。
2. **瓶颈定位**：展开出来的绝大多数内容是**一模一样整份 `nums` 的重复**。窗口长到 10^9 量级，只是因为里面含了 `Count` 个整份；而 `Count` 由 `target // total` 唯一确定，是个已知常量，根本不需要枚举。
3. **关键转化**：把窗口"拆成整份 + 零头"。
   - 设某个和等于 `target` 的窗口起点为 `p`，由周期性可把 `p` 平移进 `[0, n-1]`。
   - **起点对齐份边界**（`p = 0`）：窗口 = `q` 个整份 + `nums` 的一段连续子数组，和 = `q·total + x`（`0 ≤ x < total`），要等于 `Count·total + rem`，只能是 `q = Count`、`x = rem`。
   - **起点不对齐**（`p > 0`）：窗口 = `nums[p..n-1]` 后缀 + `q` 个整份 + `nums[0..t-1]` 前缀，和 = `(q+1)·total + (prefix[t] - prefix[p])`，而括号内落在 `(-total, total)` 内，所以 `q+1 = Count` 或 `Count+1`：
     - `q+1 = Count` 时，把最前面那 `n-p` 个元素切掉，`nums[p..t-1]` 本身就是一段和为 `rem` 的**不跨末尾**的连续子数组，长度更短 —— 被第一种情况完全覆盖；
     - `q+1 = Count+1` 时，"后缀 + 前缀"拼起来恰好是一段和为 `rem` 的**环形片段**，且长度 `n-p+t < n`。
   - ⇒ 所有候选窗口 = `Count` 个整份 + 一段和为 `rem` 的连续片段（含环形版本），**片段长度恒 `< n`**。
4. **最优解**：在"虚拟的 `nums + nums`"上滑滑动窗口，找**和等于 `rem` 的最短片段**。
   - 元素全为正 ⇒ 固定右端时左端右移会让窗口和**单调不增** ⇒ 双指针成立。
   - 代码没有真的拼出 `nums + nums`（那要 O(n) 额外空间），而是用 `for i in range(2)` **让 `left`、`temp` 两趟连扫不重置**：第一趟右端在 `nums` 内部；第二趟右端继续前进，窗口自然变成"后缀 + 前缀"，正好是环形片段。
   - 比较只用一个变量：`temp` 维护的是 `Count·total + 窗口内元素和`，于是 `temp == target` 恰好等价于"窗口内元素和 == rem"，省掉一个变量和一次减法。

### 关键点

- **窗口的目标不是 `target` 而是 `rem`**：整份部分的贡献 `Count·total` 是恒定偏移，不参与滑动。
- **两趟扫描缺一不可**：示例 2 的答案就来自第二趟（跨份边界那段）。
- **`left` 单调不回退**：两趟合计最多推进 `2n` 格，这是 O(n) 的来源。
- `rem == 0` 时最短窗口就是"恰好 `Count` 个整份"，片段为空（段长 0），答案 `Count·n`。
- 复杂度与 `target` **无关**：`target` 只参与一次除法。

### 正确性论证

设 `total = sum(nums)`，`Count = target // total`，`rem = target - Count·total`。

**不变量（窗口语义）**：代码里 `temp` 恒等于 `Count·total + (left..right 片段的元素和)`。`left`/`right` 是片段在虚拟倍增数组 `nums + nums` 上的坐标：第一趟 `right ∈ [0, n-1]`；第二趟循环变量仍是 `0..n-1`，实际终点是 `n + right`，所以长度写作 `right + i·len(nums) - left + 1`。

**① 每个被记录的长度都是合法答案**：`temp == target` ⟺ 片段和 `== rem`；此时"`Count` 个整份 + 该片段"就是 `infinite_nums` 中一段和等于 `target` 的连续子数组，长度 `Count·n + 片段长`，故返回的 `ans + len(nums) * Count` 必为合法答案。

**② 没有漏掉更短的答案**：任取一个和等于 `target` 的窗口，把起点平移进 `[0, n-1]` 后按上面的分类讨论：
- 对齐情形（`p = 0`）：`q = Count`、`prefix(r) = rem`，该片段是 `nums` 的不跨末尾连续段，第一趟滑窗必然扫到它（元素全正 ⇒ 对每个右端，和为 `rem` 的窗口唯一，滑窗收缩到第一个 `≤ target` 的状态时正好取到），记录的长度与原窗口相同。
- 非对齐情形（`p ≥ 1`）：
  - `q+1 = Count`：由 `prefix(t) - prefix(p) = rem ≥ 0` 且 `prefix` 严格递增得 `t > p`，原窗口长度 `= Count·n + (t - p)`，而 `nums[p..t-1]` 是一段和为 `rem` 的非环形片段，第一趟扫到的长度同为 `Count·n + (t-p)`，**不劣于原窗口**。
  - `q+1 = Count+1`：由 `prefix(p) - prefix(t) = total - rem > 0` 得 `p > t`，原窗口长度 `= Count·n + (n-p+t)`；而"后缀 `nums[p..n-1]` + 前缀 `nums[0..t-1]`"这段环形片段的和 `= (total - prefix(p)) + prefix(t) = rem`，长度 `n-p+t < n`，第二趟扫到的就是它，长度完全相同。
  ⇒ 任何合法窗口，都有一段被代码扫到的片段不长于它，取 `min` 后即为全局最优。

**③ 终止与 `-1`**：被记录的片段长恒 `< n`（第一趟里 `≤ n-1`，因为长度恰好 `n` 意味着片段是整份、和为 `total ≠ rem`；第二趟里 `n-p+t < n`）。而哨兵 `len(nums) * (Count + 1) ≥ n`，所以 `ans < 哨兵` **当且仅当确实找到过解**，未找到时 `ans = inf` 返回 `-1` 正确。

## 三、代码实现

### 最终代码

```python
from math import inf          # 截图里没有，已补：原代码直接用到了 inf
from typing import List       # 截图里没有，已补


class Solution:
    def minSizeSubarray(self, nums: List[int], target: int) -> int:
        Numsum = sum(nums)
        Count = target // Numsum
        left = 0
        temp = Count * Numsum
        ans = inf

        for i in range(2):
            for right, j in enumerate(nums):
                temp += j
                while temp > target:
                    if left > len(nums) - 1:
                        break
                    temp -= nums[left]
                    left += 1
                if temp == target:
                    ans = min(ans, right + i * len(nums) - left + 1)
        n = len(nums) * (Count + 1)
        return ans + len(nums) * Count if ans < n else -1
```

> 这段代码来自提交通过的截图（题目页显示"通过"），除补上 `inf`、`List` 两个 import 外逐字保留（含 `Numsum`、`Count` 这类命名）。

逐行要点：

| 行 | 作用 |
| :--- | :--- |
| `temp = Count * Numsum` | 窗口先"预装" `Count` 个整份，之后每向右扩一格就 `+=`，于是窗口和 = `Count·total + 片段和` |
| `for i in range(2)` | 两趟扫描 = 在虚拟的 `nums + nums` 上滑窗；`left`/`temp` **不重置**，第二趟自然产生环形片段 |
| `if left > len(nums) - 1: break` | 左端最多推到 `n`（此时窗口已在第二份开头），防止 `nums[n]` 越界 |
| `right + i * len(nums) - left + 1` | 片段在倍增数组中的长度：第一趟 `i = 0`，第二趟右端实际在 `n + right` |
| `ans + len(nums) * Count if ans < n else -1` | 片段长加回 `Count` 个整份；`ans` 仍是 `inf` 就说明无解 |

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) | O(1) |
| 朴素解法（真展开 `infinite_nums` + 枚举所有区间） | O((Count·n)²) | O(Count·n) |
| 理论下界 | Ω(n) | O(1) |

> 复杂度中的 n 指 `nums` 的长度（`Count = target // total` 可能到 10^9 / 1 = 10^9，**不参与复杂度**）。

- 时间 O(n)：两趟扫描共推进 `2n` 次右端；`left` 单调不回退，两趟合计最多收缩 `2n` 次（均摊 O(1)/步），与 `target` 无关。
- 空间 O(1)：只有常数个标量（`left`、`temp`、`ans`），没有真的构造倍增数组。
- 下界 Ω(n)：`Count` 与 `rem` 依赖 `total`，必须完整读一遍数组才能确定；且第一趟扫描本身就要看每个元素。

## 五、优化评估

**结论**：**渐近已最优**（时间 O(n) 达到下界、空间 O(1)），仅剩常数级优化空间。

### 瓶颈分析

- 时间几乎全部花在 2n 次"扩一格 + 收缩"上，这部分不可去（就是答案的搜索空间）。
- 可去的是**重复求值**：`len(nums)` 出现在内层 `while` 的每一轮（收缩多少次就调多少次 `len()`），一个局部变量即可消掉。
- 另有一处**结构性浪费**：`rem == 0` 时答案必然是 `Count·n`（片段为空），原代码仍要白扫 2n 格。实测这一场景占 32 ms，占满全部可去时间（见下表 A 行，88 倍）。
- 哨兵 `len(nums) * (Count + 1)` 依赖"被记录的片段长 `< n`"这一推得较绕的结论，可换成更直白的 `n`（同样成立，见上方正确性论证 ③）。

### 可优化空间

三个点：① `rem == 0` 直接 `return Count * n` 早退；② `len(nums)` 提升为局部变量 `n`；③ 比较量从 `temp`（`Count·total + 片段和`）改回 `seg`（片段和）与 `rem` 比较 —— 省掉每次 `+=` 时无意义的偏移量（数值大小不影响 `int` 运算量，但少一个"必须和 `Count` 保持同步"的心智负担）。哨兵随之简化为 `n`。

### 优化代码

```python
class Solution:
    def minSizeSubarray(self, nums: List[int], target: int) -> int:
        n = len(nums)
        total = sum(nums)
        Count = target // total
        rem = target - Count * total
        if rem == 0:                       # 最短窗口就是恰好 Count 个整份，无需扫描
            return Count * n
        best = n                           # 和为 rem 的片段长恒 < n，用 n 作哨兵
        seg = 0
        left = 0
        for i in range(2):                 # 两趟 = 在 nums + nums 上滑窗（O(1) 空间）
            for right, j in enumerate(nums):
                seg += j
                while seg > rem:
                    if left == n:          # 左端最多推到 n，防止 nums[n] 越界
                        break
                    seg -= nums[left]
                    left += 1
                if seg == rem:
                    L = right + i * n - left + 1
                    if L < best:
                        best = L
        return Count * n + best if best < n else -1
```

**优化理由**：算法与判据完全同构（同样的"两趟扫描 + 单调左指针 + 片段和 == rem"），只在三处去掉了可去成本。语义上无损：`seg + Count·total` 即原代码的 `temp`，`seg == rem` ⟺ `temp == target`。

**实测（n = 10^5，各取 9 轮转测量的最小值）**：

| 场景 | 原代码 | 优化版 | 提速 |
| :--- | ---: | ---: | ---: |
| A `nums = [1]*n`，`target = 10^9`（`rem = 0`） | 32.21 ms | **0.36 ms** | 88.6× |
| B 随机 `1..1000`，`target = 999999937`（`rem ≠ 0`、无解，全扫不收缩） | 27.87 ms | **23.58 ms** | 1.18× |
| C `nums = [1]*n`，`target = 9000n + 50000`（有解、需收缩） | 31.67 ms | **25.06 ms** | 1.26× |
| D `1..n` 的随机排列，`target = 999999937`（值域 ≈ n） | 45.47 ms | **40.92 ms** | 1.11× |

四档场景优化版都不劣于原版：A 的 88 倍来自早退（省掉整整 2n 格扫描），B/C/D 的 1.1~1.3 倍来自消掉内层 `len()` 重复调用与 `min()` 调用。注意 A 行是**结构性收益**（不做扫描），不是常数微调 —— 若只做 ②③ 而不做早退，A 行仍然要 30 ms 左右。

### 常数级优化（可选）

- `divmod(target, total)` 比 `//` 再 `-` 少一次大整数乘法（`Count * total` 的乘法结果可达 10^9 量级，但 Python 里都是单机器字，影响很小）。
- 第二趟可以用 `itertools.chain(nums, nums)` 替代 `for i in range(2)`，但 `chain` 的对象开销反而更大，**不建议**。
- 若后续要加"最短段"以外的统计，`while` 里的 `if left == n: break` 需重新审视（改为显式跳过第二份开头的无效窗口），别直接照抄。

## 六、易错点与总结

### 易错点

- **只扫一趟会漏解**。把 `for i in range(2)` 去掉（或把最后的 `return` 挪进循环里，就只执行了第一趟），`nums = [1,1,1,2,3], target = 4` 会返回 3 而不是 2 —— 最短解跨过了份边界，只有第二趟能看到。
- **左指针越界保护不是"优化"而是必需**。第二趟里 `left` 可能被一路推到 `n`，所以 `while` 内部必须**先**判 `left > len(nums) - 1` 再 `temp -= nums[left]`；少了这一句，`nums[n]` 直接 `IndexError`。
- **忘了加回 `len(nums) * Count`**：`ans` 只是"片段长"，答案要加上 `Count` 个整份。
- **`ans` 的初值是 `inf`（浮点）**，判定"是否找到"要像原代码那样用哨兵比较，不能拿它当整数直接参与运算/比较。哨兵取 `len(nums) * (Count + 1)` 是成立的，因为被记录的片段长恒 `< n ≤ 哨兵`。
- **`rem == 0` 的退化**：此时最短窗口就是 `Count` 个整份本身，滑动窗口要靠"收缩到空窗口"才能记录到段长 0（原代码正是这样）；若给 `while` 加了"不许收缩到空"之类的条件，这一情形会被漏掉。
- **别把 `target` 直接当窗口目标和**：窗口里带着 `Count` 个整份的恒定偏移，忘了偏移会让窗口永远偏小、收缩过度。

### 题型套路沉淀

- **虚拟倍增 + 滑窗**：凡是"环形数组上找满足条件的连续段"，先想"在 `nums + nums` 上滑窗"。要省空间就学本题 —— **两趟 `for` + 指针不重置**，等价于倍增但空间仍是 O(1)；直接 `nums + nums` 会多付 O(n) 空间。
- **商余分解压规模**：答案形如"`k` 个整份 + 一个零头"时，用 `divmod` 把整份部分用乘法一次性记入，问题规模立刻与 `k` 无关。识别信号：目标值远大于数组规模、解里有周期性重复的长结构。本题 `target` 到 10^9 而复杂度只跟 `n` 有关，就是这一招的效果。
- **滑窗成立的判据是单调性**：窗口度量随左端右移单调（本题靠"元素全为正"）才能上双指针；一旦允许负权，单调性消失，必须换成前缀和 + 单调队列一类结构。
- **把"窗口里恒定的偏移"留在窗口变量里**（`temp = Count·total + 片段和`）是一个顺手的小技巧：省一个变量、让判断直接写成 `temp == target`。代价是偏移量必须始终与 `Count` 同步，改动时容易出错 —— 优化版改成裸片段和 + `rem`，可读性更好。
