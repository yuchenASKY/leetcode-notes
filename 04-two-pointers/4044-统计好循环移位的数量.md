# 4044. 统计好循环移位的数量

> **难度**：中等
> **标签**：数组 · 前缀和 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/count-good-cyclic-rotations/

---

## 一、题目描述

给定长度为偶数 `n` 的整数数组 `nums`。一次「循环移位」指：取 `nums` 的一个长度在 `0 .. n-1` 之间的**前缀**，整体搬到数组末尾，元素相对顺序不变 —— 也就是把数组看成环，左旋 `k` 位（`k = 0 .. n-1`，共 `n` 种）。

若某种移位后，新的前 `n/2` 个元素之和**严格大于**后 `n/2` 个元素之和，称它是**好循环移位**。求好移位的数量。

### 示例

```text
输入：nums = [1,2,3,4,5,6]
输出：3
解释：六种移位的前半/后半和依次为 (6,15) (9,12) (12,9) (15,6) (12,9) (9,12)，
      其中后四种里有三种前半严格大于后半。
```

```text
输入：nums = [1,2,1,2]
输出：0
解释：四种移位前后半和恒为 (3,3)，从不出现「严格大于」，答案 0。
```

### 约束条件

- `2 <= n == nums.length <= 10^5`，`n` 为偶数
- `1 <= nums[i] <= 10^9`

---

## 二、解题思路

### 核心思想

**把「旋转后」的数组还原成原数组上的一个环形窗口。** 左旋 `k` 位后，第 `0` 位是原来的 `nums[k]`，所以前 `n/2` 个元素恰好是原数组里从 `k` 出发、长度 `n/2` 的一段（下标对 `n` 取模）。于是问题变成：让一个长度固定为 `n/2` 的窗口在环上跑一圈，数一数有多少个起点满足「窗口内和 > 总和 − 窗口内和」。窗口逐位滑动，一进一出，每次判定 O(1)。

### 思路演进

1. **暴力解法**：枚举 `k = 0 .. n-1`，真的把数组切出来拼成 `nums[k:] + nums[:k]`，再求前一半和后一半的和比大小。每个 `k` 要拼一次数组 + 扫一遍，单次 O(n)，总计 O(n²)。`n = 10^5` 时是 10^10 量级，必超时。

2. **观察一（不必真的构造旋转）**：左旋 `k` 位后，位置 `j` 上的元素是原来的 `nums[(j + k) % n]`。代入 `j = 0 .. n/2-1`，前一半就是原数组中下标 `k, k+1, ..., k + n/2 - 1`（超过 `n-1` 后绕回 0）这一段连续（环形）元素。**旋转这个动作被彻底消掉了，只剩"窗口起点在哪"。**

3. **观察二（补集求和）**：前后两半互斥且并集是全体，所以后半和 = `total - first`，`total` 只在最开始算一次。判定条件直接写成 `first > total - first`，每次只需知道一个窗口和。

4. **观察三（相邻起点只差一进一出）**：从起点 `k` 换到 `k+1`，窗口只丢掉 `nums[k]`、只加进 `nums[k + n/2]`（同样 mod `n`），长度始终是 `n/2`。于是每个起点的窗口和都能由上一个 O(1) 推出来，不必重扫。

5. **落地**：先算起点 0 的窗口（原数组前 `n/2` 个）判一次，然后 `while` 往右滑 `n-1` 次，把剩下 `n-1` 个起点判完，正好覆盖全部 `n` 种移位。

> 另一条同复杂度的路线是「前缀和 + 跨环拆分」（每段窗口拆成"尾段 + 头段"两次查表），时间一样是 O(n)，但要多开 `n+1` 的数组并单独处理跨界，边界更容易写错，没有必要。

### 关键点

- **旋转后的下标映射**：位置 `j` ← 原下标 `(j + k) % n`。这一步写对，整题就只剩滑动窗口。
- **窗口长度恒为 `n/2`**：滑动时永远「减一个、加一个」，绝不改变长度。
- **起点一共 `n` 个**：`k = 0` 对应空前缀（不移位），也在计数范围内。
- **严格大于**：相等不算好移位（示例 2 全是相等，答案为 0）。
- **右端越界必须 mod `n`**：`k` 靠近末尾时，窗口会跨越数组末尾绕回头部。
- **总和只算一次**：靠 `total - first` 得到后半和，避免重复累加。

## 三、代码实现

### 最终代码

```python
class Solution:
    def countGoodRotations(self, nums: list[int]) -> int:
        total = sum(nums)          # 后半和靠 total - first 推出，只算一次
        ans = 0
        n = len(nums)
        half = n // 2

        # 起点 k = 0：前 half 个元素就是原数组的前半段
        first = 0
        for i in range(half):
            first += nums[i]
        if first > total - first:
            ans += 1

        # 起点 k = 1 .. n-1：窗口右移一位，一进一出
        left = 0
        right = half
        while left < n - 1:
            first -= nums[left]        # 丢掉滑出窗口的左端
            first += nums[right]       # 加入新进入的右端
            left += 1
            right += 1
            right %= n                 # 右端绕环
            if first > total - first:
                ans += 1

        return ans
```

> 截图代码里的 `first = 0 / n = len(nums) / right = n // 2 / left = 0` 已按功能归并到对应位置，逻辑与提交通过的版本完全一致；没有用到需要 `import` 的模块。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码（环形滑动窗口）** | O(n) | O(1) |
| 前缀和版（每个窗口两次查表） | O(n) | O(n) |
| 朴素解法（每个 k 重构数组并求和） | O(n²) | O(n) |
| 理论下界 | O(n) | O(1) |

> 复杂度中的 n 指数组 `nums` 的长度（偶数，`2 <= n <= 10^5`）。

## 五、优化评估

**结论**：**已是最优** —— 时间 O(n) 达到下界，额外空间已是 O(1)。

### 瓶颈分析

时间上有两件不可省的事：① 必须把数组每个元素至少看一遍才能得到 `total`（也是窗口滑动本身的需要）；② `n` 个起点每一个都要给出一次判定，而每个判定至少要拿到该窗口的和。于是 Ω(n) 无法绕开，当前实现正好是 O(n)，没有第二个数量级可省。

空间上只用了 `total / first / left / right / ans` 几个标量，与 `n` 无关。

### 可优化空间

- **时间**：无。`n = 10^5` 时 O(n) 已远低于时限，不存在需要再降一档的空间。
- **空间**：已 O(1)。走前缀和路线虽然时间同为 O(n)，却要多开 `n+1` 的数组，还要把跨环窗口拆成两段拼接、单独处理 `k + n/2 > n` 的越界分支 —— 用空间和边界复杂度换不到任何时间收益，不值得。
- **常数级优化（可选）**：
  - 判定写成 `first + first > total`（或 `first * 2 > total`），比 `first > total - first` 少一次减法，语义完全等价。
  - 把 `nums` 上的访问提前绑到局部变量，循环体内少一层属性查找。
  - k = 0 的判定可以和滑窗循环合并成 `for k in range(n)` + 一个 `if`，代码更短，但滑窗的"一进一出"顺序就不再线性可读，小规模下也不算收益。**注意别写成 `first > total / 2`**：浮点比较在大总和下不稳，用整数运算。

## 六、易错点与总结

### 易错点

- **忘了取模**：把窗口右端直接写成 `k + n/2 - 1`，`k` 一靠近末尾就越界。正确的是 `(k + n/2 - 1) % n`；滑动版本里体现为 `right %= n`。
- **滑动更新顺序写反**：必须先 `first -= nums[left]` 再 `left += 1`，加的是 `nums[right]` 然后 `right += 1`。顺序一乱，减掉的和加进去的就不是同一个窗口，长度会漂。
- **循环次数差一**：`k = 0` 已在循环前判过，`while` 只能再跑 `n-1` 次（`left < n - 1`）。写成 `left < n` 会多跑一轮，把 `k = n`（与 `k = 0` 同一种移位）重复计数。
- **比较用了 `>=`**：题目要求**严格**大于。相等时算好移位就会在示例 2 上直接错（正确答案 0）。
- **后一半重复求和**：既然 `total` 已经算过，后半就是 `total - first`；再单独滑一个窗口不仅多余，还容易把两段窗口的边界搞混。
- **把"前 n/2 个"当成原数组的前半段**：只有在 `k = 0` 时才恰好重合，`k > 0` 时窗口起点跟着移位一起动了。
- **C++ 版的溢出**：总和最大约 `10^5 × 10^9 = 10^14`，`int` 装不下，必须 `long long`。Python 整数无上界，无此问题。

### 题型套路沉淀

- **环形窗口模型**：数组首尾相接，长度固定的窗口沿环滑动，下标一律 `% n`。写法固定为「先算初始窗口 → 循环 n-1 次做一进一出 → 每次更新后判定」，是旋转/循环类题目的标准骨架。
- **操作 → 下标映射**：遇到「旋转 / 移位 / 循环」时，第一步永远是把操作后的位置写成原下标的函数（本题：位置 `j` ← `(j + k) % n`）。一旦写出映射，"对每个操作结果做统计"就退化成"对原数组的某个滑窗做统计"，复杂度立刻降一个档。
- **补集求和**：若两部分互斥、并集为全体，第二部分的 sum 永远用 `total - 第一部分`，不要重复累加 —— 既省时间也少一个可能写错的边界。
- **固定长度滑窗的判定模板**：`while` 里"先更新窗口、后判定"，且起点的首轮在循环外单独处理，是避免差一错误最稳的写法；也可以统一改写成 `for k in range(n)` 配 `if k > 0: 更新窗口`。
