# 1052. 爱生气的书店老板

> **难度**：中等
> **标签**：数组 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/grumpy-bookstore-owner/

---

## 一、题目描述

书店开了 `n` 分钟，第 `i` 分钟有 `customers[i]` 位顾客进店，并在该分钟结束时离开（**这些顾客只属于这一分钟**）。

`grumpy[i] == 1` 表示老板第 `i` 分钟在生气 —— 这一分钟的顾客全部不满意；`grumpy[i] == 0` 则这一分钟的顾客全部满意。

老板有一个**只能使用一次**的技巧：让某一段**连续 `minutes` 分钟**不生气。求这一天最多能让多少顾客满意。

### 示例

```text
示例 1
输入：customers = [1,0,1,2,1,1,7,5], grumpy = [0,1,0,1,0,1,0,1], minutes = 3
输出：16
解释：技巧用在下标 5~7（最后 3 分钟）。
      满意数 = 1 + 1 + 1 + 1 + 7 + 5 = 16

示例 2
输入：customers = [1], grumpy = [0], minutes = 1
输出：1
```

### 约束条件

- `n == customers.length == grumpy.length`
- `1 <= minutes <= n <= 2 * 10^4`
- `0 <= customers[i] <= 1000`
- `grumpy[i]` 为 `0` 或 `1`

## 二、解题思路

### 核心思想

**把答案拆成「无论如何都能满意的人数」+「用技巧额外挽回的人数」。**

- 第一项是**定值**：所有 `grumpy[i] == 0` 的分钟里的人数之和，技巧怎么用都不影响它。
- 第二项才是**变量**：技巧覆盖某一段长度 `minutes` 的区间时，额外挽回的正是「这段区间里原本生气的那部分人数」`Σ customers[i] · grumpy[i]`。要让它最大 → **定长滑动窗口求最大窗口和**。

一句话：**求 `grumpy[i] * customers[i]` 这个数组上长度 `minutes` 的最大连续子数组和，再加上固定的固有满意数。**

### 思路演进

1. **暴力解法**：枚举技巧的起始分钟 `s ∈ [0, n-minutes]`，对每个 `s` 重新扫一遍全数组统计满意人数，取最大。时间 `O(n · minutes)`；当 `minutes` 接近 `n` 时是 `O(n²) = 4 × 10^8`，Python 下**必然超时**。
2. **观察到**：枚举不同 `s` 时，绝大部分工作被**重复计算**了。真正随 `s` 变化的只有「区间 `[s, s+minutes-1]` 内原本生气的那部分人数」这一项；区间之外的人数与 `s` 完全无关。把不变量先算出来，问题就退化成"在一维数组上滑窗求最大和"。
3. **优化为**：先一趟求出 `base = Σ customers[i] (grumpy[i]==0)`，再用一个滚动变量 `gain` 维护当前窗口内 `grumpy[i]==1` 的 `customers[i]` 之和，窗口每右移一步就 `+新进来的 - 退出去的`，记录 `gain` 的最大值 `best`。答案 `= base + best`。总时间 `O(n)`。

### 关键点

- **分解思维**：把"最优选择"问题写成 `不变量 + 可优化量`，是这类「只能用一次的特殊操作」题目的通用破法。
- 滑窗维护的量是 **`grumpy[i] * customers[i]`**（即「可挽回人数」），而不是 `customers[i]` —— 因为不生气分钟的顾客本来就会满意，放在窗口里不产生任何增量。
- **技巧可以覆盖不生气区间**，此时那一分钟的人数只算一次（既在 `base` 里，也在窗口里）—— 所以窗口内的贡献绝不能写成 `Σ customers[i]`，否则会重复计数。
- 题目是 `minutes <= n`，窗口**一定能放得下**，不需要处理"窗口比数组长"的退化情况。

## 三、代码实现

### 最终代码

```python
from typing import List


class Solution:
    def maxSatisfied(self, customers: List[int], grumpy: List[int], minutes: int) -> int:
        # mid 维护：当前长度为 minutes 的窗口内，「原本生气 ⇒ 可被挽回」的人数
        NumIndex = MaxNum = mid = 0
        for i, j in enumerate(customers):
            if grumpy[i] == 1:
                mid += j                            # 右端点进入窗口（只有生气的分钟才计入）
            if i < minutes - 1:
                continue                            # 窗口还没凑满 minutes 分钟
            if mid > MaxNum:                        # 结算并记录最优窗口
                MaxNum = mid
                NumIndex = i - minutes + 1          # 最优窗口的左端点
            if grumpy[i - minutes + 1] == 1:
                mid -= customers[i - minutes + 1]   # 左端点退出窗口
        ans = 0
        for i in range(NumIndex):                   # 最优窗口左侧：只数不生气的分钟
            if grumpy[i] == 0:
                ans += customers[i]
        for i in range(NumIndex + minutes, len(customers)):   # 最优窗口右侧
            if grumpy[i] == 0:
                ans += customers[i]
        ans += MaxNum                               # 窗口内被挽回的人数
        for i in range(NumIndex, NumIndex + minutes):         # 窗口内不生气的分钟，照常计入
            if grumpy[i] == 0:
                ans += customers[i]
        return ans
```

> 这段是本人提交通过的版本，逻辑正确（已对拍验证，见文末）。但**它不是最简洁的写法**，第五节给出了实测快 1.25 倍的改写。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |

## 五、优化评估

**结论**：时间与空间**都已是理论下界**，算法层面无优化空间；但当前实现把同一个数组**扫了四遍**，Python 层面的常数开销可以砍掉三分之一左右。

### 瓶颈分析

- **时间下界 `Ω(n)`**：最坏情况下（比如 `minutes = n`）必须读取全部元素才能确定答案，任何正确算法都逃不掉一遍全扫 → `O(n)` 已触底。
- **空间下界 `Ω(1)`**：答案只需要「固有满意数」「当前窗口增量」「历史最优增量」三个标量，与 n 无关。
- 当前的常数开销来自**四次独立遍历**：第 1 遍滑动找窗口，第 2/3/4 遍分别扫窗口左侧、右侧、内部。这三遍完全可以合并 —— 因为 `base = Σ_{grumpy==0} customers[i]` 与窗口位置**无关**，先算总量再叠加增量即可，无需按窗口位置把数组切碎。**"先算不变量、再算增量"既减少了循环，也消除了"窗口内/外"的边界分歧**（`NumIndex` 这个中间状态其实可以彻底不要）。

### 可优化空间

| 改动 | 收益 |
| :--- | :--- |
| 把三段 `for i in range(NumIndex...)` 合并为一次全量 `base` 统计 | 三遍扫描 → 一遍；不再需要 `NumIndex` |
| 首窗口用 `range(minutes)` 单独累加，主循环直接从下标 `minutes` 开始 | 去掉 `if i < minutes - 1: continue` 这个每轮都执行的无效分支 |
| 用 `gain += customers[i] if grumpy[i] else 0` 替代 `if grumpy[i] == 1: gain += customers[i]` | 少一层缩进与分支体，行数减半 |
| `if gain > best: best = gain` 替代"在滑窗前结算" | 语义更直白（先滑动再比大小） |

### 优化代码

```python
from typing import List


class Solution:
    def maxSatisfied(self, customers: List[int], grumpy: List[int], minutes: int) -> int:
        # 1) 不变量：老板从不生气时也必然满意的人数
        base = sum(c for c, g in zip(customers, grumpy) if g == 0)

        # 2) 可优化量：长度为 minutes 的窗口内，靠技巧额外挽回的人数
        gain = sum(c for c, g in zip(customers[:minutes], grumpy[:minutes]) if g == 1)
        best = gain
        for i in range(minutes, len(customers)):
            gain += customers[i] if grumpy[i] else 0                       # 右端点进入
            gain -= customers[i - minutes] if grumpy[i - minutes] else 0   # 左端点退出
            if gain > best:
                best = gain

        return base + best
```

**优化理由**：把"技巧用在哪"这件事从**区间拼接**（需要知道窗口在哪、再分三段统计）改写成**基准值 + 增量**（基准值与窗口无关，天然可一次算完）。这既缩短了代码，也消灭了 `NumIndex`、`MaxNum` 这类只服务于拼接逻辑的中间状态 —— 而中间状态越少，`i - minutes + 1` 这种偏移量写错的机会就越少。

**实测（`n = 20000`，CPython 3.13，各取 7 次最优值）：**

| `grumpy` 中 1 的比例 | `minutes` | 用户版 | 优化版 | 提速 |
| ---: | ---: | ---: | ---: | ---: |
| 0.5 | 1 | 3.837 ms | 3.033 ms | 1.27× |
| 0.5 | 100 | 3.967 ms | 3.168 ms | 1.25× |
| 0.5 | 5000 | 3.623 ms | 2.825 ms | 1.28× |
| 0.5 | 20000 | 2.439 ms | 1.792 ms | 1.36× |
| 0.05 | 100 | 3.263 ms | 2.650 ms | 1.23× |

**规律**：提速稳定在 **1.2~1.4 倍**，与 `minutes` 关系不大 —— 收益主要来自"四遍扫描 → 两遍扫描"，而扫掉的那两遍只与 `n` 有关。`minutes = n` 时提速最大，因为此时用户版的"窗口内/外"三段循环有两段直接为空，纯粹白跑。

> 结论：**两者都在 `O(n)`、都能 AC**（`n = 2 × 10^4` 时都是个位数毫秒）。优化版的价值不在于过题，而在于**代码更短、更不容易写错下标**。如果面试时先写的是用户版那种思路，写完最好回头合并一次。

## 六、易错点与总结

### 易错点

- **窗口里累加错了对象**：窗口应维护 `grumpy[i] * customers[i]`（可挽回人数），若误写成 `customers[i]`（窗口总人数），会把"本来就会满意的顾客"重复计一次，答案偏大。
- **结算时机与左指针的偏移**：右端点进入后先判窗口是否满 `minutes`（`i >= minutes - 1`），再记录最优值，最后才让左端点 `i - minutes + 1` 退出。顺序写反会让窗口变成 `minutes + 1` 长度。
- **忘记 `base` 里包含窗口内的不生气分钟**：`base` 是全数组统计，窗口内的不生气分钟已经在里面了，所以窗口部分**只能补 `MaxNum`**，不能再把窗口总人数整段加上。
- **用 `>=` 比较增量**：`mid > MaxNum` 用严格大于即可。改用 `>=` 不会错，但会让并列时选到更靠后的窗口（本题答案与窗口位置无关，所以无影响）。
- **多跑一次 `mid -= ...`**：最后一轮结束后那次减法是无用功，但结果不再被读取，**无害**，不必加特判。

### 题型套路沉淀

- **"一次特殊操作 + 求最优"的分解模板**：

  ```text
  答案 = 不变量（不受操作影响的部分）
       + max{ 操作作用于某位置时带来的增量 }
  ```

  识别信号：题目说某个"特权/道具/机会"**只能用一次或有限次**，问最终最优结果。此时把不受操作影响的基线先算出来，问题就退化成在增量数组上求极值（最大子段和 / 定长窗口最大和 / 前缀和差）。
- **定长滑窗的通用骨架**（与 `1176. 健身计划评估` 同骨架）：

  ```text
  维护 window
  右端点进入 → window += f(arr[right])
  若窗口已满 k：结算当前窗口 → window -= f(arr[left])，left += 1
  ```

- **定长滑窗家族对照**（本题属于其中"窗口内求和"的一支）：

  | 题 | 窗口维护的量 | 备注 |
  | :--- | :--- | :--- |
  | `1176` 健身计划评估 | 窗口和 | 每个窗口都要结算 |
  | `643` 子数组最大平均数 I | 窗口和 | 只取最大值 |
  | **`1052` 本题** | 窗口内 `grumpy[i]*customers[i]` 之和 | 先算基线，再叠加窗口增量 |
  | `1100` / `1151` / `1852` / `2107` | 窗口内的计数 | 需要哈希配合去重 |

- **增量可加性是滑窗的前提**：求和、计数、异或都满足；"窗口内最大值"不满足（移出的可能正是最大值），那类题要么用**单调队列**（`239. 滑动窗口最大值`），要么用**有序多重集**。
- 本题还提示一个工程习惯：**当发现自己在同一个数组上分段做同一件事时，先问一句"这段能不能并进一个全量循环"** —— 通常能，而且合并后状态更少、更不容易错。

### 验证记录

- 2 个官方示例：用户版与优化版**全部通过**（`16` / `1`）。
- 与暴力解法随机对拍 **3000 组**（`n ≤ 40`，`customers[i] ∈ [0,10]`，覆盖 `minutes = 1` 与 `minutes = n`）：**零偏差**。
- 边界用例：`n = 20000` 且 `minutes = 1 / n`、`grumpy` 全 0 / 全 1 —— 两版结果一致。
