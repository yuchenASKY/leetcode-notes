# 2799. 统计完全子数组的数目

> **难度**：中等
> **标签**：滑窗 · 数组 · 哈希表
> **原题链接**：https://leetcode.cn/problems/count-complete-subarrays-in-an-array/

---

## 一、题目描述

给定正整数数组 `nums`。记**整个数组**的不同元素种类数为 `n`，若某个**连续非空子数组**中不同元素的种类数恰好也是 `n`，则称它为**完全子数组**。求完全子数组的总数。

### 示例

```text
输入：nums = [1,3,1,2,2]
输出：4
解释：完全子数组有：[1,3,1,2]、[1,3,1,2,2]、[3,1,2] 和 [3,1,2,2]。
```

```text
输入：nums = [5,5,5,5]
输出：10
解释：数组仅由 5 组成，任意子数组都满足条件，子数组总数为 4*5/2 = 10。
```

### 约束条件

- `1 <= nums.length <= 1000`
- `1 <= nums[i] <= 2000`

## 二、解题思路

### 核心思想

**对每个右端点 `r`，合法的左端点是一段「前缀」，把它的长度累加起来就是答案。** 而这段前缀的长度随 `r` 单调不减，于是可以用双指针在 O(n) 内求出全部 n 个前缀长度。

### 思路演进

1. **暴力解法**：枚举全部 O(n²) 个子数组，对每个子数组再用 `set` 数一遍不同元素种类，与全局种类数比较。时间 O(n³)；稍作改进——固定起点向右扩展时增量维护 `set`——可以降到 O(n²)，空间 O(n)。
2. **观察到瓶颈**：O(n²) 版本仍然对「每个右端点都重新枚举一遍左端点」。但本题的判定条件对左端是**前缀封闭**的：窗口越大越容易包含全部种类，一旦 `[i, r]` 覆盖了全部种类，那么 `[i', r]`（`i' <= i`）必然也覆盖。⇒ 对固定的 `r`，合法左端**必然构成一段前缀** `[0, L(r)-1]`，答案是 `Σ_r L(r)`。于是问题从「判断 O(n²) 个子数组」变成「只求 n 个分界点」。
3. **关键转化**：`L(r)` 随 `r` **单调不减**——因为 `[L(r)-1, r]` 合法 ⇒ 它加上一个元素后的 `[L(r)-1, r+1]` 仍是它的超集、仍然合法 ⇒ `L(r+1) >= L(r)`。左指针只会单向前进，整趟总移动量 ≤ n ⇒ 双指针成立，总时间降为 O(n)。
4. **最优解**：维护窗口 `[left, right]` 内各值的出现次数，并让 `while` 循环把左端收缩到「窗口刚好不再覆盖全部种类」为止。跳出时 `[left-1, right]` 恰好是最后一个合法窗口，故 `left` 就等于 `L(right)`，直接累加即可。

### 关键点

- **判据**：窗口 `[left, right]` 是完全子数组 ⟺ 窗口内**不同元素种类数** == 全局种类数 `n`。
  这是**按键数**判定的判据（不是「某个值的计数超过阈值」那种按值判据），这个区别决定了实现细节：**计数归零时必须删键**，否则 `len(cnt)` 只增不减，左指针会被一路推到数组外。
- **`while` 用 `==` 而非 `>=` 是安全的**：因为恒有「`len(cnt) <= n`」——`cnt` 的键只可能是数组中真实出现过的值，它们的种类数不会超过全局种类数。语义上 `==` 也更准确。
- **`ans += left` 的语义不是「窗口长度」**，而是「以 `right` 结尾的合法子数组个数」= 合法起点的个数。跳出 `while` 时 `[left, right]` 已不合法、而刚被移出视野的 `[left-1, right]` 是合法的，所以合法起点恰好是 `0..left-1` 这 `left` 个。
- `L(r)` 还有一个等价刻画：`L(r) = min_x last_r[x] + 1`，其中 `last_r[x]` 是 `x` 在 `nums[0..r]` 中最后一次出现的下标（窗口包含全部种类 ⟺ 左端不超过每个种类的最后出现位置）。这个刻画好用来论证「为什么不必换结构」：`last` 是**被更新**而不是被追加的，单调队列不适用，直接维护 `min(last)` 需要堆 ⇒ O(n log n)，**并不比滑动窗口更优**。
- `while` 的摊还成本：`left` 整趟最多从 0 走到 n，所以内层循环总计 O(n) 次迭代，均摊 O(1)/轮。

## 三、代码实现

### 最终代码

```python
from collections import defaultdict
from typing import List


class Solution:
    def countCompleteSubarrays(self, nums: List[int]) -> int:
        n = len(set(nums))            # 整个数组的不同元素种类数
        ans = left = 0
        cnt = defaultdict(int)        # 窗口 [left, right] 内各值的出现次数
        for right, j in enumerate(nums):
            cnt[j] += 1
            while len(cnt) == n:      # 窗口已覆盖全部种类 → 左端逐个右推
                cnt[nums[left]] -= 1
                if cnt[nums[left]] == 0:
                    del cnt[nums[left]]        # 按键数判定，必须删键
                left += 1
            ans += left               # 跳出时 [left-1, right] 刚好合法 ⇒ 合法起点数 = left
        return ans
```

> 截图里只有 `class Solution:`，`defaultdict` / `List` 来自 LeetCode 的预置环境。为让笔记里的代码可直接运行，已补上 `from collections import defaultdict` 与 `from typing import List`（截图里没有、已补）。
> `for right, j in enumerate(nums)` 中的 `right` 在循环体内并未被使用（`right` 只是被 `enumerate` 顺带产出），下文的优化版顺手去掉了它。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) 均摊（`left` 整趟最多推进 n 次） | O(min(n, 值域)) |
| 朴素解法（枚举 + 增量 `set`） | O(n²) | O(n) |
| 理论下界 | O(n) | O(min(n, 值域)) |

> 复杂度中的 n 指数组 `nums` 的长度（与题面里「不同元素种类数」的记号无关）。

时间下界为什么是 Ω(n)：至少要读完全部元素才知道总种类数 `n`；而且答案在**每个**右端点都可能非零（例如全相同元素的数组），n 个右端点一个都不能跳过。

## 五、优化评估

**结论**：时间复杂度已是理论下界，**但常数仍有 1.5~2.0× 的压缩空间**（把哈希表换成定长数组）。

### 瓶颈分析

- 题面上限只有 `n <= 1000`，任何 O(n) 写法都是 0 ms 级 —— 这里的优化属于「**泛化到任意 n 时压缩常数**」的研究，**不是**「不优化会超时」。
- 时间花在两处：① `defaultdict` 的哈希查找与插入；② 每轮 `del` 删键时会改动哈希表结构。两者都发生 O(n) 次。
- 空间：`dict` 最多 n 个键，每个键值都是一个装箱的 Python `int`，外加哈希表槽位；而值域上界只有 2000 ⇒ 一个 C 层的定长数组可以整块替掉它。

### 可优化空间

- **时间已到 Ω(n) 下界，无法再降**（依据见上一节的论证）。剩下的只有常数。
- 常数压缩的切入点：题面给出 `1 <= nums[i] <= 2000`，值域有硬上界 ⇒ 用 `[0] * 2001` 定长数组计数，同时用一个整数 `kinds` 顶替 `len(cnt)`（数组版本没法 O(1) 问出「有几种不同的值」，所以额外维护一个计数器，只在计数 0↔1 翻转时增减）。

### 优化代码

```python
from typing import List


class Solution:
    def countCompleteSubarrays(self, nums: List[int]) -> int:
        total = len(set(nums))        # 全局不同元素种类数
        cnt = [0] * 2001              # 值域上界 2000（题面约束），定长数组替代哈希表
        ans = left = kinds = 0        # kinds = 窗口内不同元素种类数
        for x in nums:
            if cnt[x] == 0:
                kinds += 1
            cnt[x] += 1
            while kinds == total:
                y = nums[left]
                cnt[y] -= 1
                if cnt[y] == 0:
                    kinds -= 1
                left += 1
            ans += left
        return ans
```

**优化理由**：把「字典的哈希 + 装箱 + 删键」全部换成整型数组的下标访问，`len(cnt)` 换成 `kinds` 整数比较；顺手把 `nums[left]` 缓存进 `y`，少一次索引。算法结构完全不变，实测提速 1.55×~2.02×。

> 注意：这一版**依赖题面约束 `nums[i] <= 2000`**。若值域无上界，改回 `defaultdict` 或先做一次坐标压缩。

### 常数级优化（可选）

- `while kinds == total` 中，`kinds` 是整数比较，比 `len(dict)` 少一层 C 调用；再往下压只能靠 PyPy 之类的运行时，算法层面已无空间。
- 不要试图用「每种值的最后出现位置 + 求最小值」来省掉窗口计数：`last` 数组是被覆盖更新的，单调队列不适用，得配堆 ⇒ O(n log n)，比现方案更慢。

## 六、易错点与总结

### 易错点

- **按「键数」判定却不删键**：`len(cnt)` 是「窗口内有几种值」的依据，计数归零后必须 `del`，否则键数只增不减 ⇒ `while` 永不退出、左指针越界。
  实测最小反例 `[1, 1]`：真值 3，不删键版实得 4（该版本还得靠越界保护才能跳出循环，不加保护会死循环）。
- **把 `while` 换成 `if`（每轮只缩一格）**：本题的单轮收缩可能**连缩多格**（分界点一次前进不止 1 格），只缩一格会让 `left` 滞后，少算答案。
  实测最小反例 `[1, 1, 2]`：真值 2，只缩一格版实得 1。
- **`ans += left` 写在收缩之前**：此时 `left` 还是上一轮的陈旧值，会把本该排除的起点也统计进去。
  实测最小反例 `[1]`：真值 1，提前累加版实得 0（收缩前 `left = 0`，直接加了个 0）。
- **不要把「窗口长度」当成答案口径**：本题答案是「以 `right` 结尾的合法子数组**个数**」，等于分界点 `left`，而不是窗口长度 `right - left + 1`。这也是本题不能套用「长度单调 ⇒ 平移版等价」那套结论的原因 —— 上面实测的 `while→if` 反例就是证据。
- 收缩循环不会把窗口抽空：`kinds < total` 时立刻跳出，故 `nums[left]` 不会越界（全相同元素的用例已覆盖验证）。

### 题型套路沉淀

- **「分界点 + 累加」是滑窗计数题的固定骨架**：① 写出窗口合法的判据；② 论证合法性对一端**前缀封闭**，从而每个右端点存在唯一分界点 `L(r)`；③ 论证 `L(r)` 单调 ⇒ 双指针成立；④ 累加 `L(r)` 而非统计窗口长度。
- **先分清判据是按「值」还是按「键数」**：按值（某元素计数超限）归零不必删键；按键数（不同种类数超限）**必须删键**。写之前先把这一条定下来，边界错误基本就消掉了。
- 看到「窗口里必须包含全部 X 种元素」这类**前缀封闭**的条件，就可以放心用左指针单向推进，不必回退。
- 值域有上界的题，用定长数组替代哈希表通常是稳赚的常数优化（本题实测 1.55×~2.02×）。
