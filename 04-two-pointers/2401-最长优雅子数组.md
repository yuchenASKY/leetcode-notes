# 2401. 最长优雅子数组

> **难度**：中等
> **标签**：滑动窗口 · 位运算 · 数组
> **原题链接**：https://leetcode.cn/problems/longest-nice-subarray/

---

## 一、题目描述

给定一个由**正**整数组成的数组 `nums`。若某个**连续**子数组内任意两个**不同位置**的元素按位与（AND）都为 `0`，则称该子数组为**优雅**子数组（长度为 1 的子数组恒为优雅）。求**最长**优雅子数组的长度。

### 示例

```text
输入：nums = [1,3,8,48,10]
输出：3
解释：最长的优雅子数组是 [3,8,48]：3 AND 8 = 0，3 AND 48 = 0，8 AND 48 = 0。
      可以证明不存在更长的优雅子数组。

输入：nums = [3,1,5,11,13]
输出：1
解释：任意长度 ≥ 2 的子数组都存在两个共有同一位的元素，最长只能取 1。
```

### 约束条件

- `1 <= nums.length <= 10^5`
- `1 <= nums[i] <= 10^9`

---

## 二、解题思路

### 核心思想

**「优雅」⟺ 窗口内每个二进制位至多属于一个元素 ⟺ 窗口 OR 里没有「共享位」。** 用一个变量 `or_` 表示窗口已占用的位集合，加入新元素 `x` 时只需判 `or_ & x == 0`；收缩时，**因为 while 结束后窗口必定优雅**，`or_ ^= nums[left]` 就是精确的「按位删除」。

### 思路演进

1. **暴力解法**：枚举所有 O(n²) 个子数组，对每段再两两比较（O(len²)）⇒ O(n³)。子数组数量本身已是 O(n²)，n = 10^5 时完全不可行。

2. **观察到（把 O(len²) 的两两比较降成一次 O(1) 的位判断）**：「每对元素 AND 都为 0」这个检查可以换成等价式 —— 只要窗口**此前已经优雅**，那么 `or_` 中出现过的位就是「已被某个元素占用」的位，于是
   **加入 `x` 后窗口仍优雅 ⟺ `or_ & x == 0`**。
   另一种等价说法：**优雅 ⟺ 窗口 OR == 窗口内元素算术和**（没有进位，即没有哪个 bit 被两个元素共有）。
   ⚠️ 这里要先排除一个看起来很像、实则错误的判据：**「窗口 OR == 窗口 XOR」并不等价于优雅**。逐位看，OR 的该位为 1 ⟺ 该 bit 出现 ≥ 1 次，XOR 的该位为 1 ⟺ 该 bit 出现**奇**数次，两者相等只说明「每个 bit 要么没出现、要么出现奇数次」—— 3 个元素共有同一个 bit 时照样相等。实测 `[3,1,5,11,13]` 上 `OR = XOR = 1`，而它显然不优雅。（本次写暴力基准时就踩了这一步，被基准自检抓出来。）

3. **优化为（把 O(n²) 的「枚举起点」降成 O(n) 双指针）**：该约束对**左端点前缀封闭** —— 从窗口左侧删元素只会**消除**冲突，绝不会制造冲突（删掉元素不会把非法窗口变成合法所需的相反方向）。所以固定右端点时，合法的左端点构成一段前缀，左指针**只增不减**：整趟最多移动 n 次，右端点扫一遍即可，内层 `while` 是**摊还 O(1)**。

4. **最后一个细节：怎么把左端元素的位从 `or_` 里「减掉」。** 因为每一步 while 结束时窗口都优雅（`or_ & x == 0`，即窗口内每位只属于一个元素），所以左端元素 `nums[left]` 的每一位都不属于窗口里其他任何元素 —— `or_ ^= nums[left]` 就是**精确的按位删除**。⚠️ 这一点是整套写法的前提：**XOR 不是通用的「按位删除」**，一旦窗口内存在重复位，XOR 会把仍然存在的位静默抹掉（见 §六 的 `if` 版反例）。

### 关键点

- **判据**：窗口优雅 ⟺ 每位至多属于一个元素；加入 `x` 的检查是 `or_ & x == 0`，O(1)，无需按位循环。
- **`or_ ^= nums[left]` 的前提是「窗口此刻优雅」**，不能当成通用的逆运算。
- **答案口径必须是「每轮取 max」**：while 版窗口长度序列可能下降，用终值 `n - left` 会错（最小反例 `[1,2,2]`，官方示例 1 同样会错），详见 §六。
- **左指针不会越界**：`left == right` 时窗口为空 ⇒ `or_ == 0` ⇒ while 立即退出，所以循环体内 `nums[left]` 恒有 `left <= right`，不存在负索引/越界。
- **窗口长度上界是常数 30**：`nums[i] <= 10^9 < 2^30`，优雅窗口内每位至多一个元素 ⇒ 长度 ≤ 30。这解释了 n = 10^5 时内层 while 的实际迭代量上限（但不能据此把摊还 O(1) 的收缩改成固定回扫，见 §五）。

## 三、代码实现

### 最终代码

```python
from typing import List          # 截图里没有（LeetCode 环境自带），为让代码可直接运行已补


class Solution:
    def longestNiceSubarray(self, nums: List[int]) -> int:
        ans = left = or_ = 0
        for right, x in enumerate(nums):
            while or_ & x:           # or_ 与 x 有共享位 ⇒ 从左边收到不冲突为止
                or_ ^= nums[left]    # 窗口此刻必然优雅，XOR 即「按位删除」
                left += 1
            or_ |= x
            ans = max(ans, right - left + 1)
        return ans
```

## 五、优化评估

**结论**：时间已是理论下界 O(n)、空间 O(1)，**算法层面没有可优化空间**；只剩常数项，实测只有一处改动值得做。

### 瓶颈分析

每轮的固定成本是：一次 `or_ & x` + 一次 `or_ |= x` + 一次 `max()` 调用；收缩段的总迭代次数 ≤ n（左指针只增不减）。n = 10^5 时整趟约 15 ms，**几乎全是解释器层的循环与函数调用开销，与算法无关**。所以能动的只有常数。

### 可优化空间（实测表，n = 10^5，4 档场景、9 轮轮转取最优）

| 版本 | S1 随机 30 位 | S2 全相同 1 | S3 循环 2 的幂 | S4 全相同 2^29 |
| :--- | :--- | :--- | :--- | :--- |
| A 用户版（while + `max()`） | 15.5 ms | 14.1 ms | 15.6 ms | 15.3 ms |
| **B 内联比较（`if w > ans`）** | **14.4 ms（1.08×）** | **13.4 ms（1.05×）** | **14.7 ms（1.06×）** | **14.3 ms（1.07×）** |
| C 位级「最后出现位置」跳跃 | 273.0 ms（0.06×） | 23.0 ms（0.61×） | 25.1 ms（0.62×） | 25.3 ms（0.61×） |
| D 30 格回溯 | 15.2 ms（1.02×） | 14.5 ms（0.98×） | 224.6 ms（0.07×） | 15.4 ms（0.99×） |

### 优化代码

```python
from typing import List


class Solution:
    def longestNiceSubarray(self, nums: List[int]) -> int:
        ans = left = or_ = 0
        for right, x in enumerate(nums):
            while or_ & x:
                or_ ^= nums[left]
                left += 1
            or_ |= x
            w = right - left + 1     # 与 A 版唯一差异：max() 换成内联比较
            if w > ans:
                ans = w
        return ans
```

**优化理由**：`max()` 每轮多一次全局名称查找 + 函数调用 + 参数打包，而这里比较的是两个局部整数。四档场景**全胜、幅度一致（1.05× ~ 1.08×）**，不随数据形态反转，属稳赚的常数优化。

### 常数级优化

两条**看起来更聪明、实测被证伪**的改法（保留在此，避免重犯）：

- ❌ **「位级最后出现位置」跳跃版**（把「记录每个值的最后出现位置 + 左边界跳转」这套动作从**值**换成**bit**：维护 `last[b]`，每轮 `left = max(left, max_{b∈x} last[b] + 1)`）。
  判据上它**是与 while 版精确等价的**（55 组对拍 0 偏差，且推导可见 §六 注释：`while` 收缩的终止位置正是「所有冲突位最后一次出现位置的最大值 + 1」，不是「每轮只挪一格」那种平移近似）。但在 Python 里每轮要按位迭代 popcount 次：**稀疏档 0.06×（慢 16 倍）**、其余档 0.61× ~ 0.62×。
  ⇒ 教训：位宽固定（≤ 30）**不等于**按位循环便宜 —— 它的常数远大于「摊还一次比较」。
- ❌ **「利用窗口长度 ≤ 30，每个右端点向左回看」版**：等价正确（0/55），但最坏要回看 30 格。S3（窗口真的长到 30）**0.07×**，其余档 ≈ 1.0×。
  ⇒ 「窗口长度上界是常数」只用来说明内层循环有上界，**不能**反过来把摊还 O(1) 的收缩改成固定 30 次扫描。

## 六、易错点与总结

### 易错点

- **把 `or_ |= x` 写进 while 体内**：每次 OR 之后 `or_ & x == x ≠ 0` 恒成立 ⇒ **死循环**（本题 nums 全为正整数，`x` 不为 0）。它必须在 while 之外。
- **把 `while` 换成 `if`**（想「每轮最多缩一格」省点开销）：**实测 10/55 错，反例 `[1,2,3,4]`（真值 2、实得 3）**；`n <= 3` 的 84 组小范围搜索全部正确 ⇒ **4 是它最短的出错长度**。
  失效机理不是「缩得不够」这么简单：`if` 版允许窗口**带着重复位继续存在**，而 `or_ ^= nums[left]` 的精确性依赖「窗口优雅」这个不变量 —— 一旦窗口非法，XOR 会把仍然被别人占着的位静默抹掉，`or_` 从此与真窗口 OR 不再一致，判据 `or_ & x` 也就失真了。**插桩实测：55 组用例里出现 72 轮状态失真**，首个失真用例 `[3,12,1,10,5,6,10,3,7]`（right = 6 时窗口为 `[6,10]`，重复位被 XOR 抹掉）。
  ⇒ 换 `if` 不是「保守一点」，而是**同时破坏了判据与状态维护** —— 这类写了 `^=`／`&= ~` 做「删除」的滑窗，收缩方式不能随便降级。
- **答案口径用终值 `n - left`**：**实测 15/55 错，最小反例 `[1,2,2]`（真值 2、实得 1）**，**官方示例 1 `[1,3,8,48,10]` 也会错**（真值 3、实得 2）；`n <= 2` 时恒正确 ⇒ 3 是最短出错长度。原因：while 版窗口长度序列会下降（本轮可能连缩多格），终值只反映「以最后一个元素结尾的最长优雅窗口」，不等于历史最大值。
- **把「OR == XOR」当作优雅的判据**：见 §二 第 2 步 —— 它等价于「每个 bit 出现奇数次」，不是「至多一次」；正确等价式是 **OR == 算术和**。
- **误判复杂度**：看到 `while` 嵌在 `for` 里就判 O(n²)。左指针只增不减、总移动 ≤ n，是摊还 O(1)（本题左指针的移动来自「按位删除」，且每轮增量 ≤ 1 个元素，所以右移步长可以任意长，但整趟总量受限）。

### 题型套路沉淀

- **「合法性由整窗的位集合决定 + 约束对左端前缀封闭」⇒ 变长滑窗**。这两条支柱缺一不可：前者给出可增量维护的判据（`or_ & x == 0`），后者保证左指针单调。
- **位运算 + 滑窗的通用动作**：用「窗口 OR」代表已占用的位；判据 `or_ & x == 0`；只有**在窗口恒优雅的前提下**，才可以用 XOR（或 `&= ~`）做「精确删除」。凡是拿位集合当集合用的写法，都要先问一句「这个不变量在收缩方式换掉后还成立吗」。
- **不要把「记录最后出现位置 + 跳转」这一族当成本题的优化**：它在判据上确实与逐格收缩精确等价，但在 Python 里是**常数更劣**的等价写法（本题位宽 ≤ 30、每轮按位迭代，实测慢 1.6× ~ 16×）。
- **收缩方式与答案口径必须配套**：`while` 收缩 ⇒ 长度不单调 ⇒ 每轮取 max；换成 `if` 收缩才可能长度单调、才有「终值即答案」的口径。**只换一半必错**（本题会错的两格正是「只换一半」的组合）。
