# 2762. 不间断子数组

> **难度**：中等
> **标签**：滑窗 · 滑动窗口 · 单调队列 · 哈希表 · 数组
> **原题链接**：https://leetcode.cn/problems/continuous-subarrays/

---

## 一、题目描述

给定一个整数数组 `nums`，若某个子数组内**任意两个元素之差的绝对值都 ≤ 2**，则称该子数组为「不间断」的。求 **不间断子数组的总数目**（子数组是连续、非空的）。

一句话等价改写：**子数组内 max − min ≤ 2**（因为「任意两元素差 ≤ 2」取到最值即可判定）。

### 示例

```text
输入：nums = [5,4,2,4]
输出：8
解释：
大小为 1：[5] [4] [2] [4]              -> 4
大小为 2：[5,4] [4,2] [2,4]            -> 3
大小为 3：[4,2,4]                      -> 1
大小为 4：[5,4,2,4] 的 max-min = 3 > 2 -> 0
合计 4 + 3 + 1 = 8

输入：nums = [1,2,3]
输出：6
解释：[1] [2] [3] + [1,2] [2,3] + [1,2,3] = 3 + 2 + 1 = 6
```

### 约束条件

- `1 <= nums.length <= 10^5`
- `1 <= nums[i] <= 10^9`

## 二、解题思路

### 核心思想

**判据：窗口 `nums[left..right]` 合法 ⟺ `max(窗口) − min(窗口) ≤ 2`。**

判定只看窗口的两端极值 ⇒ 固定右端、左端右移只会让值域变小（**合法性对「削掉左侧元素」封闭**）⇒ 双指针成立。再加上一个关键观察：**合法窗口的值域 ≤ 2，所以窗口内不同的取值至多 3 种**，于是「值 → 出现次数」的哈希表规模有常数上界，取窗口极值就是 O(1)。

### 思路演进

1. **暴力解法**：枚举全部 `n(n+1)/2` 个子数组，每个子数组扫一遍求 max/min 再判断 ⇒ **O(n³)**；即便对每个左端增量维护 max/min，也只是 **O(n²)**，n = 10⁵ 时约 5×10⁹ 次操作，不可行。
2. **观察到**：瓶颈不在「判断合法性」（判断本身只是两个极值相减），而在**每个右端都从 0 开始重扫左端**。而合法性有个单调性：若 `nums[left..right]` 合法，那么去掉最左元素后的 `nums[left+1..right]` **必定**也合法（子区间只可能比原区间值域更小），反之不一定。这类「约束对删左侧元素封闭」的性质，正是滑动窗口的准入条件。
3. **优化为**：对每个 `right`，把 `left` 一直右推到「以 `right` 结尾的最长合法窗口」为止；`left` 全程只增不减，总移动次数 ≤ n ⇒ 均摊 O(1) / 轮。窗口状态用一个哈希表 `cnt` 维护「值 → 出现次数」，判据直接看 `max(cnt) − min(cnt) > 2`。
4. **最优解**：见「三、代码实现」——**每轮均摊 O(1)**，总时间 O(n)，额外空间 O(1)（`cnt` 的键数有常数上界）。

### 关键点

- **`right − left + 1` 的含义**：收缩结束后 `nums[left..right]` 是「以 `right` 结尾的最长合法窗口」，以 `right` 结尾的合法子数组恰好是它的 `left..right` 共 `right − left + 1` 个（长度 1 ~ 窗口长）。所以答案 = 每个右端点上的窗口长度之和。
- **窗口内元素可以很多，但「不同的值」最多 3 个**：合法窗口值域 ≤ 2 且元素都是整数 ⇒ 取值只能落在一个长度 ≤ 3 的整数区间里；再加上正在判定的新元素，`cnt` 最多 4 个键。**这才是 `min(cnt)` / `max(cnt)` 能当 O(1) 用的真正原因** —— 它扫的是「键」，不是「窗口元素」。

  > 这也是本题最反直觉的一点：复杂度分析里的 O(1) 来自**值域有界**，不是来自「窗口很短」。若题目把 2 放大到 10⁹，同一份代码的 min/max 扫描就退化，必须换单调队列。

- **截图里那条判据是「条件等价」而非「无条件等价」**：`abs(j - min(cnt)) > 2 or abs(j - max(cnt)) > 2`（`j = nums[right]`，且此时 `cnt` 已包含 `j`）**并不**等同于 `max(cnt) − min(cnt) > 2`。反例状态：窗口为 `[1, 4, 2]`（`j = 2` 落在内部），跨度 3 > 2，但 `|2−1| = 1`、`|2−4| = 2`，两式全假 ⇒ 漏判。

  它之所以在本题成立，靠的是一条**归纳不变量**：每轮 `while` 结束时窗口都合法，所以「加入 `j` 之前的旧窗口跨度 ≤ 2」。于是：
  - 若 `j` 落在旧窗口值域**内部** ⇒ 新窗口就是旧窗口，跨度 ≤ 2，两式必为假（因为 `j − min ≤ max − min ≤ 2`）；
  - 若 `j` 是**新的最大/最小值** ⇒ 两式中恰有一式等于新跨度 − 2，与「跨度 > 2」完全等价。

  ⇒ 这条判据只在「**上一轮窗口一定合法** + `j` 位于窗口末尾」的前提下可靠。一旦把收缩方式改掉（例如 `while` → `if`），窗口可能残留非法状态，前提就没了（见「六、易错点」第 2 条）。

- **`del cnt[x]` 是承重的，不是洁癖**（实测见「七、验证记录」）：计数归零却不删键，`min`/`max` 会读到**已经滑出窗口的值**，判据被这个幽灵键持续触发，`left` 会被一路推到 `right` 之外 ⇒ `nums[left]` 直接 `IndexError`。实测 30 组随机用例中有 26 组抛异常，官方示例 `[5,4,2,4]` 也抛。

## 三、代码实现

### 最终代码

```python
from collections import defaultdict
from typing import List


class Solution:
    def continuousSubarrays(self, nums: List[int]) -> int:
        ans = left = 0
        cnt = defaultdict(int)          # 窗口内 值 -> 出现次数
        for right, j in enumerate(nums):
            cnt[j] += 1
            # j 在窗口内、且上一轮窗口合法（归纳不变量）=> 这两式等价于 max(cnt)-min(cnt) > 2
            while abs(j - min(cnt)) > 2 or abs(j - max(cnt)) > 2:
                cnt[nums[left]] -= 1
                if cnt[nums[left]] == 0:
                    del cnt[nums[left]]   # 必须删键，否则 min/max 会读到窗口外的值
                left += 1
            ans += right - left + 1       # 以 right 结尾的合法子数组个数
        return ans
```

> **来源说明**：以上为用户本人提交并通过的版本（截图 1~13 行完整、末行是 `return ans`，无裁切）。截图里只有 `class Solution`，`defaultdict` 与 `List` 的 import 为**补全**（让笔记里的代码可直接运行），未改动任何算法逻辑。
> `abs(j - min(cnt)) > 2 or abs(j - max(cnt)) > 2` 的等价性与 `del` 的必要性均见「二、关键点」，两者都由本题自身推出，未与其他题目类比。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) 均摊 | O(1) |
| 朴素解法（枚举 + 增量维护最值） | O(n²) | O(1) |
| 理论下界 | Ω(n) | O(1) |

> 复杂度中的 n 指数组 `nums` 的长度（不是值域大小）。

- **时间 O(n)**：`left` 全程只增不减、最多推进 n 次，所以内层 `while` 的**总**执行次数 ≤ n；每轮判据求值只遍历 `cnt` 的键，而键数 ≤ 4（合法窗口至多 3 种取值 + 新元素）⇒ 每轮均摊 O(1)。
- **空间 O(1)**：`cnt` 的键数有常数上界 4；除此之外只有几个标量。注意这**不是**「O(窗口长度)」——窗口长度本身可以是 O(n)，但不同取值个数被值域卡死在 3。
- **理论下界**：末尾插入一个远值（如 `nums = [1,2,3,10^9]`）会把窗口从 4 压到 1，说明**每一个元素都可能实质影响答案**，任何算法都必须完整读一遍输入 ⇒ Ω(n) 不可突破。空间上 O(1) 已达成，也无须更多（单调队列版同样是 O(1)）。

## 五、优化评估

**结论**：时间与空间**都已到达理论下界**，大 O 无可再优化；但**常数层面还有空间**——把判据改写成窗口值域跨度（一行改动），实测四种输入全部更快（1.08×~1.19×）。

### 瓶颈分析

n = 10⁵ 时总耗时 0.029~0.066 s，即每元素 0.3~0.7 µs，已经**全是解释器层面的固定开销**，算法层面没有浪费。热点按顺序是：

1. 每轮一次判据求值：`min(cnt)` 与 `max(cnt)` 各一次 C 层遍历（键数 ≤ 4，常数很小）+ 两次 `abs` + 一次 `or` 短路判断；
2. `cnt[j] += 1`（dict 写入，`defaultdict` 的 `__missing__` 回退）；
3. 收缩时的 `cnt[...] -= 1` + 比较 + 条件性 `del`。

**没有可去掉的环节，只有更小的常数**：`abs()` 是两次函数调用，`or` 短路还要多一次分支；而判据本身只需要一次减法 + 一次比较。

### 为什么不直接上单调队列

这类题的教科书最优解是**双单调队列**维护窗口最大/最小值（每元素进出各一次，均摊 O(1)）。但本题的 `min`/`max` 本来就只扫 ≤ 4 个键，**常数小到不足以被 deque 的固定开销盖过**，实测结果并不全场景更快：

| 场景（n = 10⁵，9 次轮转取最优，单位 s） | 最终代码 | 单调队列版 | 判据改为值域跨度 | 单调队列提速 | 改判据提速 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 随机 · 值域 1e9（窗口极短、频繁收缩） | 0.0663 | 0.0426 | 0.0605 | **1.56×** | 1.10× |
| 随机 · 值域 {1,2,3}（窗口长、几乎不收缩） | 0.0352 | 0.0384 | 0.0296 | 0.92× | **1.19×** |
| 交替 1 / 1e9 | 0.0646 | 0.0424 | 0.0600 | **1.52×** | 1.08× |
| 全等值 | 0.0287 | 0.0314 | 0.0248 | 0.91× | **1.16×** |

> 「提速」列 = 最终代码耗时 ÷ 该版本耗时，**> 1 表示比最终代码快**。同一轮实验中 A / B / E 三种实现交替测量，避免机器状态漂移。

- 单调队列的收益（省掉每轮 min/max 扫描）只在**值域宽、窗口普遍很短**时兑现（1.5×）；窗口长时 `min`/`max` 只扫 1~3 个键，省下的钱还不够付每轮 4 次 deque 操作的账，于是**反而慢约 9%**。
- 「改判据」这一类改动则是**全场景不亏**：去掉两次 `abs` 与 `or` 短路，四种输入都快了 8%~19%。

### 优化代码

```python
from collections import defaultdict
from typing import List


class Solution:
    def continuousSubarrays(self, nums: List[int]) -> int:
        ans = left = 0
        cnt = defaultdict(int)
        for right, j in enumerate(nums):
            cnt[j] += 1
            while max(cnt) - min(cnt) > 2:      # 窗口值域跨度，判据本身就等价于合法性
                cnt[nums[left]] -= 1
                if cnt[nums[left]] == 0:
                    del cnt[nums[left]]
                left += 1
            ans += right - left + 1
        return ans
```

**优化理由**：

1. **常数更小**：判据变成「一次减法 + 一次比较」，省掉两次 `abs` 调用与 `or` 的短路分支。实测 1.08×~1.19×（四种输入全部更快）。
2. **正确性加固（顺带的好处）**：`max(cnt) − min(cnt) > 2` 对**任意窗口**都成立，不再依赖「上一轮窗口必合法」这条归纳前提 —— 它是原写法的**无条件版本**（原写法是它的一个「前提成立时才可用」的加速变体）。
3. 小批量对拍：30 组随机（`n ≤ 20`）+ 11 条手工用例，与暴力基准偏差 0，无异常。

### 常数级优化（可选）

以下单调队列版**按场景选用**：值域宽、窗口普遍很短时更快（实测 1.5×），其余场景不如上面的 dict 版。

```python
from collections import deque
from typing import List


class Solution:
    def continuousSubarrays(self, nums: List[int]) -> int:
        ans = left = 0
        maxq = deque()      # 下标，对应值单调递减
        minq = deque()      # 下标，对应值单调递增
        for right, x in enumerate(nums):
            while maxq and nums[maxq[-1]] <= x:
                maxq.pop()
            maxq.append(right)
            while minq and nums[minq[-1]] >= x:
                minq.pop()
            minq.append(right)
            while nums[maxq[0]] - nums[minq[0]] > 2:
                left += 1
                if maxq[0] < left:
                    maxq.popleft()
                if minq[0] < left:
                    minq.popleft()
            ans += right - left + 1
        return ans
```

**适用条件**：值域大、合法窗口普遍很短的输入（此时 `cnt` 的键数优势消失，而 deque 的「每元素进出一次」不受值域影响）。若值域上限放宽（如把 2 改成 5×10⁵），窗口内不同取值数量不再有常数上界，**本版就是唯一正确的选择**，dict 版的 min/max 会退化成 O(窗口长度)。

## 六、易错点与总结

### 易错点

1. **`del cnt[...]` 不能省**（有实测）：计数归零仍留着键，`min`/`max` 会一直读到那个**已滑出窗口的值**，判据被幽灵键持续触发，`left` 被推到 `right` 之外 ⇒ `IndexError: list index out of range`。实测 30 组随机用例 **26 组抛异常**；官方示例 `[5,4,2,4]` 也抛，而 `[1,2,3]` 因为「全程不需要收缩」侥幸返回正确值 6 —— 这种「小样例看不出问题」正是它容易被误删的原因。
2. **`while` 改成 `if`（平移版）会算错**：滑窗题里常见一招是「左指针每轮最多前进一格」，靠「窗口长度单调不减」保证答案仍对。**本题不适用** —— 本题答案不是「某个窗口的长度」，而是**各右端点窗口长度之和**；窗口残留非法状态时，那一段非法长度照样被累加进去，答案偏大。
   - 最小反例 `nums = [1, 1, 4]`：真值 4（三个单元素 + `[1,1]`），平移版实得 5 —— 在 `right = 2` 处窗口只收缩了一格变成 `[1,4]`（跨度 3，非法），却按长度 2 累加。
   - 小批量对拍：30 组随机用例中 **14 组出错**，且都是偏大。
3. **判据的等价性是有前提的**：`abs(j - min) > 2 or abs(j - max) > 2` 只在「加入 `j` 之前窗口合法」时等价于值域跨度判据；例如状态 `[1, 4, 2]`（`j = 2` 落在内部）跨度为 3 却漏判。**换收缩方式前先回到 `max(cnt) - min(cnt) > 2`**，别把带前提的加速写法当通用判据用。
4. **`min(cnt)` / `max(cnt)` 取的是键（值），不是计数**：写成 `min(cnt.values())` 语义就完全变了（那是「最少出现几次」，恒 ≥ 1，判据永远为假）。
5. **答案要加 1**：每轮贡献是 `right - left + 1`（子数组非空），漏掉 `+ 1` 会把所有单元素子数组丢掉。

### 题型套路沉淀

- **判据族定位：本题属「窗口内值域受限（max − min ≤ K）」族**。同族成员的合法性只看窗口**极值**，与「窗口内元素求和受限（Σ ≤ K）」「窗口内元素出现次数受限（某值计数 ≤ K）」是**不同的两族**：后两族的约束是**可加/可数**的，可以在移动指针时增量维护；而值域约束在元素进出时需要维护**最大值与最小值**这一对结构（单调队列，或本题这种「值域小 ⇒ 用计数表取极值」）。写代码前先确认属于哪一族，判据不要串用。
- **「值域有界」是滑窗里的一个甜点条件**：它让「窗口长度」与「窗口内不同取值个数」解耦 —— 长度可以是 O(n)，不同取值却被卡死在 3 种。凡是需要「窗口内不同值」「窗口极值」的题，先看值域上界能不能给出这个常数上界；能给，哈希表就够了，不必上单调队列。
- **双指针的准入条件要显式检查**：约束对「删左端元素」封闭（合法只可能保持合法）⇒ `left` 单调 ⇒ 总移动 O(n)。若约束不是这种形式（例如允许负数权重后和不再单调），滑窗立即失效。
- **收缩方式必须与答案口径配套**：本题唯一安全的组合是「`while` 收缩到合法」+「每轮累加窗口长度」。把 `while` 换成 `if` 时，一定要重新推导答案口径是否还成立，而不是照搬别的题的结论。

1. **官方示例（用于确认暴力基准本身无误）**：`[5,4,2,4] → 8`、`[1,2,3] → 6`，两个基准实现均通过。

   | 变体 | 偏差组数 | 异常组数 | 结论 |
   | :--- | :--- | :--- | :--- |
   | 单调队列版（第五节可选版） | 0 / 30 | 0 | 正确 |
   | 判据改为值域跨度版（第五节优化版） | 0 / 30 | 0 | 正确 |
   | `if` 平移版（易错点 2） | 14 / 30 | 0 | **错**，最小反例 `[1,1,4]`（真值 4，实得 5） |
