# 2730. 找到最长的半重复子字符串

> **难度**：中等
> **标签**：字符串 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/find-the-longest-semi-repetitive-substring/

---

## 一、题目描述

给定一个只含数字字符的字符串 `s`。称字符串 `t` 是**半重复的**，当且仅当 `t` 中「相邻且相等的字符对」**至多有一对**。例如 `"0010"`、`"002020"`、`"0123"`、`"2002"`、`"54944"` 都是半重复的，而 `"00101022"`（含 `00`、`22` 两对）不是。求 `s` 中最长半重复**子串**的长度。

### 示例

```text
输入：s = "52233"
输出：4
解释：最长的半重复子字符串是 "5223"（只含 22 一对）；整个串有两对 22 和 33，最多只能取一对。

输入：s = "5494"
输出：4
解释：s 本身就是半重复字符串。

输入：s = "1111111"
输出：2
解释：最长的半重复子字符串是 "11"；"111" 已含两对，最多允许一对。
```

### 约束条件

- `1 <= s.length <= 50`
- `'0' <= s[i] <= '9'`

---

## 二、解题思路

### 核心思想

**把「至多一对相邻相等」当成窗口的一格代价预算，用滑窗维护预算消耗。** 记 `cnt` = 窗口内相邻且相等的字符对数，右端每进一个字符只在**新增的那一个邻位**上 `+1`，`cnt` 涨到 2 就收缩左端，回到预算内。

### 思路演进

1. **暴力解法**：枚举所有子串 `s[i..j]`，对每个子串重新数一遍相邻相等对数，取合法的里面最长的一个 —— O(n³)。固定左端 `i`、右端 `j` 向右扩展时增量维护 `cnt`（只在 `s[j] == s[j-1]` 时 `+1`），可以降到 O(n²)：一旦 `cnt > 1` 就 `break`。
2. **瓶颈定位**：O(n²) 里绝大多数枚举是**重复验证**。因为「至多一对」这个约束对**左端前缀封闭** —— 把一个合法窗口再砍掉左边一个字符，绝不会变非法。所以对每个右端点 `r`，满足约束的左端点必然构成 `[L(r), r]` 一段连续区间，且 `L(r)` 单调不减；一旦确定 `L(r)`，所有更小的 `i` 全都不用再看。第二个瓶颈是：若每个窗口都重新数一遍 `cnt`，又把「扫过就不会再变」的局部信息重算了 n 遍 —— 相邻字符是否相等是**固定的**，窗口滑动时它只会被整体加进来或整体剔出去。
3. **关键转化**：把 `cnt` 做成**增量量**。右端扩展一个字符，代价只可能来自新暴露的邻位 `(s[r-1], s[r])`；左端右移一格，代价只可能减少在被丢掉的邻位 `(s[left], s[left+1])` 上。于是每步都是 O(1)，而左指针全程只前进 n 次 ⇒ 摊还 O(n)。**原来不行是因为对每个子串重复统计；现在行是因为代价可增量维护，且单调性保证左指针永不回头。**
4. **最优解**：用户代码（见下）—— `while cnt == 2` 把窗口收缩回合法、每轮更新答案，时间 O(n)、空间 O(1)。把「逐格收缩」换成「一次跳转」可再省一截常数（见「五、优化评估」）。

### 关键点

- **判据**：窗口合法 ⟺ `cnt`（窗口内相邻相等对的数量）`<= 1`。
- **代价的单位是「相邻位」不是「元素」**：窗口有 `L` 个字符时邻位只有 `L-1` 个。本题最容易翻车的就是这个差 1 —— 用户代码用 `for right, j in enumerate(s[1:])` 遍历，`right` 是**偏移后的下标**（真实右端点 = `right + 1`），所以窗口长度写的是 `right - left + 2`。这不是笔误，但换写法时最容易漏。
- **单调性从哪来**：每个邻位贡献 0 或 1，非负；左端右移只可能让 `cnt` 变小 ⇒ 固定右端时 `cnt` 随 `left` 右移**单调不增** ⇒ 双指针成立。若代价允许为负，这条就断了，得换前缀和 + 单调队列一类的结构。
- **内层 `while` 是摊还 O(1)**：左指针整趟总共只前进 n 格，均摊到每轮 ≤ 1 格。想用 O(log n) 的查找去替换它是负优化。
- `ans = 1` 的初值**不是冗余**：`n = 1` 时循环体一次都不执行，若初值取 0 会返回 0。

## 三、代码实现

### 最终代码（用户代码，截图转录）

```python
class Solution:
    def longestSemiRepetitiveSubstring(self, s: str) -> int:
        cnt = left = 0
        ans = 1
        for right, j in enumerate(s[1:]):
            if j == s[right]:
                cnt += 1
            while cnt == 2:
                if s[left] == s[left + 1]:
                    cnt -= 1
                left += 1
            ans = max(ans, right - left + 2)
        return ans
```

> 截图里没有 `import`，这段代码本身也不需要（`enumerate`、`max` 都是内建），可直接提交。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) | O(1) |
| 朴素解法（枚举子串 + 每次重数） | O(n³) | O(1) |

> 复杂度中的 n 指字符串 `s` 的长度（字符数）；内层 `while` 的摊还代价为 O(1)，理由见「关键点」。

## 五、优化评估

**结论**：时间复杂度已到理论下界，空间 O(1) 也不可能更省；但**常数层面仍有可观优化空间** —— 把「逐格收缩」改成「一次跳转」，实测提速 1.09x ~ 1.84x。

### 瓶颈分析

用户版每轮多出来的是 `while` 里那一格一格试探左边界的工作。它的总次数是摊还 O(n)（左指针整趟只走 n 格），所以**大 O 上无懈可击**；但每一次循环体都要做「取下标 → 比较两个字符 → `left += 1` → 重新判条件」这一串 Python 层动作，而任务本质只是「把 `left` 推到上一对相邻相等字符的右端点」—— 这个位置完全可以**直接算出来**，不必试。

n = 20000 正实测量化：最坏场景（全相同字符）用户版 3.39 ms，跳转版 2.01 ms，前者多出的 1.38 ms 全是 `while` 的试探开销（占用户版耗时 41%）。剩下的约 2 ms 是纯 Python 逐字符循环的固有成本（每轮一次 `enumerate` 取值、一次字符比较、一次 `max()` 调用），删不掉 —— 这就是本题在 CPython 下的天花板，优化的余地到 1.69x 为止。

### 优化代码（一次跳转版）

```python
class Solution:
    def longestSemiRepetitiveSubstring(self, s: str) -> int:
        n = len(s)
        ans = 1                   # n >= 1，单字符本身就是半重复
        left = 0
        last_pair = -1            # 上一对「相邻相等」的右端点下标
        for i in range(1, n):
            if s[i] == s[i - 1]:          # 新暴露了一个相等邻位
                if last_pair != -1:       # 窗口里已经有一对了 → 必须丢掉更早的那对
                    left = last_pair
                last_pair = i
            ans = max(ans, i - left + 1)
        return ans
```

**优化理由**：用户版的 `while` 逐格收缩，效果等价于「把 `left` 一路推到上一对相等字符的右端点」（推到 `left = p1` 时，边界邻位 `(p1-1, p1)` 被剔除，`cnt` 从 2 掉回 1，循环正好退出）。既然 `p1` 就是上一轮的 `last_pair`，直接赋值即可，省掉整段试探。

**这不是近似改写，而是精确等价**：实测把两版的**逐轮状态序列**（每轮结束时的 `left` 与 `ans`）摆在一起比对，84,133 组穷举 + 100,000 组随机共 184,133 组，差异 **0 组**。跳转版的窗口也不再需要「收缩到合法为止」这一步 —— 它的窗口天然只含一对。

### 实测提速表

n = 20,000，轮转测量、每档取 9 次最优（避免机器状态漂移）；真实约束 `n <= 50`，本表属泛化研究。

| 场景 | 用户版 while+max | 一格平移版 | 跳转版 | 跳转版提速 |
| :--- | :--- | :--- | :--- | :--- |
| 全相同（`0000…`，最坏） | 3.39 ms | 3.18 ms | 2.01 ms | **1.69x** |
| 两两相同（`0011` 循环） | 3.21 ms | 2.96 ms | 1.84 ms | **1.74x** |
| 周期 `0101` | 2.02 ms | 2.03 ms | 1.85 ms | 1.09x |
| 无相邻对（10 进制循环） | 2.07 ms | 2.07 ms | 1.88 ms | 1.10x |
| 随机 `0-9` | 3.25 ms | 2.99 ms | 1.77 ms | **1.84x** |

规律：**跳转版在「相等邻位多」的场景赚得最多**（试探的那一格被彻底省掉），在本来就没什么可跳的场景只赚 10% 左右；一格平移版则基本不赚（1.00x ~ 1.09x），却带了个隐藏陷阱（见易错点 2）。

### 常数级优化（可选）

- 跳转版每轮只剩「一次字符比较 + 一次 `max()` 调用」。`max()` 是函数调用，理论上可换成 `if` 三行，但 `n <= 50` 的量级上收益为 0，只会牺牲可读性 —— **不建议改**（本条未做实测，仅作方向说明）。
- 用户版的 `while cnt == 2` 与 `while cnt > 1` 在本写法下**等价**（`cnt` 每轮至多 +1、进循环时必为 2）：实测 G 变体 0/18,030 错。但仍然建议写 `cnt > 1` —— 它不依赖「每轮只加一个字符」这个前提，更不容易被后续改动弄碎。

## 六、易错点与总结

### 易错点

1. **下标口径错位**：`enumerate(s[1:])` 里的 `right` 是偏移下标，长度必须写 `right - left + 2`。改成 `+ 1` 会整体少 1 —— 用示例一（`"52233"`）一测就露馅（会返回 3）。
2. **`while` 换成 `if` 时判据不能随手写**。改成「每轮只收缩一格」是允许的，但条件必须用**整个窗口**的度量 `cnt > 1`；若写成看着等价的 `cnt == 2` 就会出事：一格平移版的窗口会连续多轮处于非法状态，`cnt` 会累积到 3 甚至 11，`cnt == 2` 再也触发不了，窗口越滑越长、报出非法长度。实测量化：宽搜索空间 284,133 组里 **60.73% 出错**，最小反例 `s = "10000"`（真值 3、实得 4 —— 窗口滑到 `[1,4] = "0000"`，里面已经有 3 对相等，却按长度 4 记了答案）。
3. **「每轮取 max」和「取终值 `n - left`」不能随便换**，这取决于收缩方式：

   | 收缩方式 | 窗口长度序列 | 答案口径怎么取 | 实测结果 |
   | :--- | :--- | :--- | :--- |
   | 收缩到合法（`while` / 一次跳转） | **可下降** | **只能**每轮取 `max` | 取终值实测 46.64% 错，最小反例 `"1000"`（真值 3、实得 2） |
   | 每轮只挪一格（`if` 平移版） | 单调不减 | 两种口径都对 | 均为 0/284,133 |

   ⇒ **真正会错的是"只改一半"**：把 `while` 换成 `if` 却不改口径、或保留 `while` 却改用终值口径，都会翻车。
4. **平移版"看着更省一个变量"，代价是窗口长期非法**：实测 603,928 轮里有 **380,172 轮（62.95%）** 窗口内 `cnt > 1`，最长连续非法 57 轮，`cnt` 峰值 11。它能给出正确答案靠的是「长度只在合法轮次增长」+「长度单调不减」，**不是**「窗口始终合法」。这类写法的正确性属**实测等价、未给严格证明**：复用前必须先穷举验证，别直接搬到别的题上。本题既然跳转版更快也更清晰，没必要用它。
5. **删掉 `while` 里的 `cnt -= 1` 会直接崩**：`cnt` 只增不减，`while` 会一直收缩到左指针越界，宽空间里 82.10% 的用例抛异常（最小触发例 `"000"`）。这一行不是装饰。

### 题型套路沉淀

- **「窗口内度量 ≤ 预算」型滑窗**的通用前提：度量**逐个单位累加、每个单位非负** ⇒ 固定右端时度量随左端右移单调不增 ⇒ 双指针成立。识别信号：题面出现「至多 k 个」「最多翻转 k 次」「代价 / 预算」。
- 上手这族题固定走四步，任一步偷懒就会掉进上面的坑：① 定义代价的**单位**（元素？相邻位？字符种类？）→ ② 写出右端加什么、左端减什么 → ③ 决定用 `while`（收缩到合法）还是 `if`（只挪一格）→ ④ **配套**决定答案口径。③④ 必须成对选，不能各改一半。
- **左指针「逐格推」与「一跳到位」绝大多数时候等价，一跳版通常更快**（本例 1.09x ~ 1.84x），但替换前必须先用穷举验证逐轮状态等价。

## 七、验证记录

### 1) 官方示例断言

`52233 → 4`、`5494 → 4`、`1111111 → 2`，**3/3 通过**；另测 `n = 1`（`s = "7"`）→ 1。

### 2) 基准自检

用**完全独立**的 O(n³) 暴力（枚举所有子串 + 对每个子串重新扫一遍数相邻对）核验 O(n²) 基准：字母表 `{0,1,2}`、`n <= 8` 全枚举 **9,840 组**，两者偏差 **0**。

### 3) 随机对拍（用户代码 vs O(n²) 暴力）

1,500 组（`n <= 40`，字母表 2 / 3 / 10），**偏差 0**。退化边界专测 8 项，全部一致：`n = 1`、全相同 `n = 40`、全相同 `n = 2`、无相邻对 `n = 40`、`"0011"`、`"1111111"`、`"00110"`、`"01234567890"`。

### 4) 插桩量化（3,000 组随机，逐轮核对）

- `cnt` 恒等于窗口内相邻相等对的**真实数量** —— 违反 **0** 次；
- 每轮取答案前窗口恒合法（`cnt <= 1`）—— 违反 **0** 次；
- `right - left + 2` 恒等于实际窗口长度 —— 违反 **0** 次。

⇒ 用户代码的**中间状态每轮都满足约束**，答案不是靠"口径兜住非法状态"得来的。

### 5) 「收缩方式 × 答案口径」穷举

字母表 `{0,1}`（`n <= 12`）+ `{0,1,2}`（`n <= 8`），共 **18,030 组**。

| 变体 | 出错率 | 最小反例 |
| :--- | :--- | :--- |
| A `while` + 每轮 max（**用户版**） | 0.00% | — |
| B `while` + 终值 `n-left` | 46.64% | `"1000"`：真值 3、实得 2 |
| C `if(cnt>1)` + 每轮 max | 0.00% | — |
| D `if(cnt>1)` + 终值 `n-left` | 0.00% | — |
| E 一次跳转 + 每轮 max | 0.00% | — |
| F 一次跳转 + 终值 `n-left` | 46.64% | `"1000"`：真值 3、实得 2 |
| G `while cnt == 2` + 每轮 max | 0.00% | — |
| H 删掉 `while` 内 `cnt -= 1` | 82.10% | `"000"`：越界抛异常 |

### 6) 宽空间复测

`{0,1} n <= 14` + `{0,1,2} n <= 9` + `{0,1,2,3} n <= 7` 共 **84,133 组穷举** + **200,000 组随机**（`n <= 60`）：

- 用户版、跳转版：**0 错**；
- `if(cnt>1)` 版（取 max 与取终值两种口径）：各 **0/284,133 错**；
- **`if(cnt==2)` 版：172,550/284,133 = 60.73% 出错**，最小反例 `"10000"`（真值 3、实得 4）。

### 7) 逐轮等价性（用户版 vs 跳转版）

84,133 组穷举 + 100,000 组随机，共 **184,133 组**比对每轮的 `(left, ans)` 序列：差异 **0 组** ⇒ 两版是精确等价改写。

### 8) 平移版非法率

20,000 组随机（`n <= 60`）共 **603,928 轮**，其中窗口仍非法（`cnt > 1`）**380,172 轮 = 62.95%**，最长连续非法 **57 轮**；`{0,1}` 字母表下 `cnt` 峰值 **11**（`n <= 60`）。

### 9) 微基准

n = 20,000，轮转测量、9 次取最优（见「五、优化评估」的提速表）。结论：跳转版 1.09x ~ 1.84x；一格平移版 1.00x ~ 1.09x（不赚）。
