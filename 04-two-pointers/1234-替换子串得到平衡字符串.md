## 一、题目描述

给定一个只含 `Q`、`W`、`E`、`R` 四种字符、长度为 `n` 的字符串 `s`。若四种字符各出现恰好 `n/4` 次，则称它是「平衡字符串」。

允许把 `s` 的**一个子串**整体替换成**长度相同的任意字符串**，求使结果变为平衡字符串所需的**最小子串长度**；若 `s` 本身已平衡则返回 `0`。

### 示例

```text
输入：s = "QWER"
输出：0
解释：s 已经平衡了。

输入：s = "QQWE"
输出：1
解释：把一个 'Q' 替换成 'R'，得到 "RQWE"（或 "QRWE"）。

输入：s = "QQQW"
输出：2
解释：把前面的 "QQ" 替换成 "ER"，得到 "ERQW"。

输入：s = "QQQQ"
输出：3
解释：替换后 3 个 'Q'，使 s = "QWER"。
```

### 约束条件

- `1 <= s.length <= 10^5`
- `s.length` 是 `4` 的倍数
- `s` 中只含有 `'Q'`、`'W'`、`'E'`、`'R'` 四种字符

## 二、解题思路

### 核心思想

**把「被替换的子串」当成窗口，判据落在窗口外：窗口外每种字符的出现次数都 ≤ n/4 时，窗口内就一定填得满。** 而「合法」这个性质对窗口扩张单调，于是能用双指针滑窗求最短。

### 思路演进

1. **朴素解法**：枚举所有子串 `[l, r]`（共 O(n²) 个），对每个子串统计「窗口外」四种字符的计数，判断是否都 ≤ n/4。单次判定只要 O(1)（只有 4 种字符），总时间 O(n²)。n = 10^5 时约 5×10^9 次操作，必然超时。

2. **观察到**：慢的不是「判定」，而是**候选区间的数量**。右端右移一格，变化的只是「有 1 个字符从窗口外移进窗口内」—— 合法与否完全可以增量维护，一次 O(1)。也就是说：**判定成本不是瓶颈，枚举空间才是。**

3. **关键转化**：抓住两条性质，把 O(n²) 个候选压到 O(n) 个。

   - **判据（充要）**：窗口 `[l, r]` 合法 ⟺ 窗口外每种字符的计数 `out(c) <= k`（`k = n/4`）。
     - *必要性*：窗口外的字符改不了。若某个 `out(c) > k`，则无论窗口里填什么，`c` 的总数都会超过 `k`。
     - *充分性*：设窗口长度为 `w`，则窗口内需要补 `k - out(c)` 个字符 `c`。而 `Σ(k - out(c)) = 4k - Σout(c) = 4k - (n - w) = w`，**恰好等于窗口长度**，所以每种缺口都补得上，不会多也不会少。
   - **单调性**：窗口只扩大不缩小时，每个 `out(c)` 单调不增 ⇒ 判据**一旦成立，继续扩大仍然成立**。于是固定右端 `r` 时，合法的左端恰好构成一段前缀 `[0, L(r)]`，且 `L(r)` 随 `r` **单调不减**。求「最短合法窗口」，等价于对每个 `r` 把左端**尽量往右推到刚好还合法**，此时窗口 `[l, r]` 就是该 `r` 下的最短合法窗口。
   - 一句话：**原来不行是因为要枚举 O(n²) 个区间；现在行是因为「合法」对扩张单调，最短窗口只用两个单向移动的指针就能枚举完。**

4. **最优解**：维护 `cnt` = **窗口外**各字符的计数，初始为整个字符串的计数（窗口为空）。右端 `right` 推进时 `cnt[s[right]] -= 1`（该字符进入窗口）；随后 `while` 判据成立：记录长度 `right - left + 1`，再 `cnt[s[left]] += 1`、`left += 1`（把左端吐回窗口外）。时间 O(n)。

### 关键点

- **判据写在「窗口外」，不是「窗口内」**。判据要的是「窗口外是否超标」，直接从外部计数写就是一行；若从内部写，得先用总数与 `k` 反推出每个字符的缺口（`need(c) = max(0, total(c) - k)`），多一层转换、也更容易漏掉字符串里根本没出现过的字符。
- **必须单独处理「已经平衡」**。因为 `Σ out(c) = n = 4k`，「每种都 ≤ k」等价于「每种都恰好 `== k`」，也就是原串已平衡 —— 此时**空窗口就是合法答案**（长度 0）。而滑窗模板的最小记录单位是 1，不提前 `return 0` 会输出 1。
- **内层 `while` 不会把复杂度推到 O(n²)**：左端每轮最多 +1、且从不回退，整趟累计只前进 n 次 ⇒ 内层摊还 O(1)/轮。
- 判据只查 4 个字符（`for c in "QWER"`），是严格 O(1)，与 n 无关。

## 三、代码实现

### 最终代码

```python
from collections import Counter


class Solution:
    def balancedString(self, s: str) -> int:
        n = len(s)
        k = n // 4
        cnt = Counter(s)                      # cnt = 窗口外各字符的计数（窗口初始为空）
        if all(cnt[c] == k for c in "QWER"):
            return 0                          # 已平衡：替换长度 0

        ans = n
        left = 0
        for right, ch in enumerate(s):
            cnt[ch] -= 1                      # 右端入窗：它不再属于「窗口外」
            while left <= right and all(cnt[c] <= k for c in "QWER"):
                ans = min(ans, right - left + 1)
                cnt[s[left]] += 1             # 左端出窗：吐回「窗口外」
                left += 1
        return ans
```

> `Counter` 取缺失的键会返回 `0`（且不落键），所以字符串里没出现过的字符天然满足 `0 <= k`，不必特判；`all(cnt[c] == k ...)` 同理。

## 四、复杂度分析

复杂度中的 `n` 指字符串 `s` 的长度（也是被计数的字符总数），`k = n / 4`。字符集固定为 4，故每次判据检查是 O(1)。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) | O(1) |
| 朴素解法（枚举子串） | O(n²) | O(1) |
| 理论下界 | O(n) | O(1) |

- **时间**：右端走 `n` 步；左端全程累计最多推进 `n` 次且不回退 ⇒ 内层 `while` 总执行次数 ≤ n，摊还 O(1)/轮 ⇒ 总计 O(n)。
- **空间**：只需 4 个计数器 ⇒ O(1)（不计输入本身）。
- **为什么不可能更好**：任何正确算法都必须至少把 `s` 读完一遍 —— 不读完就不知道某种字符的总数是否超过 `n/4`，也就无法判断最小窗口，故时间下界 Ω(n)，已达下界。空间方面，答案只依赖「窗口外 4 种字符的计数」，4 个整数既是信息量下限也是 O(1)，同样到顶。

## 五、优化评估

**结论**：**大 O 已是理论下界（时间 O(n)、空间 O(1)），只剩常数级空间可压。**

### 瓶颈分析

用 n = 10^5 的随机串实测，本篇「最终代码」耗时约 130 ms —— 这份开销几乎全在 1e5 轮里反复走 Python 层的哈希查表（`Counter.__getitem__`）与生成器 `all(...)`，而**不是**遍历次数：把同一套逻辑换成「4 个整型变量 + 展开的短路布尔判据」后，同样的遍历次数把耗时压到约 37 ms。⇒ 瓶颈在常数项，不在算法结构。

### 可优化空间

大 O 不变，只能压常数。实测两版（同机、同一批数据、9 轮轮转取最优；早退档另做 15 轮）：

| 场景（n = 10^5） | Counter 版 | 4 整型变量版 | 比值（后者 / 前者） |
| :--- | ---: | ---: | ---: |
| 随机串（几乎必须滑窗到底） | 130.4 ms | 36.7 ms | **0.28×** |
| 偏斜串（`Q` 占一半） | 68.6 ms | 19.1 ms | **0.28×** |
| 已平衡（两版都直接 `return 0`） | 3.6 ms | 6.6 ms | 1.83× |

- 需要真正滑窗时，整型变量版快约 **3.5 倍**，两档稳定复现（0.28×）。
- 但**早退档反而慢 1.83 倍**：那一档的时间几乎全花在「统计初始计数」上，`Counter(s)` 是 C 实现，而整型版要跑 1e5 次 Python 字典查表 + 分支。⇒ 只有在输入**频繁早退**的场景下整型版才吃亏。
- 想两头都要可以 hybrid：仍用 `Counter(s)` 做初始计数，再拆成 4 个整型变量维护窗口（此写法未实测，故不给数字）。

### 优化代码

以下为「常数级优化版」，同上表实测数据：

```python
class Solution:
    def balancedString(self, s: str) -> int:
        n = len(s)
        k = n // 4
        idx = {"Q": 0, "W": 1, "E": 2, "R": 3}
        cnt = [0, 0, 0, 0]
        for ch in s:
            cnt[idx[ch]] += 1
        if cnt[0] == k and cnt[1] == k and cnt[2] == k and cnt[3] == k:
            return 0

        ans = n
        left = 0
        for right in range(n):
            cnt[idx[s[right]]] -= 1
            while (left <= right and cnt[0] <= k and cnt[1] <= k
                   and cnt[2] <= k and cnt[3] <= k):
                ans = min(ans, right - left + 1)
                cnt[idx[s[left]]] += 1
                left += 1
        return ans
```

**优化理由**：把「字典 + 生成器 + 4 次 `__getitem__`」换成「list 下标 + 展开的短路布尔链」，剥掉哈希与迭代器的解释器开销；判据仍然只查 4 项，语义与最终代码完全一致。

### 常数级优化（可选）

- 判据展开成短路布尔表达式：四种字符只要有一个超标就立刻停。
- 提前 `return 0` 是唯一能让两版「打平」的分支，成本极低，务必保留。
- **不要**在 `while` 里写 `max(cnt.values()) <= k`：那是「构造视图 + 扫一遍」的隐藏常数，且语义上比展开判据多绕一层。

## 六、易错点与总结

### 本次首刷为什么没做出来（复盘）

截图里留下的原样代码（注意：整段可见代码从第 1 行 `class Solution:` 开始，**没有任何 import**）：

```python
class Solution:
    def balancedString(self, s: str) -> int:
        n = len(s) // 4
        ans = inf
        left = 0
        cnt = Counter(s)
        if len(cnt) == 4 and min(cnt.values()) == n:
            return 0
        for right, j in enumerate(s):
            cnt[j] -= 1
            while max(cnt.values()) <= n:
                ans = min(ans, right - left + 1)
                cnt[s[left]] += 1
                left += 1
        return ans
```

三段式诊断：

1. **思路其实是对的。** 它的骨架与本篇最终代码同构：`cnt` 维护窗口外计数、`max(cnt.values()) <= n`（此处的 `n` 即 `n/4`）就是本条判据、收缩方式也一样。把 `Counter` 和 `inf` 两个 import 补上后，把它当作对照变体纳入同一批小批量对拍（40 组随机 n ≤ 20 + 8 条手工边界），**偏差 0 组**。
2. **卡住的是书写/环境层面，不是算法层面。** `Counter` 与 `inf` 都没有定义 —— 缺 `from collections import Counter` / `from math import inf` 时，第 6 行就直接 `NameError`，代码根本没有机会跑起来。
3. **命名有误导性。** `n = len(s) // 4` 把「字符串长度」这个名字挪用给了「单字符目标次数」，读到后半段 `max(...) <= n` 时极易误以为是在和「串长」比较。建议拆成 `n = len(s)` / `k = n // 4`。

⇒ 二刷要练的不是「想不出判据」，而是**先把可运行的骨架写出来**（import、变量命名），再落算法。

### 易错点

- **判据写反在「窗口内」**：窗口内「缺什么」是由窗口外的计数决定的，从内部写必须先算 `need`；从外部写（`out(c) <= k`）一行就能判定，还天然覆盖「某个字符一个都没出现」的情况。
- **忘记单独处理「已经平衡」**：空窗口是合法答案（长度 0），但滑窗模板的最小记录单位是 1，不提前 `return 0` 会输出 1。
- **`max(cnt.values()) <= k` 的脆弱处**：`max()` 对空 `Counter` 会抛 `ValueError`。本题里 `Counter` 减法不删键、`cnt` 非空，所以不会触发；但这个写法本身比展开的 4 项判据脆，改用 `out(c) <= k` 的显式判据更稳。
- **误以为内层 `while` 会退化成 O(n²)**：左端全程累计只前进 n 次，摊还下来是 O(1)/轮。
- **别把「窗口内」和「窗口外」的计数混着维护**：二者互为补集（`in(c) = total(c) - out(c)`），但判据只在「窗口外」这一侧简单，混用容易在「某字符从未出现」时判断落空。

### 题型套路沉淀

- **「舍弃一段 + 剩余部分满足计数上限」型滑窗**的固定套路：
  1. 把「要替换 / 要丢弃的那一段」当成窗口，判据落在**窗口外**；
  2. 判据形如 `∀c: out(c) <= k`；
  3. 「窗口越大越容易满足」⇒ 固定右端后合法左端是一段前缀 ⇒ 用 `while 合法` 收缩求最短，答案取每轮的 `right - left + 1`。
- **识别信号**：题面出现「替换 / 删除 / 保留一部分，使剩余部分满足某个计数上限」，且这个上限对「丢元素」是**前缀封闭**的（丢元素只会让约束更容易满足）—— 前缀封闭 + 上限型，基本就是双指针滑窗。
- **一行判据的价值**：本题能把「能不能补齐」简化成「窗口外是否超标」，靠的是恒等式 `Σ(k - out(c)) = w`（因为 `n = 4k`，需要补位的总数必然等于窗口长度）。先写出这类恒等式，边界条件会自己浮上来：正是它同时证明了「判据充分」和「已平衡时答案为 0」。
