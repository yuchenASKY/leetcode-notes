# 1358. 包含所有三种字符的子字符串数目

> **难度**：中等
> **标签**：哈希表 · 字符串 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/number-of-substrings-containing-all-three-characters/

---

## 一、题目描述

给定一个只由 `a`、`b`、`c` 三种字符组成的字符串 `s`，返回其中 **`a`、`b`、`c` 都至少出现过一次** 的子串个数。子串按位置区分，内容相同的不同子串要分别计数。

### 示例

```text
输入：s = "abcabc"
输出：10
解释：以各左端点计——l=0 有 4 个（"abc"、"abca"、"abcab"、"abcabc"）、
      l=1 有 3 个（"bca"、"bcab"、"bcabc"）、l=2 有 2 个（"cab"、"cabc"）、
      l=3 有 1 个（"abc"，下标 3-5）。合计 4+3+2+1 = 10。

输入：s = "aaacb"
输出：3
解释："aaacb"、"aacb"、"acb"（左端点 0 / 1 / 2，右端点固定为 4）。

输入：s = "abc"
输出：1
```

### 约束条件

- `3 <= s.length <= 5 * 10^4`
- `s` 仅由字符 `'a'`、`'b'`、`'c'` 组成

---

## 二、解题思路

### 核心思想

**固定右端点 `r`，以 `r` 结尾的合法子串在左端点上恰好构成一段前缀 `[0, K_r]`** —— 于是每轮只需要求出分界线 `K_r`，`ans += K_r + 1`。滑动窗口维护的 `left` 就是"最小非法左端点"，收缩结束时它本身即 `K_r + 1`。

判据：

> 窗口 `[left, r]` 含全 `a`/`b`/`c` ⟺ `len(cnt) == 3`（`cnt` 为窗口内的字符计数）。

这是一个 **按键数**（不同字符的种类数）的判据 —— 记住这一点，它直接决定了要不要 `del` 键。

### 思路演进

1. **暴力解法**：枚举全部 O(n²) 个子串，每个用 `set(s[l:r+1])` 判断是否含三种字符 → O(n³)；改成增量维护字符集合可降到 O(n²)。但 `n = 5×10⁴` 时子串总数达 `1.25×10⁹`，即使每个子串 O(1) 判重也远超 1 秒预算。

2. **瓶颈定位**：浪费不在"判重"，而在"**把以同一个 `r` 结尾的左端点逐个枚举**"。而这些左端点的合法性其实是 **成段** 的：一旦 `[p, r]` 含全三种字符，那么所有更靠左的 `[p', r]`（`p' < p`）必然也含全三种 —— 因为把窗口往左扩只会让字符集合只增不减。**合法性对左端点前缀封闭**，逐个枚举纯属重复劳动，我们缺的只是那条分界线。

3. **关键转化**：把"求分界线"变成"**维护一条只会向右走的边界**"。令 `left` = 使 `[left, r]` **不含**全三种字符的最小下标。那么以 `r` 结尾的合法子串恰好有 `left` 个（左端点为 `0…left-1`）。
   *为什么原来不行、现在为什么行*：原来每个 `r` 都要独立扫一遍左端点；现在 `r` 右移只会让窗口更"富"，`left` 只增不减 —— 单调性一确立，就可以用一条不回退的指针在整趟 O(n) 里摊还出所有分界线。
   证明：`[left, r]` 不含全三种 ⟺ 存在某字符 `x` 在 `[left, r]` 内不出现 ⟺ `left > last_x`；故最小非法左端点 = `min(last_a, last_b, last_c) + 1`。这同时给出了一个闭式解（见「五、优化评估」）。

4. **最优解**：每轮把 `s[r]` 计入计数；`while len(cnt) == 3` 时说明窗口仍"含全三种"，左端点是合法左端点，需要右移 `left` 把它踢出窗口（计数归零就删键）；循环结束时窗口恰好缺至少一种字符，`left` 即分界线，`ans += left`。`left` 整趟最多移动 `n` 次 ⇒ 内层 `while` 摊还 O(1)，总时间 O(n)，额外空间 O(1)（`cnt` 至多 3 个键）。

### 关键点

- **`while` 的退出条件是"窗口非法"，不是"窗口合法"**。这与"最长无重复子串"那种"收缩到合法为止"的写法语义相反：这里是"收缩到恰好非法"，再用边界值 `left` 充当"合法左端点的个数"。写成"收缩到合法后 `ans += 窗口长度`"是错的（语义从"计数"变成了"取最长"）。
- **按键数判据 ⇒ 计数归零必须 `del` 键**。若省掉 `del`，`len(cnt)` 一旦涨到 3 就再也不会下降，`while` 会一直收缩到 `left` 越界。这是本题最容易踩的坑。
- `ans += left` 与 `left` 初值 0 天然配合：还没凑齐三种字符时 `left = 0`，贡献 0，无需对"前 k 个字符"做特判。
- 下标安全：`left` 只在 `len(cnt) == 3`（窗口非空）时自增，恒有 `left <= right < n`，不存在 `x - k` 型负下标风险。

## 三、代码实现

### 最终代码

```python
from collections import Counter


class Solution:
    def numberOfSubstrings(self, s: str) -> int:
        cnt = Counter()
        ans = left = 0
        for right, j in enumerate(s):
            cnt[j] += 1
            while len(cnt) == 3:
                cnt[s[left]] -= 1
                if cnt[s[left]] == 0:
                    del cnt[s[left]]
                left += 1
            ans += left
        return ans
```

> 说明：截图里的代码没有 `from collections import Counter`，此处已补全（补 import 仅为让笔记里的代码可直接运行）。
> 另外 `enumerate` 给出的 `right` 在函数体内并未被使用（循环体只用到字符 `j`），等价于 `for j in s:`，属可读性冗余，无功能影响。

## 四、复杂度分析

> 复杂度中的 `n` 指字符串 `s` 的长度。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码**（滑窗，摊还） | O(n) | O(1) |
| 末次出现位置版（优化版） | O(n) | O(1) |
| 朴素解法（枚举子串 + 增量集合判重） | O(n²) | O(1) |
| 朴素解法（枚举子串 + 每段重建 `set`） | O(n³) | O(n) |
| 理论下界 | O(n) | O(1) |

- **时间下界 Ω(n)**：必须读完全部输入才能知道任意位置何时出现第三种字符，无法低于一遍扫描。最终代码达到该下界。
- **空间 O(1)**：`cnt` 至多 3 个键；`left`/`ans` 为常数个变量。
- **摊还而非"内层循环 O(n)"**：内层 `while` 单轮最多可执行多次（见「六、易错点」的 `"ccba"` 等构造），但 `left` 全程单调不减、总量 ≤ n，故每轮摊还 O(1)。

## 五、优化评估

**结论**：时间复杂度 O(n) 已触理论下界，**大 O 层面无法再优化**；但常数项有约 4~6 倍的实测空间（把 O(n) 的滑窗收缩换成 O(1) 的闭式结算）。

### 瓶颈分析

最终代码每轮要做的事：`Counter` 取键 / 自增、`len(cnt)` 判断、以及内层 `while` 的逐格收缩（每次收缩又是一轮 `Counter` 取值、自减、判零、`del`）。其中 `while` 的**逐格**收缩是纯粹的过程代价 —— 而收缩的终点其实可以直接算出来：

> 以 `r` 结尾、左端点为 `p` 的子串含全三种字符 ⟺ `p <= min(last_a, last_b, last_c)`，其中 `last_x` 是字符 `x` 在 `[0, r]` 内最后出现的下标。

⇒ 合法左端点个数 = `min(last_a, last_b, last_c) + 1`，与滑窗版收缩后的 `left` 完全同值（后者就是把 `left` 逐格推到 `min(last) + 1`）。于是内层循环整段消失，每轮只剩 1 次写入 + 1 次 `min` + 1 次加法。

### 可优化空间

闭式版仍是 O(n) 时间 / O(1) 空间（只维护 3 个整数），属**同阶常数优化**，不是复杂度级改进。若要求"为什么不可能更好"：`ans` 的量级可达 Θ(n²)（如 `"abc"` 循环），但每步只做常数次加法，输出量级不构成额外代价，故 Ω(n) 就是终点。

### 优化代码

```python
class Solution:
    def numberOfSubstrings(self, s: str) -> int:
        la = lb = lc = -1
        ans = 0
        for right, ch in enumerate(s):
            if ch == 'a':
                la = right
            elif ch == 'b':
                lb = right
            else:
                lc = right
            ans += min(la, lb, lc) + 1
        return ans
```

**优化理由**：

- 与最终代码**语义完全等价**：`min(last_a, last_b, last_c) + 1` 恒等于滑窗收缩后的 `left`（已对拍，偏差 0，见「七、验证记录」）。
- 某字符尚未出现时 `la/lb/lc = -1` ⇒ `min(...) + 1 = 0`，贡献 0，与滑窗版"未凑齐时 `left = 0`"一致，**无需特判**。
- 每轮从"若干次 `Counter` 操作 + 不定次收缩"降到"1 次分支赋值 + 1 次 `min` + 1 次加法"，常数大幅下降。

### 常数级优化（可选）

同为闭式写法，容器选择也会影响常数（实测 `n = 5×10⁴`，9 轮取最优，单位 ms）：

| 场景 | 最终代码（滑窗） | 末次出现 · 字典 | **末次出现 · 三变量** | 末次出现 · 列表 |
| :--- | :--- | :--- | :--- | :--- |
| `random n=5000` | 2.30 | 0.70 | **0.53** | 0.73 |
| `random n=50000` | 23.02 | 7.13 | **5.35** | 7.30 |
| `cyclic "abc" n=49998` | 33.35 | 6.89 | **5.01** | 7.01 |
| `all-"a" n=50000`（窗口永不收缩） | 8.42 | 6.37 | **4.06** | 6.62 |
| **相对最终代码提速** | 1.00x | 3.23x | **4.30x** | 3.16x |

- 三个局部整数变量比"字典 / 列表 + `min(list)`"再快约 1.0~1.3 倍：省掉了哈希查找与容器对象创建。
- 第四行是**反向参照**：`all-"a"` 场景下窗口永远凑不齐三种字符、滑窗几乎不做收缩，此时最终代码只慢 1.32x —— 说明最终代码的额外开销主要来自"每轮维护 `Counter` + 收缩"，而不是判断本身。
- ~~`enumerate` 的 `right` 未使用，可删~~：实测与性能无关，纯可读性调整。

## 六、易错点与总结

### 易错点

- **省掉 `del cnt[s[left]]` ⇒ 死循环式越界**。本题判据是"不同字符种类数 == 3"（按键数），必须让键数能回落；漏掉 `del` 后 `len(cnt)` 只增不减，`while` 会把 `left` 一路推到 `n` 并越界。
- **把 `while` 换成 `if` 是错的**（本题内层需要连续收缩多格）。最小反例：`s = "ccba"` —— 真值 2（`"ccba"`、`"cba"`），`if` 版只得 1：`r = 3` 时窗口计数为 `{c:2, b:1, a:1}`，`if` 只把 `left` 从 0 推到 1（`c` 的计数从 2 降到 1、没归零，窗口仍然含全三种），于是只结算了 1 个合法左端点，漏掉左端点 0。
- **答案口径不能照搬"最长窗口"那一套**：本题答案是**计数**（每轮累加"合法左端点个数"），不是窗口长度，因此不能改成 `ans = max(ans, 窗口长度)` 或 `n - left`。一般规律——"把 `while` 换 `if`、答案取 `n - left`"这类等价写法建立在"答案是窗口长度且长度单调不减"之上；一旦答案口径变成计数/求和，这套等价关系直接失效。
- **别把"退出时窗口非法"当成 bug**：收缩结束时 `[left, r]` 是**非法**窗口（缺至少一种字符），这正是"`left` 等于合法左端点个数"的原因，不要额外补一次"收缩到合法"。
- **期望值不能凭感觉写**：`"abcabcabc"` 这类例子手算极易出错（真值 28），构造自定义用例时先用暴力解算一遍。

### 题型套路沉淀

- **计数型滑窗通用模板**（"求满足条件的子数组 / 子串数目"，约束形如"乘积/和/字符种类 < K"或"含全某集合"）：
  `for r: 加入 s[r] → while 窗口仍满足"计数条件": 收缩 → ans += 收缩后的 left`。
  核心是把"以 `r` 结尾的合法左端点个数"视为一个**单调不减的边界**（本题取"恰好跨过界线的位置"），从而每轮 O(1) 结算。
- **判据二分法**：判据落在"**值**"（某元素计数 > k）时，计数归零不用删键；判据落在"**键数**"（窗口内不同种类数 > K / == 3）时，必须删键。本题属后者。
- **O(n) 滑窗 ⇒ O(n) 闭式** 是这一族常见的二次优化：把"指针逐格移动"换成"用 `last[...]` 直接算出指针终点"。手法相同、常数差一个数量级，但复杂度结论不变 —— 写题解时要把"同阶常数优化"和"复杂度级改进"分开表述。
- **可复用的验证姿势**：滑窗题写完先手工构造一个"单轮需要连续收缩多格"的输入（如 `"aabba...c"`），用来验证 `while` 没有被误写成 `if`。
