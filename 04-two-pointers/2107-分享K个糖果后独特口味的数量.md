## 一、题目描述

给定一个 0-indexed 整数数组 `candies`，`candies[i]` 表示第 `i` 颗糖果的口味。
妈妈要求你**把 `k` 颗连续的糖果送给妹妹**（只能选一段连续区间），但你想让自己留下的糖果
**口味种类尽可能多**。返回送完之后，你手上**最多**能有多少种不同的口味。

换句话说：在数组里选一个长度恰为 `k` 的窗口送出去，剩下的 `n - k` 颗里不同数值的个数要最大。

### 示例

```text
示例 1
输入：candies = [1,2,2,3,4,3], k = 3
输出：3
解释：把下标 [1,3] 的 [2,2,3] 送出去，自己剩 [1,4,3]，共 3 种口味。

示例 2
输入：candies = [2,2,2,2,3,3], k = 2
输出：2
解释：送出 [2,3]（下标 [3,4]），自己剩 [2,2,2,3]，共 2 种。
     也可以送 [2,2]，自己剩 [2,2,3,3]，同样是 2 种。

示例 3
输入：candies = [2,4,5], k = 0
输出：3
解释：k = 0 表示一颗都不用给，自己保留全部 [2,4,5]，共 3 种。
```

### 约束条件

- `1 <= candies.length <= 10^5`
- `1 <= candies[i] <= 10^5`（口味编号有界，**这是个可以利用的条件**）
- `0 <= k <= candies.length`（`k` 可以是 `0`，也可以是 `n`）

## 二、解题思路

### 核心思想

**用补集思考：不去数"手上还剩几种口味"，而去数"被窗口吃光了几种口味"。**

设全局共有 `D` 种口味。对任意一种口味 `f`：只要它**在窗口外还留着一颗**，你就还能吃到它；
只有当 `f` 的**全部**出现位置都落在窗口内时，这种口味才彻底失去。
因此：

```text
答案 = D − (所有出现位置都被窗口覆盖的口味种数)
```

记后者为 `lose`（被吃光的口味数）。判据非常干净：

```text
口味 f 被吃光  ⟺  win_cnt[f] == total_cnt[f]
```

这个判据是本题最漂亮的一步 —— 它**不需要知道 `win_cnt[f]` 是否为 0**，
也不需要知道"窗口内有几种口味"，只要"窗口内该口味的个数恰好等于全局个数"就够了。

### 思路演进

1. **暴力解法**：枚举 `n - k + 1` 个起点 `s`，每次把"窗口外"的 `n - k` 颗拼起来丢进 `set` 数个数。
   单次构造 + 去重是 O(n)，总时间 O(n²)，`n = 10^5` 时约 10^10 次操作，不可能通过。

2. **想直接滑窗，却发现滑不动**：把窗口右移一格，只需让一个元素出窗、一个元素进窗 —— 这是滑窗的标准场景。
   但麻烦在于：**我们要维护的是"窗口外"的口味数，而窗口外是数组的两段（前缀 + 后缀），不是连续区间**。
   "加入一个元素到窗口"对应"从手上拿走一个元素"，而**"拿走"对"不同口味数"的影响需要先查计数**，
   朴素地想会绕进"维护一个会退化为 0 的计数表 + 每步判零"的纠结里（其实能做到，见优化代码）。

3. **换个方向数：数"被吃光的口味"**：既然窗口外不连续，那就把注意力放回**窗口内**（它是连续的，好滑）。
   而"窗口内"与"手上剩几种口味"之间恰好有一条桥：
   `手上还有 f` ⟺ `win_cnt[f] < total_cnt[f]`。
   于是把统计量换成 `lose = #{ f : win_cnt[f] == total_cnt[f] }`，答案 = `D - lose`。
   `lose` 的问题域在窗口上，可以滑窗维护。

4. **滑窗怎么更新 `lose`**（本题唯一需要小心的细节）：
   - 窗口右移，元素 `lv = candies[r-k]` **出窗**：如果它出窗**之前** `win_cnt[lv] == total_cnt[lv]`，
     说明它正是"最后一块拼图"，出窗后该口味就不再被吃光了 → `lose -= 1`；
   - 元素 `nv = candies[r]` **进窗**：进窗**之后**如果 `win_cnt[nv] == total_cnt[nv]`，
     说明该口味刚被吃光 → `lose += 1`。
   - 出窗看**动作前**、进窗看**动作后** —— 这是因为判据比较的是"更新后的状态"：
     出窗后 `win_cnt[lv]` 必然小于 `total_cnt[lv]`，"是否仍相等"恒为假，所以只能从动作前推出信息。

5. **最后合并两段循环 + 顺手处理边界**：先铺满前 `k` 个（含 `k = 0` 时空窗，`lose` 自然为 0、
   答案 = `D`，正好符合示例 3），再统一从 `r = k` 滑到 `n-1`。

### 关键点

- **答案 = `D - lose`**，其中 `lose` 是"所有出现位置都在窗口内"的口味种数。这一步转化是整题的门槛。
- **判据 `win_cnt[f] == total_cnt[f]` 天然覆盖 `k = 0`**：空窗时 `win_cnt[f]` 恒为 0、`total_cnt[f] >= 1`，
  永不相等 ⇒ `lose = 0` ⇒ 答案 = `D`。**不需要为 `k = 0` 写特判**。
- **不需要 `del` / `pop`**：因为用的是"相等比较"而不是 `len()`，所以本解法**天然避开了**
  `1100` / `1852` 里那个"忘删零键导致 `len()` 统计到历史值"的坑。
- **更新顺序不能乱**：出窗"**先判后减**"、进窗"**先加后判**"。详见第六节实测。
- **当 `lv == nv`（同一口味既出窗又进窗）时两步净抵消**：先 `lose -= 1`（若原本吃光），
  再 `win_cnt[lv] += 1` 后若又相等则 `lose += 1`，净变化为 0 —— 这正是正确答案，
  因为窗口里该口味的数量压根没变。

## 三、代码实现

### 最终代码

> 本题**未独立做出**，以下为看懂题解后提交的版本（`Counter` + `lose`）。

```python
from typing import List
from collections import Counter


class Solution:
    def shareCandies(self, candies: List[int], k: int) -> int:
        total_cnt = Counter(candies)      # 每种口味的全局出现次数
        win_cnt = Counter()               # 送出去的窗口内，每种口味的出现次数
        lose = 0                          # 被窗口"吃光"的口味种数
        n = len(candies)

        # 1) 铺满前 k 个（k = 0 时这一步是空转，lose 保持 0）
        for i in range(k):
            val = candies[i]
            win_cnt[val] += 1
            if win_cnt[val] == total_cnt[val]:
                lose += 1
        ans = len(total_cnt) - lose       # 手上一开始的口味数

        # 2) 窗口右移：左端出窗 -> 右端进窗
        for r in range(k, n):
            left_val = candies[r - k]
            if win_cnt[left_val] == total_cnt[left_val]:   # 出窗前判断：它是否是最后一块拼图
                lose -= 1
            win_cnt[left_val] -= 1

            new_val = candies[r]
            win_cnt[new_val] += 1
            if win_cnt[new_val] == total_cnt[new_val]:     # 进窗后判断：是否刚被吃光
                lose += 1

            ans = max(ans, len(total_cnt) - lose)

        return ans
```

> **自检**：三示例输出 `3 / 2 / 3` ✓。
> 与暴力解做了 **8000 组随机对拍（值域 1~5，`n <= 15`，`k` 覆盖 `0 ~ n`）零 mismatch**，
> 另加 3000 组大值域（含 `100000`）对拍零 mismatch。
> 边界实测：`k = 0`、`k = n`、`n = 1`、口味全相同 均正确。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码**（定长滑窗 + 哈希计数） | O(n) | O(min(n, 值域)) |
| 暴力解法（枚举起点重建集合） | O(n²) | O(n) |
| 优化版（计数数组，见第五节） | O(n + 值域) | O(值域) |
| 差分数组另解（见第五节） | O(n + 值域) | O(n) |
| 理论下界 | Ω(n) | — |

> 复杂度中的 `n` 指 `candies` 的长度；`k` 是**送出去的**窗口长度，`n - k` 是**留下的**糖果数。
> 空间上的 O(min(n, 值域))：`win_cnt` 的键最多 `min(k, 值域)` 个，`total_cnt` 的键最多 `min(n, 值域)` 个。

## 五、优化评估

**结论**：大 O **O(n) 已是理论下界**（必须读完整串才知道每种口味的总数），不可突破；
但**常数因子还有约 2 倍空间**，且能顺手把"计数表"从哈希换成数组。

### 瓶颈分析

1. **为什么 Ω(n) 不可突破**：判据 `win_cnt[f] == total_cnt[f]` 依赖**全局计数** `total_cnt`，
   而全局计数必须扫完整个数组才能得到。不知道 `total_cnt` 就无法判断"是否被吃光"。
2. **实际开销在哪**：每移动一次窗口，代码要操作 `Counter` 共 3 次
   （读 `win_cnt[left_val]`、改 `win_cnt[left_val]`、改 `win_cnt[new_val]`），外加一次 `Counter.__missing__` 兜底。
   **哈希（dict）的每次读写都要算 `hash()` 并做冲突探测，是纯 Python 循环里最贵的一类操作**。
   而 `candies[i] <= 10^5` 已经把值域钉死，用数组可以把这 3 次 O(1) 变成"纯列表下标访问 + 整数比较"。

### 可优化空间

**方向一：值域有界 ⇒ 用计数数组替代 `Counter`。**
窗口外的计数 `out[f]` 与"手上的不同口味数 `distinct`"直接维护：
滑出的元素**回到手上**（`out[lv] += 1`，若变 1 则 `distinct += 1`），
滑入的元素**离开手上**（`out[nv] -= 1`，若变 0 则 `distinct -= 1`），
每轮多记一次 `max` 即可 —— **不需要 `lose` 这个反向统计量，思路更直白**。

**方向二：贡献法 + 差分数组（离线另解，思维拓展）。**
对每种口味 `f`，记它第一次出现的位置 `L`、最后一次出现的位置 `R`。
要让 `f` 被吃光，窗口起点 `s` 必须满足 `s <= L` 且 `s + k - 1 >= R`，即

```text
s ∈ [ max(0, R - k + 1) , min(L, n - k) ]
```

于是每种口味在"起点区间"上贡献一次 +1 —— 这是典型的**区间加一，求单点最小值**，
用差分数组一遍前缀和即可求出 `min(lose)`，答案 = `D - min(lose)`。
它完全不做滑窗，是同一问题的另一种建模。

**方向三：常数级**
- 把 `max(ans, ...)` 换成 `if x > ans: ans = x`；
- `len(total_cnt)` 提成局部变量 `D`，别在循环里反复调用；
- 早退：`k >= n` 时手上必然是空的（返回 0），`k == 0` 时返回 `len(set(candies))`，都可直接短路。

**实测对比**（本机 Python 3.13，`n = 10^5`，取两次运行较小值，单位 ms）：

*表 A：口味值域 = 1000（10^5 颗糖只有 1000 种口味）*

| 实现 | k=1 | k=1000 | k=50000 | k=99999 |
| :--- | ---: | ---: | ---: | ---: |
| 本题最终代码（Counter + lose） | 49.2 | 50.9 | 37.4 | 25.8 |
| 官方写法（Counter(kept) + `len()`） | 42.2 | 42.1 | 21.8 | **≈0.0** |
| **计数数组 + 直接维护 distinct** | **21.3** | **21.3** | **17.5** | 13.9 |
| 差分数组（另解） | 12.7 | 12.5 | 10.4 | 9.2 |

*表 B：口味几乎全不同（10^5 颗糖 ≈ 10^5 种口味）*

| 实现 | k=1 | k=1000 | k=50000 | k=99999 |
| :--- | ---: | ---: | ---: | ---: |
| 本题最终代码 | 91.6 | 93.7 | 84.0 | 64.8 |
| 官方写法 | 92.4 | 88.9 | 46.5 | **≈0.0** |
| **计数数组 + 直接维护 distinct** | **39.5** | **41.0** | **39.3** | 30.9 |
| 差分数组 | 68.1 | 65.6 | 66.0 | 60.1 |

**读表结论**：
- **计数数组版在所有 16 种组合里都是最快的**，相比本题代码稳定快 **1.7 ~ 2.4 倍**，且思路更短。
- **官方写法 `Counter(candies[k:])` + `len(cnt)` 的耗时随 `k` 增大反而下降**，`k = 99999` 时几乎 0 ms ——
  因为它的工作量是 `O(n - k)`：`k` 接近 `n` 时只统计 1 个元素、只滑 1 步。
  这是它的隐藏优势，也是它 `k` 很小时（40+ ms）并不出色的原因。
- **差分数组在"口味种类少"时最快**（10 ms 量级），但在"口味几乎全不同"时**反而最慢**（60+ ms）——
  因为它要为 10^5 种口味各做一次区间更新，而滑窗只需滑 10^5 步。**选型要看 `D / n` 的比值。**

### 优化代码

计数数组版（推荐，实测最快，且不需要 `lose` 这个反向统计量）：

```python
from typing import List


class Solution:
    def shareCandies(self, candies: List[int], k: int) -> int:
        n = len(candies)
        if k == 0:                        # 一颗都不用给
            return len(set(candies))
        if k >= n:                        # 全送出去了，手上啥也不剩
            return 0

        M = max(candies) + 1              # 值域 <= 10^5，可以直接开数组
        total = [0] * M
        for v in candies:
            total[v] += 1
        distinct = sum(1 for x in total if x)     # 全局不同口味数 D

        out = total[:]                    # out[f] = 手上（窗口外）还剩几颗口味 f
        for i in range(k):                # 先把前 k 颗送出去：它们离开了手上
            v = candies[i]
            out[v] -= 1
            if out[v] == 0:               # 手上这种口味彻底没了
                distinct -= 1
        ans = distinct

        for r in range(k, n):
            lv = candies[r - k]           # 滑出窗口 -> 回到手上
            out[lv] += 1
            if out[lv] == 1:
                distinct += 1
            nv = candies[r]               # 滑入窗口 -> 离开手上
            out[nv] -= 1
            if out[nv] == 0:
                distinct -= 1
            if distinct > ans:
                ans = distinct

        return ans
```

**优化理由**：

- 把 3 次哈希读写换成 3 次列表下标访问，每次省掉 `hash()` 与冲突探测，实测 1.7 ~ 2.4 倍。
- 直接把答案量 `distinct` 维护出来，**省掉了 `lose` 的反向映射与 `D - lose` 的换算**，可读性更好。
- 空间代价：`M <= 10^5 + 1` 个指针的列表，约 800 KB，相对收益微不足道。若值域可能极大而 `n` 很小，
  则退回哈希版（或做一次压缩映射）。

> 自检：该版本三示例输出 `3 / 2 / 3` ✓，与暴力解 **12000 组随机对拍 + 3000 组大值域对拍零 mismatch**。

差分数组另解（口味种类少时最快，理解"区间覆盖"模型的极佳练习）：

```python
from typing import List


class Solution:
    def shareCandies(self, candies: List[int], k: int) -> int:
        n = len(candies)
        first, last = {}, {}
        for i, v in enumerate(candies):
            if v not in first:
                first[v] = i
            last[v] = i

        m = n - k + 1                     # 窗口起点 s 的取值范围：0 .. n-k
        diff = [0] * (m + 1)
        for v, L in first.items():
            lo = last[v] - k + 1          # s 必须 >= R-k+1 才能覆盖最后一次出现
            if lo < 0:
                lo = 0
            hi = L if L < m else m - 1    # s 必须 <= L 才能覆盖第一次出现
            if lo <= hi:
                diff[lo] += 1
                diff[hi + 1] -= 1

        best = 10 ** 9                    # 每种起点下"被吃光的口味数"的最小值
        s = 0
        for i in range(m):
            s += diff[i]
            if s < best:
                best = s
        return len(first) - best
```

## 六、易错点与总结

### 易错点

- **概念错误：把"窗口内的不同口味数"当成答案。** 这两者毫无关系 —— 窗口里有 3 种口味，
  你可能还剩 1 种；窗口里只有 1 种口味，你可能还剩 5 种。实测对照：

  | candies | k | 正确答案 | 若输出窗口内 distinct |
  | :--- | ---: | ---: | ---: |
  | `[1,1,2]` | 1 | **2** | 1 |
  | `[1,2,1]` | 2 | **1** | 2 |
  | `[1,2,1,2]` | 2 | **2** | 2（碰巧对） |

  注意最后一行的"碰巧对"—— 这种偶然会让人误以为自己的思路没问题。

- **出窗元素写成"先减后判"**。`lose` 版里，出窗的检查必须发生在 `win_cnt[lv] -= 1` **之前**：

  ```python
  if win_cnt[lv] == total_cnt[lv]: lose -= 1   # ✓ 先判
  win_cnt[lv] -= 1
  # ---- 下面是错的 ----
  # win_cnt[lv] -= 1
  # if win_cnt[lv] == total_cnt[lv]: lose -= 1   # ✗ 减完必然不等，恒不触发
  ```

  实测这种改写**在 20000 组随机小数据里有 15.8% 的输入会算错**（反例：`candies=[2,1,3,1,3,3,1,3], k=2`
  正确 3、错解 2；`candies=[1,2,4,3,4], k=1` 正确 4、错解 3）。
  **危险之处在于它时常"看不出错"** —— 简单示例往往照样通过。

- **用 `len(cnt)` 当统计量却忘了 `pop` / `del` 零键**。这是本仓库 `1100` / `1852` 的同款坑，
  在官方写法（`Counter(candies[k:])` + `len(cnt)`）里最容易犯：

  ```python
  cnt[candies[i - k]] += 1
  cnt[candies[i]] -= 1
  if cnt[candies[i]] == 0: cnt.pop(candies[i])   # ← 少这一句，len(cnt) 统计的是"历史出现过的口味"
  ans = max(ans, len(cnt))
  ```

  实测**20000 组随机数据里 22.5% 出错**（反例：`candies=[1,3,3,4], k=3` 正确 1、错解 2）。
  `len(cnt)` 只会降不会升（键一旦留下就永不消失），所以一旦多算，就再也回不来。
  **对策**：要么严格 `pop`，要么改用本题这种"相等比较"的判据，从根上不依赖 `len()`。

- **`lv == nv` 时以为要特殊处理**（同一个口味既出窗又进窗）。实测多虑：先 `-1` 再 `+1` 且两处判据
  时机正确时，净变化恰为 0，与"窗口内该口味数量不变"的事实一致，无需任何特判。

- **`k = 0` 与 `k = n`**
  - `k = 0`：本题代码**不用特判**，空窗使 `lose = 0`，答案 = `D`（示例 3 即为此）；
  - `k = n`：全部送出，手上为空 ⇒ 答案 0。本题代码靠 `lose = D` 得到 `D - D = 0`；
    优化版则显式 `if k >= n: return 0` 更清楚。

- **`max(candies)` 在空数组上抛异常**：优化版用计数数组前若不加 `k == 0` / `n == 0` 的早退，
  遇到空输入会直接崩。本题官方约束 `n >= 1`，但多写一句早退不亏。

### 题型套路沉淀

- **"窗口统计量 + 补集换算"这一范式值得单独记一笔**：当你要维护的目标是"窗口**外**的性质"
  而窗口外不连续时，**不要硬维护窗口外**，而是找一个与之互补的、只依赖窗口内的量。
  本题的桥就是 `手上还有 f ⟺ win_cnt[f] < total_cnt[f]`，于是补集量 `lose` 可以滑窗维护。
- **"判据式滑窗"**：不做 `len(cnt)` 这样的聚合查询，而是用**逐键的相等/归零判据**维护一个计数器。
  好处是**天然免疫"忘删零键"**，代价是要写清楚"比较发生在动作前还是动作后"。
- **定长滑窗家族（本仓库已连成一条线）**：

  | 题 | 窗口内统计量 | 怎么用这个统计量 |
  | :--- | :--- | :--- |
  | `1100` 长度为 K 的无重复字符子串 | 不同字符数 `len(cnt)` | **判等**：`len(cnt) == k` 才算一个答案 |
  | `1176` 健身计划评估 | 窗口内总和 | **与阈值比较**，计数达标窗口 |
  | `1852` 每个子数组的数字种类数 | 不同元素个数 `len(cnt)` | **直接收集**成答案数组 |
  | `1151` 最少交换次数来组合所有的 1 | 窗口内 1 的个数 | **取最大**后与窗口长度相减 |
  | **`2107` 本题** | 被窗口吃光的口味数 `lose` | **取最小**后用总口味数相减 |

  五题共用同一骨架：`右端进 → 更新统计量 → 窗口达标则产出 → 左端出`。
- **值域有界时的通用提速**：`candies[i] <= 10^5` 这种提示不是摆设 ——
  凡是用 `Counter`/`dict` 做计数的滑窗题，只要值域可控，**换计数数组几乎总能拿到 ~2 倍**。
- **同型题**：
  - `2461. 长度为 K 子数组中的最大和`（定长窗口 + 去重计数）；
  - `1876. 长度为三且各字符不同的子字符串`（定长窗口 + 计数数组）；
  - `2653. 滑动子数组的美丽值`（定长窗口 + 计数数组，值域有界的经典用例）；
  - `1100` / `1151` / `1852`（本仓库同目录）。
