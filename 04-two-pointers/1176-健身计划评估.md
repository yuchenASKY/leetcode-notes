# 1176. 健身计划评估

> **难度**：简单
> **标签**：数组 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/diet-plan-performance/

---

## 一、题目描述

给定数组 `calories`，`calories[i]` 表示第 `i` 天消耗的卡路里。再给定窗口长度 `k` 与阈值 `lower`、`upper`。

对**每一个**长度为 `k` 的连续子数组（起始下标 `i` 满足 `0 ≤ i ≤ n-k`），记窗口和为 `T`：

- `T < lower` → 计划糟糕，**扣 1 分**
- `T > upper` → 计划优秀，**加 1 分**
- 否则（`lower ≤ T ≤ upper`）→ **分值不变**

返回评估完所有窗口后的总分。注意**总分可能为负**。

### 示例

```text
示例 1
输入：calories = [1,2,3,4,5], k = 1, lower = 3, upper = 3
输出：0
解释：k=1 即逐天评估。1、2 小于 lower 共扣 2 分；3 落在区间内不变；
      4、5 大于 upper 共加 2 分。总分 = -2 + 2 = 0。

示例 2
输入：calories = [3,2], k = 2, lower = 0, upper = 1
输出：1
解释：唯一窗口 [3,2]，T = 5 > upper，加 1 分。

示例 3
输入：calories = [6,5,0,0], k = 2, lower = 1, upper = 5
输出：0
解释：[6,5] → T=11 > 5，+1；[5,0] → T=5 落在区间内，不变；
      [0,0] → T=0 < 1，-1。总分 = 1 + 0 - 1 = 0。
```

### 约束条件

- `1 <= k <= calories.length <= 10^5`
- `0 <= calories[i] <= 20000`
- `0 <= lower <= upper`

---

## 二、解题思路

### 核心思想

**固定长度滑动窗口**：相邻两个窗口的区间只差「出去一个、进来一个」，所以窗口和不必重算 —— 维护一个滚动变量，每次 `+新进来的 -退出去的` 即可，O(1) 完成一次滑动。

### 思路演进

1. **暴力解法**：枚举每个起点 `i`，再内层循环累加 `calories[i..i+k-1]`。共 `n-k+1` 个窗口、每个窗口加 `k` 次 → 时间 `O(n·k)`。当 `k` 也接近 `10^5` 时约 `10^10` 次运算，**必然超时**。
2. **观察到**：第 `i` 个窗口与第 `i+1` 个窗口的元素有 `k-1` 个是重叠的，唯一的差异是首尾各一个元素。既然只是"替换了一个元素"，就没有理由把整个窗口重新加一遍。
3. **优化为**：用一个变量 `window` 保存当前窗口和。窗口右移一步时：

   ```text
   window += calories[新进入的下标]
   window -= calories[退出的下标]
   ```

   每个元素一生只被加一次、减一次 → 总时间 `O(n)`。

### 关键点

- **窗口的起止与原数组下标要对齐**。题目是"第 `i` 天及之后连续 `k` 天"，即窗口为 `[i, i+k-1]`；右移一步时新进来的是 `i+k`，退出去的是 `i`。**下标差一个就是满盘皆错**，这是本题最容易翻车的地方。
- **判断条件用严格不等号**。`T == lower` 或 `T == upper` 都属于"普普通通"，不加不减。
- **总分可以为负**，所以不能用 `max(0, ...)` 之类的兜底。

## 三、代码实现

### 最终代码

```python
from typing import List


class Solution:
    def dietPlanPerformance(self, calories: List[int], k: int, lower: int, upper: int) -> int:
        ans = mid = 0
        for i in range(len(calories)):
            mid += calories[i]          # 右端点进入窗口
            if i < k - 1:
                continue                # 窗口还没凑满 k 天
            if mid > upper:
                ans += 1
            if mid < lower:
                ans -= 1
            mid -= calories[i - k + 1]  # 左端点退出窗口
        return ans
```

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) | O(1) |
| 朴素解法 | O(n·k) | O(1) |
| 前缀和 + 差分 | O(n) | O(n) |
| 理论下界 | O(n) | O(1) |

> 复杂度中的 n 指 `calories` 的长度。注意时间复杂度与 `k` **无关** —— 这正是滑动窗口的价值所在。

## 五、优化评估

**结论**：**时间与空间都已是理论下界，不存在算法层面的优化空间**。但 Python 层面仍有可观的常数优化，实测差距不小。

### 瓶颈分析

- **时间下界 O(n)**：由约束 `k <= n` 可知，每个元素至少属于一个窗口，因此任何正确算法都必须至少读一遍全部输入 → `Ω(n)`。当前实现恰好是 `O(n)`，已触底。
- **空间下界 O(1)**：答案只需维护"当前窗口和 + 累计分"两个标量，与 n 无关 → `Ω(1)`。当前实现也是 `O(1)`。
- 常见误区是"用前缀和优化到 O(1) 取和" —— 取和确实变成 O(1)，但**要先花 O(n) 时间和 O(n) 空间建前缀和数组**，反而比现在的纯滚动更差。**本题不需要前缀和。**

### 可优化空间

算法层面无。以下是**大 O 不变、但常数更小**的 Python 实现优化，值得改：

1. `for i in range(len(calories))` 里那句 `if i < k - 1: continue` 会**在每一次迭代都执行一遍**，而它对前 `k-1` 次以外的迭代都是无用判断。可以拆成"先算首个窗口、再进入主循环"，主循环直接从下标 `k` 开始，彻底省掉这个分支，且循环次数从 `n` 降到 `n-k`。
2. `sum(calories[:k])` 的累加发生在 **C 层**，比 Python 逐元素 `+=` 快一个数量级；首窗口正好可以用它。
3. 两个 `if` 可以合并成布尔运算 `(mid > upper) - (mid < lower)`，省掉分支跳转。代价是可读性下降，**是否采用看团队规范**。
4. 变量名 `mid` 语义不清（它是**窗口和**，不是"中间值"），建议改为 `window` 或 `s`。

### 优化代码

```python
from typing import List


class Solution:
    def dietPlanPerformance(self, calories: List[int], k: int, lower: int, upper: int) -> int:
        n = len(calories)
        window = sum(calories[:k])                      # C 层求和，比 Python 循环快
        ans = (window > upper) - (window < lower)       # 布尔运算替代分支
        for i in range(k, n):                           # 从 k 开始，循环 n-k 次
            window += calories[i] - calories[i - k]     # 进一个、出一个
            ans += (window > upper) - (window < lower)
        return ans
```

**优化理由**：

| 改动 | 收益 |
| :--- | :--- |
| `sum(calories[:k])` 求首窗口 | 首窗口的 k 次累加由 C 完成，Python 层零开销 |
| 主循环从 `k` 起、去掉 `continue` 分支 | 去掉 n 次无用的 `i < k-1` 判断 |
| `(a > x) - (a < x)` | 用 `True/False`（即 `1/0`）的算术替代两次分支跳转 |
| 循环次数 `n` → `n-k` | 少跑 `k` 次迭代 |

**这个改动与题意无关，纯粹是把 Python 的解释器开销压小。实测（`n = 10^5`，各取 7 次最优值，CPython 3.13）：**

| k | 原版 | 优化版 | 提速 |
| ---: | ---: | ---: | ---: |
| 1 | 12.28 ms | 11.25 ms | 1.09× |
| 10 | 13.27 ms | 11.14 ms | 1.19× |
| 1000 | 13.79 ms | 11.03 ms | 1.25× |
| 10000 | 14.35 ms | 10.84 ms | 1.32× |
| 50000 | 10.04 ms | 6.24 ms | 1.61× |
| 100000 | 5.70 ms | 1.21 ms | 4.72× |

**规律**：`k` 越大收益越明显 —— 因为首窗口的 k 次累加被挪到了 C 层的 `sum()` 里，同时 Python 主循环的迭代次数从 `n` 降到 `n-k`。`k = n` 时只剩一个窗口，Python 循环几乎不执行，差距拉到 4.7 倍。

> 注：`k` 很小时（如 `k = 1`）提升微乎其微，此时原版的可读性优势更值得保留。**先保证正确和清晰，再用数据决定要不要上这些技巧。**

### 已是最优的论证

- 时间：`Ω(n)` 的论证见上，不存在 `o(n)` 的正确算法。
- 空间：只需常数个标量，`Ω(1)`。
- 因此**不需要**引入前缀和、单调队列、哈希表等任何额外结构 —— 加了只会更慢或更占内存。

## 六、易错点与总结

### 易错点

- **下标错位**：新进入窗口的是 `calories[i]`，退出的是 `calories[i - k + 1]`（而不是 `calories[i - k]`）。写错就会算成"长度为 k+1 的窗口"之类的错误区间。
- **边界条件写成 `<=` / `>=`**：`T == lower` 或 `T == upper` 都**不加不减**，必须是严格不等号。
- **窗口未满就统计**：`i < k - 1` 时必须跳过，否则会把前缀和当窗口和来评分。
- **多算一次减法不影响结果**：最后一轮循环结束后那次 `mid -= calories[i-k+1]` 是多余的，但**无害**（结果不再被使用），不必为它加特判。
- **试图用前缀和"优化"**：见上，只会把空间从 O(1) 变成 O(n)。

### 题型套路沉淀

- **固定长度滑动窗口的通用骨架**（本题是它的最简形态）：

  ```text
  维护 window
  右端点进入 → window += arr[right]
  若窗口已满 k：结算当前窗口 → window -= arr[left]，left += 1
  ```

- **识别信号**：题目问"每个长度为 k 的连续子数组的某个聚合值"，且聚合满足**可增量更新**（和、计数、异或…）→ 直接上定长滑窗，把 `O(n·k)` 压成 `O(n)`。
- **对照组**：若聚合不可增量更新（如"窗口内最大值"，因为移出元素可能正是最大值），则要换 `单调队列`（见 239. 滑动窗口最大值）。
- 同型题：`643. 子数组最大平均数 I`、`1343. 大小为 K 且平均值大于等于阈值的子数组数目`、`1456. 定长子串中元音的最大数目`。
- 本题还体现了一个通用工程直觉：**算法最优 ≠ 实现最优**。当大 O 已经触底时，把 Python 层的分支和解释器开销压掉仍有实际收益。

- 与暴力解法随机对拍 **2000 组**（`n ≤ 40`，覆盖 `k = 1`、`k = n` 等边界）：**零偏差**。
