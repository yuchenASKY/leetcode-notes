# 3679. 使库存平衡的最少丢弃次数

> **难度**：中等
> **标签**：数组 · 哈希表 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/minimum-discards-to-balance-inventory/

---

## 一、题目描述

`arrivals[i]` 表示第 `i` 天（**1 起编号**）到达的物品类型。每个物品只能在**到达当天**决定「保留」或「丢弃」。

约束：对每一天 `i`，取窗口 `[max(1, i - w + 1), i]`（截至第 `i` 天的最近 `w` 天）。在这个窗口内，**被保留**的物品中每种类型最多出现 `m` 次。

求满足该约束时**最少**要丢弃多少个物品。

⚠️ 注意题面的措辞陷阱：它写成"在第 `i` 天保留会导致超过 `m` 次，那么该物品**必须**被丢弃"，看起来像一条**确定性规则**（照着模拟就行）；真正的问句才是关键 —— **最少**丢弃多少。二者结果一致，但后者才是需要论证的部分（见「关键点」的贪心正确性）。

### 示例

```text
示例 1
输入：arrivals = [1,2,1,3,1], w = 4, m = 2
输出：0
解释：第 5 天到达物品 1 时，窗口 [2,1,3,1] 中类型 1 只出现 2 次（第 1 天的那个已被挤出窗口），
      仍然合规。全程无需丢弃。

示例 2
输入：arrivals = [1,2,3,3,3,4], w = 3, m = 2
输出：1
解释：第 5 天物品 3 到达时，窗口 [3,3,3] 内类型 3 已有 2 个被保留，
      再保留就是 3 次 > m，只能丢弃第 5 天这一个。
```

### 约束条件

- `1 <= arrivals.length <= 10^5`
- `1 <= arrivals[i] <= 10^5`
- `1 <= w <= arrivals.length`
- `1 <= m <= w`

## 二、解题思路

### 核心思想

**约束对每种类型是解耦的** —— 窗口内"类型 `t` 最多 `m` 个"这条限制只跟类型 `t` 自己的保留决策有关，跟别的类型毫不相干。

因此可以拆成：`答案 = Σ_t (类型 t 的到达次数 − 类型 t 最多能保留的个数)`。

而单个类型的子问题非常经典：**一个序列上，任意长度 ≤ `w` 的窗口内最多保留 `m` 个**，要求保留数最大 → 当然要**尽量保留靠前的**。落到实现上就是一句贪心：

> 从左往右扫，维护「当前窗口内该类被保留的个数」；**只要窗口里已经有 `m` 个，就只能丢弃当天这个新的**；否则保留它。

### 思路演进

1. **暴力解法**：把"每天丢还是留"当成 `n` 个二值决策，枚举 2ⁿ 种方案，逐个检查所有窗口是否合规，取丢弃数最少的。`n = 10^5` 时天文数字，**完全不可行**。即使用回溯 + 剪枝，最坏情况依旧是指数级。
2. **观察到（解耦）**：检查约束时，不同类型之间没有任何交互 —— 每种类型各自数自己那一份就够了。于是全局最优 = 每种类型各自最优之和，问题从"全局搜索"降级为"单类型贪心"。
3. **观察到（贪心的方向）**：单类型上，出现次数是**过期的**——越早到达的越早滑出窗口，越晚到达的会在越多的未来窗口里占位。所以当窗口已满 `m` 个时，**丢最新的那个对自己最有利**：它未来待在窗口里的时间最长，丢掉它相当于给后续腾出最大空间；反过来丢掉一个老的，等于把"要爆"的风险留给更早的将来 —— 一换一必然更差。
4. **优化为**：用一个哈希表 `cnt` 维护「**当前窗口内被保留**的各类型计数」（注意不是到达数），配合滑动窗口左端点退役：
   - 右端点进入：若 `cnt[arrivals[i]] == m` → 丢弃（答案 +1）；否则保留，`cnt[arrivals[i]] += 1`。
   - 左端点退役：`i >= w-1` 时，下标 `i-w+1` 滑出窗口 —— **它当年是被保留的才需要把计数减一**，被丢弃的本来就从未计入。

### 关键点

- **窗口包含第 `i` 天自身**（`[max(1,i-w+1), i]`），所以"是否超限"的判断必须放在**把第 `i` 天纳入窗口之后**。
- **滑出窗口时要不要减计数，取决于该位置当初是"保留"还是"丢弃"**。这是本题最容易写错的地方：无脑减一会让被丢弃的物品也占掉一次额度，答案偏大。
  用户代码用 `ObjDel` 数组逐下标记录保留/丢弃标记来解决（正确做法）。
- **贪心的正确性需要一句论证**（交换论证）：设贪心保留集合为 `G`，任一合法集合为 `S`。按归纳可证对任意前缀 `[0..i]` 都有 `|G ∩ [0..i]| ≥ |S ∩ [0..i]|` —— 因为贪心在每个位置都"能留就留"，而留得越早，后续腾挪空间越大。前缀计数逐点占优 ⇒ `|G| ≥ |S|`，故贪心最优。
- **"丢最新的"与"留最早的"是同一件事的两面**。做题时用"窗口内已满就丢当前"来写代码，比"先全留再回头踢老元素"简单得多。
- 用户代码把变量命名为 `ObjQuantity`（物品数量），但它在 `i-w+1` 退役时做的减法说明它语义上维护的是「窗口内**保留**数」。**变量名与语义不符是隐患**，容易在维护时被误改。

## 三、代码实现

### 最终代码

```python
from typing import List
from collections import defaultdict


class Solution:
    def minArrivalsToDiscard(self, arrivals: List[int], w: int, m: int) -> int:
        ObjQuantity = defaultdict(int)      # 实际语义：当前 w 窗口内「被保留」的各类型计数
        ObjDel = []                         # 每个到达日的删除标记：0 保留 / 1 丢弃
        ans = 0
        for i, j in enumerate(arrivals):
            ObjQuantity[j] += 1
            ObjDel.append(0)
            if ObjQuantity[j] > m:          # 保留它就超限 → 只能丢这一个（它是最新的）
                ObjQuantity[j] -= 1
                ObjDel[-1] = 1
                ans += 1
            if i < w - 1:
                continue                    # 窗口还没满 w 天，无需退役左端点
            if ObjDel[i - w + 1] == 0:      # 左端点退役：只对「被保留」的减计数
                ObjQuantity[arrivals[i - w + 1]] -= 1
        return ans
```

> 本人提交通过的版本，逻辑正确（已对拍验证，见文末）。但 `+= 1` 再 `-= 1` 的"先加后退"写法对每个**被丢弃**的元素都做两次字典写入，实测比第五节的重写版慢 1.5~2 倍。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) | O(n) |
| 优化版（第五节） | O(n) | O(w) |
| 按类型队列版（第五节） | O(n) | O(distinct + Σ min(m,·)) |
| 朴素解法（子集枚举） | O(2ⁿ · n · w) | O(n) |
| 理论下界 | O(n) | Ω(min(w, n)) |

> 复杂度中的 n 指 `arrivals` 的长度，`distinct` 指窗口内出现的不同类型数（最坏 min(n, 10^5)）。
>
> - **时间下界 `Ω(n)`**：每个到达物品都必须被"看"一眼才能决定去留，无法跳过 → O(n) 已触底，且**与 `w`、`m` 无关**。
> - **空间**：为了在左端点退役时判断"它当年是否被保留"，至少要保存最近 `w` 天的保留标记 → `Ω(min(w, n))`（这是真实的信息需求，不是实现缺陷）。用户代码用长度 `n` 的列表承载，最坏与 `w = n` 同阶，但**用 `deque` + `popleft()` 与窗口同步出队就能压到 O(w)**。

## 五、优化评估

**结论**：时间已是理论下界 `O(n)`，**算法层面无优化空间**；但当前实现有两个可改的点 —— **常数（字典写入次数）**和**空间（标记数组长度）**。

### 瓶颈分析

- 每轮迭代的固定开销集中在「比较 + 字典写入」上。用户版对**每个被丢弃**的元素都做两次字典写入（`ObjQuantity[j] += 1` 之后立刻 `-= 1`），而实际只需要在**保留**时写一次 —— 这个差值在"大量重复类型、丢弃率高"的数据上被放大。
- `ObjDel` 是**随 `i` 增长的普通列表**，长度最终为 `n`；窗口只需要最近 `w` 个标记，多存的部分纯属浪费。
- `if i < w - 1: continue` 每轮都要判断一次，而它对 `i >= w-1` 的所有轮次都是无用功。

### 可优化空间

| 改动 | 收益 |
| :--- | :--- |
| 改成「先比较 `cnt[t] < m` 再决定写不写」 | 被丢弃的元素从 2 次字典写入降到 **0 次**；这是提速主因 |
| `ObjDel` 换成 `deque` + `popleft()` | 标记数组空间 `O(n)` → `O(w)`，且退役时免去手算下标 |
| 主循环从 `i >= w-1` 起分开处理 | 去掉每轮一次的无效分支 |
| 变量名改为 `cnt` / `kept` | 语义与行为一致（维护的是**保留**计数），防止后续误改 |

### 优化代码

```python
from typing import List
from collections import defaultdict, deque


class Solution:
    def minArrivalsToDiscard(self, arrivals: List[int], w: int, m: int) -> int:
        cnt = defaultdict(int)      # 当前 w 窗口内「被保留」物品的计数
        kept = deque()              # 与窗口对齐的保留标记：1 保留 / 0 丢弃，长度恒为 O(w)
        ans = 0
        for i, t in enumerate(arrivals):
            if cnt[t] < m:          # 窗口内该类型还没占满 m 个 → 保留（只在此处写一次字典）
                cnt[t] += 1
                kept.append(1)
            else:                   # 已满 → 只能丢最新的这个（它留在窗口里的时间最长）
                kept.append(0)
                ans += 1
            if i >= w - 1:          # 左端点 i-w+1 离开窗口
                if kept.popleft():  # 当初保留过才需要回退计数
                    cnt[arrivals[i - w + 1]] -= 1
        return ans
```

**优化理由**：三处改动各自对应一个具体浪费 ——

1. 把"先无条件加一、超了再减回来"改成"先判断、只在保留时写一次"，省掉每个被丢弃元素的那次字典写入；
2. `deque` + `popleft()` 让"左端点的保留标记"和窗口同步出队，既**把标记空间压到 O(w)**，也让下标运算 `i - w + 1` 只出现在真正需要的那一处；
3. 判定条件 `cnt[t] < m` 与语义（窗口内保留数上限）直接对应，可读性也更好。

**实测（`n = 10^5`，CPython 3.13，四版同场各取 7 次最优值）：**

| 场景 | `arrivals[i]` 上限 | `w` | `m` | 用户版 | 优化版 | 按类型队列版 | 优化版提速 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 大量重复 | 2 | 100 | 1 | 26.08 ms | **11.93 ms** | 14.54 ms | **2.19×** |
| 大量重复 | 2 | 50000 | 2 | 33.66 ms | **12.72 ms** | 16.60 ms | **2.65×** |
| 中等种类 | 100 | 1000 | 3 | 27.23 ms | **16.03 ms** | 16.37 ms | 1.70× |
| 全不相同 | 10^5 | 1000 | 1 | 48.26 ms | **41.94 ms** | 73.07 ms | 1.15× |
| `w = n` | 50 | 10^5 | 5000 | 17.47 ms | 16.68 ms | **16.67 ms** | 1.05×（基本持平） |

**规律**：**丢弃率越高，提速越大**（"大量重复"档到 2 倍以上），因为省下的正是被丢弃元素的那次多余字典写入、加上标记数组从 `n` 缩到 `w`；**类型全不相同**时几乎不丢弃，差距缩到 15%；`w = n` 时两版几乎持平 —— 此时 `i >= w-1` 只在最后一轮成立，退役逻辑几乎不执行，瓶颈全在"读元素 + 判一次"，两版做的事完全一样。

> 注意：**O(n) 的两版都能 AC**（`n = 10^5` 时几十毫秒）。优化版的价值在于丢弃率高的数据上确实快一倍以上，同时语义更清晰、标记空间更小。

### 另一种等价写法：按类型维护「最近保留的 m 个下标」

约束只关心"窗口内这类保留了几个"，所以也可以**按类型**记录下标，靠**懒删除**把滑出窗口的记录丢弃，从而完全不需要全局标记数组：

```python
from typing import List
from collections import defaultdict, deque


class Solution:
    def minArrivalsToDiscard(self, arrivals: List[int], w: int, m: int) -> int:
        pos = defaultdict(deque)        # 类型 -> 最近「被保留」的下标（最多 m 个）
        ans = 0
        for i, t in enumerate(arrivals):
            q = pos[t]
            lo = i - w + 1
            while q and q[0] < lo:      # 懒删除：滑出窗口的记录就地丢掉
                q.popleft()
            if len(q) == m:             # 窗口内已满 m 个 → 丢弃当天这个
                ans += 1
            else:
                q.append(i)
        return ans
```

**它好在哪**：每个队列天然只保留 `m` 个元素，**窗口退役是隐式的** —— 不需要"当初是否保留"的标记数组，把用户代码里最容易写错的那一处（退役时该不该减计数）从根上消掉了。

**但实测它反而更慢**（同环境同数据）：

| 场景 | 优化版 | 按类型队列版 | 差距 |
| :--- | ---: | ---: | :--- |
| 大量重复（maxv=2, w=100, m=1） | **11.93 ms** | 14.54 ms | 慢 22% |
| 中等种类（maxv=100, w=1000, m=3） | **16.03 ms** | 16.37 ms | 基本持平 |
| 全不相同（maxv=10^5, w=1000, m=1） | **41.94 ms** | 73.07 ms | **慢 74%** |

**原因**：类型数越多，`defaultdict` 里就要建越多个 `deque` 对象。`arrivals[i]` 全不相同时要创建 10 万个队列，**对象分配 + 每个队列的 `while` 空转检查压过了它省下的记账成本**。所以这版胜在**思路干净（不需要保留标记）**，适合"类型少、重复多"的输入，不适合"类型极散"的输入 —— **优雅的写法不等于更快的写法**。

### 常数级优化（可选）

- **把退役判断移出主循环**：`i >= w-1` 这个条件可以拆成「前 `w-1` 轮」和「之后每轮」，后者不再判断。
- **`dict.get` 优于 `defaultdict` 的缺省写入**：`defaultdict(int)` 在读取不存在的键时会**插入**一个 0 条目，类型极散时会让字典膨胀到 `distinct` 个键。若用 `cnt.get(t, 0) < m`，则可避免为只出现一次的类型留下常驻条目（代价是保留时需显式 `cnt[t] = cnt.get(t, 0) + 1`）。本题 `arrivals[i] <= 10^5`，字典最多 10 万条，**影响有限，可不动**。

## 六、易错点与总结

### 易错点

- **退役时无脑减计数**：被丢弃的物品从未计入 `cnt`，滑出窗口时**不能**再减一次。必须校验"当初是否保留"。
- **把判断放在纳入窗口之前**：窗口定义包含第 `i` 天自身，若先比较再加一，会把"含自己"的计数少算一次，导致该丢的没丢。
- **维护的量搞错**：`cnt` 要维护「窗口内**被保留**的个数」，不是"到达次数"。写成到达次数的话，被丢弃的物品会持续占额度，答案偏大。
- **误信题面"必须丢弃"就放弃论证**：题面那条确定性规则恰好等于贪心最优解，但它**只描述了策略，没有说明为什么这是最少丢弃**。面试时该补一句交换论证。
- **`w = 1` 的退化情况**：此时窗口只有一个位置，因为 `m <= w` 即 `m = 1`，所以全程**永不丢弃**（`cnt[t] < 1` 在计数清零后总成立）。可以拿它做自检。

### 题型套路沉淀

- **"每种类型在窗口内最多出现 k 次"型约束 → 按类型解耦 + 懒删除**：

  ```text
  全局最优 = Σ_{type} (单类型最优)        # 因为约束不跨类型
  单类型：维护「最近保留的若干个下标」，滑出窗口的就地丢弃
  ```

- **滑窗家族的第二支**：本题与 `1176` / `1052` 那种"窗口内求和"不同，属于**窗口内计数约束**一支，同族还有：

  | 题 | 窗口维护的量 | 关键动作 |
  | :--- | :--- | :--- |
  | `1100` 长度为 K 的无重复字符子串 | 哈希计数 | 出现重复就收缩窗口 |
  | `1151` 最少交换次数来组合所有的 1 | 窗口内 1 的个数 | 定长窗口求最大 |
  | `2107` 分享 K 个糖果后独特口味的数量 | 哈希计数 | 统计被窗口"吃光"的类型数 |
  | **`3679` 本题** | 每类型「**保留**」计数 | 满了就**丢弃**当前，滑出窗口的按保留标记回退 |

- **"越晚到达的越先被牺牲"是很常见的贪心方向**：凡是"窗口内某类资源有容量上限，且元素会随时间过期"的题（库存、限流、去重、缓存淘汰），第一反应都该是**保留靠前的，砍掉最新的**。反直觉但正确的另一类是 LRU 式"淘汰最久未用"，识别依据是**代价是否随时间递增**。
- **信息需求决定空间下界**：本题"必须记住最近 `w` 天谁被保留了"是**任务本身要求的信息**，不是实现偷懒 —— 看到 O(n) 空间时先问一句"这个状态能不能不算"，而不是直接认定它可优化到 O(1)。

### 验证记录

- 2 个官方示例：四个版本（用户版 / 优化版 / 按类型队列版 / 对照版）**全部通过**（`0` / `1`）。
- **对拍方式**：因为本题"最少丢弃"的正确性不能只靠官方样例验证，这里用**子集枚举暴力解**（枚举所有保留方案 + 逐窗口校验，`n ≤ 11`）作基准，随机对拍 **3000 组**（`arrivals[i]` 取值范围取 2/3/5 以制造高重复，`w`、`m` 全随机）：**零偏差**（四个版本结果均与暴力解一致）。
