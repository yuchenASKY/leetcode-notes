# 1248. 统计「优美子数组」

> **难度**：中等
> **标签**：滑动窗口 · 数组 · 哈希表 · 数学
> **原题链接**：https://leetcode.cn/problems/count-number-of-nice-subarrays/

---

## 一、题目描述

给定整数数组 `nums` 和整数 `k`，统计**恰好包含 `k` 个奇数**的连续子数组个数。偶数不参与计数，只看奇数。

### 示例

```text
输入：nums = [1,1,2,1,1], k = 3
输出：2
解释：恰好含 3 个奇数的子数组是 [1,1,2,1] 与 [1,2,1,1]

输入：nums = [2,4,6], k = 1
输出：0

输入：nums = [2,2,2,1,2,2,1,2,2,2], k = 2
输出：16
```

### 约束条件

- `1 <= nums.length <= 50000`
- `1 <= nums[i] <= 10^5`
- `1 <= k <= nums.length`

---

## 二、解题思路

### 核心思想

**把「恰好 k 个」拆成「至少 k 个」减「至少 k+1 个」。** 一趟扫描里同时维护两个滑动窗口，对每个右端点 `right`，两个窗口的左边界之差就是「以 `right` 结尾的优美子数组个数」。

### 判据

对固定的右端点 `right`，记：

- `left1` = 使 `[left1, right]` 内奇数个数 `< k` 的**最小**左边界；
- `left2` = 使 `[left2, right]` 内奇数个数 `<= k` 的**最小**左边界。

因为「奇数个数」关于左端点单调不增（偶数贡献 0、奇数贡献 1，非负可加），所以：

- `[l, right]` 奇数个数 `>= k` ⟺ `l < left1`，这样的 `l` 恰有 **`left1`** 个（`l = 0 .. left1-1`）；
- `[l, right]` 奇数个数 `>= k+1` ⟺ `l < left2`，恰有 **`left2`** 个；
- 两者相减：恰好 `k` 个 ⟺ `left2 <= l < left1`，数量 = **`left1 - left2`**。

⇒ 答案 `ans = Σ_{right} (left1 - left2)`。

### 思路演进

1. **暴力解法**：枚举所有 `(l, r)`，统计区间内奇数个数。O(n²) 个区间，n = 5×10⁴ 时约 1.25×10⁹ 个区间，必然超时。
2. **观察到**：把「奇数个数」换成前缀和 `pre[i] = nums[0..i-1]` 里的奇数个数，问题就是「统计 `pre[r+1] - pre[l] == k` 的 `(l, r)` 对数」—— 一趟扫描 + 哈希表计数即可 O(n)/O(n) 解决（与原题同构的经典前缀和套路）。
3. **关键转化（本题要走的路）**：注意到**固定右端点时，奇数个数关于左端点单调不增** ⇒ 「合法的左端点」必然是一段**从 0 开始的前缀**。既然合法集合是前缀，只要知道**前缀的右端点在哪**（那个分界点），数量一眼得出，根本不需要哈希表 —— 空间从 O(n) 压到 O(1)。
4. **最优解**：对每个右端点，用两个左指针 `left1` / `left2` 分别卡住「奇数个数 `< k`」与「奇数个数 `<= k`」的分界。`left1`、`left2` 都随 `right` 只增不减（因为同一窗口内奇数个数随右端点扩展单调不减），整趟最多各移动 n 次 ⇒ 内层 `while` 摊还 O(1)，总时间 O(n)、额外空间 O(1)。

### 关键点

- **收缩方向：窗口停在「非法」一侧。** 两个 `while` 都写成 `while 度量 >= 阈值`（收缩到刚好跌破阈值），而不是常见的 `while 不合法: 左指针右移`。此时窗口自身不合法，合法左端点数 = `left1`，**不是窗口长度**。
- **两个窗口只差一个等号**：条件分别是 `temp1 >= k` 与 `temp2 >= k + 1`，它们互为反面（一个是「奇数个数 ≥ k」，一个是「≥ k+1」）。写成同一个条件就会两窗重合、答案恒为 0。
- **`while` 不能换成 `if`**：出窗的那个元素若是偶数，左指针挪一格**不会**减少窗口内的奇数个数，违规量根本没被消除（实测最小反例见 §七）。
- **`ans += left1` / `ans -= left2` 必须分别写在对应 `while` 收缩之后**，写在外面或提前取，拿到的就是上一轮的左边界。
- 两个窗口的度量各自独立（两个左边界不同），所以 `temp1`、`temp2` 不能合并成一个变量。

## 三、代码实现

### 最终代码

（与截图逐行一致，行尾注释为笔记所加；截图共 16 行、末行为 `return ans`，无截断，且用了 `list[int]` 内置泛型，无需补 import。）

```python
class Solution:
    def numberOfSubarrays(self, nums: list[int], k: int) -> int:
        ans = left1 = left2 = temp1 = temp2 = 0
        for right, j in enumerate(nums):
            if j % 2 == 1:                      # 只有奇数会改变窗口度量
                temp1 += 1
                temp2 += 1
            while temp1 >= k:                   # 窗口 1：收缩到「奇数个数 < k」
                temp1 -= 1 if nums[left1] % 2 == 1 else 0
                left1 += 1
            ans += left1                        # 以 right 结尾、奇数个数 >= k 的左端点数
            while temp2 >= k + 1:               # 窗口 2：收缩到「奇数个数 <= k」
                temp2 -= 1 if nums[left2] % 2 == 1 else 0
                left2 += 1
            ans -= left2                        # 减去「奇数个数 >= k+1」的左端点数
        return ans
```

## 五、优化评估

**结论**：**渐进复杂度已是理论下界**（时间必须看一遍数组，空间 O(1) 无法再省），但**常数级仍有明显更快的等价写法**：换用「奇数下标 + 哨兵」的思路，实测比原版快 **1.76× ~ 5.39×**。

### 瓶颈分析

本题 n ≤ 5×10⁴，所有 O(n) 写法都在几毫秒量级（实测 4.7 ~ 13.5 ms），**不存在"不优化会超时"的问题**，下面讨论的是同一渐进复杂度下的常数差异。

耗时全部落在 Python 层的逐元素循环：每轮一次奇偶判定 + 两次 `while` 条件比较。**偶数元素是纯空转开销** —— 稀疏奇数场景（每 100 个元素里 1 个奇数）中，5×10⁴ 次循环里只有 500 次真正更新了计数，却仍花了 11.7 ms。这提示优化方向：**让循环规模只与奇数个数相关**。

### 可优化空间

子数组「恰好含 k 个奇数」只由它的**首、尾两个奇数**决定。设所有奇数的下标为 `p[1..m]`（两侧加哨兵 `p[0] = -1`、`p[m+1] = n`）。若某个优美子数组的首个奇数是第 `i` 个、末个奇数是第 `i+k-1` 个，则：

- 左端点可取 `p[i-1] + 1 .. p[i]`，共 `p[i] - p[i-1]` 种；
- 右端点可取 `p[i+k-1] .. p[i+k] - 1`，共 `p[i+k] - p[i+k-1]` 种。

⇒ 答案 = `Σ_i (p[i] - p[i-1]) * (p[i+k] - p[i+k-1])`，枚举 `i = 1 .. m-k+1`。循环规模从 n 降到 `m - k + 1`，代价是 O(m) 额外空间。

### 优化代码

```python
class Solution:
    def numberOfSubarrays(self, nums: list[int], k: int) -> int:
        n = len(nums)
        p = [-1]                                   # 左哨兵
        p += [i for i, x in enumerate(nums) if x & 1]
        p.append(n)                                # 右哨兵
        m = len(p) - 2                             # 奇数个数
        ans = 0
        for i in range(1, m - k + 2):
            ans += (p[i] - p[i - 1]) * (p[i + k] - p[i + k - 1])
        return ans
```

**优化理由**：把「逐元素滑窗」换成「逐奇数枚举」。滑窗每轮都要处理一个元素，而这里每轮只处理一个**奇数**，且每轮的运算是两次减法 + 一次乘法，没有 `while` 比较。奇数越稀疏收益越大（§七 实测 S5 快 5.39×）；即使全为奇数（`m = n`）也因内层无 `while` 而快 1.76×。

**代价**：额外 O(m) 空间，以及一次 O(n) 的列表构造。若题目要求 O(1) 空间（例如追加限制「只允许常数额外空间」），仍应使用最终代码。

### 常数级优化（可选）

- `j % 2 == 1` → `x & 1`：实测稳定提升 **1.15× ~ 1.22×**（五个场景全部为正收益，见 §七），改法零成本。
- ~~先把奇偶压成 `bytes` 再跑同一套双窗~~：实测 0.87× ~ 1.14×，在「全奇」「全偶」两档反而更慢 —— 多出的那一趟构建 + 一份 n 字节副本并没被省下的 `% 2` 抵消。
- ~~改用前缀和 + 哈希~~：渐进复杂度相同但空间退到 O(n)。实测只在「稀疏奇数」档领先（S5 1.96×、S4 1.50×），在「全奇」档被反超（0.85×）—— 哈希表每轮的字典读写开销在均匀稠密的输入上摊不掉。属"看起来更聪明"的改法，用场景换收益，**不推荐**。

## 六、易错点与总结

### 易错点

- **把 `while` 写成 `if`**：窗口收缩一格并不保证消除违规（出窗元素是偶数时，奇数个数一点不减），会漏计合法左端点。最小反例 `nums = [2,1], k = 1`：真值 2、`if` 版实得 1（实测 30 组随机用例错 5 组，见 §七）。
- **答案口径写成「窗口长度」**：本族答案是**合法左端点数**，写成 `(right - left1 + 1) - (right - left2 + 1)` 恰好等于正解的**相反数**（最小反例 `nums = [1], k = 1`：真值 1、实得 −1）。**答案出现负数，就是口径写错的信号。**
- **两个 `while` 的条件写成同一个**（都写 `>= k`）：两窗口左边界重合，`left1 - left2 ≡ 0`，答案恒为 0。
- **两个 `while` 的方向写反**（写成「收缩到合法为止」，即 `while 度量 < k`）：那样得到的窗口是**最后一个**合法窗口而不是分界点，语义完全变了 —— 本族与「收缩到合法为止」的模板方向相反，是这套写法最容易串用的地方。
- **`ans += left1` 的位置**：必须紧跟窗口 1 的 `while` 之后（收缩完成才取），提前取会拿到上一轮的边界。
- **隐含前提 `k >= 1`**：若允许 `k = 0`，第一个 `while` 的条件 `temp1 >= 0` 对空窗口也恒真，`left1` 会一路越过 `right`，直到 `nums[left1]` 越界报 `IndexError`。本题约束 `1 <= k` 保证不会发生，但把这个模板迁移到别处时要留意。

### 题型套路沉淀

- **计数型滑动窗口（约束是「度量 ≥ 下限」）**：窗口停在**非法**一侧，答案 `+= 合法左端点数`（本题是 `left1 - left2`，**不是**窗口长度）。成立需要两根单调性：度量关于左端点单调不增（⇒ 合法集合是前缀）、关于右端点单调不减（⇒ 左指针只增不减，内层 `while` 摊还 O(1)）。
- **「恰好 = ≥ 下界 − ≥ 下界+1」**：一趟扫描里同时跑两个**只差一个等号**的窗口，比正反各扫一趟更省；两个 `while` 的条件互为反面，是本族最容易写错的地方。
- **凡「恰好 k 个」型计数题，先问三件事**：① 度量是否非负可加（决定能不能滑窗）？② 固定一端时合法集合是不是前缀（决定能不能只维护分界点）？③ 答案口径是「计数」还是「长度」（决定收缩方式与答案公式的配套）？
- **把滑窗降维到「关键元素下标」**：当度量只由某一类元素贡献（本题是奇数），可以只枚举这类元素的位置，把循环规模从 n 降到 m —— 这是计数型滑窗常见的常数级优化入口。
