# 209. 长度最小的子数组

> **难度**：中等
> **标签**：数组 · 二分查找 · 前缀和 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/minimum-size-subarray-sum/

---

## 一、题目描述

给定一个含 `n` 个**正整数**的数组 `nums` 和一个正整数 `target`，找出数组中**和 ≥ `target` 的、长度最小的连续子数组**，返回其长度；若不存在这样的子数组，返回 `0`。

### 示例

```text
示例 1：
输入：target = 7, nums = [2,3,1,2,4,3]
输出：2
解释：子数组 [4,3] 是该条件下的长度最小的子数组。

示例 2：
输入：target = 4, nums = [1,4,4]
输出：1

示例 3：
输入：target = 11, nums = [1,1,1,1,1,1,1,1]
输出：0
解释：全部元素之和 8 < 11，不存在合法子数组。
```

### 约束条件

- `1 <= target <= 10^9`
- `1 <= nums.length <= 10^5`
- `1 <= nums[i] <= 10^4`
- **进阶提示**：如果你已经实现 O(n) 时间复杂度的解法，请尝试设计一个 O(n log n) 时间复杂度的解法。

## 二、解题思路

### 核心思想

**因为元素全为正整数，窗口和关于左右端点都单调 —— 于是「最短合法窗口」这个 O(n²) 的搜索空间可以压成一条只向右走的路径**：右指针负责扩张，左指针只在窗口非法时收缩，两个指针各自最多移动 `n` 次，总代价 O(n)。

### 思路演进

1. **暴力解法**：枚举所有子数组 `nums[i..j]`，求和判断是否 ≥ `target`，取最小长度。用切片求和是 O(n³)，边扩边累加是 O(n²)。`n = 10^5` 时 O(n²) 已是 10^10 量级，必然超时。

2. **瓶颈定位**：慢在两处 ——
   - **窗口数太多**：枚举了全部 O(n²) 个窗口，而其中绝大多数既不合法、也不是任何一个右端下的最短路。
   - **相邻左端之间计算完全重复**：固定右端 `j` 时，从小到大枚举左端 `i` 得到的和是同一个 `sum(nums[i..j])` 的重复计算，本该只算一次。

3. **关键转化**：把"枚举窗口"换成"让窗口自己滑动"。观察 **`nums[i] > 0` 这条约束的全部力量**：
   - 固定右端时，**窗口和随左端右移单调不增** ⇒ 一旦某个左端使窗口合法，更靠左的一定也合法 ⇒ 对每个右端，最短合法窗口是**唯一且贴着边界的那一个**；
   - 固定左端时，窗口和随右端右移单调不减 ⇒ **右端不需要回退**：左指针右移只会让窗口更容易变非法，不可能把"非法"变回"合法"。
   
   ⇒ 一句话：暴力解的瓶颈是「每个左端都要重新枚举所有右端」，而全正约束保证了**右端一路向前就是完备的**。两个指针都只增不减，总移动量 2n。

4. **最优解**：滑动窗口（内层 `while` 精确收缩到刚不合法为止），时间 O(n)、空间 O(1)。

### 判据

把解法压成一条可判定真假的命题，边界条件会自然浮出来：

> **窗口 `nums[left..right]` 合法 ⟺ `sum(nums[left..right]) >= target`。**
> 又因元素全正，该判据对"左端右移"**前缀封闭的反面**成立：左端越靠右越可能不合法。

由此推出本题**最短型滑窗的标准动作**：对每个 `right`，让 `left` 一直右移、**在每个还合法的状态上登记长度**，直到窗口和 < `target` 为止；这一串登记里的最后一个就是"以 `right` 为右端的最短合法窗口"。这正是 `ans = min(ans, right - left + 1)` 写在 `while` **内部**的原因。

⚠️ 这与"最长型滑窗"（例如"预算内最长子数组"）是**两套不同的判据与口径**，见「易错点」的实测 —— 本题是**最短型**，答案必须**每轮取 min**。

### 关键点

- **元素全为正**是全部推理的前提。含负数时窗口和不再随左端单调，滑窗直接失效，需要改用**前缀和 + 单调队列**。
- **左指针累计只前进 `n` 次** ⇒ 内层 `while` 是**摊还 O(1)**，总复杂度仍是 O(n) 而不是 O(n²)。用"内层有 while 就是 O(n²)"来判断复杂度是错的。
- **无解要返回 0**：`ans` 初值取 `inf`（或 `n + 1`），最后靠 `ans <= len(nums)` 判断它是否被更新过。
- 因 `target >= 1 > 0`，进入 `while` 时窗口和 ≥ target ⇒ 窗口必非空 ⇒ `left < right` 恒成立，`nums[left]` 不会负索引。

## 三、代码实现

### 最终代码

> 截图里只有 `class Solution`，`from math import inf` 与 `from typing import List` 是为让代码可直接运行而补上的（LeetCode 环境自带，不影响提交）。

```python
from math import inf
from typing import List


class Solution:
    def minSubArrayLen(self, target: int, nums: List[int]) -> int:
        ans = inf
        left = temp = 0
        for right, j in enumerate(nums):
            temp += j                        # 右端扩张
            while temp >= target:            # 左端收缩到刚不合法为止
                ans = min(ans, right - left + 1)
                temp -= nums[left]
                left += 1
        return ans if ans <= len(nums) else 0
```

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码**（滑动窗口） | O(n) | O(1) |
| 暴力（边扩边累加） | O(n²) | O(1) |
| 暴力（切片求和） | O(n³) | O(1) |
| 前缀和 + 二分 | O(n log n) | O(n) |
| 理论下界 | O(n) | O(1) |

> 复杂度中的 **n 指数组 `nums` 的长度**（与 `target`、元素值域无关）。
> 最终代码的精确移动量：`right` 前进 `n` 次，`left` 累计前进 ≤ `n` 次 ⇒ 总迭代 ≤ 2n 次，故为 O(n)；辅助空间只用了 `ans` / `left` / `temp` 三个标量。

## 五、优化评估

**结论**：时间复杂度**已到理论下界 O(n)**，算法层面无优化空间；只存在常数级优化。

### 瓶颈分析

时间几乎全部花在"把数组读一遍 + 2n 次指针移动"上。

- **时间下界 Ω(n) 的论证**：任何正确解法都必须检查每一个元素 —— 否则无法排除"某个元素本身就 ≥ `target`"（此时答案是 1）的情形。因此 O(n) 不可再降，最终代码已经贴着下界。
- **空间下界 O(1)**：滑动窗口只用三个整型变量；比它更"结构化"的做法（前缀和 / 单调队列）都要 O(n) 额外空间。
- 反向验证：题面"进阶"提示的 **O(n log n) 前缀和 + 二分** 解法**方向上是"变慢"而非"变快"** —— 它多出一次 O(n) 的前缀和数组构建和 n 次二分查找，实测见下表，慢 2.1~5 倍。

### 可优化空间

只有常数级：窗口长度的**下界是 1**，所以一旦 `ans == 1` 就不可能更优，可以立即返回（早退）。

### 优化代码

```python
from typing import List


class Solution:
    def minSubArrayLen(self, target: int, nums: List[int]) -> int:
        n = len(nums)
        left = total = 0
        ans = n + 1
        for right in range(n):
            total += nums[right]
            while total >= target:
                w = right - left + 1
                if w < ans:
                    ans = w
                    if w == 1:              # 长度下界，命中即全局最优，直接收工
                        return 1
                total -= nums[left]
                left += 1
        return ans if ans <= n else 0
```

**优化理由**：`w == 1` 是长度下界，命中即无需再扫；`min()` 换成条件赋值省掉每次函数调用；`ans` 初值用 `n + 1` 而非 `float('inf')`，避免 int 与 float 比较的类型转换。

### 实测

同一台机器、**同一轮内轮转测量**（每轮跑遍所有变体，各取 9 轮最优值，`perf_counter`）：

| 场景（n = 10^5） | 用户版 | 早退版 | 前缀和+二分 |
| :--- | ---: | ---: | ---: |
| 一般随机 | 12.90 ms | 10.88 ms | 27.44 ms |
| 无解（`target > sum(nums)`） | 4.70 ms | 4.03 ms | 23.63 ms |
| 存在元素 ≥ `target` | 13.34 ms | **0.36 ms** | 27.21 ms |
| 全 1、`target = n` | 4.60 ms | 3.93 ms | 23.17 ms |

**拆解归因**（另一轮测量，n = 10^5，同机同轮）：

| 写法 | 一般随机 | 存在元素 ≥ target |
| :--- | ---: | ---: |
| 用户版（`min` + `enumerate`） | 13.18 ms（1.00×） | 14.51 ms（1.00×） |
| 仅把 `min()` 换成条件赋值 | 12.19 ms（1.08×） | 12.99 ms（1.12×） |
| 仅加早退 | 12.02 ms（1.10×） | 1.30 ms（**11.18×**） |
| `range` + 条件赋值 + 早退 | 10.98 ms（1.20×） | 1.18 ms（**12.28×**） |

**读法**：早退的价值是**条件性**的 —— 只有在"存在元素 ≥ `target`"（答案必为 1）的输入上才兑现 11~12 倍；在一般随机场景下早退根本不触发，此时 1.2× 的差距来自写法本身（`min()` → 条件赋值、`float('inf')` → `int` 初值、`enumerate` → `range`+索引），其中只有约 8~10% 能明确归因于 `min()`，余量与噪声同量级，**不宜过度解读**。二分版在四个场景下一律慢 2.1~5 倍（无解场景最悬殊：23.63 ms vs 4.70 ms）。

## 六、易错点与总结

### 易错点

1. **把 `while` 换成 `if`（左指针每轮最多挪一格）** —— 这在"**最长窗口**"家族里是成立的等价改写（长度单调不减 ⇒ 终值即历史最大），但本题是"**最短型**"，会大面积出错：56 组小批量对拍偏差 **12 / 56**，最小反例 `target = 2, nums = [1, 2]` → 得 **2**，正解 **1**（`[2]` 本身合法，但平移版左指针前进太慢，右端到 2 时窗口仍是 `[1, 2]`）。
   ⇒ **"换个写法省掉变量"这类结论不可跨家族迁移**；最短型必须把左端收缩到"刚不合法"为止，`while` 逐格收缩不能省。
2. **答案口径写成"终值"**（如直接返回 `n - left`）—— 这也是"最长型"的合法口径，搬到最短型上 56 组偏差 **45 / 56**；最小反例 `target = 1, nums = [1]` → 得 **0**，正解 **1**（左指针被推到的那个窗口早就不是最短的了）。`if + 终值` 同样错（偏差 42 / 56）。
   ⇒ **本题只认"每轮取 `min`"这一种口径。**
3. **忘记无解返回 0** —— `ans` 初值 `inf` 若从未被更新会直接把 `inf` 返回出去；必须有 `ans <= len(nums)`（或 `ans != inf`）兜底。这不是冗余特判。
4. **把内层 `while` 当成 O(n²) 的证据** —— `left` 累计只前进 n 次，摊还 O(1)。
5. **忽略"含 0 / 含负数"的边界** —— 本题约束已保证 `nums[i] >= 1`，`target >= 1`；若 `target == 0`，空窗口也满足 `0 >= 0`，上面代码会在 `while` 里空转到越界；若元素可为负，滑窗整体失效。

### 题型套路沉淀

- **滑窗成立性的判断入口**：先问"固定一端时，另一端单调移动会不会把**非法变合法**"。本题因**元素全正 ⇒ 窗口和随左端右移单调不增**，右端无需回退 ⇒ 滑窗成立。这条不成立时（度量可负），一律改用前缀和 / 单调队列 / DP。
- **最短型与最长型是两套必须成套记忆的口径**：

  | | 收缩方式 | 答案口径 | 中间状态 |
  | :--- | :--- | :--- | :--- |
  | **最短型**（本题） | `while` 收缩到刚不合法 | **每轮取 `min`** | 每轮合法 |
  | 最长型（预算内最长） | `while` 收缩到合法（或左指针平移版用 `if`） | 每轮取 `max`，或平移版取终值 `n - left` | 平移版可短暂非法 |

  两套的收缩方式、口径、能否换 `if` **全部不可互换** —— 这是本题最贵的两个坑。
- **判据写在"整个窗口"上**：本题判据 `total >= target` 天然是全局量；若换成"只看新加入元素"的局部判据（如"新元素自身 ≥ target"），就会漏掉"窗口整体超限但每个元素都不够"的情形，必然漏解。
- **识别信号**：题面出现"和 ≥ target 的最短连续子数组""乘积 < k 的最长""最多翻转 k 个的最长" ⇒ 都属于滑窗家族，先确认"度量逐元素累加且每个元素非负"，再按最短型 / 最长型套对应口径。
