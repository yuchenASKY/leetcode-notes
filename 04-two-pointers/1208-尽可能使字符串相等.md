# 1208. 尽可能使字符串相等

> **难度**：中等
> **标签**：字符串 · 滑动窗口 · 前缀和 · 二分查找
> **原题链接**：https://leetcode.cn/problems/get-equal-substrings-within-budget/

---

## 一、题目描述

两个**等长**字符串 `s`、`t`。把 `s` 的第 `i` 个字符改成 `t` 的第 `i` 个字符，要花 `|s[i] - t[i]|`（即两个字符 ASCII 码值之差的绝对值，可以为 0）。给定总预算 `maxCost`，问：`s` 中**最长**的连续子串（长度记为答案），使得把这一整段逐位改成 `t` 中对应位置的总开销不超过预算。若一个字符都改不动（任何单字符的开销都超预算），返回 0。

**要点**：题目问的是**子串**（连续区间），不是子序列；"转化整段"意味着把该区间内每一位的代价**求和**，而不是取最大值。

### 示例

```text
输入：s = "abcd", t = "bcdf", maxCost = 3
输出：3
解释：s 中的 "abc" 可以变为 "bcd"。逐位开销 1 + 1 + 1 = 3 ≤ 3，所以最大长度为 3。

输入：s = "abcd", t = "cdef", maxCost = 3
输出：1
解释：s 中任一字符变成 t 中对应字符的开销都是 2（a→c、b→d、c→e、d→f），
     预算 3 只够 1 个字符，所以最大长度为 1。

输入：s = "abcd", t = "acde", maxCost = 0
输出：1
解释：只有下标 0（a→a）和 2（c→c）开销为 0，它们不相邻，所以最大长度为 1。
```

### 约束条件

- `1 <= s.length <= 10^5`
- `t.length == s.length`
- `0 <= maxCost <= 10^6`
- `s` 和 `t` 都只含小写英文字母（故单字符开销落在 `[0, 25]`）

## 二、解题思路

### 核心思想

先把"两个字符串"压成"一个代价数组"，题目就只剩下面这一句话：

```text
c[i] = |ord(s[i]) - ord(t[i])|          (0 <= c[i] <= 25)

原题  ⟺  在【非负】数组 c 中，求元素和 <= maxCost 的【最长连续子数组】长度
```

于是它变成一道纯粹的"带预算的最长窗口"题 —— 和 `1004`（最多改 k 个 0）、`1493`（窗口里 0 的个数 ≤ 1）是同一族。

### 思路演进

1. **暴力解法**：枚举所有区间 `(l, r)`，用一个内层循环把 `c[l..r]` 求和，判断是否超预算。枚举 O(n²) × 求和 O(n) = **O(n³)**；把内层换成前缀和差分降一维，仍然 **O(n²)**。`n = 10^5` 时 O(n²) 是 10¹⁰ 量级，必然超时。

2. **观察到（关键的性质）**：`c[i] >= 0`。非负 ⇒ 固定右端 `r` 时，窗口和 `c[l] + ... + c[r]` 随 `l` 右移**单调不增**。所以：
   - 对每个 `r`，合法的左端点构成一个后缀 `l ∈ [L(r), r]`，其中 `L(r)` 是**唯一**的最小合法左端；
   - 想要最长的合法窗口，取 `l = L(r)` 即可 —— 以 `r` 结尾的最长合法窗口是唯一的。

3. **再观察到（单调性）**：`r` 右移一格时，窗口里只多了一个非负数，`L(r)` **只会右移、绝不左移**。于是左右指针都单调右移，总移动量 O(n)：

   ```text
   right 从 0 扫到 n-1：
       cost += c[right]
       while cost > maxCost:          # 收缩到合法为止
           cost -= c[left]; left += 1
       此刻 (left, right) 是"以 right 结尾的最长合法窗口"，长度 = right - left + 1
   取所有轮次长度的最大值
   ```

4. **落地到下标**：本题不需要真的把 `c` 建出来（见「六、常数级优化」里"预存代价数组反而慢"的实测），在窗口里进出时各算一次 `abs(ord(...) - ord(...))`，每个下标最多被算两次。

### 关键点

- **`c[i] >= 0` 是滑动窗口能用的全部依据**。若代价允许为负，"固定 `r` 时窗口和关于 `l` 单调"就不成立，滑窗直接失效 —— 那种题要换成**前缀和 + 单调队列**（典型如 `862`）。本题的 `|差值|` 天然非负，所以滑窗成立。
- 窗口的合法性由**窗口内部状态（和）**决定 —— 是滑窗的**第一类骨架**（对照 `3634` 的第二类：合法性只看两端点的值）。
- `left` 每轮最多前进 1 格、整趟最多 n 格 ⇒ **摊还 O(1)**，所以总复杂度 O(n)。
- 用户版每轮末尾的窗口是"**以 `r` 结尾**的最长合法窗口"，这个长度序列**不单调**：实测 3000 组随机输入里有 **82.9%** 出现过"长度下降"（例如 `c = [0, 0, 1, 0]`、`maxCost = 0`，长度序列是 `1, 2, 0, 1`）。所以 `ans = max(ans, temp)` 必须**每轮**做，不能只在最后取一次。
- 收缩用的 `while` **不能**换成 `if`：单步可能需要连缩多格（详见「五、优化评估」）。

## 三、代码实现

### 最终代码（用户提交版）

```python
class Solution:
    def equalSubstring(self, s: str, t: str, maxCost: int) -> int:
        ans = mid = left = temp = 0
        for i, j in zip(s, t):
            mid += abs(ord(j) - ord(i))      # mid: 当前窗口内代价和
            temp += 1                        # temp: 当前窗口长度
            while mid > maxCost:             # 超预算 → 收缩左端
                mid -= abs(ord(s[left]) - ord(t[left]))
                left += 1
                temp -= 1
            ans = max(ans, temp)             # 每轮都记峰值（长度序列不单调）
        return ans
```

> 变量语义：`mid` 是**窗口代价和**（名字容易误解成"中点"，实际是 `mid(sum)`），`temp` 是**窗口长度**，`left` 是左指针。
> 截图里的代码 **import 齐全**（本题只用 `str` / `int`，不需要 `typing` / `collections`），可直接运行。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码（用户版）** | **O(n)** | **O(1)** |
| 优化版 E（bytes + if 平移） | O(n) | O(n)（`s.encode()` 产生等长副本） |
| 优化版 C（预存代价数组） | O(n) | O(n) |
| 前缀和 + 二分（版本 D） | O(n log n) | O(n) |
| 暴力解（枚举区间 + 内层求和） | O(n³) | O(1) |
| 暴力解（枚举区间 + 前缀和差分） | O(n²) | O(n) |
| 理论下界 | Ω(n) | — |

> 复杂度中的 **n 指 `s` 的长度**（`t` 与它等长，故 2n 与 n 同阶）。
> 下界 Ω(n) 的依据：最坏情况下（例如 `maxCost >= 总和`）答案依赖**每一个**字符的开销，任何算法都必须至少读一遍全部输入，故不可能低于 O(n)。用户版与优化版都已达到该下界。

## 五、优化评估

**结论**：用户版**正确且已是 O(n) / O(1)**，但常数不是最小的 —— 官方 3 例、穷举 196,596 组、随机对拍 5000 组全部通过；实测存在一个**快 1.50~1.65×** 的等价写法（版本 E）。下面三处都经过实测，不是目测。

### 瓶颈分析

对用户版插桩统计（`n = 10⁵`）：

| 场景（n = 10⁵） | `ord` 调用次数 | 左指针推进格数 | 答案 |
| :--- | ---: | ---: | ---: |
| 随机小写, maxCost=30（频繁收缩） | 399,996 | 99,998 | 12 |
| 随机小写, maxCost=0（每步都收缩） | 400,000 | 100,000 | 3 |
| 随机小写, maxCost=1e9（从不收缩） | 200,000 | 0 | 100000 |
| s == t（全 0 代价）, maxCost=0 | 200,000 | 0 | 100000 |
| s == t（全 0 代价）, maxCost=1e9 | 200,000 | 0 | 100000 |
| 每位位移 1, maxCost=500 | 398,964 | 99,482 | 534 |
| a^n vs z^n（恒 25）, maxCost=1000 | 399,920 | 99,960 | 40 |
| t 按 a/z 交替, maxCost=25 | 399,998 | 99,999 | 8 |

读出来的三件事：

1. **循环体的主成本是 `ord()` 调用**：不收缩时 2n 次，频繁收缩时接近 **4n** 次（每个下标进窗口算一次、出窗口再算一次）。因为 `ord(s[left])` 在 `while` 里被重复求值 —— 每个下标最多被算两遍，所以仍是 O(n)，但常数被放大了一倍。
2. **左指针推进总格数 ≤ n**（实测 99,998 / 100,000），证实摊还 O(1) —— 没有隐藏的二次行为。
3. **每轮还有 `temp += 1` / `max()` 的固定开销**，在"从不收缩"的场景里它成了唯一的额外成本（此时窗口每次都在变长，`max` 每轮必做）。

### 可优化空间

三个独立的小改动，逐个实测（三种改法里有**两种在部分场景下是负优化**，一并列出）：

1. **`temp` 是纯冗余派生量**：`temp` 恒等于 `right - left + 1`。插桩断言（给用户代码加 `assert temp == right - left + 1`，跑 5000 组随机输入、共 **153,230 轮**）：**违反 0 次**。但要注意：删掉它需要引入 `enumerate` 拿 `right`，只是把一次自增换成一次拆包，收益很小 —— **真正能省掉它的办法是换写法**（版本 E 完全不需要长度变量）。
2. **`while` 不能退化成 `if`**（**如果要求"每轮结束时窗口合法"**）：`1100` / `3` / `3090` / `1493` 那几题"`while` 可退化成 `if`"依赖"每轮只加一个元素 ⇒ 超出量恒为 1"的前提，本题**没有**这个前提 —— 一次新加入的代价可以是 25，而要被移出的最左元素代价可能是 0，必须连缩多格。实测单步收缩格数分布（`n = 10⁵`）：

   | 场景 | 单步收缩 ≥ 2 格的轮次占比 | 单步最多收缩格数 |
   | :--- | ---: | ---: |
   | 全 1 代价, maxCost=0 | 0.0% | 1 |
   | 全 1 代价, maxCost=1 | 0.0% | 1 |
   | 0/25 交替, maxCost=25 | **50.0%** | 2 |
   | 随机 0..25, maxCost=25 | 22.3% | **9** |
   | 随机 0..25, maxCost=100 | 25.2% | 7 |
   | 随机 0..25, maxCost=1e9 | 0.0% | 0 |

   ⇒ **用户用 `while` 是对的**：它能保证"每轮结束时窗口都合法"。"恒定代价"输入上恰好不用连缩，但随机输入里近 1/4 的轮次要连缩 2~9 格。
   （若**只**关心答案、不关心窗口本身，`if` 版也是正确的 —— 见下面第 4 条与 `904` 笔记的四象限表。）
3. **换一个写法可以同时省掉 `temp`、`max()` 和多余收缩**（版本 A/E）：放弃"每轮窗口合法"，改成**窗口只平移、不收缩**，答案直接取 `len(s) - left`。详见下节。

### 优化代码（版本 E：推荐）

```python
class Solution:
    def equalSubstring(self, s: str, t: str, maxCost: int) -> int:
        sb, tb = s.encode(), t.encode()      # 迭代 bytes 直接拿 int，省掉 ord()
        left = cost = 0
        for right in range(len(sb)):
            cost += abs(tb[right] - sb[right])
            if cost > maxCost:               # 只前进一格 —— 窗口只平移、不收缩
                cost -= abs(tb[left] - sb[left])
                left += 1
        return len(sb) - left                # 窗口长度单调不减 ⇒ 答案 = n - left
```

**优化理由**：

| 改动 | 收益 |
| :--- | :--- |
| `while` → `if` + 答案改成 `n - left` | 窗口长度**单调不减** ⇒ 不需要任何长度变量、不需要每轮 `max()`；收缩逻辑从"缩到合法"变成"最多进一格" |
| `s.encode()` 后迭代 `bytes` | 迭代直接产出 `int`（ASCII 字节值），**`ord()` 调用从最坏 4n 次降到 0 次**，也顺带免掉 `zip` 的元组拆包 |
| 变量名 `cost` / `left` | 语义直白（`mid` 这个名字容易被误读成"中点"） |

**为什么"只平移不收缩"还能给出正确答案** —— 这一步反直觉，值得记牢：

- 这个写法**不再保证每一轮窗口都合法**。实测举例：`c = [1, 1, 5, 1, 1]`、`maxCost = 2` 时，`right = 2 / 3` 两轮的窗口和都是 **6 > 2**，是非法窗口。
- 它正确靠的是另一条论证：**左指针每轮最多前进 1 格 ⇒ 窗口长度 `right - left + 1` 单调不减**（实测 3000 组随机输入，长度下降 **0 次**；同规模下用户版的长度序列有 82.9% 的输入会下降）。于是"最终窗口长度" = "历史最大合法窗口长度" = 答案，`n - left` 直接就是答案。
- ⇒ **它靠的是"窗口长度的单调性"，不是"窗口的合法性"。** 这也决定了它的适用边界（见下一节）。

**实测（`n = 10⁵`，CPython 3.13.14，轮转测量、各取 9 次最优，单位 ms）：**

| 场景 | 用户版 | A `if` 平移 | B `bytes` | C 预存代价数组 | **E 合体** | D 前缀和+二分 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 随机小写, maxCost=30（频繁收缩） | 21.82 | 18.80 | 18.11 | 17.11 | **13.94** | 26.93 |
| 随机小写, maxCost=0（每步都收缩） | 21.17 | 18.54 | 16.75 | 16.03 | **13.86** | 26.93 |
| 随机小写, maxCost=1e9（从不收缩） | 11.92 | 10.98 | 11.98 | 14.02 | **7.95** | 26.15 |
| s == t 全 0 代价, maxCost=0 | 10.63 | 9.89 | 10.35 | 12.40 | **6.43** | 23.32 |
| s == t 全 0 代价, maxCost=1e9 | 10.73 | 9.93 | 10.40 | 12.84 | **6.63** | 24.21 |
| 每位位移 1, maxCost=500 | 21.09 | 18.09 | 18.69 | 17.46 | **13.60** | 26.84 |
| a^n vs z^n（恒 25）, maxCost=1000 | 21.20 | 19.41 | 17.59 | 16.48 | **13.54** | 26.22 |
| t 按 a/z 交替, maxCost=25 | 21.96 | 17.98 | 17.95 | 16.60 | **13.33** | 26.96 |
| **相对用户版** | 1.00× | 1.08~1.22× | 0.98~1.26× | 0.83~1.33× | **1.50~1.65×** | 0.44~0.81× |

读表和取舍：

- **版本 E 全场景最快（1.50~1.65×）**，而且 8 个场景里相对顺序完全一致 —— 说明差距是真实的，不是噪声。
- **版本 B（只换 `bytes`）的收益取决于收缩次数**：频繁收缩的场景里省下的是接近 2n 次 `ord()`，能快 1.13~1.26×；"从不收缩"场景的 `ord()` 本来就只有 2n 次，`s.encode()` 的拷贝成本正好抵掉，实测 **0.98~1.03×（持平）**。⇒ 单换 `bytes` 是"收缩越多越赚"，收益不稳定。
- **版本 C（先把 `c` 整个算出来）在部分场景反而更慢（0.83~0.86×）**：白建一个 n 长的列表 + 多一趟完整遍历，只有收缩极频繁时（1.28~1.33×）才划得来。
- **版本 D（前缀和 + 二分，O(n log n)）慢到 0.44~0.81×**：和 `3634` 那轮踩到的坑**完全同款** —— 左指针的推进是**摊还 O(1)**（整趟只推进 n 格），用 O(log n) 的二分去"替它算"，是典型负优化。**算法上更优雅 ≠ 跑得更快。**

> 版本 E 的空间从 O(1) 变成 O(n)（`s.encode()` 的副本）。`n ≤ 10⁵` 时这点内存可忽略；若题目把空间卡到 O(1)，就退回用户版的 `ord` 写法、只保留 `if` 平移的改动（即版本 A，实测仍有 1.08~1.22×）。

### 常数级优化（可选）

- 循环内**不要重复求值**：`abs(ord(s[left]) - ord(t[left]))` 在 `while` 里每轮都算一次 —— 这是文档里"把下标算两遍"的根源，`bytes` 版本顺手解决了。
- `for i, j in zip(s, t)` 每轮建一个元组再拆包；`for right in range(len(sb))` + 下标访问省掉这次拆包（也顺手拿到了 `right`）。
- `max(a, b)` 是函数调用；在热循环里换成 `if L > ans: ans = L` 更便宜（版本 E 干脆不需要）。

## 六、易错点与总结

### 易错点

- **把"子串"当"子序列"**：题目问连续区间。`示例 3`（`s="abcd", t="acde", maxCost=0`）答案 1 而不是 2，就是因为两个 0 代价的位置不相邻。
- **漏绝对值**：开销是 `|s[i] - t[i]|`。写成 `ord(s[i]) - ord(t[i])` 会让"变大"的方向变成负代价，滑窗的非负前提被破坏，结果全错。
- **把用户版里的 `while` 换成 `if`（但答案仍取每轮 `max`）**：**答案不会错，但窗口不再每轮合法**。实测随机输入里 22~25% 的轮次需要连缩 ≥ 2 格（单步最多 9 格），换 `if` 后这些轮次结束时窗口仍超预算（只是"长度数字"恰好等于某个真实存在的合法窗口长度，见本仓库 `904` 笔记的「收缩方式 × 答案口径」四象限表）。**若后续还要用这个窗口做别的事，就必须留在 `while`。**
- **只换一半（`while` 配"终值"口径）**：会错，34% 量级（`904` 上穷举 19,394 组错 6,600 组）。`while` 版左端一次可能走多格，终值窗口不是最长窗口，必须每轮取 `max`。
- **`ans` 放到循环外**：只统计最后一轮窗口长度，会把中间的峰值丢掉（本题长度序列 82.9% 的输入会下降）。
- **把"`if` 平移 + 答案取 `n - left`"这个把戏搬到"最短型"题目上**：会错。同样的搜索空间穷举对比（代价取值 `{0,1,2,3}`、`n ≤ 6`，5460 个代价数组）：本题（**最长**型，`maxCost = 0..5`）32760 组 **0 错**；换成 `209`（**最短**型，和 ≥ target 的最短子数组，target = 1..7）38220 组里 **错 30568 组（80.0%）**，首个反例是 `c = [1, 1], target = 1`（把戏给 2，真值 1）。原因就是上面那条：它靠的是"窗口长度单调不减"，而"最短"要的恰恰是长度变小。
- **忘写 `maxCost` 可以为 0 的情况**：此时只有"全 0 代价"的连续段合法（任一段 `s[i] == t[i]`），别漏。
- **复杂度别写成 O(n·25)**：单字符开销有上界 25 只是让常数可控，与复杂度无关；`n = 10^5` 时 O(n) 与 O(25n) 要分清。

### 题型套路沉淀

- **转化模板**：把"两个字符串/数组的逐位差异"先收成一个**代价数组** `c[i]`，题目就退化成"在 `c` 上找和 ≤ 预算的最长窗口"。识别信号：题面出现"逐位 / 对应位置 / 开销（cost）/ 预算（budget）"。
- **`c[i] >= 0` 决定算法路线**：
  - 非负 → 同向双指针（本题）；
  - 允许负数 → 固定右端时窗口和不单调，滑窗失效，必须换**前缀和 + 单调队列**（`862` 最短子数组和 ≥ k）。
- **带预算的最长滑窗，有两个正确写法，必须分清它们维护的是什么**：

  | 写法 | 每轮窗口是否合法 | 维护的状态 | 答案 | `while` 能否换 `if` |
  | :--- | :--- | :--- | :--- | :--- |
  | 收缩版（用户版） | **是**（收缩到合法为止） | 窗口和 + 窗口长度 + 左指针 | 每轮取长度的 `max` | 能换（但换了窗口就不再每轮合法；**答案口径必须一起换成 `n - left`**，只换一半会错） |
  | 平移版（版本 E） | **否**（可以短暂非法） | 窗口和 + 左指针 | `n - left` | 只能是 `if`（本就是"只进一格"） |
  | 适用题型 | 最长 / 最短**都行**，最短型必须用收缩版 | — | 平移版**只适用最长型** | — |

  > **口径与收缩方式必须配套**（`904` 笔记有完整的四象限穷举）：`while` + 终值 ❌（错 34%）、`while` + 每轮 `max` ✅、`if` + 终值 ✅、`if` + 每轮 `max` ✅。
  > 原因：`if` 版的窗口长度**单调不减**且恒等于"到 r 为止出现过的最大合法窗口长度"，所以终值即答案；`while` 版窗口每轮合法但长度会下降，所以必须每轮 `max`。

- **同型题**：
  - `1493. 删掉一个元素以后全为 1 的最长子数组`（**本仓库同目录已有**）—— 同为"窗口内某度量 ≤ 上限"的变长滑窗，判据是"0 的个数 ≤ 1"，答案口径是"长度 − 1"；
  - `904. 水果成篮`（**同目录已有**）—— 同为"窗口内某度量 ≤ 上限"，那里是"**不同种类数** ≤ 2"（按键数），本题是"代价和 ≤ 预算"（按和）；两题的「收缩方式 × 答案口径」四象限表结论完全一致；
  - `1004. 最大连续 1 的个数 III` —— 判据换成"窗口内的 0 不超过 k 个"，骨架一模一样；
  - `424. 替换后的最长重复字符` —— 判据换成"窗口长度 − 最多字符数 ≤ k"；
  - `3 / 3090. 每个字符最多出现 k 次`、`1100. 长度为 K 的无重复字符子串`（同目录已有）—— 判据换成"字符出现的次数"；
  - `209. 长度最小的子数组` —— **最短**型的对照组（本题的把戏不能搬过去）；
  - `3634. 使数组平衡的最少移除数目`（同目录已有）—— 同为双指针，但窗口合法性由**两端点的值**决定（第二类骨架）。
