# 904. 水果成篮

> **难度**：中等
> **标签**：数组 · 哈希表 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/fruit-into-baskets/

---

## 一、题目描述

一排果树，`fruits[i]` 是第 `i` 棵树的**水果种类**。你有两个篮子，每个篮子只能装**一种**类型，但容量无限。从任意一棵树开始向右连续采摘，每棵恰好摘一个；一旦遇到两种篮子都装不下的类型就必须停下。求最多能摘多少个。

一句话：**求最长的连续子数组，要求其中不同元素种类数 ≤ 2。**

### 示例

```text
输入：fruits = [1,2,1]
输出：3
解释：可以采摘全部 3 棵树。

输入：fruits = [0,1,2,2]
输出：3
解释：可以采摘 [1,2,2] 这三棵树。

输入：fruits = [1,2,3,2,2]
输出：4
解释：可以采摘 [2,3,2,2] 这四棵树。

输入：fruits = [3,3,3,1,2,1,1,2,3,3,4]
输出：5
解释：可以采摘 [1,2,1,1,2] 这五棵树。
```

### 约束条件

- `1 <= fruits.length <= 10^5`
- `0 <= fruits[i] < fruits.length` —— 值域被 **n 卡住**，这一条后面会用到（可以用桶数组代替哈希表）

## 二、解题思路

### 核心思想

```
答案 = max{ r - l + 1 : [l, r] 内不同元素种类数 <= 2 }
```

约束只跟**窗口内部有多少种元素**有关，且「从左端删掉元素」只会让种类数变少不会变多（**前缀封闭**）⇒ 固定右端时，合法的左端构成一个后缀 ⇒ 同向双指针成立：左指针整趟只推进 `≤ n` 次，摊还 O(1)。

### 思路演进

1. **暴力解法**：枚举 `(l, r)` 再数种类数，O(n³)（`set(fruits[l:r+1])`）；用「右端扩张时增量维护 set」降到 O(n²)。`n = 10^5` 时 O(n²) 是 10^10，不可行。
2. **观察到**：窗口右端右移 1 格，种类数**最多 +1**；但窗口左端右移 1 格，种类数**最多 −1**。也就是说"违法量"不是恒等的 —— 这一点决定了收缩逻辑必须用 `while` 而不是 `if`（见下）。
3. **优化为**：变长滑窗。`cnt[x]` 记窗口内类型 `x` 的个数，`len(cnt)` 就是当前种类数，`len(cnt) > 2` 时从左端逐个吐元素，**计数归零就 `del`**（这是本题的关键细节）。

### 关键点

- **判据是「按键数」`len(cnt) > 2`，不是「按值」`cnt[x] > k`**。这把它和 `3` / `3090`（每字符最多 k 次）彻底分开：那两题的判据只看 `cnt[ch]`，所以**不需要 `del`**；本题的判据是"有多少个键"，**必须 `del`**，否则 `len(cnt)` 只增不减。
  （`1100` 的「定长窗口里 `len(cnt) == k`」是同一个"按键数"判据的定长版本 —— 两道题合起来正好覆盖两种窗口形态。）
- **被淘汰的永远是"右端那一种之外的那一种"**。因为窗口右端的类型最后出现位置就是 `right`（最大），而另一种的最后出现位置 `≤ right-2`，从左端吐元素时必然是它先被吐光。实测：3000 组随机输入里共 **42,416 次收缩，淘汰掉右端类型的次数 = 0**。
- **单步收缩量可以很大**：实测"三段轮流出现、每段 400 个"的输入上，单步最多吐 **400** 个元素；26 种随机输入上 7.1% 的轮次需要连吐 ≥ 2 格（最多 5 格）。所以「`while` 可退化成 `if`」在这里不成立 —— 但注意，**这只影响"窗口是否每轮都合法"，不影响答案正确性**，见第五节的四象限表。

## 三、代码实现

### 最终代码

> 截图里只有 `class Solution:` 开头，`List` 与 `defaultdict` 都**没有 import**，已补上。
> 缺 `List` 会在**函数定义的那一刻**就抛 `NameError`（比缺失 `defaultdict` 的"调用时才抛"更早暴露）。

```python
from typing import List
from collections import defaultdict


class Solution:
    def totalFruit(self, fruits: List[int]) -> int:
        ans = left = 0
        cnt = defaultdict(int)
        for right, in_ in enumerate(fruits):
            cnt[in_] += 1
            while len(cnt) > 2:
                out = fruits[left]
                cnt[out] -= 1
                if cnt[out] == 0:
                    del cnt[out]
                left += 1
            ans = max(ans, right - left + 1)
        return ans
```

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码（用户版）** | O(n) | O(1)（哈希表同时最多 3 个键） |
| 方案一 `C` 桶数组 + `distinct` | O(n) | O(n)（借 `fruits[i] < n` 开桶） |
| 方案二 `D` 双类型位置法 | O(n) | **O(1)**（4 个整型变量，零哈希） |
| `A` 平移版（`if` + `n - left`） | O(n) | O(1) |
| 朴素解法（增量 set 枚举左端） | O(n²) | O(3) |
| 暴力解法（枚举 + 重数种类） | O(n³) | O(n) |
| 理论下界 | Ω(n)（至少要读一遍数组） | Ω(1) |

> 复杂度中的 **n 指 `fruits` 的长度**。
> "O(1) 空间"要说清楚：用户版的字典里**同时**至多 3 个键（两种在窗口内 + 刚加进来的一种），所以是 O(1) 而不是 O(值域)；`del` 的作用正是把删空的键及时清掉。

## 五、优化评估

**结论**：用户版**正确**，而且是标准模板；但"标准"不等于"最快" —— 换成**桶数组**可提速 1.1~1.8×，换成**双类型位置法**可提速 1.4~3.9×，且后者把空间压到 O(1)、完全不用哈希。

### 瓶颈分析

瓶颈**全在哈希表**。用户版每元素要付的字典操作实测如下（`n = 10^5`，插桩计数）：

| 场景 | 写 `cnt[x]+=1` | `len(cnt)` | 读 + 写（吐元素） | `del` | 合计/元素 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 全相同（从不收缩） | 1.00 | 1.00 | 0 | 0 | 2.00 |
| 26 种随机 | 2.00 | 2.00 | 1.92 | 0.92 | ≈ 6.8 |
| 3 种循环 | 2.00 | 2.00 | 2.00 | 1.00 | 7.00 |

对照方案 `D`（双类型位置法）在同样场景下每元素只做 **1~2 次整数比较、0 次哈希**。这解释了下面那张表里 3~4 倍的差距：**不是循环结构的问题，是数据类型的问题。**

### 可优化空间

| 场景（n = 10⁵） | 用户版 | `A` if 平移 | `C` 桶数组 | `D` 双类型 O(1) | `F` 桶 + 平移 | `D` / 用户版 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 全相同 | 15.87 | 8.56 | 13.97 | 7.83 | **7.58** | 2.03× |
| 2 种交替 | 15.57 | 8.33 | 14.14 | 11.27 | **7.56** | 1.38× |
| 3 种循环 | 38.37 | 29.04 | 21.76 | **10.79** | 15.50 | 3.56× |
| 26 种随机 | 39.19 | 26.52 | 22.69 | **11.61** | 15.90 | 3.38× |
| 全不同 | 38.10 | 27.83 | 23.06 | **11.04** | 16.95 | 3.45× |
| 长段 1+1+1 交替 | 28.74 | 18.53 | 21.06 | **7.43** | 14.18 | 3.87× |
| 两段式（2 种 → 3 种） | 30.35 | 13.70 | 22.12 | **9.99** | 11.55 | 3.04× |

> 单位 ms，CPython 3.13，**轮转测量 21 轮各取最优**；随后用另一份 3 轮独立复测，同版本波动约 2%（见「七、验证记录」）。

三条规律：

- **`D` 在"种类多 / 收缩重"的输入上碾压**（3.3~3.9×）——因为它连哈希都没有；在"只有 2 种类型、从不收缩"的输入上优势收窄到 1.4×，因为此时两种实现做的事都很少。
- **`F`（桶 + 平移）在"从不收缩"的输入上最快**（7.56~7.58 ms），但在收缩重的输入上反而是最慢的一档（15.9~16.9 ms）—— 每次收缩都要"读 `distinct`、读写两个桶位、再判一次 `distinct`"，比 `D` 的纯比较贵得多。
- **`C`（骨架几乎不动，只把 dict 换成桶数组 + 显式 `distinct`）是最省心的改良**：1.1~1.8×，且代码结构和用户版一一对应，不会引入新的不变量。

### 优化代码

```python
# 方案一（性价比最高，推荐）：dict → 桶数组 + 显式 distinct，骨架不变
from typing import List


class Solution:
    def totalFruit(self, fruits: List[int]) -> int:
        cnt = [0] * len(fruits)      # 约束保证 fruits[i] < n，所以桶开 n 个就够
        left = ans = distinct = 0
        for right, x in enumerate(fruits):
            if cnt[x] == 0:          # 新类型进窗口
                distinct += 1
            cnt[x] += 1
            while distinct > 2:
                y = fruits[left]
                cnt[y] -= 1
                if cnt[y] == 0:      # 有类型被吐光 -> 种类数减一
                    distinct -= 1
                left += 1
            w = right - left + 1
            if w > ans:
                ans = w
        return ans
```

```python
# 方案二：零哈希、O(1) 空间 —— 只盯住「右端类型」与「另一种类型」
from typing import List


class Solution:
    def totalFruit(self, fruits: List[int]) -> int:
        ans = left = 0
        cur = fruits[0]          # 窗口右端的类型
        other = -1               # 窗口里的另一种类型（只可能有这一种）
        last_other = -1          # other 在窗口内最后一次出现的位置
        for right, x in enumerate(fruits):
            if x == cur:                        # 同类型：直接延长
                pass
            elif x == other:                    # 换成另一种：交换角色
                other, cur = cur, x
                last_other = right - 1          # 原来的 cur 就在上一格
            else:                               # 第三种类型：把 other 整块丢掉
                left = last_other + 1
                other, last_other = cur, right - 1
                cur = x
            w = right - left + 1
            if w > ans:
                ans = w
        return ans
```

**优化理由**：

- 方案一：桶数组替代字典，`distinct` 替代 `len(cnt)`。**语义与用户版逐行对应**（`distinct > 2` ↔ `len(cnt) > 2`，`del cnt[out]` ↔ `distinct -= 1`），只是把哈希换成数组下标。代价：依赖 `fruits[i] < n` 这条约束，空间从 O(1) 变 O(n)。
- 方案二：既然是"至多 2 种"，就**没必要维护一张计数表** —— 只要知道"右端是哪种、另一种是哪种、另一种最后出现在哪"。第三方类型到来时，必须把 `other` 整块丢掉，新窗口就是 `[last_other + 1, right]`。全程只有 4 个整型变量，O(1) 空间、零哈希。
  ⚠️ 这里最容易写错的是「怎么算新的左端」：**不是** `right - cnt[cur]`（`cur` 的出现可以是不连续的，`[1,2,1]` 里类型 `1` 有 2 个但第一段只有 1 个），而必须是 `last_other + 1`。
- 方案 `A`（平移版）代码最短（连 `ans` 都不用维护），但见下面「常数级优化」的最后一条：它省下的是常数，不是复杂度，而且"窗口是否合法"这个性质会丢。

### 常数级优化（可选）

| 改动 | 效果 |
| :--- | :--- |
| `ans = max(ans, w)` → `if w > ans: ans = w` | 小（约 3~5%），但零风险 |
| `for right, x in enumerate(fruits)` → `for x in fruits`（配合"平移版"就不需要 `right`） | **在"从不收缩"的输入上很显著**：全相同 15.87 → 8.56 ms，2 种交替 15.57 → 8.33 ms。省的是每轮一次元组拆包 + 一次 `right - left + 1` 运算 + 一次 `max()` 调用 |
| 把 `while` 换成 `if`（左指针每轮最多走一格） | 只在"收缩重"的输入上省一点（38.37 → 29.04 是 1.32×）；**但要连答案口径一起换**（见下表），不要只换一半 |

**「收缩方式 × 答案口径」四象限**（穷举验证，`七、验证记录` 有原始数据）：

| 收缩方式 | 答案怎么取 | 是否正确 | 实测 |
| :--- | :--- | :--- | :--- |
| `while`（收缩到合法为止） | 每轮 `max`（用户版） | ✅ | 21,251 组穷举 0 错 |
| `while` | 终值 `n - left` | ❌ **34.0% 错** | 反例 `fruits = [0,0,1,2]`（把戏给 2，真值 3） |
| `if`（每轮最多走一格） | 终值 `n - left` | ✅ | 21,251 组穷举 0 错 |
| `if` | 每轮 `max` | ✅（与上一行等价，因长度单调不减） | 23,490 组穷举 0 错 |

为什么后两行都对？关键不变量：**`if` 版每轮结束时窗口长度 `ℓ_r` 恰好等于「前 r 个元素里出现过的最大合法窗口长度 `B_r`」** ——
- `ℓ` 单调不减（`left` 每轮最多走一格），且 `ℓ_r ≤ B_r` 恒成立（窗口合法时显然；不合法时本轮没长，归纳即可）；
- 若某轮 `B` 增加，那么"以 `r` 结尾的最长合法窗口"就是 `[r - B_r + 1, r]`，而 `if` 版此时的左端恰好就在这里（归纳），于是无需收缩，`ℓ_r = B_r`。

所以 `if` 版的**窗口本身可能是非法的**（实测 26 种随机输入：10⁵ 轮里 **99,953 轮** `len(cnt) == 3`），但它的**长度数字**始终对应一个真实存在的合法窗口，终值就是答案。
反过来，`while` 版每轮窗口都合法，但长度会下降（实测 26 种随机输入 7.1% 的轮次下降），所以必须每轮 `max`。
**这就是"两种写法都正确"的原因，也是"只换一半（`while` 配终值）会错 34%"的原因。**

## 六、易错点与总结

### 易错点

- **忘记 `del cnt[out]`**：`len(cnt)` 从此只增不减，`while len(cnt) > 2` 会把 `left` 一路推到越界。实测 `[1,2,3]`、`[1,2,1,3]`、`[1,2,3,2,2]` 三种输入全部 `IndexError`。
- **把「收缩版」配上「终值」口径**：穷举 19,394 组里错 **6,600 组（34.0%）**，首个反例 `fruits = [0,0,1,2]`。收缩版的 `left` 会一次跳多格，终值窗口不是最长窗口。
- **以为 `if` 版的窗口每轮都合法**：它只是**长度**对，窗口内容可能仍含 3 种类型（10⁵ 轮里 99,953 轮如此）。如果后续还要拿这个窗口做别的事（统计、判重），就必须用 `while`。
- **用 `cur` 在窗口内的个数当"它紧贴右端的连续段长度"**（即写 `left = right - cnt[cur]`）：会错，穷举 19,394 组**错 1,776 组（9.2%）**，首个反例 `fruits = [0,1,1,2,1]`（真值 4，该写法给 3）—— 一个类型的出现可以**不连续**，`[1,2,1]` 里类型 `1` 有 2 个但第一段只有 1 个。正确做法是用 `last_other + 1`。
- **位置法少写那个 `+1`**（`left = last_other`）：穷举 19,394 组**错 19,324 组（99.6%）**，连 `[0,1]` 都错。
- **以为"丢最左边那一种"就行**：要丢的是**最后出现位置最小**的那一种（等价于"除去右端类型后的那一种"），不是"最左边那个元素所在的类型"。
- **值域约束别忽略**：方案一的桶数组依赖 `fruits[i] < fruits.length`；如果题目改成"种类可以是任意大的整数"，桶数组就不成立（要么开 `max+1`，要么退回字典）。

### 题型套路沉淀

- **识别信号**：题面出现"两种 / 两个篮子 / 至多 K 种"，且问**最长连续段** ⇒ 「不同种类数 ≤ K」的变长滑窗。K=2 就是本题；K 可变的版本见 `159`（K=2 的字符串版）、`340`（任意 K）。
- **本仓库滑窗家族里，这是第三种判据**（前两种：按值计数 `3`/`3090`/`1493`、按和 `1208`/`1493`）：

  | 判据 | 收缩到"谁"被吐光 | 需要 `del` 吗 | 已归档 |
  | :--- | :--- | :--- | :--- |
  | 按键数 `len(cnt) > K` | 一种类型整体吐光（可能要连吐很多格） | **必须** | `904`（K=2）、`1100`（定长版，`len(cnt) == k`） |
  | 按值 `cnt[ch] > k` | 只需吐一格（超出量恒 1） | 不需要 | `3`、`3090`、`1493` |
  | 按和 `窗口和 > 预算` | 看代价大小，可能要连吐多格 | 不需要 | `1208` |

- **同型题**：
  - `159. 至多包含两个不同字符的最长子串` —— 本题的字符串版，判据 `len(cnt) > 2` 完全一致；
  - `340. 至多包含 K 个不同字符的最长子串` —— 把 2 推广成任意 K，骨架一字不改；
  - `3. 无重复字符的最长子串`、`3090. 每个字符最多出现两次的最长子字符串`（**本仓库同目录已有**）—— 同为变长滑窗，但判据是**按值**，正好是"需不需要 `del`"的对照组；
  - `1208. 尽可能使字符串相等`（**同目录已有**）—— 同为"窗口内某度量 ≤ 上限"，那里是"和"，这里是"种类数"；两题的「收缩方式 × 答案口径」四象限表结论完全一致；
  - `1100. 长度为 K 的无重复字符子串`（**同目录已有**）—— 同一个"按键数"判据的**定长**版本；
  - `992. K 个不同整数的子数组` —— 从"最长一段"变成"计数所有合法子数组"，滑窗要额外做"恰好 K = 至多 K − 至多 K−1"的容斥。

另补 8 条边界用例（`[7]→1`、`[5,5]→2`、`[1,2]→2`、`[1,2,3]→2`、`[1,1,1,1,2,3]→5`、`[1,1,1,1,2,3,3,3,3,3]→6`、`[0,0,0]→3`、`[1,2,1,2,1,2,3]→6`），
期望值**全部先用独立的 `O(n³)` 暴力解逐条核实**再写进脚本。

**2. 基准自检**：先用完全独立的 `O(n³)` 暴力（枚举所有 `(l, r)` + 每次重新 `set`，不依赖任何增量假设）校验 `O(n²)` 基准，800 组（`n ≤ 9`、字母表 2~6）：**偏差 0 组**。再用它当真值。

**3. 穷举扫描**：字母表 2/3/4/5 分别取 `n ≤ 10/8/6/5`，共 **21,251 组**全枚举，与 `O(n³)` 真值逐一比对 —— 6 个版本**错误均为 0 组**。

**4. 随机对拍**：**5000 组**（`n ≤ 40`，字母表取 2/2/3/3/4/5/8/40/1000）：6 个版本**偏差全部为 0**。

**5. 插桩探测**（`n = 10⁵`）：

| 输入 | 单步收缩最大格数 | 连缩 ≥ 2 格轮次占比 | 用户版窗口非法轮次 | 平移版窗口非法轮次 | 收缩版长度下降轮次占比 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 全相同 | 0 | 0.0% | 0 | 0 | 0.0% |
| 2 种交替 | 0 | 0.0% | 0 | 0 | 0.0% |
| 3 种循环 | 1 | 0.0% | 0 | 0 | 0.0% |
| 26 种随机 | 5 | 7.1% | 0 | **99,953** | 7.1% |
| 全不同 | 1 | 0.0% | 0 | 0 | 0.0% |
| 长段 1+1+1 交替 | **400** | 0.2% | 0 | **98,952** | 0.2% |

> 「用户版窗口非法轮次 = 0」验证了"收缩版每轮窗口都合法"；「平移版非法 99,953/10⁵」验证了"`if` 版只是长度对、窗口不对"。
> 「收缩版长度下降」正是用户版必须每轮 `max` 的原因。

**6. 被淘汰的类型**：3000 组随机输入（`n ≤ 60`、字母表 4）里共 **42,416 次收缩事件**，其中"淘汰掉窗口右端类型"的次数 = **0** ⇒ 印证"被淘汰的必然是另一种类型（最后出现位置最小者）"。

**7. 「收缩方式 × 答案口径」四象限穷举**（与 `1208` 同款矩阵，本题数据）：

| 组合 | 搜索空间 | 错误数 |
| :--- | :--- | :--- |
| `while` + 每轮 `max` | 21,251 组 | 0 |
| `while` + 终值 `n-left` | 19,394 组 | **6,600（34.0%）**，首例 `[0,0,1,2]` |
| `if` + 终值 `n-left` | 21,251 组 | 0 |
| `if` + 每轮 `max` | 23,490 组 | 0 |

> 顺带复核了 `1208` 笔记里"把 `while` 换成 `if` 会错"的说法：用 `1208` 自己的穷举空间（代价 `{0,1,2,3}`、`n ≤ 6`、`maxCost 0..5`，共 **32,760 组**）重测，`if` + 每轮 `max` 与 `if` + 终值**错误均为 0**，收缩版也是 0 —— 该说法已被本次实验推翻，两处笔记（`1208` 的易错点与结论表）已同步修正。

**8. 微基准**：`n = 10⁵`，7 个场景（含"从不收缩 / 收缩重 / 种类极散 / 长段交替"），**轮转测量**（`for rep in range(21): for variant: ...`，各版取自身最优）。
随后用同一输入连续 3 轮独立复测（每轮各版取 15 次最优）核对噪声：`user 31.37/31.01/31.27 ms`、`A_if 18.09/18.42/17.94`、`D_pos 9.78/9.53/9.63`、`F_listIf 13.98/14.36/13.94` ⇒ 同版本波动约 **2%**，远小于版本间差距，表中排序可信。数据见「五、优化评估」两张表。

**9. 两种"看起来更聪明"的优化写法被实测证伪**（穷举 19,394 组，字母表 2/3/4、`n ≤ 11/8/6`）：

| 写法 | 错误组数 | 首个反例 |
| :--- | ---: | :--- |
| `left = right - cnt[cur]`（把计数当连续段长度） | 1,776（**9.2%**） | `[0,1,1,2,1]`：给 3，真值 4 |
| `left = last_other`（少写 `+1`） | 19,324（**99.6%**） | `[0,1]`：给 3，真值 2 |

还有两条是"直接崩"而非"算错"：忘记 `del cnt[out]` 会让 `while` 把 `left` 推到越界（`[1,2,3]` / `[1,2,1,3]` / `[1,2,3,2,2]` 全部 `IndexError`）；收缩版配"终值"口径错 34.0%（见第 7 条）。
