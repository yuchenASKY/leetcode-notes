# 2537. 统计好子数组的数目

> **难度**：中等
> **标签**：数组 · 哈希表 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/count-the-number-of-good-subarrays/

---

## 一、题目描述

给定整数数组 `nums` 和整数 `k`。若某个子数组 `arr` 中有**至少 `k` 对**下标 `(i, j)` 满足 `i < j` 且 `arr[i] == arr[j]`，它就是**好子数组**。

求 `nums` 中好子数组的**个数**（子数组指原数组中一段连续、非空的元素序列）。

注意：本题要统计的是所有好子数组的**条数**，不是最长长度。同一个值可能出现多次，`n` 可达 `10^5`，答案本身可以到 `10^9` 量级。

### 示例

```text
示例 1：
输入：nums = [1,1,1,1,1], k = 10
输出：1
解释：全数组共 5 个 1，相等对数为 C(5,2) = 10，是整个数组唯一能满足 k = 10 的子数组。

示例 2：
输入：nums = [3,1,4,3,2,2,4], k = 2
输出：4
解释：4 个好子数组分别是
      [3,1,4,3,2,2]（2 对：两个 3、两个 2）
      [3,1,4,3,2,2,4]（3 对）
      [1,4,3,2,2,4]（2 对）
      [4,3,2,2,4]（2 对）
```

### 约束条件

- `1 <= nums.length <= 10^5`
- `1 <= nums[i], k <= 10^9`
- 子数组内某值的出现次数为 `c` 时，它贡献 `c * (c - 1) / 2` 对

## 二、解题思路

### 核心思想

记 `f(l, r)` 为区间 `[l, r]` 内的相等对数。**固定右端点 `r` 时，`f(·, r)` 关于 `l` 单调不增** —— 左端点右移等于从窗口里删元素，对数只会变少或不变。所以「以 `r` 结尾的好子数组」的左端点集合一定是一段**前缀** `[0, T_r]`，个数就是 `T_r + 1`。

于是每轮只需要维护「最右的那个合法左端点的右边一格」这一个指针（记作 `left`），答案 `ans += left`。

### 思路演进

**1. 暴力解法**

两层循环枚举所有子数组 `[l, r]`，每得到一个子数组就数一遍内部相等对数 —— 数对数本身还要 O(n²)，总计 O(n⁴)。稍作改进即可降到 O(n²)：固定 `l` 向右扩 `r`，边扩边维护「窗口内每个值的出现次数」，新加入元素 `x` 时它带来的新对数恰好等于 `cnt[x]`（`x` 在窗口内已有的出现次数）：

```python
for l in range(n):
    cnt, pairs = {}, 0
    for r in range(l, n):
        pairs += cnt.get(a[r], 0)
        cnt[a[r]] = cnt.get(a[r], 0) + 1
        if pairs >= k:
            ans += 1
```

时间 O(n²) + 空间 O(n)。`n = 10^5` 时约 `5 × 10^9` 次内层迭代，必然超时。

**2. 瓶颈定位**

慢在两处叠加：

- 同一对元素之间的「相等关系」被反复重算 —— 外层换一个 `l`，内层就从零重建一遍计数，前一轮的 `cnt` / `pairs` 信息全被丢掉；
- 从「答案」的角度看更明显：答案只关心 *每个右端点 `r` 上有多少个左端点合法*，而暴力把 `(l, r)` 的每一种组合都枚举了一遍，其中大量组合只为得出「合法 / 不合法」这一个比特。

**3. 关键转化**

两个单调性把 O(n²) 砍成 O(n)：

- **`f(l, r)` 关于 `l` 单调不增** ⇒ 以 `r` 结尾的合法左端点是一段前缀，个数 = `T_r + 1`。不需要枚举每一个 `l` 去判断，只要知道分界点 `T_r` 在哪。
- **`f(l, r)` 关于 `r` 单调不减**（右端延长只会新增对数，不会消去）⇒ 「以 `r - 1` 结尾合法的左端点，以 `r` 结尾依然合法」⇒ 分界点 `T_r` **只增不减**，可以用一个单向移动的指针维护，整趟摊还 O(n)。

一句话：**原来对每个 `l` 各自统计（重复劳动）；现在利用「关于 `l` 单调」把答案压成每轮一个计数，再利用「关于 `r` 单调」保证左指针单向移动。**

实现时维护窗口 `[left, j]`，其语义是「**以 `j` 结尾的最长的非好窗口**」——

- 收缩结束时 `pairs < k`，即窗口 `[left, j]` 自己**不合法**；
- 而 `[left - 1, j]` 一定合法（否则上一轮 `while` 不会停）；
- 所以合法的左端点恰好是 `0 .. left - 1`，共 `left` 个，`ans += left`。

⚠️ 这与常见的「收缩到合法为止、再取窗口长度」的滑窗模板**方向相反**：本题约束是「度量 ≥ 下限」，所以窗口停在**刚好跌破下限**的位置，而要求的长度不是窗口长度、是「从 0 到 `left - 1` 的候选数」。两个模板的 `while` 条件互为反面，很容易串用。

`pairs` 的 O(1) 维护（一条通用规律）：

| 动作 | 对数变化 | 代码顺序 |
| :--- | :--- | :--- |
| 右端加入 `x` | `+`（`x` 入窗**前**在窗口内的旧计数） | 先 `pairs += cnt[x]`，再 `cnt[x] += 1` |
| 左端删掉 `y` | `-`（`y` 出窗**后**的剩余计数） | 先 `cnt[y] -= 1`，再 `pairs -= cnt[y]` |

两处都是「先动计数、再算对数」，但方向相反 —— 这是本题最容易写错的地方。

**4. 最优解**

时间 O(n)、空间 O(n)，代码见下节。时间上已不可能更好（至少要读一遍输入才能知道有哪些元素）。

### 关键点

- **判据**：`[l, j]` 是好子数组 ⟺ `pairs(l, j) >= k`。判据只依赖「窗口内各值计数」，属窗口内部状态型。
- **窗口语义要记牢**：`[left, j]` 恒为「跌破下限」的非法窗口，合法窗口是它在左侧的所有扩展。答案取 `left` 而不是窗口长度。
- **`while` 条件写 `pairs >= k`**（收缩到跌破 `k` 为止），不是 `pairs > k`；`k` 是「至少 `k` 对」。
- **`ans += left` 必须在 `while` 之后**：收缩前的 `left` 还指向合法位置，会把不合法的左端点也计入（实测 40 组随机用例错 31 组）。
- **不能用 `if` 代替 `while`**：出窗元素的剩余计数可能是 0（该值在窗口内只出现一次），此时删掉它 `pairs` 一点不减，违规量根本没被消除（实测 40 组随机用例错 27 组，最小反例 `nums = [1,2,2], k = 1`：真值 2、`if` 版 1）。
- **`left` 只增不减** ⇒ 内层 `while` 的总迭代次数 ≤ n，摊还 O(1)，不要因为「看到 while 嵌 for」就误判成 O(n²)。
- **答案量级**：`k = 1` 且全相同时答案 = `n(n+1)/2` ≈ `5 × 10^9`，超过 32 位有符号上限（C++ 要用 `long long`；Python 无溢出问题）。
- **值域到 `10^9`**，不能开数组计数，必须用哈希表。
- **等价口径**：对每个 `j`，`好 = left`、`总数 = j + 1`，故 `坏 = j + 1 - left`；累加可得
  `ans = n(n+1)/2 - Σ(j + 1 - left)`。两者算术上恒等，本文采用前者（`ans += left`）。

## 三、代码实现

### 最终代码

```python
from collections import defaultdict
from typing import List


class Solution:
    def countGood(self, nums: List[int], k: int) -> int:
        cnt = defaultdict(int)          # 窗口 [left, j] 内各值的出现次数
        ans = left = pairs = 0          # pairs: 窗口内相等对数；left: 最右合法左端点 + 1
        for j in nums:
            pairs += cnt[j]             # 先累加对数（此时 cnt[j] 是入窗前的旧计数）
            cnt[j] += 1                 # 再更新计数
            while pairs >= k:           # 收缩到「跌破下限」为止
                cnt[nums[left]] -= 1    # 先减计数
                pairs -= cnt[nums[left]]  # 再扣掉剩余计数（= 删除前计数 - 1）
                left += 1
            ans += left                 # [0, left-1] 共 left 个合法左端点
        return ans
```

## 四、复杂度分析

这里的 `n` 指数组 `nums` 的长度；`m` 指窗口内出现过的**不同值**个数（`m <= min(n, 值域大小)`）。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) | O(m) = O(n) |
| 朴素解法（固定 `l` 向右扩） | O(n²) | O(m) = O(n) |
| 朴素解法（逐子数组重新数对） | O(n⁴) | O(1) |
| 理论下界 | O(n) | O(n) |

**为什么时间 O(n)**：外层 `for` 共 `n` 轮，每轮两处 O(1) 的计数维护；内层 `while` 每执行一次 `left` 加 1，而 `left` 取值范围 `[0, n]` 且**全程只增不减**，因此内层总迭代次数 ≤ `n`。外层 O(n) + 内层 O(n) = O(n)，是**摊还**结论，不是 `O(n) × O(n)`。

**为什么空间 O(n) 不可再降**：`pairs` 必须能 O(1) 地反映「窗口内每个值出现了几次」，否则每轮都要重新扫窗口（回到 O(n²)）。要保存这些计数，最坏情况下（窗口中所有值互不相同或值域极大）键数就是 O(n)。本题值域到 `10^9`，也无法用数组替代哈希表。

**为什么时间下界是 O(n)**：任何正确算法都要至少读一遍输入（否则无法知道数组里有哪些元素），所以 O(n) 已经到头 —— 剩下的只是常数项。

## 五、优化评估

**结论**：时间复杂度已到达理论下界 O(n)，**不存在算法级的优化空间**；只有常数项可以压一压，其中一处实测有效（1.29 ~ 1.61×），另有一处「看起来更聪明」的改法**被实测证伪**。

### 瓶颈分析

`n = 10^5` 时用户版耗时约 18 ~ 23 ms（见下表实测）。主循环的成本几乎全部落在**哈希表操作次数**上，每轮：

- 外层：1 次读（`cnt[j]`）+ 1 次写（`cnt[j] += 1`）；
- 每次收缩：1 次读 `nums[left]` + 1 次写 `cnt[x] -= 1` + 1 次读 `cnt[x]`。

也就是说，一轮 `O(1)` 里真正做算术的部分可以忽略，**耗时基本由 `dict` 的读写次数决定**。因此优化的方向只有「减少 / 加快 dict 访问」，不可能减少访问的次数（每次访问都携带必要信息）。

具体到用户版：`cnt = defaultdict(int)` 在**每一次** `cnt[j]` 取值时都要经过 `__missing__` 这条 Python 层的方法调用链（即使键已存在）；换成 `dict.get` 是 C 层实现，单次更便宜 —— 这就是下表中稳定 1.3 ~ 1.6× 的来源。另外 `while` 体内 `nums[left]` 被索引了两次，用局部变量缓存一次即可。

### 可优化空间

唯一还能动的是常数项，且**收益有上限**：

- 哈希访问次数由算法本身决定，无法再减 —— 想再快只能换掉「哈希表」这个数据结构本身（值域压缩成数组下标）；
- 但值域压缩需要**额外一趟预处理**建映射表，这笔开销在「值域 ≈ n」（几乎每个元素都是新值）时无法被摊掉，反而亏（见下）。

⇒ 结论：**O(n) 已是最优，常数优化到此为止。**

### 优化代码

保留用户版逻辑与代码结构，只做两处等价改写：`defaultdict(int)` → `dict.get`，并把 `nums[left]` 缓存到局部变量。

```python
from typing import List


class Solution:
    def countGood(self, nums: List[int], k: int) -> int:
        cnt = {}                        # 改：普通 dict，配合 .get 取值
        ans = left = pairs = 0
        for j in nums:
            c = cnt.get(j, 0)           # 改：C 层实现，避开 defaultdict.__missing__
            pairs += c
            cnt[j] = c + 1
            while pairs >= k:
                x = nums[left]          # 改：缓存下标访问，只索引一次
                c = cnt[x] - 1
                cnt[x] = c
                pairs -= c
                left += 1
            ans += left
        return ans
```

**优化理由**：两处改动都不改变任何状态转移，只是把 Python 层的 `defaultdict.__missing__` 换成 C 层的 `dict.get`，并省掉一次多余的下标运算。实测全场景收益 1.29 ~ 1.61×，且**没有反向场景**（见下表）。

### 常数级优化（可选）

实测表（`n = 10^5`，轮转 9 轮取各版本最优值，同一台机器、同一轮测量；括号内为相对用户版 `defaultdict` 的加速比）：

| 场景 | 用户版 `defaultdict` | 优化版 B（`dict.get`） | 值域压缩 + list 计数 | 口径 E（总数 − 坏数） |
| :--- | :--- | :--- | :--- | :--- |
| S1 小值域 `1..3`，`k = 10`（大量收缩） | 22.26 ms（1.00×） | **17.24 ms（1.29×）** | 20.54 ms（1.08×） | 20.24 ms（1.10×） |
| S2 值域 ≈ n（全不同），`k = 1`（几乎不收缩） | 18.18 ms（1.00×） | **11.32 ms（1.61×）** | 21.03 ms（0.86×） | 16.24 ms（1.12×） |
| S3 全部相同，`k = 10^5`（单轮长距离收缩） | 22.86 ms（1.00×） | **17.70 ms（1.29×）** | 21.34 ms（1.07×） | 22.49 ms（1.02×） |

- ✅ **采纳：优化版 B（`dict.get` + 缓存下标）** —— 三档场景全部领先，无反向情形，改动量也最小。
- ⚪ **口径 E（`ans = n(n+1)/2 − Σ(j+1−left)`）**：算术上与主解恒等（对每个 `j`，`好 = left`、`总 = j+1`，故 `坏 = j+1−left`），实测 1.02 ~ 1.12×，**收益稳定但幅度明显小于 B**，且只是换了个累加口径、没减少任何字典访问。可作为思路储备，不推荐替换主解（可读性下降换来的是个位数百分比）。
- ❌ ~~**值域压缩 + 数组计数**~~：先扫一遍 `nums` 把每个值映射到 `0..m−1`，主循环改用 `list` 当计数器（`list` 的读写比 `dict` 快得多，所以 S1 / S3 两档「重复度高」的场景小赚 7% ~ 8%）。**但「值域 ≈ n」时反而慢 14%**（21.03 ms vs 11.32 ms，相对用户版只有 0.86×）：此时预处理那一趟建映射表的成本完全无法摊薄，而主循环本来也没省下多少。⇒ 收益不稳定、代码还更长，**不采用**。（该版本仅用于本次对照测试，未纳入笔记正文。）
- 其他试过但**不推荐**的写法：`try/except KeyError` 替代 `get`（异常开销远大于省下的查找；且本题「首次出现」是常见分支，走异常路径的比例不低）；把 `while` 换成「先算好要挪几格再一次性挪」（本题的挪动格数取决于每个出窗元素的剩余计数，无法 O(1) 预知）。

## 六、易错点与总结

### 易错点

- **`while` 写成 `if`**（每次只挪一格）：出窗元素在窗口内可能只出现 1 次，删掉它 `pairs` 一点也不减 —— 违规量没被消除，`left` 也没到位。实测 40 组随机用例错 **27** 组；最小反例 `nums = [1,2,2], k = 1`（真值 2、`if` 版 1）：删掉 `nums[0] = 1` 后 `pairs` 仍为 1，`if` 只挪一格就停了，`ans += 1` 少算一个。
- **`ans += left` 放在收缩之前**：收缩前的 `left` 还指着「合法」的位置，会把不合法的左端点也算进去。实测 40 组随机用例错 **31** 组。
- **入窗 / 出窗时 `pairs` 与计数的先后顺序写反**：入窗必须「先 `pairs += cnt[x]`，再 `cnt[x] += 1`」；出窗必须「先 `cnt[y] -= 1`，再 `pairs -= cnt[y]`」。写反了每次都会多算 / 少算一对（`c` 与 `c ± 1` 之别），而且示例规模小的时候可能仍然通过，很难发现。
- **收缩条件写成 `pairs > k`**：会漏掉 `pairs == k` 这一批（题面是「至少 `k` 对」）。
- **误判复杂度**：看到 `while` 嵌在 `for` 里就以为是 O(n²)。`left` 全程只增不减、上限 n，内层总迭代 ≤ n，是摊还 O(1)。
- **溢出**：`k = 1` 且数组元素全相同时答案为 `n(n+1)/2 ≈ 5 × 10^9`，C++ 用 `int` 会溢出，需 `long long`（Python 无此问题）。
- **值域陷阱**：`nums[i]` 最大 `10^9`，不能开数组 / 计数桶，只能用哈希表。

### 题型套路沉淀

- **「计数型滑窗」的判据形态**：不求最长 / 最短，而是**对每个右端点统计合法左端点的个数再累加**。落地条件是「合法性关于左端点单调」⇒ 合法集合必是一段前缀 ⇒ 只需维护分界点。模板：

  ```python
  for j in 区间右端:
      把 j 纳入窗口（O(1) 更新度量）
      while 违反约束:            # 收缩到刚好不满足
          从左端移除（O(1) 更新度量）
      ans += left                # [0, left-1] 是全部合法左端点
  ```

- **注意窗口停在哪一侧**：本模板的窗口**自己是不合法的**（`pairs < k`），合法窗口是它向左的扩展，答案取 `left`；而「求最长合法窗口」的模板窗口是**合法的**（收缩到满足为止），答案取窗口长度。两者 `while` 条件互为反面，**别串用**——串用是本族最容易犯的错。
- **滑窗成立的两根柱子**（缺一不可，缺了就要换结构如前缀和 + 单调队列）：
  ① 度量关于**左端点**单调（决定「合法集合是前缀」）；
  ② 度量关于**右端点**单调（决定「左指针单向移动、总代价摊还 O(n)」）。
- **可加度量的 O(1) 维护通式**：加入 `x` ⇒ `度量 += 与 x 相关的贡献数`（本题 = `x` 的旧计数）；移除 `y` ⇒ `度量 -= 移除后与 y 相关的贡献数`（本题 = `y` 的剩余计数）。凡是形如「窗口内某条件成立的配对 / 组合数」的度量，都可以套这个通式先写出增量式，再决定用 `while` 还是 `if`。
- **「先假设 O(1) 维护可行」这一步往往就是全题关键**：本题没有前缀和、没有排序，唯一能压掉 O(n²) 的观察就是「新增一个元素只影响与它同值的那部分对数」。
