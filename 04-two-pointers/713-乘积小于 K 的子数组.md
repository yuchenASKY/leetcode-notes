# 713. 乘积小于 K 的子数组

> **难度**：中等
> **标签**：数组 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/subarray-product-less-than-k/

---

## 一、题目描述

给定整数数组 `nums` 和整数 `k`，返回**乘积严格小于 `k`** 的**连续子数组**的数目。三个要点：① 必须连续；② 是「**严格**小于」；③ 元素全为正整数（`nums[i] >= 1`）—— 第三条是本题双指针能成立的命根子，不是可有可无的约束。

### 示例

```text
示例 1：输入 nums = [10,5,2,6], k = 100
输出：8
解释：8 个子数组分别是 [10]、[5]、[2]、[6]、[10,5]、[5,2]、[2,6]、[5,2,6]。
      注意 [10,5,2] 的乘积正好等于 100，不满足「严格小于」。

示例 2：输入 nums = [1,2,3], k = 0
输出：0
解释：元素均 >= 1 ⇒ 任何子数组的乘积都 >= 1 > 0，一个都没有。
```

### 约束条件

- `1 <= nums.length <= 3 * 10^4`
- `1 <= nums[i] <= 1000`
- `0 <= k <= 10^6`

---

## 二、解题思路

### 核心思想

**元素全 ≥ 1 ⇒ 乘积随窗口扩张单调不减 ⇒ 对每个右端点 `right`，合法左端点恰好构成一段后缀 `[left*, right]`。** 于是左边界可以做成「单调右移、永不回退」的双指针，每个 `right` 直接贡献 `right - left* + 1` 个答案。

### 思路演进

1. **暴力解法**：枚举左端点 `l`，内层把 `r` 从 `l` 往右扩、边扩边累乘；乘积 `< k` 就计数，一旦 `>= k` 立刻 `break`（元素 `>= 1`，继续乘只会更大）。最坏 O(n²)（窗口能拉满时），空间 O(1)。

2. **瓶颈定位**：这里有**两处重复劳动**。
   - 一是**乘积被反复连乘**：`product(l, r)` 在枚举每个 `l` 时都从 1 开始再乘一遍，而 `product(l+1, r)` 与 `product(l, r)` 只差一个因子 `nums[l]`——上一次的结果明明可以复用。
   - 二是更要命的——**同一个 `r` 被反复考察**：`[l, r]` 这段区间，在枚举 `l = 0, 1, 2, ...` 时被一遍遍重扫。信息没被沉淀下来，所以是纯浪费。

3. **关键转化**：**把「枚举区间 `(l, r)`」换成「枚举右端点 `right`，只维护一个左端点 `left`」**。依据是一条单调性：因为 `nums[i] >= 1`，固定 `right` 时 `product(left..right)` 关于 `left` **单调不增**，所以集合 `{ left : product(left..right) < k }` 是**一段后缀** `[left(right), right]`；并且 `right` 右移时 `left(right)` **只增不减**（左指针永不回退，才有摊还 O(n)）。
   一句话说清为什么原来不行、现在为什么行：**原来不行，是因为每个 `l` 都要把它右边的一切重新扫一遍；现在行，是因为「乘积对左端点单调」，所以左边界只能朝一个方向走，走过的格子再也不用回头。**

4. **最优解**：每个 `right` 只做一次乘法；需要收缩时用 `product //= nums[left]` 把最左元素**除出去**（整除精确），把「重算整段乘积」的 O(窗口长) 压成 O(1)。`left` 全程最多前进 n 步 ⇒ 摊还 O(n)。答案口径也随之确定：`ans += right - left + 1`，即以 `right` 结尾的合法起点个数。

### 关键点

- **判据（一句话能判真假）**：`[left, right]` 合法 ⟺ `product(left..right) < k`。对固定 `right`，合法左端点是一段**后缀** `[left*, right]`，贡献数 = `right - left* + 1`。
- **判据的前提是 `nums[i] >= 1`**：若允许 `0`，整除收缩会 `ZeroDivisionError`；若允许负数，乘积不再随窗口单调，「左指针不回退」的论证直接崩掉，就得改换结构（前缀和 + 二分 / 单调队列）。
- **`if k <= 1: return 0` 是补丁，不是修饰**：① 语义上——元素 ≥ 1 使乘积 ≥ 1，`k <= 1` 时答案必然为 0；② 机械上——`k = 0` 时 `while product >= k` **恒真**（`product >= 1 > 0`），`left` 会被一路推过 `right` 继续前进，最终 `nums[left]` 越界 `IndexError`。这一行同时消灭了这两种情况。
- **收缩用「除出去」而不是「重新连乘」**：`product //= nums[left]` 精确（`product` 恰好是窗口内元素之积，除以最左元素即下一个窗口之积），O(1) 取代 O(窗口长)，是摊还 O(n) 的另一半来源。
- **全程不会溢出**：每轮乘法前必有 `product < k`（否则上一轮已经收缩过），所以乘积最大只到 `(k - 1) * max(nums) < 10^6 * 1000 = 10^9 < 2^31 - 1`。Python 无所谓，但换 C++/Java 写时这条保证很值钱 —— `int` 就够，不需要 `long long`。
- **答案口径是「计数」而不是「最长」**：本题把每轮的窗口长度**累加**进答案，不是取 `max`。所以滑窗框架里那个「把 `while` 换成 `if`」的平移版优化，**在本题直接出局**（原因与反例见「六、易错点 1」）。

## 三、代码实现

### 最终代码

```python
from typing import List


class Solution:
    def numSubarrayProductLessThanK(self, nums: List[int], k: int) -> int:
        if k <= 1:                     # 元素均 >= 1 ⇒ 乘积 >= 1，k <= 1 时必为 0
            return 0
        ans = left = 0
        product = 1                    # 空窗口的乘积（乘法单位元）
        for right, j in enumerate(nums):
            product *= j
            while product >= k:        # 收缩到合法为止
                product //= nums[left] # 把最左元素除出去（精确整除）
                left += 1              # left 单调不减 ⇒ 全程总步数 <= n
            ans += right - left + 1    # 以 right 结尾的合法子数组个数
        return ans
```

> 截图里只有 `class Solution:` 起的内容，`from typing import List` 与空行是**补全项**（截图来源的代码缺 import 会跑不起来），不影响逻辑。
> 截图共 13 行、`return ans` **完整未被裁掉**，无需结构性补全。

## 四、复杂度分析

n = 数组 `nums` 的长度（题面上限 3 × 10⁴）。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | **O(n)** 摊还 | O(1) |
| 朴素解法（枚举 `l` + 内层右扩、提前 `break`） | 最坏 O(n²)；实际 O(n·L) | O(1) |
| 理论下界 | Ω(n) | Ω(1) |

> 复杂度中的 n 指：数组 `nums` 的长度。表中朴素解法的 L 指「每轮内层实际扫过的窗口长度」——`k` 小 / 元素大时 L 很小，暴力接近 O(n)；`k` 大且元素全为 1 时 L → n，退化成 O(n²)。这也解释了实测里两种场景的提速差了几百倍。

**摊还 O(n) 怎么来的**：外层循环 n 次；内层 `left += 1` 全程累计最多执行 n 次（`left` 单调不减，且不会超过 `right + 1`），所以内层总代价 O(n)，与循环轮数无关 —— 平均到每个 `right` 上是 O(1)。

**空间**：只维护 `left / right / product / ans` 四个标量。

## 五、优化评估

**结论**：**已是最优** —— 时间已到理论下界 O(n)，空间 O(1) 无法再压，单轮动作也已是不再可减的最小集。

### 瓶颈分析

- **时间下界 Ω(n)**：答案依赖数组的全体元素（任何一个没读过的元素都可能改变某个子数组的乘积，进而改变计数），所以必须至少扫一遍；本解正好 n 次外层循环 + 摊还 O(1) 内层，没有可去除的环节。
- **单轮动作清单**：1 次乘法（扩展窗口）+ 摊还 1 次整除（收缩窗口）+ 1 次加法（累加答案）。三者各司其职、缺一不可：乘法是扩张的必要代价，整除是替代「重算整段乘积」的关键，加法是答案口径本身。没有冗余操作可以消掉。
- **空间**：4 个标量，O(1)，没有压缩余地。

### 可优化空间

大 O 层面没有。能想到的常数级改法有两条，**都被证伪**（见下）。

### 常数级优化（可选）

- ~~**把 `while` 换成 `if`（平移版）**~~ —— **本题禁用**。平移版每轮最多让 `left` 前进一格，窗口可以**短暂非法**；而本题的答案口径是「按窗口长度**累加**」，非法窗口会把乘积 ≥ k 的子数组也一并计进去。
  手工逐步推演的最小反例：`nums = [2,2,100], k = 10` —— 真值 3（`[2]`、`[2]`、`[2,2]`），平移版得 **5**：在 `right = 2` 那轮只除了一次（`400 // 2 = 200`，仍然 `>= 10`）却照样加了 `right - left + 1 = 2`，把两个乘积超限的子数组计了进去。
  ⇒ 滑窗框架里「平移版只对『最长』型成立、答案口径必须是窗口长度」这条限制，在本题这种**计数**口径上直接命中。**必须用 `while` 收缩到合法为止。**
- **用 `log` 把乘积换成加法**（试图规避大数）：本题**不必要** —— 上面已证 `product < 10^9`（见关键点⑤），Python 更无溢出之虞；而 `log` 会引入浮点误差，在 `product` 恰好等于 `k` 的边界上（示例 1 的 `[10,5,2] = 100` 就是这种点）可能把「等于」判成「小于」。风险与收益完全不成比例。
- **`enumerate` 换手写下标循环**：实测落在噪声级别，不值得改。

### 实测（计时对照，只比快慢、不判对错）

环境：本机 Windows / Python 3.13.12；每档 7 轮取最小值（**轮转测量**：每轮跑遍全部版本，避免机器状态漂移污染）。`k = 10^6`。

| 输入 | 暴力 O(n²) | 本解 O(n) | 提速 |
| :--- | ---: | ---: | ---: |
| n = 1000，随机 1..1000 | 0.27 ms | 147.9 µs | 1.8× |
| n = 2000，随机 1..1000 | 0.54 ms | 286.0 µs | 1.9× |
| n = 1000，全 1（窗口拉满） | 26.78 ms | 86.9 µs | 308× |
| n = 2000，全 1（窗口拉满） | 109.58 ms | 172.5 µs | 635× |

**读表要点：**

- **规模翻倍的增长斜率**：暴力 `26.78 → 109.58 ms`（**4.09×**，二次 ✓）；本解 `86.9 → 172.5 µs`（**1.99×**，线性 ✓）；随机档两边也都是约 2×（0.27 → 0.54，147.9 → 286.0）。这两组斜率就是复杂度差异的直接证据。
- **提速倍数完全取决于窗口长度，不是固定值**：随机档元素均值约 500、`k = 10^6`，暴力内层约 2 个元素就 `break`，实际代价是 O(n·L) 而非 O(n²)，所以只快 1.8~1.9×；全 1 档里 `product` 恒为 1、永不收缩，窗口拉到满，暴力退化成 n²/2 次内层迭代，才拉开 300~635×。
  ⇒ 结论：**「滑窗比暴力快多少」必须指明输入形态才有意义**，单说一句「快 N 倍」是误导。
- **全 1 才是本族真正的最坏输入**：它同时放大了暴力的重复劳动（窗口最长），又让滑窗的状态最省（`left` 几乎不动）。
- **按上表斜率线性外推（⚠️ 非实测，仅由实测值推算）**：全 1 输入在题面上限 n = 3×10⁴ 时，暴力约需 `109.58 ms × (30000 / 2000)² ≈ 24.7 s`，必然 TLE；本解按线性约 `172.5 µs × 15 ≈ 2.6 ms`。⇒「暴力能不能过」在这个约束量级下是有明确结论的：不能。

## 六、易错点与总结

### 易错点

1. **把内层 `while` 写成 `if`（平移版）**：窗口会短暂非法，而答案按窗口长度累加 ⇒ 多计数。最小反例 `nums = [2,2,100], k = 10`：真值 3，平移版得 5（见「五、常数级优化」）。
2. **漏掉 `if k <= 1: return 0`**：`k = 0` 时 `product >= k` 恒真（`product >= 1`），`left` 会被推过 `right + 1` 继续前进 ⇒ `nums[left]` 越界 `IndexError`；`k = 1` 时答案恒为 0，早退还能省一遍扫描。示例 2 走的就是这个分支。
3. **「乘积 ≥ k 就收缩一次」而不是「收缩到合法」**：单个元素自己就可能 `>= k`（如 `nums = [1000], k = 100`）。必须收缩到**空窗口**（`left = right + 1`、`product = 1`）才停，此时 `right - left + 1 = 0`，恰好不多计 —— 这也是为什么用 `while` 而非 `if`，以及为什么空窗口的乘积要初始化成 1。
4. **答案写成 `right - left`**：闭区间元素个数是 `right - left + 1`，差一个。
5. **担心 `product //= nums[left]` 不精确**：不会 —— `product` 就是窗口内元素的乘积，整除精确无余数。
6. **换语言时忽略溢出**：本题最坏 `product < 10^9`，`int` 够用（见关键点⑤）；若元素上限调大，要么换 `long long` / `BigInteger`，要么改成「对数求和 + 容差判定」。
7. **把 `nums[i] >= 1` 当成废约束**：允许 `0` 会让整除收缩抛 `ZeroDivisionError`；允许负数则单调性消失、双指针失效。这题的解法完全架在「元素为正」上。

### 题型套路沉淀

- **「度量不超过上限」的计数型滑窗**：先确认度量对窗口**单调**（元素 ≥ 1 ⇒ 乘积单调不减；非负 ⇒ 和单调不减），再做「枚举右端 + 单调右移左端」。
- **答案口径决定写法**：以 `right` 结尾的合法窗口数 = `right - left + 1`；「最长窗口」型则要每轮取 `max` 长度。**两种口径不能混** —— 计数口径下 `while` 不可退化成 `if`。
- **收缩靠「逆运算摘掉最左元素」而非「重算整段」**：和 / 乘积 / 计数这类**可逆度量**都能用一次逆运算把左端摘掉 ⇒ 收缩 O(1)，这是把 O(n·L) 打成 O(n) 的关键动作。
- **识别信号**：题面出现「连续子数组 + 乘积或和不超过某阈值 + 求个数 / 求最长」，先套这个模板，再单独确认单调性前提是否成立（元素非负或为正）。
