# 3439. 重新安排会议得到最多空余时间 I

> **难度**：中等
> **标签**：数组 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/reschedule-meetings-for-maximum-free-time-i/

---

## 一、题目描述

活动总时长 `eventTime`（区间 `[0, eventTime]`），其中有 `n` 个互不重叠的会议，第 `i` 个占 `[startTime[i], endTime[i]]`。

你可以**至多平移 `k` 个会议**（会议时长不变），要求：

- 所有会议之间的**相对顺序保持不变**；
- 会议之间仍然互不重叠；
- 会议不得越出 `[0, eventTime]`。

问平移之后，**相邻会议之间（含活动首尾）最长的那段连续空余时间**能达到多少。

### 示例

```text
示例 1
输入：eventTime = 5, k = 1, startTime = [1,3], endTime = [2,5]
输出：2
解释：把 [1,2] 挪到 [2,3]，空余变成 [0,2]，长度 2。

示例 2
输入：eventTime = 10, k = 1, startTime = [0,2,9], endTime = [1,4,10]
输出：6
解释：把 [2,4] 挪到 [1,3]，空余变成 [3,9]，长度 6。

示例 3
输入：eventTime = 5, k = 2, startTime = [0,1,2,3,4], endTime = [1,2,3,4,5]
输出：0
解释：所有时间都被会议占满，挪不动也用不上。
```

### 约束条件

- `1 <= eventTime <= 10^9`
- `2 <= n == startTime.length == endTime.length <= 10^5`
- `1 <= k <= n`
- `0 <= startTime[i] < endTime[i] <= eventTime`
- `endTime[i] <= startTime[i + 1]`（即输入本身已按时间排好且不重叠）

## 二、解题思路

### 核心思想

**把"会议"换成"空隙"来看：答案就是空隙序列上「`k+1` 个连续空隙」的最大和。**

```text
时间轴:  0 ─g0─ [会议0] ─g1─ [会议1] ─g2─ … ─ [会议n-1] ─gn─ eventTime
                 ↑ 共 n+1 个空隙 g[0..n]
搬走连续 k 个会议 i..i+k-1  →  这一段跨度被腾空，合并了 g[i]、g[i+1] … g[i+k] 共 k+1 个空隙
答案 = max{ Σ_{j=i}^{i+k} g[j] }，  i ∈ [0, n−k]
```

其中 `g[0] = startTime[0]`、`g[j] = startTime[j] - endTime[j-1]`（`1 ≤ j ≤ n-1`）、`g[n] = eventTime - endTime[n-1]`。

### 思路演进

1. **暴力解法**：枚举"移动哪几个会议、各自移到哪里"。位置是连续值，但只需考虑"贴着别的会议或活动边界"的有限个候选点即可离散化；即便如此，组合数仍随 `n` 指数增长，`n = 10^5` 完全不可行。真正的出路是**换视角**，不是剪枝。
2. **观察到（移动的会议必然是连续一段）**：最终那段最长空余 `[a, b]` 的两侧一定被会议（或活动边界）夹住。设它原本覆盖的会议是 `i, i+1, …, i+l-1` —— 因为**顺序不能变**，这一段里不可能"跳过"某场会议而只腾空中间，所以被腾空的必然是一段**连续**的会议。腾空这段需要把它们全部挪走，故 `l ≤ k`。
3. **观察到（这一段只能在它自己的跨度里活动）**：设 `endTime[-1] = 0`、`startTime[n] = eventTime`。会议 `i..i+l-1` 的左右邻居是会议 `i-1` 和 `i+l`，顺序不变 ⇒ 这一段只能整体滑动在 `[endTime[i-1], startTime[i+l]]` 之间。于是把它推到跨度的一端，就能得到一段长为
   `(startTime[i+l] - endTime[i-1]) - Σ 时长 = Σ_{j=i}^{i+l} g[j]`
   的连续空余。**"跨度长度"恰好等于这 `l+1` 个空隙之和** —— 会议自身长度被抵消掉了。
4. **优化为**：把 `k+1` 个连续空隙的和在空隙序列上做**定长滑动窗口**取最大，`O(n)` 一趟扫完。

### 关键点

**正确性需要两头都堵上**（这题很容易"凭感觉觉得对"）：

- **上界**：任一合法方案的最长空余，对应某个 `l ≤ k` 的连续块 `i..i+l-1`，其长度 `≤ Σ_{j=i}^{i+l} g[j] ≤ max{ Σ_{j=i}^{i+k} g[j] }`（空隙非负，窗口可以向右扩到 `k+1` 个；若 `i` 靠右越界，就取更靠左的整窗，它包含原区间）。
- **可达性**：任一窗口 `i..i+k` 都能通过"把会议 `i..i+k-1` 整体推到跨度的一端"实现。`k = n` 时窗口只剩 `i = 0` 一个，对应"把所有会议挤到一边"。

两头合起来 ⇒ 答案就是那个最大窗口和，**贪心的"移动连续性"结论不需要额外证明，它由顺序不变这条规则直接给出**。

其它要点：

- **空隙个数是 `n+1` 而不是 `n`**：活动首尾的两段也算空余（示例 1 的答案 `2` 就是首段 `[0,2]`）。
- **"至多 `k` 个"与"恰好 `k` 个"等价**：移动更少 ⇒ 窗口更小 ⇒ 和非减（空隙非负），所以按 `k+1` 个空隙算最大值不会漏解。
- **会议时长在答案里被完全消掉**：跨度 - 块时长 = 空隙和 —— 这也是为什么本题可以完全不看时长。

## 三、代码实现

### 最终代码

```python
from typing import List


class Solution:
    def maxFreeTime(self, eventTime: int, k: int, startTime: List[int], endTime: List[int]) -> int:
        ans = mid = startTime[0]                # mid = 当前窗口的空隙和（g[0] 起步）
        n = len(startTime)
        for i in range(n - 1):
            mid += startTime[i + 1] - endTime[i]        # 加入空隙 g[i+1]
            ans = max(ans, mid)
            if i < k - 1:
                continue                                # 窗口还没攒够 k+1 个空隙
            if i == 0:
                mid -= startTime[0]                     # k == 1 时滑出 g[0]
            else:
                if i == k - 1:
                    mid -= startTime[0]                 # 滑出 g[0]
                    continue                            # ⚠️ 这个 continue 不能删，见第五节
                mid -= startTime[i - k + 1] - endTime[i - k]   # 滑出 g[i-k+1]
        if eventTime > endTime[-1]:                          # 尾部空隙 g[n] 只在末尾处理
            mid += eventTime - endTime[-1]
            ans = max(ans, mid)
        return ans
```

> 本人提交通过的版本，**逻辑正确**（官方 3 个示例 + 1237 组合法随机用例与暴力解零偏差，见文末）。
> 但它把"空隙"内联成了两处下标表达式，又用 `if i == 0` / `continue` 硬凑窗口对齐，可读性和稳健性都偏弱 —— 第五节给了能短一半的等价写法。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) | O(1) |
| 优化版（第五节，预存空隙） | O(n) | O(n) |
| 优化版（第五节，单趟不存空隙） | O(n) | O(1) |
| 朴素解法（枚举移动方案） | 指数级 | O(n) |
| 理论下界 | O(n) | O(1) |

> 复杂度中的 n 指会议数量 `n == len(startTime)`，空隙数为 `n+1`。
> **时间下界 `Ω(n)`**：最左/最右的边界空隙与每个会议的两端都参与答案，任何算法都必须读完两个数组 → `O(n)` 已触底。
> **空间下界 `Ω(1)`**：只需维护"当前窗口和 + 历史最大窗口和"两个标量 → 用户版与单趟版都达到了这个下界。

## 五、优化评估

**结论**：时间与空间**都已触及下界**，算法层面无优化空间；但当前实现存在**两个冗余/脆弱点**，且 Python 常数开销比等价写法高约 **1.5 倍**。

### 瓶颈分析

- 用户版每轮循环里有 `if i < k-1`、`if i == 0`、`else` 里的 `if i == k-1` 三层分支，其中前两层对绝大多数迭代都是无用判断；空隙下标被写成 `startTime[i+1] - endTime[i]` 与 `startTime[i-k+1] - endTime[i-k]` 两种形式，**一正一反容易写错**。
- 真正的冗余是 `if i == 0` 这个分支：它只有在 `k == 1` 时才可能进入，而此时 `i == 0` 同时满足 `i == k-1`，走 `else` 分支的结果**完全一样** —— 也就是**死代码**。
- 另一个更隐蔽的问题：`if i == k-1` 里的 `continue` **绝对不能删**。删掉之后会落到下面的 `mid -= startTime[i-k+1] - endTime[i-k]`；当 `i == k-1` 时 `i-k = -1`，`endTime[-1]` 会**静默取到数组最后一个元素**（Python 负索引），代码不报错但结果错。**"清理该死的死代码"这个动作在这里恰好会引爆另一个雷**，说明这段控制流本身就该被重写。

### 可优化空间

| 改动 | 收益 |
| :--- | :--- |
| 先预计算空隙数组 `g[0..n]` | 两处下标表达式统一成一个 `g[j]`，代码短一半；滑窗变成最朴素的 `cur += g[i] - g[i-w]` |
| 删掉 `if i == 0` 分支 | 去掉死代码与一处负索引隐患 |
| `ans` 初始化为"首窗口和"而非 `startTime[0]` | 语义直接（首窗口本身就是一个合法候选），不再依赖"靠后续更新扳回来" |
| 循环直接遍历空隙下标 `j` | 不再需要 `i - k + 1`、`i - k` 这类偏移换算 |

### 优化代码

```python
from typing import List


class Solution:
    def maxFreeTime(self, eventTime: int, k: int, startTime: List[int], endTime: List[int]) -> int:
        n = len(startTime)
        # 展开成 n+1 个空隙：g[0] 在首个会议前，g[n] 在末个会议后
        gaps = [startTime[0]]
        for i in range(1, n):
            gaps.append(startTime[i] - endTime[i - 1])
        gaps.append(eventTime - endTime[-1])

        # 在空隙序列上求「长度 k+1 的窗口」最大和 —— 这就是答案
        w = k + 1
        cur = sum(gaps[:w])
        ans = cur
        for i in range(w, n + 1):
            cur += gaps[i] - gaps[i - w]
            if cur > ans:
                ans = cur
        return ans
```

**优化理由**：把"会议视角 + 下标凑对齐"换成"空隙视角 + 定长滑窗"。改完之后：

- 代码从 20 行降到 15 行，且**没有任何特判分支** —— `k = 1`、`k = n`（此时 `w = n+1 == len(gaps)`，主循环不执行，直接返回首窗口和）全部由同一套逻辑走通；
- 删掉了那句"必需但看起来多余"的 `continue`，消除了负索引暗雷；
- 每一步的语义与推导一一对应：`gaps[i] - gaps[i - w]` 就是"窗口右移一格"。

**实测（`n = 10^5`，CPython 3.13，各取 7 次最优值）：**

| `k` | 用户版 | 优化版 | 提速 |
| ---: | ---: | ---: | ---: |
| 1 | 17.03 ms | 10.89 ms | 1.56× |
| 100 | 17.42 ms | 11.81 ms | 1.47× |
| 50000 | 14.60 ms | 8.96 ms | 1.63× |
| 100000（= n） | 9.84 ms | 6.32 ms | 1.56× |

**规律**：提速稳定在 **1.5 倍左右**，与 `k` 几乎无关 —— 因为省下的是"每轮多层分支判断 + 两处内联下标运算"，这部分开销只与 `n` 有关。`k = n` 时两版都变快（用户版的 `continue` 一路走到底、优化版只有一个窗口），但比例不变。

### 常数级优化（可选）

想在 `O(1)` 额外空间里跑，可以把"窗口和"直接算在原数组上（不建 `gaps`）：

```python
from typing import List


class Solution:
    def maxFreeTime(self, eventTime: int, k: int, startTime: List[int], endTime: List[int]) -> int:
        n = len(startTime)

        def gap(j: int) -> int:                      # 第 j 个空隙
            return (startTime[j] if j < n else eventTime) - (endTime[j - 1] if j else 0)

        w = k + 1
        cur = sum(gap(j) for j in range(w))
        ans = cur
        for j in range(w, n + 1):
            cur += gap(j) - gap(j - w)
            if cur > ans:
                ans = cur
        return ans
```

- 空间降到 O(1)，代价是每次 `gap()` 多一次 Python 函数调用、循环里还要多做两次条件判断。**实测这个代价很大 —— 不是慢一点点，而是慢近 1.9 倍**：

  | `k` | 预存空隙版 | 即时 `gap()` 版 | 差距 |
  | ---: | ---: | ---: | ---: |
  | 1 | 12.22 ms | 22.46 ms | 1.84× |
  | 100 | 11.72 ms | 21.97 ms | 1.87× |
  | 50000 | 9.28 ms | 17.55 ms | 1.89× |
  | 100000（= n） | 6.46 ms | 12.07 ms | 1.87× |

- 取舍：`n ≤ 10^5` 时 `gaps` 数组只占几 MB，**建议直接用预存版**；只有在内存敏感（或题目把空间卡到 O(1)）时才换这个写法。
- 顺带一个容易搞反的细节：**首窗口求和**用 `sum(gaps[:w])`（切片，C 层求和）比 `sum(gaps[i] for i in range(w))`（生成器）更快，但**只在窗口大时才明显**——实测 `k = 1` 时两者持平（12.22 vs 12.25 ms，生成器的固定开销被 Python 循环的节省抵消），`k = n` 时切片快 1.45×（6.46 vs 9.34 ms）。**窗口越大，越要用切片。**

## 六、易错点与总结

### 易错点

- **只数 `n` 个空隙**：活动开头 `[0, startTime[0]]` 和结尾 `[endTime[-1], eventTime]` 都是合法空余（示例 1 的答案就是开头那段），漏掉就会偏小。
- **窗口大小写成 `k` 而不是 `k+1`**：搬走 `k` 个会议之后，被合并的是**左右两侧加上这 k 个会议原本占据的位置**，共 `k+1` 个空隙；写成 `k` 会直接少算两个边界空隙。
- **以为"移动的会议可以乱放"**：本题明确要求**相对顺序不变**，所以一段连续会议只能在自己的跨度内滑动，不能整段搬到远处的空隙里 —— 这是本题与 `3440`（II 代，允许顺序改变）的分水岭。
- **负索引暗雷**：`i - k` 在 `i = k-1` 时等于 `-1`，`endTime[-1]` 会静默取到最后一个元素。用户版正是靠一句 `continue` 绕开它 —— 改这部分代码时务必当心。
- **删除"多余"分支前先想清楚**：`if i == 0` 是真冗余，`continue` 不是。区分标准是"删掉之后是否会有别的东西被执行"。
- **`k = n` 时没有越界问题**：此时只有一个候选窗口（把所有会议挤到一边），优化版里 `w = n+1 == len(gaps)`，主循环不执行，直接返回首窗口和。

### 题型套路沉淀

- **"最长空余/最长间隔"类问题的第一步永远是换视角**：不要盯着会议（被占用的部分），要盯着**空隙序列**。一旦把 `n+1` 个空隙摊开，很多题会立刻退化成数组上的经典模型（本题退化成"定长窗口最大和"）。
- **"顺序不可改变 + 平移连续一段" ⇒ 只能在自己的跨度内活动**。这条推理让本题的搜索空间从"任意位置"塌缩到"只挑连续块"，是解题的真正转折点。
- **上界 + 可达性两头证**：窗口类最优解容易"看着对"，但**必须补一句上界论证**（为什么不能更大）。本题的上界来自"腾空的会议必是连续一段且 `l ≤ k`"。
- **同系列对照**：

  | 题 | 可移动的数量 | 顺序约束 | 关键差异 |
  | :--- | :--- | :--- | :--- |
  | **`3439` 本题** | 至多 `k` 个 | **必须不变** | 连续块只能在自己跨度内滑动 ⇒ 纯滑窗，`k+1` 窗口最大和 |
  | `3440` 重新安排会议得到最多空余时间 II | 至多 1 个 | **可以改变** | 被移动的那场会议能塞进任意空隙，于是多出"用其他空隙容纳它"的分支 |
  | `1052` 爱生气的书店老板 | — | — | 同为"定长窗口求最大增量"，但增量定义在 `grumpy[i]*customers[i]` 上 |

- **Python 负索引是双刃剑**：`endTime[-1]` 读"最后一个元素"很好用，但**当它是从 `i - k` 算出来的时候，就是静默错误的来源**。凡是下标可能为负的地方，宁可多写一个 `if`,也别赌。

### 验证记录

- 3 个官方示例：用户版与优化版**全部通过**（`2` / `6` / `0`）。
- **对拍方式**：本题"移动方案"是连续位置，没法用子集枚举；改用**枚举所有合法排布**的暴力解 —— 枚举每场会议的全部可能起点（`0..eventTime`），筛掉重叠/越界/移动数超过 `k` 的方案，再取最长空余。随机生成 1500 组小规模数据（`eventTime ≤ 12`，`n ≤ 4`，其中 1237 组数据合法），**用户版与优化版均与暴力解零偏差**，同时覆盖 `k = 1` 与 `k = n`。
- 边界用例：会议贴头/贴尾（`g0 = 0` 或 `gn = 0`）、相邻会议贴合（空隙为 0）、全部挤在一起（答案是 0）、`k = n` —— 两版一致。
