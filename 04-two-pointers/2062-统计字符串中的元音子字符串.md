# 2062. 统计字符串中的元音子字符串

> **难度**：简单
> **标签**：哈希表 · 字符串 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/count-vowel-substrings-of-a-string/

---

## 一、题目描述

给定字符串 `word`，统计其中满足「**只由元音**（`a`/`e`/`i`/`o`/`u`）组成、且 **五种元音全部出现**」的连续子串数目。

一句话判据：子串 `sub` 合法 **⟺** `set(sub) == {'a','e','i','o','u'}`。
（元音总共只有这 5 种，所以「含全部 5 种」已经自动蕴含「只由元音组成」，两个条件可以合成一个。）

### 示例

```text
输入：word = "aeiouu"          输出：2     # "aeiou"、"aeiou"
输入：word = "unicornarihan"   输出：0     # 缺 u，无解
输入：word = "cuaieuouac"      输出：7
输入：word = "bbaeixoubb"      输出：0     # 含五种元音的子串都夹着辅音

上面 4 个示例里，示例 3（"cuaieuouac" → 7）是唯一能筛掉错误写法的那个，
因为它同时含辅音、含重复元音、且答案不为 0。
```

### 约束条件

- `1 <= word.length <= 100`
- `word` 仅由小写英文字母组成

---

## 二、解题思路

### 核心思想

**辅音把字符串切成若干「纯元音段」，段内固定右端时「合法起点」必然构成一个前缀** —— 于是每轮只要找到前缀的分界点 `lo`，就能一次贡献 `lo - start + 1` 个答案，完全不必枚举起点。

### 思路演进

1. **暴力解法**：枚举全部 O(n²) 个子串，用 `set(sub) == {'a','e','i','o','u'}` 判定，累加。
   时间 O(n²)（外加每个子串的切片与集合构造常数）。实测 n = 100 时约 0.2 ms，直接能过。
2. **瓶颈定位**：两处重复劳动。
   - 从起点 `i` 往右扩时，`word[i:j+1]` 只比 `word[i:j]` 多一个字符，却把「是否含齐 5 种」从头重算一遍；
   - 一旦在 `j` 处撞上辅音，**从 `i` 出发的所有更长子串必然都不合法**，但循环还在继续枚举。
3. **关键转化**（两处，分别消掉上面两个浪费）：
   - **断段**：辅音是天然的切割点 —— 合法子串不可能跨过辅音。于是只需在每个「纯元音段」内部统计，段内任意子串都自动满足「只由元音组成」。
   - **单调性 ⇒ 合法起点是一个前缀**：固定右端 `right`，起点 `s` 越小、窗口 `[s, right]` 越大，越容易凑齐 5 种。所以存在唯一分界点 `lo`：`s ≤ lo` 时全部合法，`s > lo` 时全部不合法。**每轮只需知道 `lo`，一次贡献 `lo - start + 1`**。
     一句话说清「原来为什么不行、现在为什么行」：原来要对每个起点各问一次「够不够 5 种」；有了前缀单调性，只要问出**分界点在哪**，它左边的起点就自动全是答案。
4. **最优解**：段内维护「窗口 `[left, right]` 内每种元音的计数」+ 左指针 `left`，用 `while len(cnt) >= 5` 把窗口一路收窄到**刚刚不足 5 种**。循环退出时，`[left-1, right]` 仍是合法的（上一次收缩前它有 5 种），所以分界点 `lo = left - 1`，本轮的答案数就是 `left - start`。
   由于「相同元音的界」是用「不同种类数」判断的，窗口最多只含 5 个键。

### 关键点

- **这一族按「键数」收缩，不是按「值」收缩**：判据是「不同元音**种类数**」，所以某种元音计数归零时**必须 `del` 掉键**，否则 `len(cnt)` 只增不减，`left` 会被一路推出界（见 §六）。
- 遇到辅音时要同时重置 **`start` 与 `left`**（`start = left = right + 1`），并把计数表清空 —— 三者语义必须同步，漏一个就会把上一段的状态带进新段。
- 答案口径是「**数目**」而不是「窗口长度」。这一点决定了「把 `while` 改成 `if`」这类在最长窗口题里常见的改写**在这里不成立**（实测见 §五）。

## 三、代码实现

### 最终代码

```python
from collections import Counter          # 截图里没有，已补（LeetCode 环境预置了 Counter）


class Solution:
    def countVowelSubstrings(self, word: str) -> int:
        ans = left = start = 0           # start: 当前纯元音段起点；left: 窗口左界
        cnt = Counter()
        for right, j in enumerate(word):
            if j not in 'aeiou':         # 辅音：切断，重置整段状态
                cnt.clear()
                start = left = right + 1
                continue
            cnt[j] += 1
            while len(cnt) >= 5:         # 仍含全部 5 种 -> 还能往右缩
                if word[left] in 'aeiou':
                    cnt[word[left]] -= 1
                    if cnt[word[left]] == 0:
                        del cnt[word[left]]     # 按键数收缩：归零必须删键
                left += 1
            ans += left - start          # 合法起点为 [start, left-1]，共 left-start 个
        return ans
```

> 截图的最后一行是第 18 行 `return ans`，与状态栏「行 14，列 21」的行数一致，**代码未被裁切**，无需补全；仅补了第 1 行的 `import`。

## 四、复杂度分析

> 复杂度中的 n 指字符串 `word` 的长度。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n) 摊还 | O(1)（计数表最多 5 个键） |
| 暴力（枚举子串 + set 判据） | O(n²) | O(1) |
| 理论下界 | Ω(n) | Ω(1) |

- **为什么内层 `while` 是摊还 O(1)**：每执行一次循环体，`left` 必前进 1；而 `left` 全程单调不减（遇到辅音时跳到 `right + 1`，也不会回退）。整个遍历中 `left` 最多走 n 格 ⇒ 内层循环总次数 ≤ n，均摊到每个 `right` 是 O(1)。所以整体是一次线性扫描。
- **空间为什么是 O(1)**：计数表的键只能是 5 种元音。
- **口径提醒（按题面约束量级）**：本题 n ≤ 100，任何正确的写法都是 0 ms —— 下面 §五 的所有实测差异都属于「**泛化到任意 n 的研究**」，不是「不优化就会超时」。

## 五、优化评估

**结论**：时间复杂度已到下界（必须读完整个字符串才能确定答案），**但常数与结构仍可压缩**：把「逐格收缩 + 维护计数表 + `del`」换成「**最后出现位置表 + 一次 `min`**」，在 n = 10⁵ 的高收缩场景下实测快 2×~3.3×；而在「整串同一个元音」这种退不收缩的输入上，两种写法基本持平。

### 瓶颈分析

各版本耗时实测（n = 10⁵，轮转 9 轮取最优，单位 ms；百分比相对原版）：

| 输入场景 | 原版（while 逐格） | 一次跳转（保留 cnt） | 位置表 + min |
| :--- | :--- | :--- | :--- |
| `'a' * n`（从不收缩） | **19.09** | 20.84 (−8%) | 18.87 (+1%) |
| 随机元音（频繁收缩） | 51.18 | 40.06 (+28%) | **25.30 (+102%)** |
| `'aeiou'` 周期（最坏） | 75.65 | 38.85 (+95%) | **22.85 (+231%)** |
| 元音 + 辅音混合 | 29.11 | 28.57 (+2%) | **19.53 (+49%)** |

- 耗时集中在**窗口左界的推进方式**上。最坏场景 `'aeiou'` 周期里，原版每一轮 `while` 都至少走一格，全程约 2n 次字典操作，其中 `del` 还会额外触发哈希表收缩 —— 于是 75.65 ms vs 22.85 ms。
  表中「一次跳转（保留 cnt）」= 只把 `while` 循环换成 `left = min(last.values()) + 1`、其余结构一行不动，用来**隔离「收缩方式」这一个变量**；「位置表 + min」则是把已经冗余的 `cnt` 与 `del` 一并删掉后的最终形态。
- 反过来，`'a' * n` 场景里 `len(cnt) >= 5` 每次都直接失败，原版只剩 n 次 `cnt[j] += 1`，**此时它并不比位置表慢**（19.09 vs 18.87）；「一次跳转」版反而慢 8%，因为多维护了一张 `last` 表却用不上。⇒ **没有在"永不收缩"这一类输入上验证过的提速结论是不可信的。**
- n = 100（题面上限）实测：原版 0.018~0.071 ms、位置表版 0.018~0.022 ms —— 都远离可测精度，对判题没有任何区别。

### 可优化空间

原版每轮做两件其实**互相蕴含**的事：既维护「窗口内计数」，又用 `while` 一格一格地把 `left` 推到分界点。而分界点本身可以**直接算出来**：它只取决于「五种元音各自最后出现在哪里」。

**引理**：记 `last[v]` 为元音 `v` 在已扫描前缀中的最后出现位置（未出现记 −1），`lo = min(last.values())`，`start` 为当前纯元音段起点。则原版每轮结束时恒有

```
left = max(start, lo + 1)     ⇒    本轮答案数 left - start = max(0, lo - start + 1)
```

**证明梗概**：
窗口 `[s, right]` 含全部 5 种元音 **⟺** 对每种元音 `v` 都有 `s ≤ last[v]` **⟺** `s ≤ lo`。所以 `lo` 恰好是**最大合法起点**。
对 `left` 归纳，断言恒有 `left = max(start, lo + 1)`：

① `while` **进入**了（窗口确有 5 种）：循环体每执行一次 `left` 增 1，窗口在「某种元音被删空」时才掉到第 4 种；由于是从左往右逐个删，**最先被删空的必然是 `last` 最小的那种** ⇒ 退出时 `left = lo + 1`，而此时 `lo ≥ start`，与 `max(start, lo + 1)` 一致。
② `while` **未**进入：说明窗口 `[left, right]` 缺了某种元音 `v`，即 `last[v] < left = max(start, lo_prev + 1)`，于是 `lo + 1 ≤ max(start, lo_prev + 1)`；又 `lo` 单调不减（`last` 只会被改大）给出反向不等号 ⇒ 两边相等。
③ 遇到辅音：`start = left = right + 1 > lo`，仍与 `max(start, lo + 1) = start` 一致。
∎ 配合实测：变体 B/D 与用户原版在 40 组随机用例上答案**逐位一致**（0 组不一致）。

据此可以把整个 `while` 循环、计数表、`del` 一并删掉 —— **不需要任何计数，只需要「最后出现位置」**。

### 优化代码

```python
class Solution:
    def countVowelSubstrings(self, word: str) -> int:
        last = dict.fromkeys('aeiou', -1)     # 每种元音的最后出现位置，只建一次
        ans = start = 0
        for right, ch in enumerate(word):
            if ch not in 'aeiou':
                start = right + 1             # 断段，无须清表：旧值必然 < start
                continue
            last[ch] = right
            lo = min(last.values())           # 最大合法起点
            if lo >= start:                   # lo < start 说明本段还没凑齐 5 种
                ans += lo - start + 1
        return ans
```

**优化理由**：

1. 把 `while` 的**逐格收缩**换成**一次 `min`**——前者总代价摊还 O(n) 但每次都是 Python 层的一轮字典读写（含 `del`），后者是一次 C 层 `min`；
2. 断段时不必清表，因为「未在本段出现的元音」其 `last` 必然 `< start`，`lo >= start` 的判据自动把它筛掉；
3. 代码路径变直：每个元音字符只做「更新位置 + 取最小值 + 一次加法」，没有分支内循环。实测最坏场景 2×~3.3×（见上表）。

### 被证伪的改法

~~把 `while len(cnt) >= 5` 改成 `if len(cnt) >= 5`（一轮只缩一格）~~ —— **实测是错的，不要改**：

- 官方示例 3 `"cuaieuouac"`：得 **6**，真值 7；
- 40 组随机用例错 **11** 组；
- **最小反例** `word = "aaeiou"`：得 **1**，真值 **2**（长度 6 处命中，是本题唯一可能的最短反例形状）。

原因：一轮里可能需要**连缩多格** —— 当某个元音在窗口内出现了不止一次时，删掉最左边那个并不会让它消失，窗口仍含 5 种。`"aaeiou"` 里 `a` 出现两次，必须连缩两格才能把 `a` 删空，而 `if` 只缩一格，于是把「起点 1」这个合法解漏掉了。

这也说明：**「`if` 版在最长窗口题里能用」的那根救命稻草是「答案 = 窗口长度 ⇒ 长度单调不减」，本题答案是「数目」，这根稻草用不上** —— 收缩方式必须老老实实收缩到临界点。

### 常数级优化（可选）

- 把 `min` 绑定为局部名（`minv = min`）可以在百万级循环里省下一点全局查找，量级在 1% 上下，不必强求。
- 计数表用 `dict.fromkeys` 一次性建好，避免每段重建；`Counter` 的 `__missing__` 机制对「只关心 5 个固定键」的场景属于额外成本。
- 若想彻底消灭哈希：元音只有 5 种，可把 `last` 换成用 `ord(ch)` 索引的 `list`（26 长度）+ `min(last[0], last[4], last[8], last[14], last[20])`，把字典查表换成数组下标。但这会把「可读性」换成边际收益，n ≤ 100 的本题完全不值得。

## 六、易错点与总结

### 易错点

- **忘记 `del`（本族最致命）**：既然判据是「不同元音**种类数**」，某种元音计数减到 0 后必须删键。不删的话 `len(cnt)` 只增不减 —— 一旦 5 个键建满，`while len(cnt) >= 5` **永远为真**，`left` 会被一路推到 `right + 1`，随后 `word[left]` 取到辅音或直接 `IndexError`（如 `"aeiou"` 就会越界）。这是按键数收缩的**结构性**要求，不是偶发边界。
- **`while` 换成 `if`**：见 §五，最小反例 `"aaeiou"`。
- **段切换时漏重置变量**：`start`（段起点）、`left`（窗口左界）、计数表三者必须同时重置，只重置其中一两个会得到「跨段的虚假答案」。
- **误用「窗口长度」口径**：这题要的是「子串的**个数**」，不是「最长合法窗口」。写成 `right - left + 1` 之类的长度口径会直接量纲错误。

### 题型套路沉淀

- **计数型滑窗的标准套路**：固定右端 → 论证「合法起点集合是一个前缀」（单调性）→ 求出分界点 `lo` → `ans += lo - start + 1`。凡是题目问「满足某性质的**子数组/子串有多少个**」，优先往这个模板上靠，而不是去枚举起点。
- **「按值」还是「按键数」收缩，决定了要不要 `del`**：判据写成「某元素出现次数 > k」是按值，计数归零可以留键；判据写成「窗口内不同元素种类数 ≥/> k」是按**键数**，归零**必须删键**。写滑窗之前先把判据归类，边界条件会自己浮出来。
- **「恰好 K 种」的备用口径**：「恰好 5 种 = 至多 5 种 − 至多 4 种」是一个通用转化（两次滑窗相减）。但本题的字母表恰好就是 5 种元音，「至多 5 种」退化成「所有纯元音子串」，于是等于把同一件事做两遍，比单趟计数更慢 —— 用之前先看这个退化是否发生。
- **最坏情况要按「收缩频率」挑输入**，不能只看 n：同一份代码在「全是同一个元音」（从不收缩）与「元音周期轮转」（每轮都收缩）上的耗时可以差 4 倍（75.65 ms vs 19.09 ms）。
