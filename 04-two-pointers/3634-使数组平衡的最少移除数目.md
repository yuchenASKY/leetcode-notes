# 3634. 使数组平衡的最少移除数目

> **难度**：中等
> **标签**：数组 · 排序 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/minimum-removals-to-balance-array/

---

## 一、题目描述

给定整数数组 `nums` 和整数 `k`。若数组的**最大值 ≤ 最小值的 `k` 倍**，则称其**平衡**。

可以移除任意数量的元素（但不能把数组变成空的），求使剩余数组平衡所需的**最少移除数**。

### 示例

```text
示例 1
输入：nums = [2,1,5], k = 2
输出：1
解释：移除 5 得到 [2,1]，max = 2 <= min*k = 1*2，平衡。

示例 2
输入：nums = [1,6,2,9], k = 3
输出：2
解释：移除 1 和 9 得到 [6,2]，max = 6 <= min*k = 2*3，平衡。

示例 3
输入：nums = [4,6], k = 2
输出：0
解释：原本就平衡（6 <= 4*2）。
```

### 约束条件

- `1 <= nums.length <= 10^5`
- `1 <= nums[i] <= 10^9`
- `1 <= k <= 10^5`

> **注意**：大小为 1 的数组**一定平衡**（最大值 = 最小值），所以答案永远存在，且 `n = 1` 时答案为 `0`。
> `k >= 1` 这个下界比看上去重要 —— 它是本题两个写法细节成立的前提（见「关键点」）。

## 二、解题思路

### 核心思想

**把「移除」换成「保留」**：移除最少 ⟺ 保留最多。

```
答案 = n - max{ |S| : S ⊆ nums 非空, max(S) <= k * min(S) }
```

然后是一句关键的观察：**约束只跟 `min(S)` 和 `max(S)` 两个值有关，中间的元素白拿。**

> 设 `S` 的最优解里 `lo = min(S)`、`hi = max(S)`。任何值落在 `[lo, hi]` 的原数组元素
> 加进 `S`，既不会变成新的最小值也不会变成新的最大值，约束仍然成立。
> 所以「值在 `[lo, hi]` 里的全部元素」一定也是合法解，且不少于 `S`。

于是**排序之后，最优保留集合必然是一段连续的下标区间** `[l, r]`，问题变成：

```
答案 = n - max{ r - l + 1 : a[r] <= k * a[l] }      a = sorted(nums)
```

这是一个标准的**滑动窗口**：右端 `r` 单调右移，左端 `l` 也跟着单调右移。

### 思路演进

1. **暴力解法 O(2ⁿ·n)**：枚举所有非空子集，检查 `max <= k*min`，取最大规模。约束 `n <= 10^5` 下完全不可行，但它是验证环节最可靠的「真值」。

2. **观察一：只需关心两个极值**。约束只看 `min` 和 `max`，所以可以枚举「最小值候选 `lo` + 最大值候选 `hi`」（`O(n²)` 个值对），再把值落在 `[lo, hi]` 里的元素全数进来 —— 降到 `O(n³)` 或配合前缀计数降到 `O(n²)`。

3. **观察二：排序后合法集合是连续区间**（上面的论证）。于是只需枚举 `O(n²)` 个下标区间 `(l, r)` 并检查 `a[r] <= k*a[l]` —— `O(n²)` 时间、`O(n log n)` 排序。

4. **观察三：双指针 ⇒ O(n)**。当 `r` 右移时，`a[r]` 变大，满足 `a[r] <= k*a[l]` 的最小 `l` **只会变大不会变小**（`a[l]` 越大阈值越宽松）。所以 `l` 全程单调不减，一次扫描即可：

   ```text
   l = 0
   for r in 0..n-1:
       while a[r] > k * a[l]:  l++      # 把最小值下限抬到恰好满足约束
       ans = max(ans, r - l + 1)
   ```

### 关键点

- **为什么可以「用 `max` 换元素」**：合法性的判定式 `max(S) <= k*min(S)` 里，`k >= 1` 意味着这个条件对「区间内部元素」是自动满足的 —— `min(S)` 与 `max(S)` 一旦定下，区间内怎么取都行。**这条性质保证了排序后最优解是连续区间**，是整题能到 O(n) 的根基。
- **本题的窗口内容和已归档的滑窗家族不同**：`1100 / 3 / 3090 / 1493` 维护的是「窗口内的**计数**」，窗口合法性由窗口内部状态决定；本题维护的是「**两端点之间的比值**」，合法性只由 `a[l]` 和 `a[r]` 决定。这个区别直接决定了收缩逻辑的形态（下一节）。
- **`k >= 1` 保证了 `while` 一定会停**：最坏情况 `l` 一路加到 `l == r`，此时判定式是 `a[r] > k*a[r]`，而 `k >= 1` 使它**恒假**，所以 `l` 永远不会越过 `r`。也就是说这里不会越界 —— 但**前提是 `k >= 1`**（约束内的输入安全）。
- **`while` 里 `l` 一次可能连跳多格**，这是本题和 `3 / 3090 / 1493` 最不一样的地方：那几题「每轮只追加一个字符 ⇒ 超额量恒为 1 ⇒ `if` 就够」；本题阈值是 `k * a[l]`，`a[l]` 可以连续跨好几个值才追上新来的 `a[r]`。
- **答案口径是「移除数」不是「保留数」**：`return n - ans`。示例 3 输出 `0` 就是提醒这一点。

## 三、代码实现

### 最终代码

用户提交的版本。**截图里第 1 行就是 `class Solution:`，没有 `from typing import List`** —— 本地实测：`List` 缺失时**在函数定义的那一刻**就抛 `NameError: name 'List' is not defined`（比 `defaultdict` 那种「调用时才抛」更早、更容易在粘贴代码时踩到）。下面这行 import 是补上的，否则代码不可直接运行。

```python
from typing import List


class Solution:
    def minRemoval(self, nums: List[int], k: int) -> int:
        n = len(nums)
        if n <= 1:
            return 0
        nums.sort()
        left = ans = 0
        for i, j in enumerate(nums):
            while (j > k * nums[left]):
                left += 1
            ans = max(ans, i - left + 1)
        return n - ans
```

**它好在哪**：

- 骨架就是最标准的「排序 + 双指针」，没有中间数组、没有额外容器；
- 原地 `nums.sort()`（而不是 `sorted(nums)`）少一次长度 `n` 的拷贝；
- 窗口合法性的判据 `j > k * nums[left]` 与题意 `max <= k*min` 一一对应，几乎不需要翻译。

**它的代价**：一句死代码（`if n <= 1: return 0`，见「优化评估」）+ 一次用不上的元组拆包以外没有别的 —— 这版基本就是这题的实用最优形态。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码（用户版）** | O(n log n) | O(n)（Timsort 最坏 n/2 临时缓冲） |
| 排序后枚举区间 `(l, r)` | O(n²) | O(n) |
| 枚举值对 `(lo, hi)` | O(n²) ~ O(n³) | O(n) |
| 朴素解法（枚举所有子集） | O(2ⁿ · n) | O(n) |
| 理论下界 | **Ω(n log n)** | — |

> 复杂度中的 `n` 指 `nums` 的长度。
>
> **时间下界为什么是 Ω(n log n)（比较模型内）**：本题的判定完全依赖**值的大小顺序** —— 要数「值落在 `[lo, k·lo]` 里的元素有多少个」，不建立有序性就无从下手。比较模型下排序的下界是 Ω(n log n)，而排序之后的双指针部分只有 O(n)，所以整体 O(n log n) 已经是这条路线的最好结果。
> 想真正线性只能靠**值域有界**做计数/基数排序（`O(n + V)`），但 `nums[i]` 可达 10⁹，既不现实、在 Python 里也不可能比 C 实现的 Timsort 快。
>
> **空间**：`nums.sort()` 原地排序，除 Timsort 自己的临时缓冲（最坏 n/2 个指针）外没有额外结构；算法的额外空间是 O(1)。

## 五、优化评估

**结论**：**用户版已经是最优的实用写法**。时间被排序占走 28%~52%，剩下的双指针循环已经是最薄的 Python 循环；本轮实测的三种「看起来更聪明」的改法**全部没有收益**（两种还明显更慢）。

### 瓶颈分析

**(1) 主成本是排序，不是双指针。**

实测（`n = 10^5`，各取 9 轮最优）：随机数据下纯 `sort()` 耗时 9.6~11.9 ms，占用户版总耗时（22~26 ms）的 **42%~52%**；已经排好序的输入上排序只占 2%。**任何在双指针循环里抠常数的努力，上限就是剩下那 50%** —— 而它已经只剩「一次乘法 + 一次比较 + 一次更新答案」。

**(2) 死代码：`if n <= 1: return 0`。**

删掉它对拍 3000 组，**零差异**；`n = 1` 单独验证也返回 0 —— 它是彻底多余的，不是防御性检查。原因是 `k >= 1` 保证了首轮 `while` 判定 `nums[0] > k*nums[0]` 恒假，`ans` 自然会变成 1，`n - ans = 0`。

> 手法沿用 `1493`：**「删掉再对拍」来定位特判的作用**，几乎零成本，可以把「这行在防什么」从猜测变成事实。

**(3) `while` 不能想当然地改成 `if` —— 虽然我没找到反例。**

`1100 / 3 / 3090 / 1493` 那几个题里「`while` 退化成 `if`」是有明确前提的（每轮只追加一个元素 ⇒ 超出量恒为 1）。**本题没有这个前提**：`a[l]` 可能要连跨几个值才追得上 `a[r]`，理论上 `l` 一次要跳多格。

但实测很奇怪：把 `while` 换成 `if`（每轮最多跳一格）后，

| 检验方式 | 规模 | `if` 版错误数 |
| :--- | ---: | ---: |
| 穷举 `n=6`，值域 1..4，`k=1..4` | 16384 组 | 0 |
| 穷举 `n=7`，值域 1..3，`k=1..3` | 6561 组 | 0 |
| 穷举 `n=8`，值域 1..2，`k=1..5` | 1280 组 | 0 |
| 随机 `n<=9`，值域含 2/3/5/10/50/1000/10⁹，`k ∈ [1, 10⁵]` | 60000 组 | 0 |

机制上能解释一半：`if` 版里 `宽度 = i - l + 1` **单调不减**（跳格时宽度不变、不跳时 +1），而宽度只会在「不跳」（即当前窗口合法）时增长 —— 所以它报出的每个宽度都对应某个**合法**窗口，`ans_if <= 最优`。反向（不会漏掉更大的合法窗口）我没能证明。

> **结论：不要改。**「没找到反例」不等于「等价」，`while` 是零风险的写法，用户这里的直觉是对的。
> 这类「实测无差异但无证明」的等价关系，记下来是为了**下次别再花时间想它**，而不是为了去改代码。

**(4) 实测过、确实更慢的三种写法。**

| 想法 | 做法 | 实测结果 |
| :--- | :--- | :--- |
| 用二分定位左边界 | `left = bisect_left(a, ceil(a[i]/k))` 取代内层 `while` | **慢 41%~91%** |
| 跳过重复值段的中间下标 | 段内 `left` 不变，窗口必然在段尾最大 → `if a[i+1] == x: continue` | **慢 0%~42%** |
| C 式下标循环 + 手写比较 | `range` + 预计算 `limit` + `if` 取代 `max()` | 快 **1%~8%**（噪声边缘，方向一致） |

- **二分版更慢是反直觉但可解释的**：`left` 在整趟循环里**总共只推进 n 次**，摊还到每个元素就是 O(1) 的「一次比较」；而 `bisect_left` 每次都要付一次 Python 函数调用 + 向上取整除法 + `log n` 次比较。**用 O(log n) 的查找去替代摊还 O(1) 的指针推进，是典型的负优化。**
- **跳重复版更慢更有教育意义**：`continue` 只省掉「算窗口宽度 + 比较」两个操作，却要额外交「取 `a[i+1]` + 比较 + 分支」；而且它**并不会减少循环趟数**（仍然逐个下标走过），所以「重复多」的输入也没占便宜（`仅10种值` 那档反而略慢）。真想跳过得先知道每段的边界，那是另一种扫描，得不偿失。
- **C 式那 1%~8% 的收益来自**：`range` 下标循环省掉 `enumerate` 的元组拆包、`if w > ans` 省掉 `max()` 的函数调用、`limit` 预计算少一次重复乘法。**收益太小，不值得为它牺牲可读性** —— 但知道「收益只有这个量级」本身有价值。

### 可优化空间

**(1) 时间：没有可优化空间。** 排序是 Ω(n log n) 下界（见复杂度分析），双指针已是 O(n) 且循环体不能再薄。

**(2) 空间：已经是最省的形态。** 唯一的「额外空间」是 Timsort 的临时缓冲；如果不想改输入数组可以换 `sorted()`，代价是多一份 `n` 长的拷贝。

**(3) 唯一值得改的两处**：补 `from typing import List`；删掉 `if n <= 1` 那三行。

### 优化代码

改动最小的一版：**只补 import、删死代码**，骨架一个字不动。

```python
from typing import List


class Solution:
    def minRemoval(self, nums: List[int], k: int) -> int:
        nums.sort()
        n = len(nums)
        left = ans = 0
        for i, x in enumerate(nums):
            while x > k * nums[left]:       # k >= 1 保证 left 不会越过 i
                left += 1
            if i - left + 1 > ans:
                ans = i - left + 1
        return n - ans
```

> `n = 1` 走这条路也返回 0，不需要特判；`nums` 为空（约束外）时循环不执行、返回 0。

**优化理由**：

- 删掉死代码，`n = 1` 由主逻辑自然覆盖（3000 组对拍零差异）；
- `nums.sort()` 原地排序，比 `sorted()` 少一次拷贝；
- `if w > ans` 取代 `max(ans, w)`：省一次函数调用（实测在噪声量级，1%~3%）。

**实测（本机 CPython 3.13，`n = 10^5`，轮转 9 轮取各版最优，单位 ms）**：

| 场景 | 用户版 | C 式下标 | 跳重复段 | 二分定位 | 纯 `sort()` | 排序占比 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 全不同，`k=1` | 26.08 | **25.74** | 30.58 | 36.66 | 11.91 | 46% |
| 全不同，`k=100` | 22.75 | **22.63** | 28.36 | 36.75 | 11.87 | 52% |
| 全不同，`k=10⁵` | 22.95 | **22.42** | 28.21 | 35.83 | 11.84 | 52% |
| 值域 1e3 重复，`k=1` | 23.76 | **23.45** | 26.40 | 34.22 | 9.98 | 42% |
| 值域 1e3 重复，`k=2` | 22.32 | **21.96** | 23.22 | 34.50 | 9.59 | 43% |
| 仅 10 种值，`k=1` | 17.69 | **16.72** | 18.10 | 26.00 | 4.90 | 28% |
| 全相同 | 10.29 | **9.45** | 10.26 | 19.65 | 0.24 | 2% |
| 已排序递增，`k=1` | 13.52 | **12.67** | 17.77 | 23.05 | 0.24 | 2% |
| 已排序递增，`k=10⁵` | 10.47 | **9.70** | 14.91 | 20.02 | 0.24 | 2% |

**怎么读这张表**：

- 用户版和 C 式下标版是**同一个量级**，差距（1%~8%）小到不足以成为「该改代码」的理由；
- **跳重复段和二分定位都是负优化**，后者在最差场景慢到接近 2 倍；
- 「排序占比」这一列说明了**优化的天花板在哪**：随机数据下有一半时间在排序里，而排序已经是最优做法 —— 这就是「已是最优」的量化依据。

### 常数级优化（可选）

- **别用 `enumerate` 换 `range`**：本题 `i` 是有用的，`enumerate` 是正解；`range` 省下的拆包开销只有几个百分点。
- **原地 `sort()` 优于 `sorted()`**：省一次 `n` 长的拷贝（10⁵ 规模下约 0.3~0.5 ms）。
- **不要试图「用二分替代内层 `while`」**：`left` 的推进是摊还 O(1)，二分的 `log n` 次比较纯属自找。
- **不要试图「跳过重复值」**：省下的两个操作抵不过多出的三次。

## 六、易错点与总结

### 易错点

- **答案口径**：返回的是**移除数** `n - ans`，不是窗口长度。示例 3（`[4,6], k=2`）答案是 `0`，最容易写成 `2`。
- **忘了排序**：不排序就没有「最优解是连续区间」这个性质，双指针完全失效。
- **`while` 写成 `if`**：本约束下实测不出错（见上表），但**没有证明**，属于「碰巧对」—— 别赌。
- **`k = 0` 会越界**：约束保证 `k >= 1`。若 `k = 0`，`while` 判定 `j > 0` 恒真，`left` 会一路推过 `i` 直到 `IndexError`。写代码时知道这个前提在哪。
- **`n = 1` 的 `ans`**：`ans` 初值 0、首轮必被更新为 1，所以 `n - ans = 0`；不需要特判，但也别把 `ans` 初值写成 1（`n >= 1` 时也无害，纯属巧合）。
- **C++ 版的溢出**：`k * nums[i]` 最大 `10^5 × 10^9 = 10^14`，**超出 `int`**，必须用 `long long`。Python 无此问题。
- **`nums.sort()` 会改调用者的数组**：LeetCode 里无所谓，如果这段逻辑嵌在别处复用同一个 list 要注意。

### 题型套路沉淀

- **「值域区间 + 最值约束」的通用转化**：

  | 约束形态 | 排序后最优解的结构 | 解法 |
  | :--- | :--- | :--- |
  | `max <= k * min`（比值） | 连续区间 `[l, r]` | 双指针滑窗，判据 `a[r] <= k*a[l]` |
  | `max - min <= d`（差值） | 连续区间 `[l, r]` | 双指针滑窗，判据 `a[r] - a[l] <= d` |
  | 窗口内**计数/种类**受约束 | 不一定是连续区间 | 计数表 / 最近出现位置（`3` / `3090` / `1493`） |

  **共同前提是「合法性只由区间两端决定」** —— 满足它，才可以把「选子集」降级成「选连续区间」；不满足（例如约束是「窗口内某值出现次数」），排序就帮不上忙。

- **比值约束的两种等价写法**：`a[r] <= k*a[l]`（乘法）与 `ceil(a[r]/k) <= a[l]`（除法 + 向上取整）。多元素类型下后者更方便二分/查表，**但本题实测二分版更慢**（见优化评估）—— 等价不等于等效。

- **双指针左端点的两种形态**（本题和 `3` 家族的对照，值得记住）：

  | 触发条件 | 左端点行为 | 写法 |
  | :--- | :--- | :--- |
  | 每轮只追加一个元素，超出量恒为 1 | 一次最多跳一格 | `if` 够用（`3` / `3090` / `1493`） |
  | 判据依赖两个端点的值，左端可能连追多格 | 需循环推进 | 必须 `while`（本题） |

- **同型题**：
  - `2779. 数组的最大美丽值` —— **本题的姐妹题**，把「比值 `max <= k*min`」换成「差值 `max - min <= 2k`」，骨架（排序 + 双指针）完全一样；
  - `1838. 最高频元素的频数` —— 排序 + 滑窗，约束是「把区间内元素都抬到 `a[r]` 的花费 ≤ k」；
  - `220. 存在重复元素 III` —— 值差约束，但要求两个下标也邻近，需要桶/有序集合，是这一族的「带下标约束」变体；
