# 2904. 最短且字典序最小的美丽子字符串

> **难度**：中等
> **标签**：字符串 · 滑动窗口
> **原题链接**：https://leetcode.cn/problems/shortest-and-lexicographically-smallest-beautiful-string/

---

## 一、题目描述

给定只含 `0` / `1` 的字符串 `s` 和正整数 `k`。若 `s` 的某个子串中 `1` 的个数**恰好等于** `k`，称它是**美丽子字符串**。设 `len` 为最短美丽子字符串的长度，要求返回**长度为 `len` 且字典序最小**的美丽子字符串；若不存在则返回空串 `""`。

### 示例

```text
输入：s = "100011001", k = 3
输出："11001"

输入：s = "1011", k = 2
输出："11"

输入：s = "000", k = 1
输出：""
解释：s 中一个 '1' 都没有，不存在美丽子字符串。
```

示例 1 里 `1` 位于下标 `0, 4, 5, 8`，恰含 3 个 `1` 的子串共 7 个：

```text
[0,5] 100011    [0,6] 1000110    [0,7] 10001100
[1,8] 00011001  [2,8] 0011001    [3,8] 011001    [4,8] 11001
```

最短长度为 5，长度为 5 的候选只有 `"11001"`。

### 约束条件

- `1 <= s.length <= 100`
- `s[i]` 只能是 `'0'` 或 `'1'`
- `1 <= k <= s.length`

## 二、解题思路

### 核心思想

**「最短」用滑动窗口的「左端收缩到底」保证，「字典序最小」只在**等长**候选之间比较。** 关键是先把两个目标解耦：靠窗口收缩锁定长度，再在等长候选里挑最小的那个。

### 思路演进

1. **暴力解法**：枚举所有子串 `[i, j]`，数其中 `1` 的个数；在个数等于 `k` 的子串里先取长度最小、再取字典序最小。枚举 O(n²) 个子串、每个再数一遍 `1` 是 O(n)，总时间 O(n³)。

2. **观察到**：固定右端 `r` 时，「以 `r` 结尾且恰含 `k` 个 `1` 的子串」是一批**连续的起点** `l`，从某个 `l₀` 一直排到某个 `l*`；`l` 越靠右，窗口越短。因此**以 `r` 结尾的最短合法窗口，就是把左端推到最右的那一个** —— 每个 `r` 只需关注「收缩到底」的窗口，不必枚举全部 O(n²) 个子串。

3. **为什么原来不行、现在为什么行**：暴力的浪费在于「对每个子串重新数一遍 `1`」。改成滑动窗口后，计数随指针移动**增量维护**：`right` 走一格就 `+1`，`left` 走一格就 `-1`，「数数」这件事从 O(n) 降到 O(1) 摊还。并且**左指针整趟只从 0 走到 n**，所以所有被处理的窗口总数是 O(n) 的。

4. **最优解**：一趟扫描。外层 `right` 从左往右；内层 `while` 在窗口内 `1` 的个数 `>= k` 时反复做「记录当前窗口 → 右移左端」，退出时窗口内 `1` 的个数 `< k`。由于每轮最多加进来一个字符，退出时左端恰好是「第一个让窗口不合法的 `l`」，故**最后一个被记录的窗口，就是以 `r` 结尾的最短合法窗口**。
   两个分支各管一个目标：
   - 候选长度 `==` 当前最优长度 → **等长比较字典序**，更小才更新起点；
   - 候选长度 `<` 当前最优长度 → 直接替换（长度优先）。

### 判据

记 `ones(l, r)` 为 `[l, r]` 中 `1` 的个数。

**判据**：`[l, r]` 是以 `r` 结尾的**最短**美丽窗口 ⟺ `l` 是满足 `ones(l, r) == k` 的**最大**左端。

- **必要性**：若还存在 `l' > l` 满足 `ones(l', r) == k`，则 `[l', r]` 更短，与「最短」矛盾。
- **充分性**：满足 `ones == k` 的窗口长度 `r - l + 1` 随 `l` 增大而减小，最大的 `l` 给出最小长度。

由这条判据再推一步：**全局最优解一定落在「收缩到底」的窗口集合里**。设答案长度为 `len`（最小），对应窗口 `[l, r]`；若 `l` 不是该 `r` 下最大的合法左端，就存在更短的合法窗口，与 `len` 最小矛盾。所以「每个 `r` 只看收缩到底的窗口」**不漏解**。

### 关键点

- **两个目标必须有优先级**：先比长度，等长才比字典序。若写成「字典序更小就替换」，会把长串选进来 —— 例如 `"0101"` 的字典序小于 `"101"`（首字符 `0 < 1`），但 `s = "0101", k = 2` 的答案应是更短的 `"101"`。
- **等长的二进制串，数值序 == 字典序**：这是原代码用 `int()` 比较的依据。`"010"` vs `"011"`：数值 `10 < 11`，字典序 `"010" < "011"`；`"001"` vs `"010"`：数值 `1 < 10`，字典序同样。**前提是两串长度相等** —— 长度不等时数值序会把 `"1"` 判成大于 `"01"`，与字典序正好相反（还多一个前导零的坑）。
- **记录必须在收缩之前**：先 `left += 1` 再记录的话，窗口在被记录前就已经不合法了，每个 `r` 的最短窗口都会被跳过。
- **`while` 进入时窗口内 `1` 的个数恰好是 `k`**：退出上一轮时计数 `< k`，每轮最多 `+1`，所以进入时 `计数 == k`，不会 `> k`。这保证了每次被记录的窗口都是合法的。

## 三、代码实现

### 最终代码

```python
from math import inf


class Solution:
    def shortestBeautifulSubstring(self, s: str, k: int) -> str:
        ans = inf                      # 当前最优长度；inf 表示尚未找到合法窗口
        ansIndex = 0                   # 当前最优窗口的左端
        left = temp = 0                # left：左指针；temp：窗口内 '1' 的个数
        for right, j in enumerate(s):
            temp += int(j)
            while temp >= k:           # 进入时 temp 恒等于 k
                if ans == right - left + 1:
                    # 等长才比字典序；等长二进制串的数值序 == 字典序
                    if int(s[left:right + 1]) < int(s[ansIndex:ansIndex + ans]):
                        ansIndex = left
                elif ans > right - left + 1:
                    ans = right - left + 1
                    ansIndex = left
                temp -= int(s[left])
                left += 1              # 先记录，后收缩
        return s[ansIndex:ansIndex + ans] if ans < len(s) + 1 else ""
```

> 补全说明：截图里只有 `class Solution:`，`inf` 未导入，已补 `from math import inf`；截图里 `if int(s[left : right + 1]) < int(s[ansIndex : ansIndex + ans]):` 被编辑器折成两行，这里合并为一行。其余逻辑、变量名与原提交完全一致。

## 四、复杂度分析

> 复杂度中的 `n` 指字符串 `s` 的长度（`1 <= n <= 100`），`L` 指最优子串的长度，`T` 指「长度等于最优长度的候选窗口」个数。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(n + T·L) | O(1) |
| 朴素解法 | O(n³) | O(1) |
| 理论下界 | Ω(n) | O(1) |

- **指针部分的摊还**：`left` 单调不减且最多走到 `n`，所以内层 `while` 的**总迭代次数**是 O(n)，不是每轮 O(n)；外层 `for` 也是 O(n)。计数增减与指针移动本身都是 O(1)。
- **额外代价全部落在比较上**：只有「候选长度 == 当前最优长度」时才切片并比较，单次代价 O(L)。设这类等长候选有 `T` 个，则额外代价 O(T·L)。最坏情况 `s = "1"×n, k = n/2`：`L = n/2` 且 `T ≈ n/2`，总代价 O(n²)。
- **空间 O(1)**：只维护常数个标量（`left` / `right` / `temp` / `ans` / `ansIndex`）。切片是临时对象，比较完即释放，属峰值开销而非持续占用。

## 五、优化评估

**结论**：**时间复杂度的量级在本题约束下已无必要再降，但常数因子有明显优化空间 —— 定向最坏场景实测可提速约 30×。**

### 瓶颈分析

把耗时按环节拆开看：

| 环节 | 原代码是否付出 | 说明 |
| :--- | :--- | :--- |
| 指针移动 + 计数增减 | 是，O(n) | 不可去，是算法的骨架 |
| 等长候选**切片** | 是，每个候选 **2 次** | `s[left:right+1]` 与 `s[ansIndex:ansIndex+ans]` 各拷一份 |
| 等长候选 **`int()` 转换** | 是，每个候选 **2 次** | 这里才是真正的大头 |

`int("111...1")`（1000 位的十进制串）在 CPython 里**不是 O(1)**：它是把一个十进制串解析成二进制大整数，属于进位制转换，代价远超一次字节比较。而这次比较真正需要的只是「两个**等长**串谁字典序更小」—— 那是 C 层 `memcmp` 级别的工作。用 `int()` 去做，等于为了比大小先造了两个大整数。

### 可优化空间

1. **去掉 `int()`**：等长二进制串的数值序与字典序等价，直接 `a < b` 即可。（本轮实测：等长随机串 2000 组，两种比较结果**不一致 0 组**。）
2. **减少切片次数**：候选只切一次，与「当前最优串」比，而不是切两次。
3. **直接维护最优串本身**，而不是「左端 + 长度」两个派生量 —— 省掉 `ansIndex`，末尾也不必再 `s[ansIndex:ansIndex+ans]` 重建一遍。
4. **加长度门禁**：窗口比当前最优还长时，连切片都不做。

为什么数量级不必再降：时间下界是 Ω(n)（不读完 `s` 无法判断有没有解）；而要把「等长候选的字典序比较」摊还到 O(1)，需要字符串哈希 + LCP 或后缀数组一类的结构。本题 `n <= 100`，为省一点常数去引入哈希结构是典型的负优化 —— 更关键的是，§二 的判据已经把「枚举全部子串、每个重新数 `1`」的 O(n²) 次计数消掉了，剩下的等长比较是必要的。

### 优化代码

```python
class Solution:
    def shortestBeautifulSubstring(self, s: str, k: int) -> str:
        best = ""
        bestLen = len(s) + 1           # 哨兵：比任何合法长度都大
        left = ones = 0
        for right, ch in enumerate(s):
            ones += ch == "1"          # bool 直接当 0/1 用，省掉 int()
            while ones >= k:
                length = right - left + 1
                if length <= bestLen:  # 比当前最优还长就跳过，连切片都省
                    cur = s[left:right + 1]
                    if length < bestLen or cur < best:
                        best, bestLen = cur, length
                ones -= s[left] == "1"
                left += 1
        return best
```

**优化理由**：

- `int(a) < int(b)` → `cur < best`：在**等长**前提下两者等价（本轮 2000 组等长随机串实测 0 组不一致），但字符串比较是 C 层 `memcmp`，不需要构造大整数。长度不等时已被 `length < bestLen` 短路，不会走到比较 —— 也就是说，正确性不依赖于「等价」这一条，只依赖于「等长才比」这个前提。
- `best` 直接存最优子串（`bestLen = len(best)` 与之同步更新），用 `len(s) + 1` 作哨兵，无解时自然返回 `""`，与原代码 `ans < len(s) + 1` 的哨兵思路一致，但少维护一个变量。
- `length <= bestLen` 门禁把「窗口已比最优长」的情况全部挡在切片之前。

### 实测对比

同一台机器、同一轮测量（轮转 9 轮取最优，`n = 2000`）：

| 场景 | V1 截图原版 | V2 仅去 `int` | V3 优化版 | V3 / V1 |
| :--- | ---: | ---: | ---: | ---: |
| A 全 `1`，`k = n/2`（等长候选多且长） | 12.18 ms | 0.55 ms | **0.41 ms** | **29.8×** |

- 场景 A、E 是针对 `int()` 的**定向最坏情况**（存在大量等长候选，且候选很长），差距主要来自大整数转换；B / C / D 的等长候选很短或很少，三者接近。
- **必须说明**：本题约束是 `n <= 100`，上表把 `n` 放大到 2000 只是为了看清常数因子的来源，属于**泛化到任意 n 的研究**。在 `n <= 100` 的实际约束下三个版本都是 0 ms，**不存在「不优化就会超时」**这回事。

### 常数级优化（可选）

- `ch == "1"` / `s[left] == "1"` 直接返回 `bool`，`ones += bool` 天然完成 0/1 累加，比 `int(ch)` 少一次函数调用。
- 若坚持保留「左端 + 长度」的写法，至少要保证**只在等长时切片**：`if length == bestLen and s[left:right+1] < s[idx:idx+bestLen]`。把切片提到长度判断之外是最常见的自伤写法。
- `ans` 即使初始化成 `0` 而不是 `inf`，行为也等价（`ans == length` 恒为假、`ans > length` 恒为真，只走 `elif` 分支，末行哨兵 `ans < len(s)+1` 在无解时返回 `s[0:0] == ""`）—— 但可读性差且容易被误改，仍建议保留 `inf`。

## 六、易错点与总结

### 易错点

- **用 `int()` 比字典序**：长度相等时结果正确，但代价是大整数转换；而这份等价关系**绑在「等长」上**，一旦去掉这个前提（比如哪天允许不同长度的候选互相比较），结论立刻翻转，别把它当通用结论。
- **把长度优先级写反**：不能只看字典序。`s = "0101", k = 2` 时 `"0101" < "101"` 为真，但答案是更短的 `"101"`。
- **记录与收缩的顺序颠倒**：先 `left += 1` 再记录，会跳过每个 `r` 的最短窗口。
- **忘记导入 `inf`**：截图代码用了 `inf` 却没 import（本次已补 `from math import inf`）。
- **末行哨兵不能删**：无解时 `ans` 仍是 `inf`，直接写 `s[ansIndex:ansIndex + ans]` 会因浮点下标抛 `TypeError`。
- **下标不会为负**：`ansIndex` 只在窗口有效时被赋值、`ans` 只在有解时是正数、`left <= right`，因此不存在 Python 负索引静默取到尾部元素的风险。

### 题型套路沉淀

- **「最短 + 字典序最小」是双目标问题，先长度后字典序**，不要试图用一个比较函数同时照顾两个目标。
- **滑动窗口的「收缩到底」原则**：固定右端时，最优解一定落在「左端推到最右」的那个窗口上。这条判据把「枚举所有合法窗口」压缩成「每个右端只看一个候选」。证明方式是反证 —— 若还能更短，则当前不是极值。
- **等长字符串的字典序 == 数值序**：想省事时可以用，但必须显式检查「等长」这一前提，并在代码注释里写出来。
- **`while` 收缩的摊还分析要点**：内层循环次数上界看的是**左指针能走多远**，不是外层循环次数。`left` 单调不减、最多到 `n`，所以内层总次数 O(n)。
- **判据族归属**：本题属滑窗家族中「合法性由**窗口内部计数**决定」的一类（而非「只看两端点的值」那一类）；又因为每轮最多只追加一个元素（超出量恒为 1），`while` 在逻辑上可以退化成带跳转的 `if`。但要特别注意：**本题的答案口径既不是窗口长度、也不是可加的数值度量，而是一个需要跨窗口比较的字符串** —— 所以长度口径下那些「收缩方式 × 答案口径」的等价性推论**不适用于本题**，这里不能套用。
