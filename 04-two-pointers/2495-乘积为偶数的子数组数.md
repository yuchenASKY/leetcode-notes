# 2495. 乘积为偶数的子数组数

> **难度**：中等
> **标签**：数组 · 数学 · 动态规划
> **原题链接**：https://leetcode.cn/problems/number-of-subarrays-having-even-product/

## 一、题目描述

给定一个整数数组 `nums`，返回其中**乘积为偶数**的子数组（连续非空区间）个数。

### 示例

```text
示例 1：
输入：nums = [9,6,7,13]
输出：6
解释：含偶数 6 的 6 个子数组的乘积都是偶数
      nums[0..1]=54、nums[0..2]=378、nums[0..3]=4914、
      nums[1..1]=6、nums[1..2]=42、nums[1..3]=546

示例 2：
输入：nums = [7,3,5]
输出：0
解释：全为奇数，没有任何子数组的乘积是偶数
```

### 约束条件

- `1 <= nums.length <= 10^5`
- `1 <= nums[i] <= 10^5`
- 结果可能超过 32 位整数：`n = 10^5` 时全部子数组数为 `n(n+1)/2 ≈ 5×10^9`，所以题面在 C++/Java 里的返回类型是 `long long` / `long`（Python 不受影响）

## 二、解题思路

### 核心思想

**乘积的奇偶性只由「子数组里有没有偶数」决定。** 于是问题从「算乘积」退化为「数一数」：固定右端点 `j` 时，合法的左端点恰好构成一个前缀 `[0, lastEven(j)]`，共 `lastEven(j) + 1` 个 —— 逐个累加即可。

### 思路演进

1. **暴力解法**：枚举全部 `n(n+1)/2` 个子数组，对每个都判断「是否含偶数」（或直接乘出乘积看奇偶）。时间 O(n²)，`n = 10^5` 时是 5×10^9 次操作，必然超时。
2. **瓶颈定位**：慢在「每个右端点都把左侧重新扫一遍」。但真正浪费的是**信息没有被复用** —— 以 `j` 结尾的子数组，其合法性只取决于「最靠右的那个偶数在哪」，而这个位置是**随 `j` 单调不减**的一条信息，扫过一次就不该再扫。
3. **关键转化**：把判据从「乘积」换成「奇偶」。由「偶数 × 任何数 = 偶数」得
   > 子数组 `nums[l..r]` 的乘积为偶数 ⟺ `[l, r]` 内存在至少一个偶数。

   再固定右端 `r`：设 `lastEven(r)` 为 `≤ r` 的最后一个偶数下标（不存在记 −1）。则
   > `nums[l..r]` 合法 ⟺ `l ≤ lastEven(r)`。

   合法性**关于左端点单调**（左端越靠左越容易合法），所以合法集合是一段前缀，数量就是 `lastEven(r) + 1`。两个相邻右端点之间 `lastEven` 只会不变或右移 ⇒ 左边界只增不减 ⇒ 一趟线性扫描即可。
4. **最优解**：按这个观察直接维护 `lastEven`（优化版 1）即可 O(n)。本次提交的代码走的是**另一条等价路线**：用一个滑窗把「当前右端结尾的全奇数后缀」裁掉，窗口收缩到全奇数为止，左指针 `left` 恰好等于 `lastEven + 1`，于是 `ans += left`。两条路线的答案口径完全一致。

### 把解法压成判据

> **判据**：对右端点 `j`，窗口 `[left, j]` 内不含偶数（`prod` 为奇数）；此时以 `j` 结尾的合法子数组数 = `left`（左端可取 `0, 1, …, left-1`）。

### 识别判据族（重要，本族最容易串用）

本题属于 **「计数型滑动窗口（约束是『度量 ≥ 下限』）」** 这一族 —— 和最常见的「收缩到合法为止、求最长/最短窗口」是**两个方向相反**的族：

| 族 | `while` 条件 | 循环结束时窗口 | 答案口径 |
| :--- | :--- | :--- | :--- |
| 收缩到合法为止（最长/最短窗口） | `while 度量 违规`（收缩到合法） | **合法** | 窗口长度 / 每轮 `max` |
| **本族：计数型（度量 ≥ 下限）** | `while 度量 >= 阈值`（收缩到**非法**） | **非法** | `ans += left`（合法左端点的个数） |

本题的度量就是「窗口内偶数个数」，阈值是 1：`while 偶数个数 ≥ 1` 一直收缩到窗口**全为奇数**（非法），此时合法左端点恰好是 `[0, left-1]`，共 `left` 个。

**两根单调性必须都在**，本族才成立：

- 度量关于**左端点**单调不增 ⇒ 合法左端点是一段前缀（固定 `j` 时成立，因为左端右移只会删元素）。
- 度量关于**右端点**单调不减 ⇒ 左指针只增不减、总移动 ≤ n ⇒ 内层 `while` **摊还 O(1)**，整体仍是 O(n)，不能因为「`while` 嵌在 `for` 里」就判成 O(n²)。

### 关键点

- **奇偶只看一位**：`x` 是否为偶数，等价于 `x & 1 == 0`。乘积的奇偶不需要真的把乘积算出来 —— 这是本题从「数值」降到「状态」的枢纽。
- **答案口径是 `left`，不是窗口长度**。这一点是本族最大的坑，见下节四象限实测。
- **`while` 不能退化成 `if`**：出窗的那个元素**可能是奇数**，删掉它「偶数个数」一点都不减 —— 违规量没被真正消除，左指针就走少了。

## 三、代码实现

### 最终代码

```python
from typing import List          # 截图里没有、已补（否则笔记中的代码无法直接运行）


class Solution:
    def evenProduct(self, nums: List[int]) -> int:
        ans = left = 0
        prod = 1
        for j in nums:
            prod *= j
            while prod % 2 == 0:
                prod //= nums[left]
                left += 1
            ans += left
        return ans
```

> 代码来自提交截图（已 AC）。**不变量**：循环体内恒有 `prod == nums[left] * … * nums[j-1]`；`while` 退出时 `prod` 为奇数，故 `left` = 以 `j-1` 结尾的「连续奇数后缀」起点 = `lastEven(j-1) + 1`。截图共 11 行、与编辑器状态栏「行 11」一致，尾部未被裁掉。

## 四、复杂度分析

> 下表 `n` 指数组 `nums` 的长度；`V = max(nums) ≤ 10^5`（二进制位数 ≈ 17）。

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码（维护 `prod`）** | 名义 O(n)（指针摊还），但 `prod` 是真大整数：单次 `*=` / `//=` 是 O(位数)，最坏 **Θ(n² · log V / w)** | O(n · log V / w)（`prod` 本身，`n = 10^5` 时约 1.7×10⁶ bit ≈ 212 KB） |
| 优化版 1（记 `lastEven`） | **Θ(n)** | Θ(1) |
| 优化版 2（滑窗数偶数） | **Θ(n)** | Θ(1) |
| 朴素解法（枚举所有子数组） | Θ(n²) | Θ(1) |
| 理论下界 | Θ(n)（每个元素至少看一次） | Θ(1) |

> `w` 为 CPython 内部的 limb 宽度（30 位）。**"指针摊还 O(n)" 只描述了控制流，没描述数值运算的代价** —— 这是本题复杂度分析里唯一需要小心的地方，实测见第五节。

## 五、优化评估

**结论**：时间上**仍有数量级的优化空间** —— 不是常数级，而是最坏情况下从 Θ(n²·log V) 降回 Θ(n)。瓶颈不在遍历结构，在 `prod` 这个**大整数本身**。

### 瓶颈分析

`prod` 始终等于「以 `j` 结尾的最长全奇数后缀」的乘积。于是：

- 只要数组里有一段长 `L` 的、元素都 > 1 的奇数段，`prod` 就会长到 ~`17L` bit，最后一次乘法要把这 1.7×10⁶ bit 全部过一遍；
- 总代价是 Σ 每轮 `prod` 的位数 ⇒ 全奇数输入下 **Θ(n²·log V / w)**。这不是"常数大"，是渐进复杂度真的退化了一档。

### 实测（同一台机器、同一轮轮转测量，各取最优值）

| 场景（n = 10⁵，除标注外） | 用户版 `prod` | 优化版 1 `last` | 优化版 2 滑窗 | 优化版 1 提速 |
| :--- | ---: | ---: | ---: | ---: |
| A 全为大奇数 99999，n = 10⁴ | 130.03 ms | 0.61 ms | 0.50 ms | **213.1×** |
| A 全为大奇数 99999，n = 3×10⁴ | 1128.67 ms | 1.81 ms | 1.47 ms | **624.4×** |
| A 全为大奇数 99999，n = 10⁵ | 12588.09 ms | 6.09 ms | 5.08 ms | **2066.7×** |
| B 全为 1 | 4.72 ms | 6.18 ms | 5.04 ms | 0.8× |
| C 交替 `2/1` | 11.86 ms | 7.76 ms | 12.44 ms | 1.5× |
| D 随机混合（值域 10⁵） | 15.17 ms | 8.62 ms | 13.30 ms | 1.8× |

测量口径：场景 A 的 n = 10⁴ / 3×10⁴ 每个变体取 3~7 次最优值，n = 10⁵ 的用户版受单次耗时限制取 2 次最优值、其余变体 7 次；B/C/D 均为各 7 次。

三点读数：

1. **增长趋势证实了 Θ(n²)**：n 从 10⁴ → 3×10⁴（3×）耗时 130.03 → 1128.67 ms（**8.68×**，二次方预测 9×）；3×10⁴ → 10⁵（3.33×）耗时 1128.67 → 12588.09 ms（**11.15×**，二次方预测 11.1×）。两条都对得上 ⇒ 12.6 s 的 n = 10⁵ 不是常数项，是规模项。
2. **场景 B 是反向结论**：全为 1 时 `prod` 恒为 1（乘 1 不增长），用户版的循环体反而最简，比 `last` 版快 **0.8×**。所以「用户版一定更慢」是错的 —— 它的锅只在「长奇数段且元素 > 1」这一种输入上。**"最坏情况"要按数据结构（这里是"大整数的位数"）挑，不能只按 n 挑。**
3. **优化版 1 是唯一全场景只赚不亏的**：最坏 2066.7×，最好也只是 0.8×（0.8× 那一档两者都只有几毫秒，对 AC 没有意义）。

### 优化代码

**优化版 1（推荐）**：不维护窗口，只维护「最后一个偶数的下标」。这正是本题官方提示给出的方向。

```python
from typing import List


class Solution:
    def evenProduct(self, nums: List[int]) -> int:
        ans = 0
        last = -1                      # 最后一个偶数的下标；不存在时为 -1
        for i, v in enumerate(nums):
            if v % 2 == 0:
                last = i
            ans += last + 1            # 以 i 结尾的合法左端点：0 .. last
        return ans
```

**优化版 2（保持滑窗形状，去掉大整数）**：把用户版里的「乘积奇偶」换成「窗口内偶数个数」，其余结构一字不动 —— 这也正是本族的标准形。

```python
from typing import List


class Solution:
    def evenProduct(self, nums: List[int]) -> int:
        ans = left = 0
        even = 0                       # 窗口内偶数个数（度量）
        for v in nums:
            if v % 2 == 0:
                even += 1
            while even >= 1:           # 收缩到窗口全为奇数（非法一侧）
                if nums[left] % 2 == 0:
                    even -= 1
                left += 1
            ans += left                # 合法左端点 0 .. left-1，共 left 个
        return ans
```

**优化理由**：判据只需要「窗口里有没有偶数」这一个布尔信息，而用户版用 `prod` 把整段乘积**实际算了出来** —— 算的是一堆与判据无关的高位信息。把状态从「乘积」换成「偶数个数」后，每轮只做 O(1) 小整数运算，最坏情况的退化随之消失。优化版 1 更进一步，连窗口都不需要，`left` 的语义被 `last + 1` 直接替代。

### 常数级优化（可选）

- 判奇偶用 `v & 1 == 0` 代替 `v % 2 == 0`，实测差异在噪声范围内，**不建议为此改动可读性**。
- 优化版 1 在「全为 1」场景比优化版 2 慢（6.18 ms vs 5.04 ms），因为 `enumerate` + 每轮无条件加法比「滑窗只在偶数处动」多绕了一点；差距在同一数量级，**不属于值得为之纠结的优化**。
- **不要为了省掉 `while` 而把它换成 `if`** —— 它是错的（下一节给了最小反例），不是优化。

## 六、易错点与总结

### 易错点

1. **把 `while` 换成 `if`（本族最常见错误）**。若只把出窗元素挪一格：`nums = [1, 2]` 时窗口 `[0,1]` 里偶数个数为 1，出窗的 `nums[0] = 1` 是**奇数**，删掉它度量一点没减，左指针却只走了一格 ⇒ 得到 1，正确答案 2。（小批量对拍 40 组中此写法错 35 组；最小反例 `[1,2]`。）
2. **答案口径写成窗口长度** `ans += r - left + 1`。本族的窗口停在**非法**一侧，长度没有意义。最小反例 `nums = [1]`：真值 0，写成窗口长度得 1。（40 组中 `while + 长度` 错 40 组。）
3. **「收缩方式 × 答案口径」四象限**（同一批 40 组随机用例 + 手工边界）：

   | 收缩方式 | 答案口径 | 结果 |
   | :--- | :--- | :--- |
   | `while`（本族正确形） | `ans += left` | ✅ 0 偏差 |
   | `if` | `ans += left` | ❌ 35/40 错，最小反例 `[1,2]`（真 2 实 1） |
   | `while` | `ans += 窗口长度` | ❌ 40/40 错，最小反例 `[1]`（真 0 实 1） |
   | `if` | `ans += 窗口长度` | ❌ 39/40 错，最小反例 `[1]`（真 0 实 1） |

   ⇒ 本族**只有一格是对的**，且必须成对使用：`while` 收缩到非法 + `ans += left`。
4. **真的去算乘积**（用户版）。判据只需要奇偶，算乘积不仅无谓，还会在最坏输入下降一档复杂度（第五节，n = 10⁵ 实测 12.6 s）。
5. **顺手查负索引**：用户版用 `for j in nums` 遍历值、`nums[left]` 用下标，两者混用容易看错 —— 但 `prod` 为偶数时窗口必非空，故 `left ≤ j`，不会越界，也不会取到 `arr[-1]`。本题没有 `x - k` 形式的偏移。
6. **其他语言的返回类型**：答案上界 ≈ 5×10⁹ > 2³¹−1，必须 `long long` / `long`，用 `int` 会溢出（本题签名本身就是 `long long`）。Python 无此问题。

### 题型套路沉淀

- **计数型滑动窗口（约束「度量 ≥ 下限」）模板**：

  ```text
  left = 0; 度量 = 0
  for r in 0..n-1:
      把 nums[r] 并入窗口（更新度量）
      while 度量 >= 阈值:      # 收缩到刚跌破下限 —— 窗口停在非法一侧
          移除 nums[left]（更新度量）; left += 1
      ans += left              # 合法左端点 = [0, left-1]
  ```

  判据是「合法左端点构成前缀」，答案是**个数**不是长度。识别信号：题目问「有多少个子数组满足……」且约束是「至少 / ≥ k」。
- **遇到「乘积 / 和 / 异或」类判据，先问一句：这个判据真的需要算出那个值吗？** 本题答案是「不需要」—— 奇偶只需要看有没有偶数。这类「把数值判据降成状态判据」的降维，是把 O(n²) 结构降成 O(n) 的常见入口。
- **"指针摊还 O(n)" ≠ "整体 O(n)"**：一旦循环体里有随数据增长而变大的数值运算（大整数、字符串拼接、切片），就必须把那个代价单独算一遍。本题是最干净的例子：控制流确实只走 n 步，但最坏 12.6 s。
