# 2024. 考试的最大困扰度

> **难度**：中等
> **标签**：字符串 · 滑动窗口 · 前缀和 · 二分查找
> **原题链接**：https://leetcode.cn/problems/maximize-the-confusion-of-an-exam/

---

## 一、题目描述

给定一个只含 `'T'` / `'F'` 的字符串 `answerKey`，最多可以把其中 `k` 个字符改成另一种字符。求改完之后，**最长的一段连续相同字符**的长度（目标是 `'T'` 或 `'F'` 都行，取更优的那个）。

换句话说：找一个**最长的子串**，使得子串里 `'T'` 的个数 ≤ `k`（把它全变成 `'F'`），**或者** `'F'` 的个数 ≤ `k`（把它全变成 `'T'`）。

### 示例

```text
输入：answerKey = "TTFF", k = 2
输出：4
解释：把两个 'F' 都改成 'T'，得到 "TTTT"，连续 4 个 'T'。

输入：answerKey = "TFFT", k = 1
输出：3
解释：改成 "FFFT" 或 "TFFF"，都有连续 3 个 'F'。

输入：answerKey = "TTFTTFTT", k = 1
输出：5
解释：改成 "TTTTTFTT" 或 "TTFTTTTT"，都有连续 5 个 'T'。
```

### 约束条件

- `n == answerKey.length`
- `1 <= n <= 5 * 10^4`
- `answerKey[i]` 要么是 `'T'`，要么是 `'F'`
- `1 <= k <= n`

## 二、解题思路

### 核心思想

**把「最大化连续相同字符」翻译成「求最长的合法窗口」，窗口合法 ⟺ `cntT ≤ k` 或 `cntF ≤ k`。** 两种目标字符（全 T / 全 F）合成一条判据，一趟滑窗即可，不需要分两趟各跑一遍。

### 思路演进

1. **暴力解法**：枚举所有 `O(n²)` 个子串 `[l, r]`，统计其中 `'T'`、`'F'` 的个数，若 `min(cntT, cntF) ≤ k` 就更新答案；统计用切片 `count()` 则为 O(n³)。n = 5×10⁴ 时 O(n²) 已是 2.5×10⁹ 次操作，必然超时。

2. **瓶颈定位**：O(n²) 全部浪费在**枚举所有子串**上。但本题的约束有一个关键性质 —— 它**对「缩小窗口」是遗传的**：若 `[l, r]` 合法，则它的任意子区间也合法（删掉字符只会让 `cntT`、`cntF` 同时不增，`min ≤ k` 依然成立）。
   于是固定右端 `r` 时，把左端 `l` 从 `r` 往左移，合法性是**单调**的：`l` 越小（窗口越大）越容易不合法，`l` 越大越合法 —— 合法的 `l` 构成一个后缀区间 `[l*(r), r]`。所以对每个 `r` 只要找到最小的合法左端 `l*(r)` 即可，**不需要枚举所有子串**。

3. **关键转化**：`l*(r)` 关于 `r` 是**单调不减**的（`r` 变大时窗口只会更"拥挤"，合法左端不可能往左跑）。这条单调性正是双指针的根基 ⇒ 左指针整趟只前进不回退，总挪动 O(n)。
   同时，把两种目标合并成一条判据：窗口能变成「全 T」⟺ `cntF ≤ k`；能变成「全 F」⟺ `cntT ≤ k`。因此
   > **窗口合法 ⟺ `cntT ≤ k` 或 `cntF ≤ k`；等价地，窗口不合法 ⟺ `cntT > k` 且 `cntF > k`。**

   这一步消掉了「跑两趟分别枚举全 T / 全 F」的重复劳动 —— 是本题从用户的两趟写法走向单趟写法的唯一关键。

4. **最优解**：一趟滑窗，右指针推进 + 左指针按需收缩，每轮用窗口长度更新答案。时间 O(n)、空间 O(1)。任何算法都必须至少读一遍字符串（否则可能漏掉答案），所以 **O(n) 就是时间下界**；只剩常数项可优化。

### 关键点

- **判据必须是「整窗口」级的**：收缩条件写成 `cntT > k and cntF > k`（同时看两个计数）。若只盯新加入的那个字符（如 `cnt[新字符] > k`），上一轮残留的违规就检测不到，会直接算错。
- **用户两趟写法里 `cnt['T'] = cnt['F'] = 0` 这行是载荷，不是冗余**：第二趟靠它把计数清空来对齐 `left = 0`（空窗口）。删掉它，窗口状态与左边界就"对不上账"了 —— 实测（见「验证记录」④）**40.36% 的输入会出错，且大部分直接 `IndexError`**。这类"看似多余的重置"绝不能顺手清理。
- **窗口每轮只追加一个元素** ⇒ 违规量每轮最多 +1 ⇒ 一次收缩动作就能消除违规（`while` 可退化成 `if`，前提是判据写成整窗口级的）。
- **答案口径必须与收缩方式配套**：`while` 版必须每轮取 `max`，`if` 版才能用终值 `n - left`。只换一半是本题最值钱的错误（见 §五）。
- `k = n` 时答案恒为 `n`，`k` 很大时左指针几乎不动 —— 属于"根本不收缩"的退化场景。

## 三、代码实现

### 最终代码

用户提交的版本（原截图中只有 `class Solution`，缺 `from collections import defaultdict`，已补上并实际调用验证过）：

```python
from collections import defaultdict


class Solution:
    def maxConsecutiveAnswers(self, answerKey: str, k: int) -> int:
        ans = left = 0
        cnt = defaultdict(int)
        # 第 1 趟：目标是全 'T'，窗口内 'F' 的个数不超过 k
        for right, j in enumerate(answerKey):
            cnt[j] += 1
            while cnt['F'] > k:
                cnt[answerKey[left]] -= 1
                left += 1
            ans = max(ans, right - left + 1)
        # 重置计数与左界，第 2 趟换成目标是全 'F'
        cnt['T'] = cnt['F'] = 0
        left = 0
        for right, j in enumerate(answerKey):
            cnt[j] += 1
            while cnt['T'] > k:
                cnt[answerKey[left]] -= 1
                left += 1
            ans = max(ans, right - left + 1)
        return ans
```

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码（两趟滑窗）** | O(n) | O(1) |
| 单趟版（见 §五） | O(n) | O(1) |
| 朴素解法（枚举子串 + 滚动计数） | O(n²) | O(1) |
| 理论下界 | O(n) | O(1) |

> 复杂度中的 n 指字符串 `answerKey` 的长度（n ≤ 5×10⁴）。左指针整趟只前进 n 次，所以两个 `while` 循环合起来是**摊还 O(1)**，总时间仍是 O(n)。
> 空间 O(1)：`cnt` 只存 `'T'`/`'F'` 两个键，与 n 无关（哨兵 `left`、`ans` 同样是常数个变量）。

## 五、优化评估

**结论**：时间复杂度已是理论下界（O(n) 不可再降），**但常数项仍有 4 倍左右的优化空间** —— 时间全花在四件事上：遍历两趟、`defaultdict` 的哈希索引、`while` 收缩、`max()` 函数调用。

### 瓶颈分析

n ≤ 5×10⁴ 时本题必然 AC，属"泛化研究"而非"不优化就超时"。但成本结构很清晰，可以量化：

| 环节 | 成本来源 | 可去掉吗 |
| :--- | :--- | :--- |
| 遍历两趟 | 两种目标字符各扫一遍 | ✅ 用 `cntT ≤ k 或 cntF ≤ k` 合并判据 |
| `defaultdict` 计数 | 每次读写走哈希字典 + `defaultdict.__missing__` | ✅ 只有两个键，换成两个局部 `int` |
| `while` 收缩 | 收缩到合法为止，可能连缩多格 | ✅ 判据是整窗口级时可换 `if`（见下） |
| `max()` 调用 | 每轮一次函数调用 | ✅ 换成 `if ... > ans:` 就地比较 |

**不可去部分**：至少读一遍字符串（O(n) 的 `for` 循环 + 每轮的加减与比较）。这部分就是下界，约占最终版本耗时的大头 —— 所以"优化到 ~0.23×"已经接近天花板。

### 可优化空间

三步走，每一步都在**实测**里核过：

1. **合并判据，两趟 → 一趟**：窗口合法 ⟺ `cntT ≤ k 或 cntF ≤ k`，一趟即可覆盖两种目标（实测省掉约一半时间）。
2. **`while` → `if`（平移版）**：因为每轮只追加一个元素，违规量每轮最多 +1，一次收缩就能回到合法。此时左指针每轮最多前进 1 格 ⇒ 窗口长度**单调不减** ⇒ 可以直接用终值 `n - left` 当答案，连长度变量都省了。正确性依据见下方「为什么平移版成立」。
3. **`dict` → 两个局部 `int`**：字母表只有两个字符，用 `cT`/`cF` 两个整数比维护字典快得多（同时 `cT += 1` 这类局部变量自增在 CPython 里走的是最快的字节码路径）。

> ⚠️ **`while` → `if` 不能单独换**（"只换一半"是本题最大的坑）。实测四象限如下（全量穷举 90,114 组，n ≤ 12，k ∈ [1, n]）：

| 收缩方式 | 答案口径 | 是否正确 | 本机实测错误率 | 最小反例 |
| :--- | :--- | :--- | :--- | :--- |
| `while` | 每轮取 `max` | ✅ | 0.000% | —— |
| `while` | 终值 `n - left` | ❌ | **14.839%** | `answerKey = "TTTFF", k = 1` → 实得 3，真值 4 |
| `if` | 终值 `n - left` | ✅ | 0.000% | —— |
| `if` | 每轮取 `max` | ✅ | 0.000% | —— |

原因：`while` 版是"收缩到合法为止"，窗口长度序列**可能下降**，历史最长窗口不会留在终态里，必须每轮取 `max`；`if` 版左指针每轮最多挪一格，长度**单调不减**，终值就等于历史最大值，两种口径才等价。
最小反例 `"TTTFF", k=1` 手算即可复核：最优窗口是 `[0..3] = "TTTF"`（长度 4），而 `while` 版在 `r=4` 时被 `"FF"` 逼着把 `left` 推到 2，终值只剩 3。

**为什么平移版（`if` + 终值）在这里成立**：设 `L*` 为真实答案、`ℓ_r` 为处理完第 `r` 个字符后的窗口长度。
- 上界：若某轮加字符后 `ℓ_{r-1} + 1 > L*`，则该窗口不可能是合法窗口（否则 `L*` 不会是最长），必然触发收缩，`ℓ_r = ℓ_{r-1} ≤ L*` ⇒ 恒有 `ℓ_r ≤ L*`。
- 下界：归纳证 `ℓ_r ≥ min(r + 1, L*)`。无收缩时 `ℓ_r = ℓ_{r-1} + 1 ≥ min(r, L*) + 1 ≥ min(r+1, L*)`；有收缩时说明收缩前的窗口不合法 ⇒ 其长度 > `L*` ⇒ `ℓ_{r-1} ≥ L*`，收缩后 `ℓ_r = ℓ_{r-1} ≥ L* ≥ min(r+1, L*)`。
- 两式合起来，`r = n - 1` 时 `ℓ = min(n, L*) = L*`。
关键前提是**约束对"取子窗口"遗传**（删字符不会把合法变非法）—— 本题满足，所以这个"省掉 `max`"的写法才安全。

### 优化代码

三步叠加后的版本（完整字母表感知，不再需要 `defaultdict`）：

```python
class Solution:
    def maxConsecutiveAnswers(self, answerKey: str, k: int) -> int:
        n = len(answerKey)
        left = 0
        cT = cF = 0                       # 窗口内 'T' / 'F' 的个数
        for c in answerKey:
            if c == 'T':
                cT += 1
            else:
                cF += 1
            if cT > k and cF > k:         # 整窗口判据：两种目标都不合法
                if answerKey[left] == 'T':
                    cT -= 1
                else:
                    cF -= 1
                left += 1                 # 左指针每轮最多挪一格
        return n - left                   # 长度单调不减 ⇒ 终值即最大值
```

**优化理由**：一趟遍历（省掉一半工作量）+ 两个整数代替字典（省掉哈希索引）+ `if` 代替 `while`（省掉收缩循环）+ 终值代替 `max`（省掉每轮函数调用）。同为大 O(n)，实测六场景合计耗时降到原版的 **0.23×**（约 4.4 倍）。

### 常数级优化（可选）

- 遍历用 `for c in answerKey` 而不是 `for right, c in enumerate(...)`：`enumerate` 多一层解包开销；`if`/终值版根本不需要下标 `right`。
- 收缩时判断 `answerKey[left] == 'T'` 而不是查表 —— 由于 `'T' > 'F'`，理论上可用 `(c > 'F')` 把计数塞进 `list[2]`，但**可读性损失远大于收益**，实测也未跑赢两个 `int`，不建议。
- 不要为了"省一行"把 `while` 和 `if` 混用（如 `while cT > k and cF > k: if ...`）——`while` 版需要配套的 `max` 口径，混用必然出错。

## 六、易错点与总结

### 易错点

- **`while` 配终值 `n - left`**：最容易踩的一个，写出来还"很像"对的。实测 14.839% 的输入会错（小规模穷举），最小反例 `"TTTFF", k=1`。
- **收缩判据只看新加入的字符**（如 `cnt[新字符] > k`）：漏检上一轮的残留违规。
- **顺手删掉第二趟开头的计数重置**：它在对齐 `left = 0`，删掉后 40.36% 的输入出错、且多半直接 `IndexError`。判断"某行是不是冗余"要用**删掉再对拍**，不能靠目测。
- **忽视 `import`**：从截图抄代码时 `from collections import defaultdict` 常被漏掉 —— 它在 `class Solution` 定义时不报错，只在**调用时**才抛 `NameError`，光 `exec` 源码验不出来。
- 把 O(n²) 的朴素解当成"能过"：n = 5×10⁴ 时是 2.5×10⁹ 次操作，必然超时。

### 题型套路沉淀

**「带预算/代价的最长窗口」模板**（度量逐元素累加且非负 ⇒ 固定右端时度量随左端右移单调不增 ⇒ 双指针成立）：

1. 先确认**约束对「取子窗口」遗传** —— 这是整套双指针的地基，不成立就得换结构（前缀和 + 单调队列等）。
2. 写出**整窗口级**的判据（本题：`cntT > k and cntF > k`），不要写成"只看新元素"的局部判据。
3. 想清楚**答案口径**：`while` 收缩 ⇒ 必须每轮取 `max`；`if` 收缩（左指针每轮最多一格）⇒ 长度单调不减，终值 `n - left` 即可。
4. 只有两个字符时把 `dict` 换成两个 `int`，并把 `max()` 换成就地 `if` —— 大 O 不变但常数能降一个量级。

本题的判据族归属：属 §3.4 ③ 里的「**按值**」一族（判据是"某元素的计数 > k"，而不是"窗口内不同种类数 > K"），因此计数归零也**不需要删键**。
