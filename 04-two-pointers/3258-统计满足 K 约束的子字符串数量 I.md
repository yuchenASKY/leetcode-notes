# 3258. 统计满足 K 约束的子字符串数量 I

> **难度**：简单
> **标签**：滑动窗口 · 字符串 · 计数
> **原题链接**：https://leetcode.cn/problems/count-substrings-that-satisfy-k-constraint-i/

---

## 一、题目描述

给定一个**二进制**字符串 `s` 和一个整数 `k`。若一个二进制字符串满足**以下任一条件**，则称它满足 k 约束：

- 串中 `0` 的个数最多为 `k`；
- 串中 `1` 的个数最多为 `k`。

求 `s` 的所有子串中满足 k 约束的子串数量。

**本题的题眼在「任一」两个字上**：合法是**析取**（`c₀ ≤ k` **或** `c₁ ≤ k`），所以**非法是合取**（`c₀ > k` **且** `c₁ > k`）—— 这个口径直接决定了 `while` 里的连接词写 `and`。

反过来把「任一」读成「同时满足」，判据会变成 `or`，那是能靠样例拦住的错：三个官方示例会立刻给出 `9 / 22 / 5`（真值 `12 / 25 / 15`）。

真正隐蔽的是另一类错误 —— 「非法是合取」还意味着窗口一次违规**可能需要连续收缩多格**，于是有人会把 `while` 顺手改成 `if`：**那个版本三个官方示例全部通过**，却在小构造用例上出错（见 §六）。

### 示例

```text
示例 1
输入：s = "10101", k = 1
输出：12
解释：除 "1010"、"10101"、"0101" 外，其余子串都满足 k 约束。

示例 2
输入：s = "1010101", k = 2
输出：25
解释：除长度大于 5 的子串外，其余子串都满足 k 约束。

示例 3
输入：s = "11111", k = 1
输出：15
解释：所有子串都满足 k 约束（`1` 只有 5 个，任何子串的 `0` 的个数都是 0 ≤ k）。
```

### 约束条件

- `1 <= s.length <= 50`
- `1 <= k <= s.length`
- `s[i]` 为 `'0'` 或 `'1'`

> 注意约束里 `n ≤ 50` 这个量级：**本题任何写法都能 0 ms 通过**，O(n²) 暴力都绰绰有余。下面的滑窗与优化讨论是"把题目当通用问题看"的产物，不是在救超时。

## 二、解题思路

### 核心思想

**固定右端点，合法性对左端点是单调的**，因此存在唯一分界点 `L*(r)`：以 `r` 结尾的合法子串恰好是 `[L*(r), r]`、`[L*(r)+1, r]`、…、`[r, r]` 这 `r - L*(r) + 1` 个。于是只需维护一个只向右走的左指针。

**判据（本题的判据族归属）**：

> 窗口 `[l, r]` 非法 ⟺ `cnt0(l..r) > k` **且** `cnt1(l..r) > k`。

这是"**合取型非法判据**"，与"单个计数超过预算"的滑窗族有本质区别，直接后果是**收缩时一轮可能挪很多格**（见 §六 易错点）。

### 思路演进

1. **暴力解法**：枚举所有 `O(n²)` 个子串，对每个子串现场数一遍 0 和 1 → O(n³)；改成"固定左端点、右端点右移时滚动累加计数"可以降到 **O(n²) 时间 / O(1) 空间**。`n ≤ 50` 时它完全够用（总子串数最多 1275 个）。

2. **瓶颈定位**：瓶颈不在"数数"，而在**枚举本身**。每个右端点 `r` 都要把 `l` 从 0 一路试到 `r`，而其中绝大多数 `l` 的合法性是重复判断的：一旦 `l` 增大到某个位置后窗口就恒合法了，再往后试纯属浪费 —— 也就是说，**`l` 的有效取值是一段后缀，不是前缀**。

3. **关键转化**：用**单调性**把这层结构挖出来。
   - **关于 `l` 单调**：固定 `r`，`l` 增大只会让 `cnt0`、`cnt1` 双双不增；非法判据 `cnt0 > k 且 cnt1 > k` 是"两个下界型命题的合取"，两边都不会因 `l` 增大而由假变真 —— 所以命题**单调**：存在分界点 `L*(r)`，`l ≥ L*(r)` 合法、`l < L*(r)` 非法。一句话总结：**原来不行是因为要逐个试 `l`；现在行是因为"合法"在 `l` 轴上是单调的，试到第一个合法的就能停**。
   - **关于 `r` 单调**：`[l, r]` 非法 ⟹ `[l, r+1]` 也非法（追加元素只会让两个计数不降，"都 > k"不会失效）⟹ `L*(r+1) ≥ L*(r)`。**左指针永不回退**，所以整趟扫描中 `left` 总共只前进 `n` 次，内层 `while` 是摊还 O(1)。
   - 于是每轮只需把 `left` 从上一轮的 `L*(r-1)` 继续往右推到 `L*(r)`，再把这 `r - left + 1` 个合法子串计入答案。

4. **最优解**：一次线性扫描 —— 右端点吃进一个字符，若窗口非法就把左端点往右收缩到合法为止，然后累加 `right - left + 1`。时间 O(n)、空间 O(1)。离理论下界（至少要读一遍输入，Ω(n)）只差常数项。

### 关键点

- **判据是合取，不是析取**：`while` 里写 `and`（`cnt['0'] > k and cnt['1'] > k`），不是 `or`。写 `or` 相当于把题意当成"两个条件同时满足"，会把 `"00"（k=1）` 这类**单边超限但合法**的串误判为非法（实测最小反例给真值 3 得 2）。
- **收缩必须 `while`**：合取型非法的窗口，一轮内可能需要连续挪动多格。实测 `k = 1`、`s = "1"×10⁵ + "0"×10⁵` 时，某一轮单次收缩了 **99999** 格；把它写成 `if` 会漏掉部分收缩，实测 51 组小用例里错 7 组，最小反例 `"11100", k = 1`（真值 13、`if` 版 14）。
- **`while` 一定终止**：非法要求 `cnt0 ≥ k+1` 且 `cnt1 ≥ k+1`，故窗口长度 ≥ `2k+2`；当窗口被收缩到长度 ≤ `k+1` 时两个计数不可能同时超限，循环必退出。
- **给 `l` 的计数是"每个 `r` 累加一次"**：答案是"所有合法子串的个数"，不是"最长合法窗口的长度"，所以每轮都要 `ans += right - left + 1`，不能只取终值。

## 三、代码实现

### 最终代码

> 截图来源：用户已在 LeetCode 提交通过（AC）的版本。
> **补全说明**：截图里只有 `class Solution:`，缺 `from collections import defaultdict`，已补上（否则笔记里的代码跑不起来）。截图的 12 行里第 11 行即 `return ans`、第 12 行为空，**代码没有被裁掉**，未做任何结构补全。

```python
from collections import defaultdict


class Solution:
    def countKConstraintSubstrings(self, s: str, k: int) -> int:
        ans = left = 0
        cnt = defaultdict(int)
        for right, j in enumerate(s):
            cnt[j] += 1
            while cnt['0'] > k and cnt['1'] > k:   # 合取：两个计数都超限才非法
                cnt[s[left]] -= 1
                left += 1
            ans += right - left + 1                # 以 right 结尾的合法子串数
        return ans
```

### 正确性论证

- **不变量**：每轮循环开始时（`while` 结束后），`[left, right]` 合法；且 `left` 恰好等于 `L*(right)`（以 `right` 结尾的合法子串中最小的左端点）。
- **归纳步**：设上一轮结束时 `left = L*(r-1)`。本轮吃进 `s[r]` 后，由 §二 的 `r` 单调性有 `L*(r) ≥ L*(r-1)`，所以从左往右推不会漏解；`while` 一退出就说明 `[left, r]` 合法，而它刚被推过的那一格 `[left-1, r]` 非法，由 `l` 单调性知更小的 `l` 全都非法 ⟹ `left = L*(r)`。
- **终态即答案**：每轮把 `[L*(r), r] … [r, r]` 共 `r - left + 1` 个子串计入，且这些子串的右端点互不相同、被唯一归属到各自的 `r`，所以既不重也不漏。

| :--- | :--- | :--- |
| **最终代码** | O(n) | O(1) |

## 五、优化评估

**结论**：**大 O 已到理论下界**（时间 Ω(n) 不可突破，空间 O(1) 已达成），**但常数项还有一倍以上的余量**。以下两个改写版本均经小批量对拍验证（偏差 0 组）。

### 瓶颈分析

- `n ≤ 50` 时任何版本都是 0 ms，所以下述计时**不是"不优化会超时"的证据**，而是把规模放大到 `n = 2×10⁵` 后对**常数项**的观测研究，用于说明"同样的 O(n)，写法差多少"。
- 最终代码里最重的常数项是 **dict 哈希**：`cnt[j] += 1` 一次哈希，`while` 里 `cnt[s[left]]` 一次哈希，而 `defaultdict` 还会在缺键时多走一次 `__missing__` 分支。本题**字母表只有 2 个字符**，用哈希表存两个计数属于"杀鸡用牛刀"，两次整数自增就能替代。
- 另一条思路是**换算法形态**：不去维护窗口，而是用**补集计数** —— 直接数非法子串，再用 `n(n+1)/2` 减掉，从而彻底去掉 `while`。

### 可优化空间

两条互不冲突的方向：

1. **常数级**：把 `defaultdict` 换成两个整数计数器 `c0` / `c1`。大 O 不变（O(n)/O(1)），只削哈希开销。
2. **形态级**：补集计数。`[l, r]` 非法 ⟺ 其中 0 有 `k+1` 个以上 **且** 1 有 `k+1` 个以上。记 `z(r)` 为 `s[0..r]` 中**倒数第 `k+1` 个 `0` 的下标**、`o(r)` 同理，则 `[l, r]` 非法 ⟺ `l ≤ min(z(r), o(r))` ⟹ 以 `r` 结尾的非法子串有 `min(z(r), o(r)) + 1` 个。全程只需维护两个递增下标列表，无需收缩窗口。

### 优化代码

**方案一（推荐）：双整数计数器 + `while`**

```python
class Solution:
    def countKConstraintSubstrings(self, s: str, k: int) -> int:
        ans = left = c0 = c1 = 0
        for right, ch in enumerate(s):
            if ch == '0':
                c0 += 1
            else:
                c1 += 1
            while c0 > k and c1 > k:      # 判据不变，仍必须是合取 + while
                if s[left] == '0':
                    c0 -= 1
                else:
                    c1 -= 1
                left += 1
            ans += right - left + 1
        return ans
```

**方案二：补集计数（无 `while`）**

```python
class Solution:
    def countKConstraintSubstrings(self, s: str, k: int) -> int:
        n = len(s)
        zeros, ones = [], []              # 各自记录出现下标，天然递增
        bad = 0
        for r, ch in enumerate(s):
            (zeros if ch == '0' else ones).append(r)
            if len(zeros) > k and len(ones) > k:
                # 倒数第 k+1 个 0 / 1 的下标取 min，即非法左端点的最大取值
                bad += min(zeros[-k - 1], ones[-k - 1]) + 1
        return n * (n + 1) // 2 - bad
```

**优化理由**：

- 方案一：判据与收缩方式**完全照搬**最终代码，只把 `cnt[字符]` 的哈希读写换成 `c0` / `c1` 的自增自减，风险最低。
- 方案二：`[l, r]` 含 ≥ `k+1` 个 `0` ⟺ `l ≤ z(r)`（`z(r)` 即倒数第 `k+1` 个 `0` 的位置）；两个条件同时成立就取 `min`。左端点的非法区间是 `[0, min(z, o)]`，长度正好 `min(z, o) + 1`，全部非法子串数一加即得，合法数 = 总数 − 非法数。**注意它把空间从 O(1) 抬到了 O(n)**（两个下标列表），这是它唯一的代价。

### 实测对照

轮转测量 9 轮取最优值（同一进程内 A/B/C 交替轮转，避免机器状态漂移），规模 `n = 2×10⁵`：

| 版本 | 随机 01 串 k=1 | 相对最终代码 | 交替 "01" k=3 | 相对最终代码 |
| :--- | :--- | :--- | :--- | :--- |
| 最终代码（`defaultdict`） | 52.18 ms | 1.00× | 50.96 ms | 1.00× |
| 方案一（双计数器） | **31.30 ms** | **1.67×** | **29.55 ms** | **1.72×** |
| 方案二（补集计数） | 43.61 ms | 1.20× | 42.87 ms | 1.19× |

> **再强调一次口径**：本题 `n ≤ 50`，任何版本都是 0 ms；上表是把规模放大后对常数项的研究，**不构成"原代码需要优化"的判断**。原代码在题目约束下已是满分写法。

### 常数级优化（可选）

- 方案二里 `min(zeros[-k-1], ones[-k-1])` 的两次负索引是热点，但它同时也免掉了 `while`；实测净收益仍不如方案一。若想保住 O(1) 空间又要去掉 `while`，可把两个列表换成容量 `k+1` 的定长环形缓冲（`deque(maxlen=k+1)`）——**此改写未实测**，仅作方向记录。
- 把 `s` 预编码成 `bytes` 再比较 `b'0'` 也是常见微优化，**本题未实测**，不写结论。
- 唯一**不要**做的"优化"是把 `while` 换成 `if`：见下节，实测会出错。

## 六、易错点与总结

### 易错点

**① 把收缩写成 `if`（头号陷阱：官方示例全过，样例抓不出来）**

合取型非法判据下，窗口一次违规**可能需要连续收缩多格**。实测该版本三个官方示例**全部通过**（12 / 25 / 15），却在 51 组小用例里错 **7 组**，最小反例：

```text
s = "11100", k = 1
  真值 13，if 版得 14
  收缩现场：r=4 时窗口 "11100" 两个计数都超限，需连删 2 个字符才回到合法
```

**② 把"满足任一条件"读成"同时满足"（判据写成 `or`）**

会把合法的**单边超限**串误杀。这个错误**官方示例就能拦住**：三个示例分别得 `9 / 22 / 5`（真值 `12 / 25 / 15`）。小用例上 51 组错 **23 组**，最小反例：

```text
s = "00", k = 1
  真值 3（"0"、"0"、"00" 全部合法 —— "00" 的 1 的个数是 0 ≤ k，满足第二个条件）
  or 版得 2（把 "00" 判成非法）
```

插桩量化（`k = 1`, `n = 2×10⁵`）单轮最大收缩格数：

| 输入形态 | 单轮最大收缩 | 全趟累计收缩次数 |
| :--- | :--- | :--- |
| 随机 01 串 | 19 格 | 199996 |
| `"1"×10⁵ + "0"×10⁵` | **99999 格** | 99999 |
| 块状（1000 个 1 + 1000 个 0，重复 100 段） | 999 格 | 198999 |

> 结论：**`while` 不是保守写法，是必需写法**。同时注意累计收缩次数仍是 O(n)，所以"挪得狠"不影响总复杂度。

**③「判据口径 × 收缩方式」四组合实测**

| 判据口径 | 收缩方式 | 51 组小用例偏差 | 最小反例 | 可用性 |
| :--- | :--- | :--- | :--- | :--- |
| `and`（正确口径） | `while` | **0** | — | ✅ |
| `and` | `if` | 7 | `"11100", k=1`：得 14、真值 13 | ❌ |
| `or` | `while` | 23 | `"00", k=1`：得 2、真值 3 | ❌ |
| `or` | `if` | 23 | `"00", k=1`：得 2、真值 3 | ❌ |

> 本表只有第一行可用。**注意本题的"答案口径"没有第二根轴可调** —— 答案是"所有合法子串的计数"，每轮都必须累加 `right - left + 1`，不存在"取终值即答案"的等价写法（那套等价性只对"最长窗口长度"型答案成立）。所以这里的四象限是「判据口径 × 收缩方式」，不是常见的「收缩方式 × 答案口径」。

**④ 其余易错点**

- 每轮漏掉累加、或只记"最长合法窗口长度"当答案（本题要的是**计数**，不是长度）。
- `left` 越界：`while` 里 `cnt[s[left]]` 依赖"窗口内一定还有元素可删"。由于 `while` 的条件在上一步已被证明必然终止（窗口长度 ≤ `k+1` 时不再非法），不会越界；但如果把判据写错成 `or`，就可能把 `left` 推到 `n` 之外，读 `s[left]` 直接 IndexError 或静默取错值。
- 误加特判 `if k >= n: return n*(n+1)//2`：其实没必要 —— 窗口永远合法，`while` 一次也不会进，原逻辑自然给出整串答案。

### 题型套路沉淀

- **先定"非法"怎么表述，再决定 `while` 里是 `and` 还是 `or`**：合法是析取 ⟹ 非法是合取；合法是合取 ⟹ 非法是析取。写反了官方示例通常当场就挂（本题 `or` 版得 `9 / 22 / 5`），属于能被样例拦住的错。
- **但"样例全过 ≠ 写法正确"**：本题 `if` 版三个官方示例全过，却错 7/51；结构性写法（收缩方式、答案口径）的错误**必须靠三五个字符的小构造用例**（`"00"`、`"11100"`）才能暴露，别拿官方示例自证。
- **收缩方式由"违规量"决定，不由"窗口内部的量"决定**：单计数超预算型 ⇒ 每轮超量恒为 1，可退化成 `if` 或用"上次出现位置"一次跳转；**合取型非法 ⇒ 一轮可能连删多格，必须 `while`**。
- **滑窗题固定要问三件事**：① 合法性对左端点是否单调（否则双指针不成立）；② 左端点分界点对右端点是否单调（决定左指针能否不回退）；③ 答案口径是"每轮累加"还是"终值"（决定怎么写 `ans`）。
- **"n 很小"的题不要被大 O 幻觉骗**：本题 `n ≤ 50`，暴力 O(n²) 与最优 O(n) 都是 0 ms；谈优化时必须把口径说清楚是"泛化研究"。
- 同源进阶：本题的加强版 `3261. 统计满足 K 约束的子字符串数量 II`（多次区间查询 + `n` 变大），需要预处理出每个位置的分界点 `L*(r)` 再配合前缀和/二分回答查询 —— 本题的 `L*(r)` 单调性正是那题的基石。
