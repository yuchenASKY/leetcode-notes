# 4032. 至多 K 个不同质因数集合的最长子数组

> **难度**：中等
> **标签**：数组 · 哈希表 · 滑动窗口 · 数论
> **原题链接**：https://leetcode.cn/problems/longest-subarray-with-at-most-k-distinct-prime-factors/

---

## 一、题目描述

给定正整数数组 `nums` 和整数 `k`。一个**子数组的质因数集合**定义为「其中所有元素的不同质因数的并集」（同一个质数只算一次）。求质因数集合中不同质数**不超过 `k` 个**的最长子数组长度；若不存在这样的子数组，返回 0。

### 示例

```text
示例 1
输入：nums = [7,6,10,12,11], k = 3
输出：3
解释：子数组 [6,10,12] 的质因数并集是 {2,3,5}，恰有 3 个不同质数；
      没有更长的子数组满足条件。

示例 2
输入：nums = [4,6,9,18], k = 4
输出：4
解释：整个数组的并集是 {2,3}，只有 2 个不同质数，2 <= 4，故全长合法。

示例 3
输入：nums = [6,10,15], k = 2
输出：1
解释：任意长度 >= 2 的子数组并集都是 {2,3,5}（3 个），超过 k，故只能取单元素。
```

### 约束条件

- `1 <= nums.length <= 10^5`
- `2 <= nums[i] <= 10^5`
- `1 <= k <= 10^4`

---

## 二、解题思路

### 核心思想

**把「并集里不同质数的个数」当成窗口的一种代价，用一张 `质数 -> 窗口内出现次数` 的哈希表增量维护** —— 这张表的**键数**就是不同质数的个数，于是「窗口是否合法」变成 O(1) 的 `len(cnt) <= k` 判断，右端扩张、左端收缩即可。

### 思路演进

1. **暴力解法**：枚举所有子数组（O(n²) 个），每个子数组重新分解质因数、并入 `set` 再看大小，整体是 O(n²·√V) 级别（V = 值域）。n = 10^5 时区间数就有 5×10^9，完全不可行。

2. **瓶颈定位**：慢在两层重复 —— ① **区间个数**是 O(n²)；② 每个区间都把质因数**从头重算**一遍。更本质的问题是：「不同质数个数」这个量在枚举过程中被反复重新计算，窗口右移一格本可以增量更新，却被整体重算。

3. **关键转化**（三步，缺一不可）：
   - **单调性 → 双指针成立**。固定右端 `r`，左端 `l` 右移只会把元素移出窗口 ⇒ 并集只会变小 ⇒ 不同质数个数**单调不增**。也就是「窗口合法」对左端是**前缀封闭**的：`l` 变大绝不会把非法变合法。这正是双指针的前提。
   - **增量维护 → O(1) 判合法**。窗口的质因数集合 = 窗口内出现过**至少一次**的质数集合 = 计数表的**键集**。加入元素 `x` 时把它每个质数 `p` 的计数 +1；计数 0→1 说明多了一个不同质数，计数 1→0 时必须**把键删掉**。于是不同质数个数恒等于 `len(cnt)`。
   - **质因数不重算 → 预处理**。值域固定 ≤ 10^5，先用筛法一次性建出每个数的质因数列表，之后每个元素查表 O(ω(x))。

4. **最优解**：右指针整趟走一遍，每个元素至多被加入一次、移出一次 ⇒ 总代价 O(n·ω)，与理论下界同阶。

### 关键点

- **这是「按键数」型滑窗，不是「按值」型**。合法判据是**键的个数** `len(cnt) <= k`，而不是某个键的计数超限。由此推出一个硬性结论：**计数归零必须 `del`** —— 否则键数只增不减，`len(cnt)` 永远降不下来，左指针会被一路推到数组外。
- **一轮可能多出好几个键，所以必须用 `while`**：一个元素最多带 **6** 个不同质数（2·3·5·7·11·13 = 30030，再乘 17 就超过 10^5），一轮最多新增 6 个键，挪一格不足以恢复合法。（对照：同族里「每值出现次数 ≤ 1」那种题，每轮超出量恒为 1，才可以退化成 `if`。）
- **收缩时删的是「整个元素」，不是「一个质数」**：`for p in prime_factors[nums[left]]` 把左端元素的所有质因子计数各减 1，只有减到 0 的那些才删键。
- **答案可以是 0**：`nums[i] >= 2` 只保证每个元素至少贡献一个质数，不保证有解 —— 例如 `nums = [30], k = 1`，`{2,3,5}` 有 3 个不同质数，任何子数组都非法，正确返回 0。

## 三、代码实现

### 最终代码

```python
from collections import defaultdict
from typing import List

MX = 100_001

# 预处理 [2, MX) 每个数的质因数列表：筛法，摊还 O(MX·log log MX)
prime_factors = [[] for _ in range(MX)]
for i in range(2, MX):
    if not prime_factors[i]:            # i 没被更小的质数标记过 ⇒ i 是质数
        for j in range(i, MX, i):       # i 的每个倍数都以 i 为质因子
            prime_factors[j].append(i)


class Solution:
    def longestSubarray(self, nums: List[int], k: int) -> int:
        cnt = defaultdict(int)          # 质数 -> 在窗口中出现的次数
        ans = left = 0
        for i, x in enumerate(nums):
            for p in prime_factors[x]:  # 右端扩张：x 的质因数全部计入
                cnt[p] += 1
            while len(cnt) > k:         # 按键数收缩，直到不同质数个数 <= k
                for p in prime_factors[nums[left]]:
                    if cnt[p] > 1:
                        cnt[p] -= 1
                    else:
                        del cnt[p]      # 计数归零必须删键，否则 len(cnt) 不降
                left += 1
            ans = max(ans, i - left + 1)
        return ans
```

> 截图中没有 `from collections import defaultdict` 与 `from typing import List`，笔记中已补全（否则 `defaultdict` / `List` 未定义，代码跑不起来）；窗口逻辑与截图完全一致。

## 四、复杂度分析

| 版本 | 时间复杂度 | 空间复杂度 |
| :--- | :--- | :--- |
| **最终代码** | O(MX·log log MX + n·ω) | O(MX·log log MX + MX) |
| 朴素解法（枚举区间 + 逐区间重算） | O(n²·ω·√V) | O(V) |
| 理论下界 | O(MX·log log MX + n) | O(MX·log log MX) |

> 复杂度中的 **n** 指 `nums` 的长度；**V = max(nums)**（筛表规模 MX = V + 1 = 10^5）；**ω(x)** 指 x 的不同质因数个数，V ≤ 10^5 时 **ω(x) ≤ 6**（2·3·5·7·11·13 = 30030 ≤ 10^5 < 510510）。

- **筛表**：`prime_factors` 里存放的 (值, 质因子) 对共有 Σ_{x≤MX} ω(x) = Σ_{p≤MX} ⌊MX/p⌋ ≈ MX·ln ln MX ≈ 2.7×10^5 条（实测 **266,400** 条），摊还到每个数上是 log log 级。
- **主循环**：每个元素在右端被加入一次、在左端被移出至多一次，每次 O(ω) ⇒ O(n·ω)；`left` 整趟只推进 n 次，所以内层收缩 `while` **摊还 O(1)**，不需要任何结构去加速它。
- **下界**：数组元素必须至少读一遍（Ω(n)），质因数信息必须至少构造一次（Ω(MX)）⇒ 本解与下界同阶，**没有数量级的余量**。
- **实测内存**：全量因子表 tracemalloc 峰值 **9.50 MB**（10^5 个 list 对象是主要开销）；同样功能的 SPF 单数组只要 **0.76 MB**。

## 五、优化评估

**结论**：**渐进复杂度已是最优** —— O(n·ω) 且 ω ≤ 6 是常数，能动的只有常数项。实测确认了三条：

1. ✅ **有效**：`while` 换成 `if` 并直接返回 `n - left`，四个场景 **1.07× ~ 1.14×**。
2. ⚠️ **几乎无效（场景依赖）**：惰性 SPF 分解替代全量因子表，在「值域≈n」的场景**反而慢约 30%**，仅在「值的种类极少」时因省下建表时间略占优。
3. ❌ **错误**：保留 `while` 却按 `n - left` 取答案，`nums = [2, 6], k = 1` 就出错。

### 瓶颈分析

把 10^5 规模的一趟跑分拆成「预处理」与「主循环」（各取 9 次最优）：

| 环节 | 耗时 | 占比（以 S1 为例） |
| :--- | :--- | :--- |
| 预处理（建全量因子表） | 28.2 ms | 24% |
| 主循环 | 87.2 ms | 76% |
| 合计 | 115.5 ms | 100% |

主循环的耗时基本就是 CPython 的 **dict 操作**：最坏场景（每个元素 6 个质数、每轮都要清空窗口）约有 10^5×6 次加入 + 10^5×6 次移出 = **1.2×10^6 次 `cnt[p]` 读写**，耗时 121.2 ms ⇒ 单次约 **100 ns**，与 CPython `dict` 的实际水平一致。**瓶颈是「哈希表操作次数」本身，不是查找方式** —— 所以任何「把查表换成更省的操作」的想法都不会有收益，只有减少操作次数才有效。

### 可优化空间

先排除两个死路：

- **惰性 SPF 分解（只对出现过的值做分解）**：建 SPF 只要 **9.5 ms**（全量表 28.2 ms），内存 **0.76 MB**（全量表 9.50 MB），看起来划算。但按需分解要在 Python 层跑试除循环（`while y > 1` + 内层除尽），这笔开销盖过了省下的建表时间：

  | 场景（n = 10^5） | 用户版（含预处理） | 惰性 SPF 版（含预处理） | 差异 |
  | :--- | :--- | :--- | :--- |
  | S1 随机均匀, k = 100 | 115.5 ms | 149.8 ms | 慢 30% |
  | S2 随机均匀, k = 10^4 | 81.1 ms | 105.5 ms | 慢 30% |
  | S3 随机均匀, k = 1 | 122.7 ms | 156.9 ms | 慢 28% |
  | S4 全为 30030, k = 1 | 149.4 ms | 142.2 ms | **快 4.8%** |

  ⇒ 只有在「值的**种类**很少」（S4 只有 1 种值，缓存全命中）时才靠省下建表时间小赚；值分散时一律亏。**默认不要换**。
- **换更省的数据结构**：已经是一张 `dict` + 若干 list；判合法必须知道**不同质数的个数**（键数），绕不开哈希表。CPython 里没有比 `dict` 更快的计数结构（`Counter` 更慢，`array` 还要自己处理值域映射）。

真正能赚的是**删掉每轮那一次 `max()`**：

- 用户代码每轮都算 `ans = max(ans, i - left + 1)`。把同一套窗口逻辑里这一句去掉（其余不动）后，S1 从 87.2 ms 降到 79.7 ms ⇒ **约 7.5 ms / 10^5 轮，即 ≈75 ns/轮**，正好是一次函数调用的量级。
- 只要把收缩从 `while` 换成 `if`（左指针每轮**至多前进 1 格**），窗口长度 `i - left + 1` 就**单调不减**，「历史最大值」必然等于「终值」⇒ 可以整段删掉 `ans`，直接 `return len(nums) - left`。

⚠️ 这一步**同时**动了「收缩方式」和「答案口径」，**两个都不能只改一半**（对拍结果见 §七）。

### 优化代码

```python
class Solution:
    def longestSubarray(self, nums: List[int], k: int) -> int:
        pf = prime_factors             # 绑局部名，省全局查找
        cnt = defaultdict(int)
        left = 0
        for i, x in enumerate(nums):
            for p in pf[x]:            # 右端每轮只扩张一个元素
                cnt[p] += 1
            if len(cnt) > k:           # 左指针每轮最多右移一格 ⇒ 窗口长度单调不减
                for p in pf[nums[left]]:
                    if cnt[p] > 1:
                        cnt[p] -= 1
                    else:
                        del cnt[p]
                left += 1
        return len(nums) - left        # 长度单调不减 ⇒ 终值即历史最大
```

**优化理由**：

- `if` 版成立要**三个条件同时满足**：① 答案口径是**窗口长度**；② 收缩判据 `len(cnt) > k` 是对**整个窗口**成立的（而不是只看新加入的那个元素）；③ 左指针每轮至多 +1 ⇒ 长度单调不减。本题三条都满足，`if` 版才与 `while` 版等价。
- **允许窗口在轮末短暂非法**：本题一轮最多新增 6 个质数，`if` 之后 `len(cnt)` 完全可能仍 > k。结果依然不错，理由**不是**「超出量恒为 1」（这里根本不成立），而是「left 追不上最优窗口的左端点 `l*`」——
  若某轮在 `left = 0` 时因非法而收缩到 1，说明 `[0, i]` 整段非法；而合法窗口的子窗口必然合法，所以长度 ≥ i+2 的合法窗口必有 `l* ≥ 1`。之后 `left` 每轮至多 +1，且当 `left = l*` 时窗口必是那个合法窗口的子窗口，不会触发收缩 ⇒ 在最优窗口右端 `r*` 处有 `left ≤ l*` ⇒ 长度 ≥ opt。又因**合法窗口长度 ≤ opt**，且长度单调不减，故终值恰为 opt。
- ⚠️ **只换一半就错**：`while` 版的长度序列会下降，此时若照搬 `return n - left` 必然出错 —— 最小反例 `nums = [2, 6], k = 1`（真值 1，实得 0），55 组小批量对拍中 25 组出错。

### 常数级优化（可选）

- `pf = prime_factors` 把模块级名字绑成局部变量，省一次全局查找/轮，收益很小（上面的 E 版已含）。
- **别**把 `for p in pf[nums[left]]` 顺手写成 `pf[x]`：`nums[left]` 与当前 `x` 通常不是同一个元素，那样会算错。
- **别**为了省掉 `del` 而只做 `cnt[p] -= 1`：本族里那样会让键数不降，`while len(cnt) > k` 恒真，`left` 直接越界 —— 在 `if` 版里则表现为答案偏大。

## 六、易错点与总结

### 易错点

- **计数归零没有 `del`**：最致命的一处 —— `len(cnt) > k` 永远为真，`left` 被推到 `n` 以外，轻则答案错成 0，重则索引越界。
- **误以为「一轮最多多一个质数」**：本题一轮最多多 **6** 个键，所以「左指针挪一格就够」的直觉是错的，收缩量必须由 `while` 跑到位。
- **把判据写成按值**（如 `cnt[p] > k`）：本题约束的是**质数种类数**，不是某个质数的出现次数；按值判会漏掉「种类数超限、但每个质数计数都没超」的情况。
- **只换一半的优化**：`while` + `n - left` 错（反例 `[2, 6], k = 1`）；`if` + `max()` 与 `if` + `n - left` 都对，二者等价。
- **把「`nums[i] >= 2`」误当成「必有解」**：`nums = [30], k = 1` 时任意子数组都非法，正确答案是 0。

### 题型套路沉淀

- 滑窗题第一步先分清**合法判据是按「键数」还是按「值」**：
  - **按键数**（不同种类 ≤ K，如本题、`904. 水果成篮`、`3. 无重复字符的最长子串`）：**必须删键**，用 `while` 收缩。
  - **按值**（某元素出现次数 ≤ k）：归零可以不删键，且每轮超出量 ≤ 1，才可以退化成带跳转的 `if`。
- 双指针的复杂度判定只有一句话：**左指针整趟只走 n 格 ⇒ 内层收缩循环摊还 O(1)**，不需要用二分/堆去「加速」它（那是负优化）。
- 值域固定的数论题，**把「质因数 / 倍数关系」预处理成筛表**是标准起手式：把 O(√V) 的试除换成 O(ω) 的查表。但注意用 Python 做「惰性分解」通常不划算（§五 实测）。
- 「删掉每轮 `max()`」这一招的适用条件要背下来：**答案口径 = 窗口长度** + **左指针每轮至多 +1**，两者同时成立才可以把 `while/if ± max` 简化成终值。
